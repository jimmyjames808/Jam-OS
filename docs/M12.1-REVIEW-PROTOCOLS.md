# M12.1 code check: M12's protocol and storage lines

Part 1a of M12.1 (ROADMAP: "every line M12 changes, with the unchanged
callers of each interface it changes"), at main f4a96d6a, by an agent that
wrote none of it. Read in full context (not only the hunks of the M12
merges IDL1, IDL2, P2, P3, P4, P5, S1a, S1b, S2a, S2b and the
close-after-send sweep):

- **genidl** (`tools/genidl.py`) through what it generates: `common.h`
  (arrays, `idl_str_ok`, the serve loop, slots, `idl_reply_*`), and the
  generated client stubs, dispatches, event dispatches, `_reply_` and
  `_take_slot`/`_run_slot` of idltest, hda, storage, dns and volumes;
- **sound**: the mixer (state layout 4, the keeper gate, `audio` /
  `audio_stream` / `audioctl`), hda (`hda` / `hda_stream`), music, libos's
  `mixer_client.c`;
- **network**: netstack's clients, sockets, TCP sockets and listeners,
  `drivers/lib/netserver.c`, dns, sntp, serve (`share` with handle
  arguments), libos's `net.c`, `nettcp.c`, `dns.c`;
- **USB**: usb-bus (`usb`, `usbbus`, `usbbus_events`), devmgr's `usb.c`,
  usb-storage (`storage`, `block`, svc.connect);
- **files**: fat (the lock by directory entry, the 12 KiB request area,
  batched readdir, `FS_EXCL`, Q9's codes), libos's `fs.c` and `fsview.c`,
  the bootfs server;
- **storage**: volumes whole (`chans.c`, `request.c`, `disk.c`, `fsvc.c`,
  `supervise.c`, `spare.c`, `calls.c`, `mounts.c`, `main.c`), fat's
  `disk.c`, libos's supervision module (`supervise.c`, `svcstate.c`,
  `svcserve.c`).

Attacker models: a program with a client channel (a `/data` view, an open
file, an `audio` or `net` opener, a watch), sending malformed messages,
wrong handles, floods, never reading its replies, or dying mid-request;
a filesystem service compromised by a hostile stick image (what volumes
reads from it); a driver answering volumes (`storage`); and a service
that dies at any point and is replayed from its slots.

Severity: **High** lets one ordinary client take a service away from
everyone else (or corrupt what it holds); **Medium** is a memory-safety
slip, data loss on a narrower path, or the same denial with more effort;
**Low** is a narrow case, a stuck state that a re-plug clears, or a
design point.

**1 High, 2 Medium, 6 Low; 3 design questions.** (Finding 9 was found by the new
`volumes_hostile` test, after the rest were written down.)

What held up:

- **The generated code.** Every varying array is read with `idl_get`
  (count, zero padding, the message's end, the maximum) and every `str`
  with `idl_str_ok` before a handler runs; a request must end exactly at
  its last array; handler results are checked against their maxima (and
  UTF-8) before `idl_place`; handle counts are checked per method, typed
  handles with `handle_info`, and every path that doesn't reach a handler
  closes what came. A `kept` protocol can't take handle arguments (genidl
  refuses it, so a replayed slot never holds a dead instance's handle
  values). Replies' handles are never closed after a send (the sweep).
- **Slots and replay.** fat's slot area (12 KiB request + 64 KiB data) is
  asserted against `FS_REQ_MAX`; a message too big for the request part
  but read into the slot is refused by the exact-size check and can't
  forge a data match (`data_seq` is per request). The mixer's caps follow
  the three protocols; both layouts were bumped with their wire changes.
- **volumes.** Every reader of a channel volumes didn't make is bounded
  (64 a turn) but one (finding 5); every task re-checks the slot's
  `serial` after each wait; a watch that falls 256 events behind is
  dropped (`handle_info`'s `peer_queued`); test disks never take `/data`.
- **fsview.** A view's flags are checked on the path as the server walks
  it, and a request the check can't read is refused by the dispatch.

## Design questions (reported, not decided)

**A. Who pays for answers a client never reads (finding 1, every
server).** A server's job pays for every answer queued at a client that
doesn't read, so any server with a job limit and a client that can call
it can be filled the same way (the mixer's openers, netstack's, dns's,
music's), only more slowly than fat with its 8 KiB readdir. Options: (a)
each server keeps the rule fat now has (generated: `idl_serve_next` and
the slot takes could refuse to read from a channel whose peer has N unread
answers, given a hook to wait); (b) the kernel charges a message written
on an end whose peer is a *client* (a reply: the txid of a request it
read) to the reader's job, as Q2 does on close. *Recommendation: (a) in
genidl at M13's start (one rule, no new kernel accounting), with fat's
numbers as the default; (b) only if M13's pipes show the same.*

**B. One shared client end per mount (finding 8).** volumes hands every
namespace a duplicate of its own client end, and reads its own unrouted
answers there. Options: (a) volumes keeps a client end of its own (a
second `fs.view` with no flags, made when the mount is made) for its
probes and syncs, and hands out the shared one; (b) leave it (only
volumes' probes and syncs can be stolen, and only by reading on purpose).
*Recommendation: (a), small, with the next volumes change.*

**C. A quota of views per client (finding 6).** fat has 32 view slots and
32 open files for everyone. *Recommendation: count views and files per
originating channel (a view's parent) and refuse past 8 each; the shell
makes one view per program, so a program can't starve another.* An
addition: after M12.1.

## Answers (2026-10-09, by the recommendation, the owner's standing order)

- **A**: yes: fat's rule (stop serving a client with too many answers
  unread, look again shortly) goes into genidl's serve loops for every
  generated server. Since the owner's change to Q2 (KCORE finding 2) the
  writer pays for what isn't read, so a server pays for answers its
  clients leave unread: the bound is what keeps that from filling its job.
- **B**: yes: volumes keeps a client end of its own for its stat probes
  and syncs.
- **C**: yes, at most 8 views and 8 files per originating channel, as an
  addition after M12.1.

### A and B as built (the follow-up track), and the choices it made

- **A, the bound in genidl.** `<proto>_serve` keeps it itself: before it
  takes the next request it asks `handle_info`; a client with
  `<PROTO>_UNREAD_MSGS` answers (8) or `<PROTO>_UNREAD_BYTES` (8 KiB)
  unread gets the waiting reply alone, and the thread looks again every
  2 ms (and at once when the client goes). A loop of a server's own keeps
  it with `<proto>_unread_full(ch)` before each `_serve_one`, `_take_slot`
  or `svc_serve_request`, and a `struct idl_held` (`idl_hold`,
  `idl_held_deadline`, `idl_held_due`): the channel is left unserved,
  the port wait ends by the next look, and nothing is looked at while
  nothing is held. A protocol raises its bound with an `unread <answers>
  <bytes>` line (at most 1024 and 1 MiB; none does yet). Choice: the rule
  is the caller's for `_serve_one` and `svc_serve_request`, not built
  into them, because a held channel needs its loop to come back to it
  (an edge-triggered binding never fires again for a queue that stays
  readable), and a status those functions never returned would make the
  loops that don't know it (init's and the console's, other tracks')
  close the client's channel. Those loops keep the old behaviour until
  they are changed.
- **Who has it**: fat (moved onto genidl's, the same numbers), serve,
  the mixer, netstack (every channel: shared, openers', sockets', TCP
  sockets' and listeners', netctl's two), dns, music, the compositor's
  control channels (compctl, notify; its Wayland side keeps its own
  rule), fsserver (bootfs, the tests' RAM filesystem), usb-storage
  (storage and block), and every `<proto>_serve` (the crasher). **Not
  yet**: init's control channels (initctl) and logd (P6b's files), the
  console (T1's), devmgr's channels and volumes' own control channels
  (hand-written loops), usb-bus's interface channels, hda, the network
  drivers' netserver and NVMe (N3's): each of those has services or
  drivers as its clients, or belongs to a track running beside this one.
- **Events count.** `peer_queued` counts everything the server wrote, its
  events too: a client that calls while it leaves the server's events
  unread is held back once they reach the bound. No protocol served
  under the rule sends events on a channel its client also calls on, so
  none raises its bound for it.
- **Shared ends** (one end duplicated to many holders: a mount's `fs`
  channel, every service's shared `/svc` channel) are one client to the
  server: one holder that writes the bound of requests with `_send` and
  never reads holds the end back for every holder, until someone reads
  those answers. The server's job stays bounded, which is what the bound
  is for; before it the same holder filled the job and every client of
  the server lost its answers. volumes reads (and drops) whatever lands
  on a mount's shared `fs` channel, as it did before B, so that one can't
  stay held. A shared `/svc` channel has no such reader (init holds its
  client end and reads nothing), so a program with `/svc/net`,
  `/svc/dns`, `/svc/audio`, ... can stop that service's new openers for
  as long as the shared end lives: its answers stay queued there after it
  ends, and nobody reads them. **Chosen** (the safer of the two): the
  bound stays on shared ends too; without it the same program fills the
  server's job (a connect's answer carries a channel: about 1 KiB
  each), and then no client of the server gets an answer at all.
  Follow-up, recommended: (a) whoever keeps a shared end's client side
  (init) reads and drops what lands on it, as volumes does; or (b) the
  kernel refuses a request without a kernel txid (an asynchronous
  `_send`) on an end with more than one handle. (a) is init's (P6b's
  files), so not done here.
- **B, volumes' own channel.** Not a second `fs.view` but a second `fs`
  channel to each service, `FAT_SR_OWN`, made with the shared one and
  kept across restarts as it is (fat serves it as the shared one,
  replays a request in progress on it, and its close ends nothing):
  no round trip before the first probe, no view slot, and no moment when
  the answer to the call that made it waits on the shared channel.
  volumes' stat probes, syncs and a restart's first-answer probe go
  there; utest `disk_own_channel`.
