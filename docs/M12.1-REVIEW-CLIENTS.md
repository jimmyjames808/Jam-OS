# M12.1 review: the desktop's clients

Part 2b of [M12.1](ROADMAP.md) (G1's code, never reviewed whole), at main
2c207a1a: findings first, then fixes (AGENTS.md's standing rule: High and
Medium fixed, one commit each with a test; Lows when trivial; design
questions reported, not decided).

Read in full: libjwl (`user/lib/jwl_*.c`, `user/lib/jwlc.h`,
`user/include/jwl.h`, `user/include/jwl_client.h`, the generated
`<jwl/*.h>` dispatchers): the JWL2 transport (flow control by the
kernel's count, the per-connection handle queue, held batches), the
codec, the object map, shm, the seat, the clipboard, windows, xdg-shell
and jam_window_memory_v1; the console's window mode
(`user/services/console/`, all of it); libfun's window path
(`user/apps/fun/wl.c`, `wlpaint.c`, `mouse.c`, `keys.c`, `gfx.c`); the
protocol XML (`abi/wayland/jam-window-memory-v1.xml`). Not here: the
compositor itself and init's terminals.

The threat models: a hostile **peer client** (any program that can open
/svc/wayland: it reaches the compositor's side of libjwl, and as a
clipboard owner it reaches every client that pastes), a hostile or broken
**compositor** (it reaches every client's side of libjwl, the console and
libfun), and the client's own memory safety under bad input.

**What holds up.** The codec is strict and careful: every length is
checked before it is used, with subtractions that can't wrap, two passes
so a refused message changes nothing, and it is fuzzed already
(`jwl_fuzz_*`). The map's id rules bound both ranges at 4096 entries
whatever the peer does; zombies keep their interface so late events
decode and are dropped, and their map data is cleared, so no event ever
reaches a freed window, buffer, pool or callback (`jwl_window_destroy`
clears its pending frame callback's data; every destroy is a destructor
the transport forgets). Held batches are bounded (64 KiB, bookkeeping
counted) and keep their handles; a refused write of handles is never
retried with stale handle numbers. Every 'h' an event carries is closed
by its handler or by `read_all`. Key codes, keymaps (only the first
128 bytes read, by `vmo_read`), modifier bits, sizes (clamped to 1 to
8192), states arrays, pointer positions and wheel values are bounded
before use in libjwl and the console; the console's grid is clamped to
480x180 whatever size the compositor gives, and every paint is clipped to
the buffer. Pasted text can't carry an ESC into a bracketed paste.

## Design questions

**DQ1. A slow reader's disconnect: fatal or not** (C12). libjwl treats every
wl_display.error as "this program broke the protocol: never again".
- (A) Keep: the compositor's no_memory means the client didn't keep up,
  and a new connection may fall behind the same way.
- (B) A `no_memory` error is a lost connection like a closed channel:
  reconnect with the usual pause; the other codes stay fatal.

*Recommendation: (B)*: the console and the apps then survive a long
pause, which is the case the window's 64 KiB of held events is sized for.

**DQ2. Empty batches** (C1's fix). The fix keeps "an empty batch is fine"
and refuses a run of more than 64.
- (A) As fixed: a run bound.
- (B) Refuse every batch with neither a message nor a handle: a simpler
  rule (a shim never sends one), but it changes what the transport's
  tests say is fine.

*Recommendation: (A)* for M12.1; (B) only if M14's freeze wants the rule
stated without a number.

**DQ3. What a client owes a hostile compositor** (C10, C11). The
compositor owns the screen and the input, so a hostile one can already
freeze every client by sending nothing. Should libjwl bound its own
loops anyway (a budget of messages per dispatch with the deadline "now"
for the rest, as the compositor bounds its clients, and a cap on a
window's committed pool below 8192x8192)?
- (A) No: the compositor is trusted with its clients' time and memory.
- (B) Yes, once ported clients (G2) run under compositors other than ours.

*Recommendation: (A)* now.
