# M12.7 stage 2 check: writes to a Jam OS disk only (W1, W2, W3)

M12.7's review R3 for stage 2 ([M12.7-PLAN.md](M12.7-PLAN.md), "The
owner's answers": R1 and R2 dropped, R3 runs at the end of stage 2,
before P2). Read in full context at branch m127-stage2 (a4d5b300) with
main bf129f4e merged in: drivers/nvme (cmd.c's gate, table.c's
create_table, block.c's writable channels, serve.c, queue.c's reset and
ending), the partition library (drivers/lib/parttable*.c: the blank rule,
W2's widened blank-in-progress rule, the mark, the maker), volumes' write
paths (mark.c, prepare.c, fsvc.c's writable starts and FAT_ARG_FORMAT,
request.c's remount, disk.c's boot-disk rule), init's prepare.c and
ctl.c's prepare_disk, the shell's `disk prepare`, the `diskro` word from
the kernel through init and devmgr to drv/nvme and across kexec, and the
host checks (tools/checknvme.py, tools/gptcheck.c, tools/gptmake.c) and
tools/nvme-write-test.sh.

Looked at first, as the stakes ask (the PC's other drive holds Windows,
and P2 runs `disk prepare` on the blank TEAM drive): can any path build a
Write or a Flush for a drive the driver hasn't positively found to be Jam
OS's (or blank, for create_table)? The write gate's modes and where they
are set; create_table's checks and order; `disk prepare`'s checks in the
shell, volumes and the driver; `diskro` from the boot menu to every
driver and across a reboot; W2's widened blank-in-progress rule; driver
restarts and resets mid-write; a crafted table on the Windows drive; a
stick that claims to be a Jam OS drive; error paths that might leave the
gate open; the time between a check and the write it allows.

Severity, as in the M12.1 and M13 checks: **High** is a write to a drive
that isn't Jam OS's, or a crash or hole a client can cause; **Medium** is
wrong behaviour the system or a test will meet, or a missing defence on
the path to Windows' drive; **Low** is a wart, a fragile limit, or a hole
only a crafted disk or a holder of a power can use.

Counts: **0 High, 2 Medium, 5 Low.** Both Mediums and two Lows are
fixed, one commit each with a test that failed before it (one Medium was
fixed by the merge of main itself); the other three Lows are reported.

Not findings (checked and correct):

- **The gate is set in one place and fails closed.** cmd_arm starts from
  MODE_OTHER every time, returns at once on `ro` or no namespace, and
  sets MODE_JAMOS / MODE_BLANK only from the library's pt_kind on the
  table the driver read itself; serve_start arms it with nothing before
  the first read, and every failed reading (the table unreadable, a read
  stuck, the controller gone, create_table's read-back failing) arms it
  with nothing again. sqe_write checks the mode before the blocks and
  ends the driver otherwise; allowed() checks it again at the one store
  of an entry; sqe_flush refuses MODE_OTHER. tools/checknvme.py keeps it
  so at build time.
- **Windows' drive can't be anything but other.** Its block 0 is a
  protective MBR, so the blank and blank-in-progress rules (block 0 all
  zeros) never apply; the mark needs both headers good, no hybrid MBR and
  exactly Jam OS's two entries by type and name. A crafted table on it
  needs a write to it first.
- **create_table**: refused before its GUIDs are looked at unless
  MODE_BLANK (serve.c and table.c both); one at a time; writes only
  PART_TABLE blocks, each FUA, each after the last one's answer, in the
  plan's order; a failed step, a reset (writes failed ERR_IO, not sent
  again) or a closed channel ends it, and the table is read back and the
  mode set from what is on the drive. The MODE_BLANK gate allows exactly
  the maker's blocks (the first 2 + 32 and the last 1 + 32 at 512 bytes),
  inside the blank rule's 64 KiB ends.
- **W2's widened rule** (cut_after_array): block 0, the primary header and
  array, the blocks before the backup array and the backup header's block
  all zeros, the array's 256 non-zero bytes exactly the maker's for this
  disk (only the two unique GUIDs taken from the bytes, non-zero and
  different), every other byte of the ends zero. A torn array write
  leaves its first block old or new and zeros elsewhere: still the rule's.
  gptcheck's 17 near-misses each read as other.
- **Writable channels**: open_partition writable only on MODE_JAMOS and
  index < 2 (serve.c, then blk_open again); block.write refused on a
  read-only channel before anything; every request's range checked against
  its partition before the start is added, and again in sqe_write against
  the gate's own copy of the two partitions; the map_buffer VMO is
  writable by the client only on a writable channel.
- **Restarts mid-write**: a new drv/nvme disables the controller before
  bus mastering, so a dead driver's writes are finished or dropped before
  the table is read; the drain rule holds a partition while a gone
  client's writes are out; a reset fails writes (ERR_IO) rather than
  sending them again. The kill and restart rounds of nvme-write-test.sh
  `restart` cover them.
- **`disk prepare`**: the shell confirms against the serial of the drive
  it shows, and the call names the drive by its id (its PCI address), not
  its name; volumes checks NVMe, 512-byte blocks, settled, nothing else
  under way, and blank to it or Jam OS's by its own mark; the driver
  decides again. FAT_ARG_FORMAT goes only to a writable start of a
  partition of a disk being prepared that volumes' mark calls Jam OS's,
  and fat formats only a partition whose first sector has no boot
  signature. A stick can't be prepared (BUS_USB: refused in the shell and
  volumes), and usb-storage reads MBRs only, so it can't show a GPT mark.
- **`diskro`**: kernel to init (both modes) to devmgr (both of init's
  starts) to every drv/nvme as `ro`; the kexec'd command line keeps it
  (`update` and `reboot` load with no command line of their own); a cold
  boot comes back by the boot menu's choice, as it should.
- **The time between check and write**: each drive's mode is its own
  driver's, decided from what that driver read, and nothing but that
  driver writes the drive; volumes' and the shell's checks only decide
  whether to ask.

## Design questions for the owner

1. **Should the blank rule look past the ends?** (finding 7) Today it
   reads block 0 and the first and last 64 KiB. Adding the first MiB of
   where each Jam OS partition will start (the plan's ESP start at 1 MiB
   and data start at 513 MiB) catches a drive that was formatted once and
   had its table wiped, at a cost of two more reads. Recommendation: yes,
   before stage 3's installer reuses the rule.
2. **If the TEAM drive doesn't read as blank at P2** (its never-written
   blocks may read as FFh, or the factory may have written something):
   stage 2 refuses it, as it should. Recommendation: stop and report the
   `disks` line and the driver's log line; don't wipe it from Windows.
