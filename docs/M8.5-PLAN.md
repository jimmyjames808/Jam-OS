# M8.5 plan: a crash kernel, and kexec

Goal ([roadmap](ROADMAP.md#later)): **a deliberate panic on the PC ends
with its full log as a file on the stick, and `reboot` kexecs into the
kernel on the stick without a firmware reboot.** It is the Linux kdump
approach: RAM reserved at boot holds a second, ready-to-run Jam OS; a
panic jumps into it on one CPU, and that kernel, booted fresh with its own
drivers, saves the crashed kernel's log ring through the normal
userspace path (usb-storage, fat, logd).

This plan is the main half. All CPUs coming back after a kexec needs the
kernel's own AP startup (INIT-SIPI-SIPI), which a second branch
(`m85-smp`) builds and documents separately; the seam between the two is
one line in `kernel/arch/x86_64/smp.c` (below).

## The rules (from the roadmap, binding)

1. The crash kernel's reserved RAM is **unmapped from the running
   kernel**: no HHDM mapping, nothing anywhere, so a wild write can't
   reach it. It is **checksummed** when loaded and the checksum is
   verified on the panic path before the jump; on a mismatch the panic
   ends as before (halt, or `panic_reboot`) and the screen says why.
2. **From "decide to kexec" to the jump the panic path takes no lock,
   allocates nothing** and calls nothing that can block or fault on bad
   state. The other CPUs are already stopped by the panic's NMI.
3. **The panicking kernel never writes to the stick** or touches USB or
   FAT. The crash kernel boots fresh and saves the log through userspace.
4. **Every device is reset by the crash kernel's drivers**, never assumed
   idle.
5. **No pstore**: nothing relies on firmware keeping RAM across a reset.
6. **A crash kernel that panics halts** with its own panic screen; it
   never kexecs again.

## Fixed decisions

**The reservation.** At boot, before the memory managers start
(`kexec_reserve` in kmain, on `struct boot_info`), the kernel takes one
physically contiguous range out of a usable memory-map entry and gives it
the new memory type `BOOT_MEM_FOREIGN` ("RAM, not this kernel's"):
- **128 MiB by default, below 4 GiB, 2 MiB aligned, the highest that
  fits** (`crashkernel=<MiB>`, 32..1024; `crashkernel=0` turns crash
  kernel and kexec off). Below 4 GiB because the crash kernel's drivers
  allocate DMA32 memory (the xHCI rings, HD Audio's BDL): a crash kernel
  with no memory below 4 GiB would have no DMA32 zone. 2 MiB aligned so
  the HHDM's large pages end cleanly at both edges. The size is measured
  in stage 5 (what the crash kernel's boot uses, plus margin) and the
  number goes here; Linux's distributions use 128-512 MiB for a bigger
  kernel and userland.
- `BOOT_MEM_FOREIGN` is RAM for `pmm_range_has_ram` (so no MMIO resource
  or physical VMO can ever cover it) but not for `boot_mem_is_ram` (no
  vmemmap, no HHDM, never given to the PMM). `vmm_init` skips it like
  reserved memory: the running kernel has no mapping of it at all.
- The kernel writes it only through a 2 MiB **window** in the vmap area:
  mapped, written, unmapped with a TLB shootdown, at boot and in
  `kexec_load`. The window's page table is made once at boot, so the
  panic path can map it read-only by storing PTEs (no lock, no
  allocation) to verify the checksum.

**The image source.** The running kernel's own image is modified at run
time (.data, .bss), so it can't be copied. **`boot/limine.conf` loads
boot/jamos.elf a second time as a module** (path ending in
`jamos.elf`) in every entry, and `tools/qemu-test.sh` does the same; the
bootfs module is already pristine (mapped read-only everywhere). Without
the kernel module no crash kernel is loaded (one log line) and the
region serves `kexec_load` only. The loaded kernel ELF is checked like any
untrusted ELF (`elf_check_range`, the user loader's checks with the
kernel's address range).

**The region's layout** (built by `kernel/kexec/image.c`, the same for
the crash kernel and for a reboot image):

| Offset | What | Type in the new kernel's memory map |
|---|---|---|
| 0 | the kernel's PT_LOAD segments, at `phys = base + (vaddr - lowest vaddr)`, bss zeroed | kernel+modules |
| next page | bootfs.img; and (reboot image only) jamos.elf, for the next crash kernel | kernel+modules |
| next page | the handoff (struct kexec_handoff), the page tables, a 64 KiB stack | loader-reclaimable |
| rest | free | usable (crash kernel) |

Everything the jump needs is built in advance: the panic path copies
nothing.

**The new kernel's page tables** map exactly: the kernel image at its
link address (2 MiB pages, RWX: the new kernel remaps itself in
`vmm_init` as with Limine's tables), the region in the HHDM, the
framebuffer in the HHDM (4 KiB pages, write-combining), the crashed
kernel's log ring and crash record read-only in the HHDM, and the
trampoline page (below). The new kernel builds its own tables in
`vmm_init` and never uses these again.

**The trampoline.** Switching CR3 needs code mapped at the same address
in both page tables, and the new kernel's image sits at the old one's
link address. So the jump code is a page of its own in the kernel's text
(kernel/kexec/tramp.S, section `.text.kexec_tramp`, page aligned), also
mapped read-execute at a fixed vmap address T in the running kernel and
at T in the new tables (W^X holds: its HHDM alias is read-only). It is
part of the checksum. It loads the new CR3, turns CR4.PGE and CR4.PCIDE
off (that flushes every TLB entry of every PCID, global ones too), loads
an empty IDT (a fault from here on triple-faults: a firmware reset, never
a hang), moves to the new stack and jumps to the new kernel's entry with
`rdi = KEXEC_ENTRY_MAGIC`, `rsi = the handoff`.

**One entry point.** Limine enters `_start` with every GPR zero
(PROTOCOL.md); a kexec enters it with the magic in rdi. `_start` picks
`limine_entry` or `kexec_entry` on that.

**The handoff** (`kernel/include/jam/kexec_handoff.h`) is a wire format,
not `struct boot_info`, because it crosses kernel builds: magic, version
1, its own size, a checksum, then fixed-size fields with explicit
numbers for memory types (never the C enum), no implicit padding,
`_Static_assert`ed. `kernel/boot/kexec.c` is the second filler of
`struct boot_info` next to `limine.c`: it validates the handoff
(`kexec_handoff_check`: magic, version, size, checksum, counts, every
string terminated, every type known) and copies it into a static
`boot_info` (the handoff's pages are loader-reclaimable and get freed).
An invalid handoff resets the machine through a triple fault: a kernel
that can't read what it was given can't print either, and a firmware
reboot is better than a hang. The handoff carries every CPU (ACPI uid,
APIC id) with no loader handle; flag `KEXEC_ONE_CPU` (the crash kernel)
keeps only the CPU that entered, found from CPUID (leaf 0Bh, else 1).
The entering CPU is the boot CPU either way, since the panicking CPU or
the one running `kexec_reboot` is not known in advance.

**The seam with `m85-smp`:** `smp_start_aps` skips a CPU whose
`boot_cpu.loader_handle` is NULL ("not parked by a loader"). Until the
join a kexec'd kernel runs on one CPU; the other branch replaces that line
with INIT-SIPI-SIPI.

**The panic path** (`panic.c` calls into kernel/kexec/jump.c):
1. `panic_begin` notes the log's position (the panic's first byte);
   `panic_end` notes it again before the log tail, so the crash kernel can
   show the panic's own lines without the tail.
2. The panic screen is drawn exactly as now.
3. Decide: a crash kernel is loaded (`KX_ARMED`, an atomic load). From
   here: no lock, no allocation, no call into anything with state.
4. The crash record (below) is filled: plain stores into a static page.
5. Verify: the window maps the region read-only page by page (PTE stores
   and INVLPG; the other CPUs are halted, so a local flush is the whole
   flush), the checksum is computed, compared; the trampoline page too.
   A mismatch prints "crash kernel: checksum mismatch ...: not used" and
   the panic ends as today.
6. **Bus Master Enable off on every PCI function but bridges and the
   display** (`pci_panic_bus_master_off`: ECAM writes, no lock, no
   read-back wait). Decided yes: a controller the dead kernel left running
   (xHCI's event ring, HD Audio's stream) would keep writing memory and
   sending MSIs until the crash kernel's driver resets it, and a device
   with a stale DMA address (the kind of bug that panics a kernel) could
   hit anything, the log ring included; BME off stops both, MSIs being
   memory writes. Bridges are left alone because clearing a root port's
   BME would block DMA from everything behind it, the crash kernel's own
   xHCI included (the PCI core never touches bridges); the display is left
   alone so the panic screen stays up. The crash kernel's PCI core then
   gives each driver a new dma_cap (BME off) and the driver turns it on
   only after its reset, as on every boot.
7. INIT to every other CPU (halted by the NMI already): they wait for a
   SIPI from then on, running nothing, so the next kernel can reuse the
   memory they halted in and start them itself (the way Linux leaves
   them).
8. Jump through the trampoline.

**The crash record** is a static page in the running kernel (its
physical address goes in the crash kernel's command line as
`crashlog=<phys>` and in its memory map as `BOOT_MEM_CRASH_LOG`, with the
log ring's pages): magic, version, the ring's physical address and size,
the log's head (bytes ever written), the panic's first byte, the tail's
first byte, the name of this boot's log file, and a checksum. The crash
kernel treats all of it as untrusted: the record must lie in a
`CRASH_LOG` range, its checksum must match, the ring must lie in a
`CRASH_LOG` range, and the name must be 1-31 of `[A-Za-z0-9_-]`.

**The crashed boot's number.** logd chooses `boot-NNNN` and, once it has
its file, tells the kernel the name with a new system call,
`klog_name(reader, name, len)` (on its klog reader handle, RIGHT_READ:
whoever follows the log names its copy; the kernel only keeps the
string). The crash kernel saves the log as `/data/logs/<name>-crash.txt`.
If the crashed boot had no name (no `/data` while it ran), the crash
kernel's logd takes the next free number by logd's own rule, and from now
on that rule counts a number as taken when either `boot-NNNN.txt` or
`boot-NNNN-crash.txt` exists.

**The crash kernel** is the same kernel and bootfs, on the command line
`crash crashlog=<phys> crash_reboot=<s>` (`crash_reboot` = the crashed
kernel's `panic_reboot`; never `panic_reboot` itself, so the crash
kernel's own panic halts):
- `crash` is a mode word: no splash, no tests, no shell. No region is
  reserved and nothing is armed, so a panic in the crash kernel halts
  (rule 6).
- Its memory map: the region usable (but for its loaded parts), the log
  ring and record `CRASH_LOG` (mapped read-only), every other RAM range
  `FOREIGN`, firmware ranges as they were. Its memory managers never see
  the crashed kernel's RAM.
- One CPU. The other CPUs stay halted in the crashed kernel's NMI handler
  (memory the crash kernel never touches).
- The LAPIC: `lapic_init_cpu` also sends an EOI for every vector still in
  service (a panic inside an interrupt handler leaves one set, which would
  block that vector and every lower one). The I/O APIC and the 8259s are
  already masked by `ioapic_init`.
- At boot (`kernel/kexec/crashlog.c`) the record and the ring are checked
  and copied into a VMO: a header (`struct crashlog_header` in
  `<jam/startup.h>`: magic, the text's length, where the panic starts in
  it, bytes lost before it, the name) and the ring's text from oldest to
  newest. userboot hands it to init as the new startup role
  `SR_CRASHLOG` (read-only).
- init's `crash` mode (`user/services/init/crash.c`): devmgr with the
  argument `storage` (PCI drivers as usual, so the xHCI and HD Audio
  controllers are reset; on USB only mass storage: no hid), wait for
  `/data` (bounded: 30 s), run `bin/logd crash` with the crash VMO, stop
  devmgr (which stops fat cleanly: the volume ends marked clean), exit.
  Why logd and not a new program: logd owns `/data/logs`' naming rule and
  file format; the crash save is a second, short mode of it (write the
  header and the text, sync, report the file's name).
- When init has ended, the kernel draws the final screen
  (`crashlog_finish`): the crashed kernel's panic lines (from the old
  ring), then the RESULTS box (with logd's "crash log saved as
  /data/logs/boot-0042-crash.txt", or why not), then halts, or counts down
  `crash_reboot` seconds and resets through the firmware into the normal
  kernel. So the everyday entry still stops on a screen to photograph, and
  the `panic_reboot=15` entry still comes back by itself.

**kexec for `reboot`.** Two system calls, both on the root resource
with RIGHT_MANAGE (what `reboot` needs; booting another kernel is at
least that much authority):
- `kexec_load(root, kernel_vmo, bootfs_vmo, cmdline, len, flags)`: the
  VMOs need RIGHT_READ; the kernel maps them read-only, checks the ELF
  (and the bootfs header), and writes a reboot image into the region:
  kernel, bootfs, the kernel file as a module (for the next boot's crash
  kernel), page tables, a handoff with the full memory map (all RAM
  usable but the region's loaded parts) and every CPU. `len` 0 keeps the
  current command line. While it writes, and afterwards, there is no
  crash kernel (`KX_IMAGE`): a panic then ends as before, with a line
  saying so. ERR_NOT_SUPPORTED without a region, ERR_NO_RESOURCES if it
  doesn't fit, ERR_INVALID_ARGS for a bad ELF or bootfs. Every check
  comes before the region is written, so a refused image changes nothing
  and the crash kernel stays armed.
- `kexec_reboot(root)`: interrupts off, the other CPUs halted by NMI, the
  image's checksum verified (a mismatch: firmware reboot), Bus Master
  Enable off, the jump. ERR_BAD_STATE if nothing is loaded.
init's `reboot` (initctl.reboot, so also Ctrl+Alt+Del): read
`/esp/boot/jamos.elf` and `/esp/boot/bootfs.img` into VMOs, `kexec_load`,
then sync, flush the log, settle (as now), stop devmgr in order (new
`DEVMGR_SHUTDOWN`: the stop devmgr does when its last client leaves:
filesystems synced and stopped clean, class drivers, then the bus
drivers with their final halt and reset), then `kexec_reboot`. Any
failure before the jump (no `/esp`, a read error, `kexec_load` refused)
falls back to the firmware reboot by itself, with a log line. New
`initctl.reboot_firmware` and the shell's `reboot -f` always take the
firmware path. M9's `update` will call the same `kexec_load` with what it
fetched.

**A test-only corruption.** The crash test `kexecbad` flips one byte of
the loaded crash kernel through the window and panics: the panic must
end with the checksum line and halt. The test word `crashtest=<name>` on
the running kernel's command line is passed to the crash kernel as
`test<name>` (a boot-time crash test), so a panic inside the crash
kernel can be provoked.

## Stages

Each stage builds, passes `make check`, and is committed.

0. **This plan.**
1. **Memory types and the reservation.** `BOOT_MEM_FOREIGN` /
   `CRASH_LOG` through pmm, vmm, `memmap`; `kexec_reserve`;
   `crashkernel=`. ktests: the region is in the memory map as foreign,
   not RAM to the PMM, no page of it is mapped in the HHDM or anywhere in
   the kernel's tables; `memmap_overlay` splits; crash test `kexecread`
   (a read through where the HHDM would map it must page-fault).
2. **The handoff and the second entry.** The wire format, its check
   (ktests: valid, every field corrupted, bad checksum, unterminated
   strings, too many entries), `kexec_entry`, `_start`'s choice, the
   smp.c seam.
3. **The loader.** The region layout, ELF load, page tables, handoff,
   checksum; the crash kernel loaded at boot from the modules. ktests: the
   checksum (stable; changes with one flipped byte), the page tables map
   what they must (walked in the staging copy), the region verifies after
   the load.
4. **The panic path.** The record, the verify, BME off, the trampoline;
   `kexecbad`. First QEMU run: a panic reaches the crash kernel's banner.
5. **The crash kernel.** crash mode in kmain, the crash VMO, init's crash
   mode, devmgr `storage`, logd crash mode and `klog_name`, the final
   screen, `crash_reboot`. tools/kdump-test.sh.
6. **kexec reboot.** The two system calls, devmgr SHUTDOWN, init's
   reboot, `reboot -f`, `initctl.reboot_firmware`.
   tools/kexec-reboot-test.sh. utests for the calls' refusals (bad
   handles, missing rights, wrong types).
7. **Docs and the regression.** ARCHITECTURE, TESTING, ROADMAP, README;
   `make check`, ktest at 4 and 8 CPUs, utest, every area and shell
   script.

## Tests

**QEMU** (tools/kdump-test.sh, each case its own boot of a stick
image; the image read afterwards with mtools as `tools/data-test.sh`
does):
- the crash save: a plain boot, `crash panic yes`; the crash kernel's
  banner, init's crash mode, logd's "crash log saved as
  /data/logs/boot-NNNN-crash.txt" on serial and in the final RESULTS box,
  "system halted."; the file exists, its NNNN is the crashed boot's own
  log's number, and it holds the panic message and the lines logged just
  before the panic;
- `panic_reboot=5`: the crash kernel counts down and resets (QEMU's
  `-no-reboot` ends the run there); the saved image then boots into the
  normal kernel and its shell lists the crash file;
- `crash kexecbad yes`: "checksum mismatch", no crash kernel, "system
  halted.";
- `crashtest=panic`: the crash kernel panics at boot and halts with its
  own panic screen; no third kernel;
- the stick pulled (the monitor's `device_del`) before the panic: the
  crash kernel says the log was not saved and why, and halts.

tools/kexec-reboot-test.sh: `reboot` kexecs (no firmware reset: QEMU's
`-no-reboot` would end the run), the new kernel says it came from kexec
and reaches the shell, which runs commands and reads `/data`; `reboot -f`
resets through the firmware; with `crashkernel=0` `reboot` falls back to
the firmware by itself.

ktests as listed per stage; utests for the system calls' refusals; the
full regression afterwards. The crash tests (`tools/crash-test.sh`) and
the shell scripts that end in a panic now pass through the crash kernel
too: they must still pass.

## What only the PC can prove

- That the reservation finds 128 MiB below 4 GiB on the PC's map and
  that the crash kernel fits in it there (28 CPUs' worth of firmware
  tables, the real vmemmap).
- The Intel xHCI (8086:7a60) and HD Audio controllers left running by a
  dead kernel, with Bus Master Enable cleared under them, then halted and
  reset by the crash kernel's drivers; the stick found again.
- The panic on any of the 28 CPUs (P- or E-core, x2APIC) becoming the
  crash kernel's boot CPU; a panic from inside an interrupt handler or an
  NMI (the watchdog).
- The NVIDIA framebuffer staying up through the jump.
- The time from panic to saved file.
- A kexec reboot with all 28 CPUs (after the join with `m85-smp`).
