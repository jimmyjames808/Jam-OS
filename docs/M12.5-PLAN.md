Goal ([roadmap](ROADMAP.md#later)): **a process (a filesystem service)
supplies the pages of a VMO on demand: mapped files (a cached read becomes
a memory copy, and M13's `mmap` has something to stand on), programs loaded
on demand instead of read whole, and the clean way to run programs from
`/data` (the pages come from fat, checked against the approved hash).
Pager failures (a pulled stick) end in a clean error, never a kernel hang.**

**Done when** (the roadmap's row made concrete):
- a file on `/data` and one on a second stick, mapped by a test program and
  read through its pages, hash the same as `sha256sum` reads them; the
  second pass over a file the cache holds makes no request to fat;
- an allowed program on `/data` runs from fat's pager: its code pages come
  in as it touches them, each checked by the kernel against the hash
  `allow` approved; a page that doesn't match is never mapped;
- pulling the stick under a mapping fails the next access cleanly: a
  system call's copy gets `ERR_IO`, a load or a fetch kills only the
  process that made it, with a line saying why; the kernel, fat's other
  mounts and every other program carry on; a fat that hangs is caught by a
  deadline; nothing waits forever;
- fat still outlives its process: `storm` on `/data`'s fat while a program
  reads a mapped file and another runs from the pager, and neither sees an
  error;
- and, as every milestone: All tests and `soak 10` on the PC.

## What M12.5 is not

- **No writable mappings of files** (question 1): mappings of a pager's
  VMO are read-only, or executable. No dirty pages, no write-back.
- **No copy-on-write child VMO** (`MAP_PRIVATE`, the kernel review's
  finding 37): M13's, with `mmap` (question 1).
- **No memory pressure across the system**: each pager has a budget and
  evicts within it (question 3); nothing reclaims pages because the
  machine is short of them, and there is no swap.
- **No `mmap` in libc**: M13 builds it on what this milestone adds.
- **One pager**: fat. The boot image (`/boot`) is in memory already;
  netstack, the mixer and the rest have nothing to page.
- **No NVMe** (M12.7): its disks are paged through fat like a stick's.

## The design

### Words

A **pager** is a kernel object; its holder (fat) supplies pages. A
**pager VMO** is a paged VMO made from a pager, under a **key** (a number
the pager chooses: fat's open file). A **request** is the kernel asking the
pager for a range of a pager VMO that some thread is waiting for. **Supply**
fills absent pages; **fail** answers a request with an error; **detach**
cuts a VMO off its pager for good.

### The pager object and its VMOs

- `pager_create` makes a pager. With question 5's answer it needs a root
  power, `RIGHT_ROOT_PAGER`, which only volumes holds (init gives volumes a
  root slice with that power alone). The pager carries its **budget** (how
  many pages its VMOs may hold at once: question 3) and its **answer time**
  (how long a request may wait: 60 s, `FS_CALL_TIMEOUT`, so a mapped file
  and a `read` give up alike).
- `pager_create_vmo(pager, key, size)` makes a pager VMO. Every page starts
  absent. The handle has `READ MAP DUPLICATE TRANSFER WAIT INSPECT`: never
  `WRITE` (`vmo_write` is refused, question 1), `RESIZE` (the size is the
  pager's: `PAGER_OP_SET_SIZE`) or `EXEC` (only `vmo_make_exec_verified`
  gives that). The pager holds no handle to it: it names it by key, so a
  fat that died left nothing to recover but the pager handle itself. A key
  is unique among the pager's live VMOs (`ERR_ALREADY_EXISTS`).
- What a pager VMO refuses: `vmo_pin` (a device can't wait for a pager),
  `vmo_map_kernel`, `VMAR_KEPT_ONLY` (a pager VMO is never kept, so the
  compositor's pool rule refuses it as it does today), `vmo_commit` and
  `vmo_decommit` (the pager's ops do both). `vmo_read` works and waits like
  a fault.
- When a pager VMO has no handle and no mapping left, the pager gets a
  `PAGER_REQ_GONE` request for its key: fat forgets the file then (an
  `mmap` outlives the `close`, as POSIX wants).

### Requests

- A fault on an absent page of a pager VMO (or a `vmo_read`, or a user
  copy) looks for a request already covering that page; if there is none
  it queues one, then waits on it. Two threads on one page make one
  request; 28 CPUs faulting one file make one request a page.
- **Size**: the page asked for, then the absent pages after it up to 16
  (64 KiB, a fat cache line), stopping at a present page or the VMO's end.
  The pager may supply more (its own read-ahead).
- The pager **reads requests** with `pager_next`, which never blocks. The
  pager object is `SIG_READABLE` while one is queued, so fat binds it to
  the port it already waits on and serves page requests between `fs` and
  `file` requests, one loop as now.
- **Requests stay in the kernel until they are answered.** `pager_next`
  marks one delivered; a successor's first call passes `PAGER_NEXT_AGAIN`,
  which puts every delivered-but-unanswered request back. Supplying a page
  that is present is a no-op, so a request answered twice is harmless.
  This is how a pager outlives its process (below, "fat as the first
  pager").
- A request whose answer time passed is failed `ERR_TIMED_OUT` by the
  first of its waiters to wake at the deadline (each waits until then), or
  by `pager_next` when it meets it: no kernel timer is needed.

### Supplying pages

- `pager_supply(pager, key, offset, buf, len)`: the kernel allocates the
  pages, copies them from the pager's buffer (a user pointer, at most 1 MiB
  a call), then publishes each into its slot under the VMO lock if the slot
  is still absent (else drops it), and wakes every request now whole. A copy,
  not Fuchsia's move of pages from another VMO: a 4 KiB copy is a fraction
  of a microsecond beside a stick's millisecond, and it needs no charge to
  move between jobs, no source VMO's mappings zapped and no rule on which
  VMOs may give pages. Moving can come later as an addition.
- A **verified** VMO (programs from `/data`, below) hashes each page before
  it is published: a page that doesn't match its table entry is dropped,
  its waiters fail `ERR_IO`, the kernel logs `pager: page <n> of <key>
  doesn't match its approved hash`, and the call returns `ERR_IO`.
- `pager_op(pager, key, op, offset, len, arg)`:
  - `PAGER_OP_FAIL`: fail the requests in the range with `arg`
    (`ERR_IO` or `ERR_OUT_OF_RANGE`; anything else is `ERR_INVALID_ARGS`):
    the stick's read error;
  - `PAGER_OP_INVALIDATE`: drop the range's present pages (zapped from
    every mapping, freed after the shootdown, as a decommit): the file was
    written through `file.write`, the next access fetches the new bytes;
  - `PAGER_OP_SET_SIZE` (`offset` is the size): truncate or grow; past the
    end is a bus error as for a shrunk VMO today;
  - `PAGER_OP_DETACH`: the key's VMO is cut off for good: its pending and
    later requests fail `ERR_PEER_CLOSED`, its present pages are dropped
    (question 6), the key is free.
- Closing the pager's last handle detaches every VMO it made.

### The fault path: waiting without a hang

`aspace_fault` holds the region lock across the whole fault today, which
is safe because a fault never waits for anyone. With pagers it may wait
for seconds, and the region lock also guards `vmar_map`, `vmar_unmap`,
`vmar_protect` and every other fault of the process, so it must not be
held while waiting (Linux's `VM_FAULT_RETRY`):

1. `vmo_fault_map` finds the slot absent on a pager VMO: it queues or
   joins a request, takes a reference on it and returns `ERR_SHOULD_WAIT`
   with the request.
2. `aspace_fault` drops the region lock and waits on the request:
   cancellable (a kill ends it, `ERR_CANCELED`), until the request's
   deadline.
3. On a supply it takes the region lock again and starts over from
   `find`: the mapping may be gone (`ERR_NOT_FOUND`, the usual kill), moved
   or changed. A supplied page is the newest in the budget's order, so it
   survives until the retry in all but a pathological thrash; after 8
   rounds the fault fails `ERR_NO_MEMORY` rather than loop.

What each failure does:

| The request ends | A fault in user mode | A user copy in a system call |
|---|---|---|
| supplied | the access is retried | the copy goes on |
| `PAGER_OP_FAIL` (`ERR_IO`) | killed: `page fault: the file's pager couldn't read it` | `ERR_IO` |
| detached, or the pager's last handle closed | killed: `page fault: the file's pager is gone` | `ERR_IO` |
| the answer time passed | killed: `page fault: the file's pager didn't answer` | `ERR_IO` |
| a page that doesn't match its hash | killed: `page fault: a page doesn't match the approved program` | `ERR_IO` |
| the waiting thread was killed | (it is dying anyway) | `ERR_CANCELED` |

Killing is the clean end a load or a fetch can have until M13's signals
(`SIGBUS`); it is what a read past a shrunk VMO does today. The copies
return `ERR_IO` instead of `ERR_INVALID_ARGS`: `usercopy.S`'s fixup path
reads the fault's status from the thread.

**Lock rules this adds** (for the kernel tracks and the review): nothing
waits for a pager with a spinlock held (the copies already refuse:
`check_copy_context`), with the region lock held (above), or with a
kernel mutex held that another process's progress needs. Every
`copy_from_user` and `copy_to_user` site that holds a mutex is listed and
checked by PK2 (none is known to hold one today, but nothing has had to
prove it: a copy's fault never waited for another process before).

### When the pager dies or hangs

- **The pager process dies** (a crash, `storm`'s kill): its requests stay
  queued in the pager object, which volumes still holds. The successor
  takes them again (`PAGER_NEXT_AGAIN`) and answers them; the waiting
  threads see only a slower page, as fat's clients see a slower answer.
- **The pager is given up on, the disk goes, the mount is stopped**:
  volumes closes the pager; every VMO it made is detached; waiting threads
  fail at once.
- **The pager hangs** (a loop, a stuck disk below it): every request ends
  at its deadline. usb-storage's own command timeouts (5 s) mean a stuck
  stick normally reaches fat as `ERR_IO` long before.
- **The pager faults on its own VMOs**: fat never maps a pager VMO; if a
  pager did, its own fault would wait on itself until the deadline, then
  die: a bug in that pager, not a hang of the kernel.
- **A hostile pager** (with question 5's power, only volumes' fat can be
  one): it can make the threads that touch its VMOs wait until the
  deadline, then die. It can't make the kernel wait, hold a lock, or keep
  memory beyond its budget.

### The page cache: budget and eviction

The pager VMOs' pages are fat's page cache. Each pager has a budget in
pages (volumes sets it: question 3 recommends 1/16 of memory per mount, 2
GiB on the PC). Pages are charged when they are supplied (question 4). A
supply that would pass the budget first evicts the oldest supplied pages
of that pager (a first-in, first-out list in the pager object, one entry
a resident page, charged with it). Every page of a pager VMO is clean
(question 1), so eviction never asks the pager anything: it zaps the page
from every mapping and frees it after the shootdown, exactly as a
decommit, and the next access fetches it again. This is the hazard Mach's
external pagers had, avoided: there, reclaiming memory meant sending dirty
pages to a pager that might never answer.

### Writes and coherence

Mappings are read-only (question 1). The file still changes through
`file.write` and `file.truncate`, and a mapping must see that:

- fat's write path, once a write's sectors are committed to the disk,
  calls `PAGER_OP_INVALIDATE` on the written range of that file's VMO (if
  it has one); `truncate` calls `PAGER_OP_SET_SIZE`. A mapping then reads
  the new bytes (`MAP_SHARED`'s rule). The ordering argument: the
  invalidate comes after the write is in fat's cache and before the write
  is answered, so a program that saw the answer and then reads the mapping
  sees the new bytes.
- A file a program **runs** from (its VMO made with `FILE_MAP_EXEC`):
  question 7 recommends that writing, truncating, renaming over and
  unlinking it is `ERR_BUSY` while that VMO lives (Unix's `ETXTBSY`). With
  the other option the write goes through and the program dies at its next
  fetch of a changed page (the hash check). Either way the program never
  runs bytes that weren't approved.
- **Unlinking a mapped file** (not running): FAT frees the clusters at
  once, so fat detaches the VMO first; later accesses fail as for a pulled
  stick. A POSIX program expects to go on reading an unlinked file; fat
  keeping the clusters of an unlinked mapped file until `PAGER_REQ_GONE`
  is M13's to weigh, not M12.5's.

### Job accounting

| What | Charged to | When |
|---|---|---|
| the pager object | the creator's job (volumes'), one handle unit | create to destroy |
| a pager VMO's struct and its table pages | the pager's job, as any VMO's | create to destroy |
| a pager VMO's pages | the pager's job (question 4), within the budget | supply to eviction, invalidation or detach |
| the eviction list | the pager's job, 16 bytes a resident page | with the page |
| a request | the faulting thread's job, as message bytes (about 128 bytes) | queued to answered; a thread queues at most one at a time, so requests are bounded by threads |
| a verified VMO's hash table | the job of whoever made it executable (the shell's), 32 bytes a page | with the VMO |

volumes' job limit must leave room for its mounts' budgets (PU sets it).
A client mapping a file bigger than the budget only makes the cache evict;
it can't make volumes' job refuse fat's own memory.

### fat as the first pager

- **Startup**: volumes makes one pager per mount when it first starts its
  fat and hands it to every instance and every promoted spare as a new
  startup role, `FAT_SR_PAGER`, with `READ WRITE WAIT` only (no duplicate
  or transfer: fat can't pass it on, as the state VMO). It is like the
  state VMO: volumes keeps it, never uses it, closes it with the mount.
- **`file.map(flags)`** on an open file's channel answers a VMO handle and
  the size. `FILE_MAP_READ`: the file's one shared VMO, made on the first
  map (key: the file's directory entry, the same key P5's lock uses), every
  mapper sharing its pages. `FILE_MAP_EXEC`: a VMO of its own every time,
  never shared, so the shell holds its only handle (`vmo_make_exec_verified`
  needs that, as `vmo_make_exec` does now). fat records the key with the
  file in its state (layout 5 becomes 6), so a successor knows what each
  key is; a mapped file stays open in fat until `PAGER_REQ_GONE`.
- **A page request** is read with FatFs into a buffer of fat's (through its
  block cache: a sequential mapper still reads 64 KiB at a time from the
  stick), then `pager_supply`; a read error is `PAGER_OP_FAIL` with
  `ERR_IO`; a request past the file's end gets zeros for the last page's
  tail and `ERR_OUT_OF_RANGE` beyond. A page request changes nothing in
  fat's state, so it needs no slot and no commit: a successor just asks
  again.
- **Restarts**: the successor's adopt (`user/services/fat/adopt.c`) calls
  `pager_next(PAGER_NEXT_AGAIN)` once, then serves as before. A mapped
  file whose key the state doesn't know (a death between `pager_create_vmo`
  and the commit) is detached. `storm` at 10 kills a second with a mapper
  reading proves it.
- **The disk goes**: volumes stops the mount and closes the pager (detach
  everything) before it forgets the disk.

### Programs from `/data`

Today the shell reads the whole program, seals it, hashes it, and only
then starts it; the trust is that nothing can change sealed bytes. With a
pager the bytes arrive later, from fat, page by page, so the check must
come with each page. Who checks: **the kernel**, against a table of page
hashes the shell hands it once. Not fat (Fuchsia's blobfs checks its own
pages, but fat parses an untrusted disk: a fat broken by a crafted
filesystem could then serve any code to every approved program), and not
a separate verifier service (one more process on every page's path, for a
check that is 30 lines of kernel code around a SHA-256).

1. **`allow`** (approval) hashes the file as now and also writes its
   **page table**: `/data/etc/allow.d/<sha-256>` holds a header (magic,
   the file's size, its whole SHA-256) and the SHA-256 of each 4 KiB page
   (the last zero-padded): 256 KiB for a 32 MiB program. `/data/etc` is
   what every program's view leaves out, so the table is as trusted as the
   allow line (question 2).
2. **Running**: the shell opens the file, asks fat for `file.map(EXEC)`,
   reads the table (its header's hash and size must be the allow line's
   and the file's), and calls `vmo_make_exec_verified(vmo, root, table)`
   (`RIGHT_ROOT_VMEX`, as now). The kernel copies the table in, drops any
   page already present (none: the VMO is new), and from then on publishes
   only pages that match it. The shell reads the program's list (`wants`)
   through a read-only mapping of that same VMO: verified pages too. Then
   `spawn` as today.
3. **An approval with no table** (made before M12.5): the first run reads
   the file whole through the pager, checks its SHA-256 against the line
   as today, writes the table, then goes on as in 2. One full read, once.

The program's code pages come in as it runs; pages the program never
touches are never read. Approval remains the owner's `allow`; no program
gains anything (`RIGHT_ROOT_VMEX` stays the shell's and init's).

### Compared with Fuchsia and Mach

- **Fuchsia** (`zx_pager_create`, `zx_pager_create_vmo` with a port and a
  key, `ZX_PAGER_VMO_READ` packets, `zx_pager_supply_pages` moving pages
  from an auxiliary VMO, `zx_pager_op_range` to fail or mark dirty,
  `ZX_PAGER_VMO_COMPLETE`): the same object model. The differences:
  requests stay in the pager object until answered, so a pager outlives its
  process (fat's successors); a copy instead of a move; a budget and
  eviction per pager; the hash checked by the kernel rather than by the
  pager; detach drops the resident pages (question 6); a pager needs a
  root power (question 5).
- **Mach's external pager** (`memory_object_data_request` and
  `_data_supply` messages on ports): the kernel trusted pagers to answer
  and, worse, to take dirty pages back under memory pressure, so a slow
  pager could stall the whole system. Here no page is ever dirty, eviction
  never involves the pager, and every wait has a deadline and a kill.

## The new interfaces (for M14's review)

### System calls

A new group, "pagers" (numbers 160-164), and one VMO call in the free
number 59. Arguments as `abi/syscalls.def` writes them; rights as
`<jam/abi.h>` names them.

|---|---|---|
| 160 | `pager_create(handle_t root, uint64_t max_pages, uint64_t answer_ns, uint32_t flags, handle_t *out)` | a pager; `RIGHT_ROOT_PAGER` on root (question 5); `max_pages` its budget (0: `ERR_INVALID_ARGS`), `answer_ns` how long a request may wait (1 ms to 600 s), flags 0. Out: `PAGER_RIGHTS` (`READ WRITE WAIT DUPLICATE TRANSFER INSPECT`) |

And in `<jam/abi.h>`:

```c
#define OBJ_PAGER          /* the next free type number */
#define RIGHT_ROOT_PAGER   (1u << 26)   /* pager_create: supply other processes' pages */
#define PAGER_NEXT_AGAIN   (1u << 0)
#define PAGER_SUPPLY_MAX   (1u << 20)
#define PAGER_OP_FAIL       1
#define PAGER_OP_INVALIDATE 2
#define PAGER_OP_SET_SIZE   3
#define PAGER_OP_DETACH     4

struct pager_request {
    uint64_t key;      /* the VMO's key */
    uint64_t offset;   /* bytes, page-aligned */
    uint64_t len;      /* bytes, page-aligned; 0 for PAGER_REQ_GONE */
    uint32_t kind;     /* PAGER_REQ_READ 1, PAGER_REQ_GONE 2 */
    uint32_t reserved; /* 0 */
};
```

`handle_info` names the new type, so a service that maps VMOs from
clients can see a pager VMO and refuse it (the compositor's kept-only rule
already does). `sys.h` gains the error mapping for the copies (`ERR_IO`).

### The file protocol

`abi/idl/file.idl` gains one method (an addition; fat's state layout
version moves with it):

```
# Map the file: a VMO whose pages are the file's, fetched as they are
# touched; `size` is the file's now (the VMO follows a truncate or growth).
# FILE_MAP_READ: the file's one shared VMO, read and map only.
# FILE_MAP_EXEC: a VMO of its own, for vmo_make_exec_verified (the shell).
# A view without the file's read right: ERR_ACCESS_DENIED. A directory:
# ERR_IS_DIR. Restart: a successor answers its keys' requests.
6  map  (u32 flags) -> (handle<vmo> vmo, u64 size)
```

### libos and startup

- `<os.h>`: `file_map(const char *path, uint32_t flags, handle_t *vmo,
  uint64_t *size)` and `fs_map_file(struct jfile *, ...)` for an open one;
  `mapped_file_open(path, &mf)` / `mapped_file_close` (map into the
  caller's own vmar, read-only) for the test program and M13's `mmap`.
- `user/include/fatsvc.h`: `FAT_SR_PAGER`. volumes' root slice
  (`RIGHT_ROOT_PAGER` alone) from init.

## Questions for the owner

Each ends with a recommendation; the plan assumes it until you say
otherwise.

### Q1. Writable mappings: now or later

- **(A)** Read-only (and executable) mappings now; files change through
  `file.write`, and mappings see the change (invalidate). Writable shared
  mappings and the copy-on-write child (`MAP_PRIVATE`) come with M13's
  `mmap`, which knows what its programs ask for.
- **(B)** Writable shared mappings now: dirty tracking, write-back by fat,
  and the order against fat's write-through (an answered write is on the
  stick: a dirty page isn't, so a pulled stick loses it).
- **(C)** (A) plus the copy-on-write child now.

*Recommendation: (A).* Clean pages are what make eviction and a dead
pager simple (no write-back can hang); (B) breaks "nothing answered is
lost when the stick goes" unless `msync` is the only promise, and that is
M13's semantics to choose. The loader doesn't need (C): it copies writable
segments.

### Q2. Programs from `/data`: the hash per page or at load

- **(A)** At load: read the file whole through the pager, hash it as now,
  then let its pages go; fat refuses writes while it runs, and trusts fat
  for every later fetch of an evicted page.
- **(B)** Per page, with the table built at each start from one full read
  (no change to `allow`'s file).
- **(C)** Per page, with the table written by `allow` next to the approval
  (`/data/etc/allow.d/<sha-256>`) and (B)'s full read only once for an
  approval made before M12.5.

*Recommendation: (C).* Only (C) loads a program on demand, as the
roadmap asks, and checks every page that ever arrives, so a broken fat or
a changed file can't put an unapproved byte in a program. Its cost is a
small file per approval and SHA-256 in the kernel (about 10 us a page in
plain C, nothing beside a stick read).

### Q3. The page cache: eviction now or later

- **(A)** No eviction: pages stay until their VMO goes; a supply over the
  job's limit fails and the reader dies.
- **(B)** A budget per pager (volumes: 1/16 of memory per mount, 2 GiB on
  the PC) with the oldest pages evicted first; no global reclaim.
- **(C)** (B) and reclaim from every pager when the machine runs short.

*Recommendation: (B).* The PC's 32 GB means (C)'s pressure never comes
today, but without (B) one big mapped file (a 4 GiB video on a stick)
kills its reader or fills volumes' job. Clean pages make (B) a decommit
with a list: about a third of a track.

### Q4. Who pays for the cached pages

- **(A)** The pager's job (volumes'), bounded by the budget: the cache is
  the filesystem's.
- **(B)** The job of the program that first touched each page.

*Recommendation: (A).* Pages are shared by every mapper; charging the
first to touch one makes one program pay for another's reads and keeps the
charge after it exits. (A) bounds the total by the budget and lets no
mapper make volumes' job refuse anything (it evicts instead).

### Q5. Who may create a pager

- **(A)** Only a holder of a new root power, `RIGHT_ROOT_PAGER` (volumes,
  then fat through the pager it is handed).
- **(B)** Any process, as in Fuchsia.

*Recommendation: (A).* A pager VMO handed to a service that maps it makes
that service wait until the deadline and then die (a service that maps
client VMOs without the kept-only rule). (A) keeps pagers to the
filesystems the system trusts; a user filesystem (FUSE's kind) can ask for
(B) later, an addition.

### Q6. A detached pager VMO's resident pages

- **(A)** Dropped: after a pulled stick every access through the mapping
  fails, whichever pages were read before.
- **(B)** Kept: pages read before stay readable, only absent pages fail
  (Fuchsia's rule).

*Recommendation: (A).* One rule a test and a person can rely on (the
stick is gone, so is the file), and the memory comes back at once. (B)
lets a program limp on with half a file.

### Q7. A file a program runs from

- **(A)** Writing, truncating, renaming over or unlinking it is `ERR_BUSY`
  while the program runs (Unix's `ETXTBSY`).
- **(B)** Allowed; the program dies at its next fetch of a changed page
  (the hash check), or of any page after an unlink (detached).

*Recommendation: (A).* A copy over a running program's file is a mistake
worth an error, not a dead program. fat knows which keys are `EXEC` maps;
the cost is one check in its write, truncate, rename and unlink paths.

### Q8. Which reads use the pages

- **(A)** Only mappers (the test program, programs from `/data`, M13's
  `mmap`); libos's `file_read` stays a request to fat, and moves onto the
  pages with M13's `read`.
- **(B)** libos's read-only reads (`file_read`, `file_read_vmo`: `cat`,
  `cp`, the music player, `spawn` from a path) map now, so every repeated
  read of a file is a memory copy.

*Recommendation: (A).* (B) puts every file read on the new path in the
milestone that builds it; M13 rewrites libos's file layer anyway, and its
`read` is where (B) belongs.

## Risks

- **A fault that waits.** Until now no fault waited on another process.
  The region lock is dropped (PK2); any other lock held across a user copy
  becomes a wait on fat. PK2 lists every copy site that holds a mutex; the
  review reads them again; the hostile-pager ktest holds a waiter at its
  deadline while the rest of the system runs.
- **fat waiting on itself.** fat must never touch a pager VMO, and nothing
  fat calls may (usb-storage, the block buffer: pins are refused for pager
  VMOs, so a buffer can't be one). A pager VMO handed to fat as a buffer is
  refused by the pin rule; one passed to any other service that maps
  client VMOs makes that service wait until the deadline: question 5 keeps
  pagers to volumes, `handle_info` lets a service refuse them.
- **fat's state across M12.5.** The layout moves to 6: a successor of a
  layout-5 fat (the update across the milestone) starts fresh, as the
  rule already says; PF1 runs the restart tests.
- **The update across M12.5.** The old build fetches and starts the new
  one; the allow file keeps its format (the tables are new files beside
  it), so the old build's approvals still run on the new one (question 2's
  fallback) and a new build's tables mean nothing to an old one.
- **Coherence holes.** A write through `file.write` that a mapping misses
  is silent. PF2's test writes under a reader at every offset class
  (inside a page, across pages, past the end, a truncate inside a page);
  the review checks every write path in fat calls the invalidate.
- **Kernel SHA-256.** A new 200-line piece of crypto in the kernel; tested
  against libos's on the same bytes and against FIPS vectors; constant
  work per page (no secret involved, so no timing concern).
- **Size creep.** Writable mappings, the copy-on-write child, system-wide
  reclaim and `mmap` are M13's or later by question 1, 3 and 8's
  recommendations; a finding that needs one becomes a question, not a
  track.

## PK1 notes

Choices PK1 made where the plan left room (the safest reasonable one each
time), and what it leaves to PK2.

- **PAGER_REQ_GONE is answered by `PAGER_OP_DETACH` of its key.** Until
  then the key stays taken (`pager_create_vmo` with it is
  `ERR_ALREADY_EXISTS`) and the GONE is redelivered by
  `PAGER_NEXT_AGAIN` like any request, so a fat that dies between reading
  a GONE and forgetting the file learns it again, and a request for the
  old VMO can never be mistaken for the new one's. The pager's close
  drops unanswered GONEs. Each VMO's link is one `JOB_LIMIT_HANDLES` unit
  of the pager's job until it goes, so a pager that never answers is
  bounded by its job.
- **A request is answered whole.** Its waiters wake when every page of it
  is present (or it fails); a pager supplies a request's range in one call
  as fat will. A request never covers a page another request covers (it
  is cut short there), so one page is in one request at most. A waiter
  whose own page arrived before the request failed reads it anyway.
- **`vmo_read`'s errors:** every way the pager fails a page
  (`PAGER_OP_FAIL` with either status, detached or gone, no answer in
  time) is `ERR_IO`; `ERR_CANCELED` when the thread is killed;
  `ERR_OUT_OF_RANGE` only past the size, as for any VMO; `ERR_NO_MEMORY`
  if the reader's job can't pay for a request, or a page went again 8
  times between its supply and the read's look (the fault path's rule).
  The wait is cancellable (`thread_cancel`), not interruptible: when M13's
  K1 adds `thread_interrupt`, a fault's wait must stay uninterruptible (a
  signal can't restart a load half way); `vmo_read` may take it later if
  M13's `read` wants `EINTR` on a mapped file, nothing needs it now.
- **The refusals:** `vmo_write`, `vmo_commit`, `vmo_decommit`,
  `vmo_set_size`, `vmo_map_kernel` and `vmo_pin` are `ERR_NOT_SUPPORTED`
  at the object layer (the handle's missing rights refuse most first);
  `vmo_seal` is `ERR_BAD_STATE`, so `vmo_make_exec` refuses a pager VMO
  (its pages would arrive unchecked: PK4's `vmo_make_exec_verified` is
  the only way, and lifts this for itself); a writable user mapping
  (`ASPACE_WRITE` or `ASPACE_CAN_WRITE`) is `ERR_ACCESS_DENIED` in
  `vmo_umap_add`; `VMAR_KEPT_ONLY` is `ERR_NOT_SUPPORTED` as for any VMO
  that isn't kept.
- **`handle_info`** names a pager `OBJ_PAGER`; a pager VMO stays `OBJ_VMO`
  (so `handle<vmo>` checks pass it) with `related_koid` its pager's koid,
  0 for any other VMO: how a service that maps client VMOs refuses one.
- **Arguments:** `pager_supply` and `PAGER_OP_FAIL` take page-aligned
  ranges with a length of at least a page (`ERR_INVALID_ARGS`);
  `pager_supply` of a key detached while it runs is `ERR_NOT_FOUND`; a
  request `pager_next` can't copy out stays delivered (AGAIN gives it
  again, or it ends at its deadline).
- **Charges:** the pager and each VMO link one handle unit of the
  creator's job; a pager VMO's struct, tables and pages that job's as any
  VMO's; a request `sizeof(struct pager_req)` message bytes of the reader's
  job until it is freed. The budget (`max_pages`) is stored, not enforced:
  PK3's.
- **The pager's close** detaches every VMO from the object teardown
  (`on_zero_handles`, interrupts on): the requests fail, the pages are
  zapped from every mapping and freed after the shootdown.
- **Files:** `sys_pager_*` are declared in `<jam/pager.h>` (not
  `<jam/sys.h>`, which other tracks edit) and the `sysc_pager_*` live in
  a new `kernel/abi/sysc_pager.c`, beside `pager_sys.c` as every area has
  them. Outside the plan's list, minimal: `tools/genidl.py` (the
  `pager` type), `kernel/object/object.c` (its name), `abi_check.c`,
  `kernel/include/jam/vmo.h` (`vmo_read`'s comment), `user/tests/utest/fuzz.c`
  (numbers 0-169), `user/tests/utest/rights.c` and
  `kernel/test/test_sysinfo.c` (the new power).

**What PK2 must add** (PK1 left `kernel/mm/aspace.c` and the user fault
path alone):
- `vmo_fault_map` returns `ERR_SHOULD_WAIT` for an absent page of a pager
  VMO and queues nothing (test `pager_fault_should_wait`); today
  `aspace_fault` hands that to `trap_page_fault`, which kills the thread
  with the generic reason. PK2's `aspace_fault`, on `ERR_SHOULD_WAIT`:
  take a reference to the VMO (`m->vmo`), call
  `vmo_page_request(vmo, idx, &r)` (spinlocks only: fine under the region
  lock), drop the region lock, `pager_req_wait(r)`, `pager_req_put(r)`,
  drop the VMO reference, and start again from `find` (8 rounds, then
  `ERR_NO_MEMORY`). `r == NULL` means the page arrived meanwhile: retry at
  once. The VMO reference matters: the request is failed when the VMO
  dies, and a waiter must not be the one that lets it die.
- The statuses to turn into kill reasons: `ERR_IO` and `ERR_OUT_OF_RANGE`
  from `pager_req_wait` (`PAGER_OP_FAIL`: "couldn't read it"),
  `ERR_PEER_CLOSED` (detached, closed, or from `vmo_page_request`: "is
  gone"), `ERR_TIMED_OUT` ("didn't answer"), `ERR_CANCELED` (dying
  anyway); `vmo_page_request`'s own `ERR_OUT_OF_RANGE` is a shrunk VMO's
  usual bus error. A user copy maps all but `ERR_CANCELED` to `ERR_IO`
  (vmo.c's `pager_fetch` is the model).
- The copy sites that hold a mutex across `copy_*_user` (the audit), and
  any kernel caller of `vmo_read` that holds one: today only the
  `vmo_read` system call reads a VMO a process gave (through a bounce
  buffer, no lock held); `kexec_load` maps with `vmo_map_kernel`, which
  refuses a pager VMO.

## PK2 notes

Choices PK2 made where the plan left room, the audit, and what it leaves
to PK3 and PK4.

- **Where the copies' status comes from: the trap frame, not the
  thread.** `trap_page_fault` puts the copy's status in the frame's `rax`
  before it resumes at the fixup, and both fixups in `usercopy.S` return
  it (nothing there keeps `rax` live across a faulting instruction but
  `copy_str_user_raw`'s index, which the fault ends anyway). So no field
  on `struct thread` (which M13's K1 was changing at the time) and no
  state left on the thread between the fault and the copy's return.
  `copy_user_raw` returns a status now instead of the bytes left (nobody
  used the count). The copies return: `ERR_IO` for every way a pager
  fails a page (`PAGER_OP_FAIL`, detached or closed, no answer in time),
  `ERR_CANCELED` when the thread was killed while it waited, and
  `ERR_INVALID_ARGS` for everything else, as before (a bad pointer, a
  shrunk VMO, `ERR_NO_MEMORY`). Only reads can wait: a pager VMO is never
  mapped writable, so `copy_to_user`'s fault is `ERR_ACCESS_DENIED`
  before anything is asked (ktest `pager_fault_copies`).
- **`aspace_fault`'s statuses** keep one meaning each: `ERR_IO` (the pager
  couldn't read it: `PAGER_OP_FAIL` with `ERR_IO` *or* `ERR_OUT_OF_RANGE`,
  turned into `ERR_IO` there), `ERR_PEER_CLOSED` (gone), `ERR_TIMED_OUT`
  (no answer), `ERR_CANCELED`; `ERR_OUT_OF_RANGE` stays the shrunk VMO's
  bus error, including `vmo_page_request`'s own. `trap_page_fault` turns
  them into the plan's kill reasons; a page that was unmapped while its
  fault waited is the plain "page fault", as for any unmapped address.
- **The request is asked for under the region lock** (as PK1's hand-over
  said: `vmo_page_request` takes spinlocks and allocates the spare, both
  fine under a mutex), and the VMO reference is taken there too: only
  under the region lock are the mapping and `m->vmo` known to be alive.
  The lock goes before the wait; the retry trusts nothing from before it.
- **A failed request that brought our page anyway counts as supplied**
  (`pager_fetch`'s rule: a request is answered whole, so a failure for
  its other pages doesn't lose this one).
- **Rounds:** each wait (each `ERR_SHOULD_WAIT` seen) is a round; the
  ninth is `ERR_NO_MEMORY` ("out of memory" for a user fault,
  `ERR_INVALID_ARGS` for a copy). Nothing can take a present page away
  yet except a detach (which ends the fault with `ERR_PEER_CLOSED`), so
  no ktest reaches the limit: PK3's eviction can.
- **A fault killed while it waits** returns to the trap's exit, where
  `return_to_user_work` ends the thread: no kill message, no
  `user_faults` count, no second `process_kill`. Its request stays for
  the pager and the others waiting on it.
- **Interrupts (M13's K1):** the wait is `pager_req_wait`'s cancellable
  one, never the interruptible kind: `thread_interrupt` is a spurious
  wakeup there, the fault keeps waiting, and the interrupt stays latched
  for the thread's next interruptible wait (ktest
  `pager_fault_interrupt`). A load can't be restarted half way, so a
  signal must wait for the page or the deadline.
- **The audit as a runtime check:** a fault that waits for a pager while
  its thread holds a mutex is counted (`aspace_pager_waits_held`) and
  reported on the console with lockdep's list of held locks. The audit
  below found none; a new one shows the first time it waits.
- **Tests** (kernel/test/test_pager.c, the fault-path section): kernel
  threads in `aspace_fault` (`pager_fault_wait`: the region lock is free
  while it waits; `pager_fault_interrupt`), ring-3 threads of no process
  running a three-instruction load-and-store program in a real address
  space (supplied, failed with either status, detached, the pager
  closed, timed out, killed while waiting, unmapped by another thread
  while waiting with the waiter's VMO reference the last, 8 threads on
  one page), kernel threads copying through the address space
  (`pager_fault_copies`, `pager_fault_copy_cancel_and_held`), and the
  hostile pager (`pager_fault_hostile`: never answers; three ring-3
  threads and a copy wait in one address space while it maps, unmaps
  and runs a bystander thread, and another reads a healthy pager's VMO;
  all four die at the deadline with the reason, and nothing is left
  queued or charged). The kill messages are read back from the kernel
  log. `pager_fault_should_wait` (PK1) became `pager_fault_wait`.
- **Outside the files listed:** comments only, in `<jam/aspace.h>`
  (`aspace_fault`'s statuses) and `<jam/usercopy.h>` (the copies').

**The mutex-across-copy audit.** Every kernel site that reads user memory
(`copy_from_user`, `copy_str_from_user`, `sysc.h`'s `copy_in`), with what
it holds. Writes (`copy_to_user`, `copy_out`) are left out: they never

**What PK3 needs:**
- A page evicted between its supply and the fault's retry makes the

  supply should see it.
- The fault's wait holds a VMO reference, never a page reference: eviction

- `PAGER_OP_SET_SIZE` shrinking: a fault past the new size gets

  finds the page past the size.

  `uentry.c`'s `fault_reason` ("page fault: a page doesn't match the

## PK3 notes

Choices PK3 made where the plan left room, what it measured, and what it
leaves to PU, PF1, PF2 and PK4.

- **Where:** the cache is `kernel/object/pager_cache.c` and its internal
  header `pager_cache.h` (pager.c would have passed 800 lines). A
  `struct pager_cache` sits in `struct pager` with a lock of its own,
  "pager cache", which nests under "vmo" only and never with the pager's
  object lock: an evictor takes it, drops it, then takes the VMO lock with
  a VMO reference held across.
- **The list:** a resident page is on its pager's list (oldest supplied
  first) through its `struct page`'s `node`, which is free while the page
  is in a table (the free lists and gathers use it only before the page is
  published and after it is taken out); `node.next` is NULL off the list.
  Its `private` points at a 16-byte record (the VMO and the index) that
  tells an evictor where the page is; the record is charged to the
  pager's job as message bytes and lives exactly as long as the page is in
  its table. So the plan's "16 bytes a resident page" is the record; the
  links cost nothing.
- **Counting:** `resident` is the listed pages plus slots reserved for
  pages being published. A supply reserves a slot before it publishes;
  with the budget full the oldest page's slot becomes the supply's and
  that page is evicted first, so the tables never hold more than the
  budget. Two exceptions, both brief: a popped page of a VMO being
  destroyed (no evictor can reach it: it goes with its VMO), and more
  supplies at once than the budget has pages (the list is all
  reservations: the count passes the budget by those).
- **Eviction** is a one-page decommit (`vmo_pager_evict` through
  `take_batch_locked`): out of the table, zapped from every mapping under
  the VMO lock, freed after the shootdown. Every path that takes a pager
  VMO's page out (decommit for a detach or an invalidate, shrink, destroy,
  eviction) tells the cache from `take_batch_locked` or
  `drop_leaf_from_locked`; for other VMOs nothing changes. A supply of a
  present page evicts nothing (checked first; its bytes are still copied).
- **Memory pressure** (the owner's Q3, no global reclaim): a supply whose
  page the machine can't give, or whose page, table or record the job
  refuses, evicts its own pager's oldest pages and tries again, at most a
  budget's worth of rounds, then fails `ERR_NO_MEMORY`. Another pager's
  pages and other jobs are never touched.
- **Answers:** a request is answered when every one of its pages arrived
  (`arrived`, a bit a page, set at publish) and the supply call that
  brought the last one ends, even if the cache evicted some of them since.
  With "all present" instead, a budget smaller than a request (or a
  supply that evicts its own first pages) would never answer it. At the
  end of the call rather than page by page so a request is answered once,
  after the evictions its own supply makes: that is what makes the 8-wait
  limit testable (`pager_cache_evict_every_supply`, below). A 1 MiB supply
  covering several requests answers them all at its end, about a quarter
  of a millisecond after the first could have been.
- **The 8-wait limit** (PK2's note): `pager_cache_evict_every_supply` has
  a one-page budget and a pager thread that answers every request with
  both of the VMO's pages, so the page asked for is evicted by the one
  after it before the answer. `vmo_read` gives up with `ERR_NO_MEMORY` and
  a ring-3 load is killed "page fault: out of memory (or the job's page
  limit)", each after exactly 8 requests.
- **`PAGER_OP_INVALIDATE`** (page-aligned, len > 0, arg 0; past the size
  `ERR_OUT_OF_RANGE`; a GONE or detached key `ERR_NOT_FOUND`): a decommit of
  the range. It isn't a writer, so a sealed VMO takes it as it takes an
  eviction. Requests are left alone. A supply that read the old bytes
  before fat's write and publishes after its invalidate caches stale
  bytes: the kernel can't see that, so the pager must not supply a range
  while it writes and invalidates it (fat's one loop serialises both;
  PF2's ordering argument).
- **`PAGER_OP_SET_SIZE`** (offset the size, rounded up; past
  `VMO_MAX_SIZE` `ERR_OUT_OF_RANGE`; len and arg 0): a writer under "vmo
  resize", so a sealed VMO refuses it (`ERR_BAD_STATE`). A shrink lowers
  the size and cuts the requests under the VMO lock, then drops the pages
  past the end. A request wholly past the end is answered OK, so its
  waiters look again and meet the end (a bus error for a fault,
  `ERR_OUT_OF_RANGE` for `vmo_read`), never `ERR_IO`; one crossing it is
  cut there and answered if its pages below arrived. A request delivered
  before the shrink keeps its old length in the pager's hands.
- **Closing a pager** with many resident pages (PK2's note): measured
  2026-10-11 in QEMU on the PC (KVM, 4 CPUs, this branch), closing a
  pager whose VMO held 65,536 pages (256 MiB), every one mapped, took
  3.5 ms; at the PC's 2 GiB budget that
  is about 28 ms with preemption off (the teardown runs in `td_run`), the
  same order as destroying any 2 GiB VMO today. Not changed here: the fix
  is to hand the detach's page drop to a kernel thread started at boot (the
  DMA quarantine's reaper is the pattern), with `vmo_read` and
  `vmo_fault_map` refusing a detached VMO's present pages at once so the
  pages are unreachable before they are freed; a follow-up for the review.

**What PU needs:**
- Each mount's pager: `max_pages` = 1/16 of memory (the plan), answer time
  `FS_CALL_TIMEOUT`.
- volumes' job limit must hold, beside fat's own memory, every mount's
  budget in pages, the VMOs' table pages (a leaf per 2 MiB and a mid table
  per GiB of each VMO, as far as it was ever touched: they stay until the
  VMO shrinks or dies) and 16 message bytes a budget page. The cache gives
  room back only to its own supplies: a fat allocation the job refuses
  fails even when the cache could have shrunk, so a limit below the
  budgets plus the rest makes fat fail, not the cache shrink.

**What PF1 needs:**
- Answer a request with one `pager_supply` of its range (or more pages:
  read-ahead), never two half calls when one will do: its waiters wake
  when the call that brings its last page ends.
- Clip every supply to the file's size now: `pager_supply` is
  `ERR_OUT_OF_RANGE` for the whole call if the range passes the VMO's
  size, and a request delivered before a `PAGER_OP_SET_SIZE` shrink may
  ask for pages past the new end.
- Read-ahead past the budget only evicts the pager's own oldest pages
  (the request it came for is still answered, and its waiters ask again
  if they must).
- **PF2**: invalidate after the write, never with a supply of the same
  range in between; `SET_SIZE` after a truncate.

**With PK4** (merged first): its check stays in `supply_page`, on the
copied page, before the cache's publish (`pager_publish_page`, which the
seal-race test now calls instead of `vmo_pager_publish`), and
`vmo_pager_publish` matches an unchecked page under the VMO lock as PK4
made it; every publish goes through there, re-fetches after an eviction
or an invalidate too (ktest `pager_cache_verified_refetch`: a page evicted
by the job's pressure, and one invalidated, are refused when the file
changed and taken again when it is back). The seal makes the VMO a sealed
one, so `PAGER_OP_SET_SIZE` is `ERR_BAD_STATE` on it while eviction and
`PAGER_OP_INVALIDATE` still work. A supply's requests are answered at its
end (the cache's rule) before PK4 fails the waiters of its unapproved
pages; a request with an unapproved page never has all its pages arrived,
so only the failure answers it.

## PK4 notes

Choices PK4 made where the plan left room, and what it leaves to PX.

- **The call:** `vmo_make_exec_verified(vmo, root, table, flags, *out)`
  (59) as the plan's table has it. Its refusals are `vmo_make_exec`'s
  (`RIGHT_ROOT_VMEX`, `READ | MAP` on vmo, the only handle, unmapped,
  vmo's handle gone whatever the status, the table's handle kept), plus:
  flags not 0 `ERR_INVALID_ARGS`; not a pager VMO `ERR_NOT_SUPPORTED` (a
  VMO of one's own is `vmo_make_exec`'s); bigger than `VMO_VERIFIED_MAX`
  (64 MiB, the shell's `PROGRAM_MAX`; 1 GiB since CR's CP1) `ERR_OUT_OF_RANGE`; a table shorter
  than 32 bytes a page `ERR_INVALID_ARGS`; detached or verified already
  `ERR_BAD_STATE`. The new handle is the old one's rights plus
  `RIGHT_EXEC` (a pager VMO's never had `WRITE` or `RESIZE`).
- **The table** is the bare array of SHA-256 digests, page 0's at byte 0
  of the table VMO (`VMO_VERIFIED_HASH_BYTES` each, in `<jam/abi.h>`):
  the call takes no offset, so a file with a header (`allow.d`) is copied
  into a VMO of its own first. The kernel copies it with `vmo_read` before
  the handle comes out of the table (a table that is itself a pager VMO
  waits for its pages, with no lock held) into whole buddy pages (128
  hashes each, a 1 KiB array of them for 64 MiB, 16 KiB for 1 GiB), charged to the
  **caller's** job (`JOB_LIMIT_PAGES`, as a pin is the pinner's), and
  owned by the VMO from the seal on (freed with it). A page past the
  table (a VMO grown since) never matches.
- **Where the check runs, and the seal's race.** `pager_supply` hashes each
  page after the copy, with no lock held (`vmo_verify_supply`), and tells
  `vmo_pager_publish` it did (its new `bool checked`). The seal
  (`vmo_seal_verified`, vmo.c) checks the VMO (pager, not detached, not
  verified, no mapping, no pin), drops every page present and sets
  `verify` in **one** hold of the VMO lock; no mapping means no entry to
  zap and no shootdown. A supply that copied its page before the seal and
  publishes after it says `checked = false`, and `vmo_pager_publish`
  hashes that page under the VMO lock (about 10 us with interrupts off,
  only on that crossing). So every page present after the seal matched,
  whatever was under way. The pages before the seal are dropped rather
  than refused, so a caller that read the VMO first (the fallback for an
  old approval could) loses nothing but the read; it must not map it
  (`ERR_BAD_STATE`).
- **A page that doesn't match** is never published. `pager_supply` goes on
  with the rest of its range (a request is answered whole, and a waiter on
  a good page of it must find that page when the request fails), then
  fails the requests waiting on each bad page with **`ERR_BAD_STATE`**
  (`pager_req_wait`'s new status, free as PK2 said) and returns `ERR_IO`
  to the pager (unless it stopped for another error, which wins). A fault
  turns `ERR_BAD_STATE` into the kill "page fault: a page doesn't match the
  approved program" (`uentry.c`'s `fault_reason`); a copy into `ERR_IO`
  (`copy_status`); `vmo_read` into `ERR_IO` (`pager_fetch`, unchanged). A
  later supply of the approved bytes is taken: nothing is poisoned.
- **Cost:** the kernel's SHA-256 runs at about 2.5 ns a byte under the
  PC's KVM (`sha256_million_a`: 2.55 ms a MiB), so 10 us a page, against
  a stick read of a page that is hundreds of microseconds.
- **The SHA-256** is a third copy (`kernel/lib/sha256.c`, beside libos's and
  the drivers'), with whole blocks hashed in place; its ktests compare it
  with FIPS 180-4's examples and with libos's digest of one page (computed
  on the host from `user/lib/sha256.c`; `shasum` agrees).
- **With PK3:** the one hook in `pager.c` is `supply_page`'s check and
  `pager_supply`'s loop (it goes on past a bad page and fails its requests
  after); `vmo_pager_publish` gained the `checked` argument and one test
  under the lock. Eviction and invalidation need nothing: a page fetched
  again is checked again. `PAGER_OP_SET_SIZE` growing a verified VMO
  gives pages with no hash: they never match (a running program's file is
  `ERR_BUSY` by Q7 anyway).
- **Outside the plan's files** (small): the declarations
  (`<jam/sys.h>`, `<jam/vmo.h>`, `<jam/pager.h>`'s publish and wait
  comments, new `<jam/vmo_verify.h>` and `<jam/sha256.h>`), the two
  constants in `<jam/abi.h>`, `sysc_vm.c`'s wrapper, `vmo.c` (the field,
  the seal, the check in publish, the free in destroy), `uentry.c`'s two
  lines, comments in `<jam/aspace.h>`, `<jam/usercopy.h>` and
  `<jam/dbghook.h>` (`DBG_VMO_EXEC_CHECK` is in the verified call too, at
  the same point), the ktests (`test_pager.c`'s last section, new
  `test_sha256.c`) and utest `vmo_make_exec_verified` (`rights.c`, the
  refusals a process without a pager reaches).

**What PX needs:**
- `allow` writes `/data/etc/allow.d/<sha-256>`: the header, then the
  SHA-256 of each 4 KiB page of the file, the last one zero-padded to
  4096 bytes. That is what the kernel hashes, so fat (PF1) must supply the
  last page zero past the end of the file.
- Running: `file.map(EXEC)` gives the pager VMO (don't map it before the
  call); read the table file, check its header against the allow line and
  the file's size, put the hashes alone into a VMO (`vmo_create` of
  pages x 32 bytes, `vmo_write`), and call
  `jam_vmo_make_exec_verified(vmo, sh_root(), table, 0, &x)`. On any
  status the VMO's handle is gone (don't close it); close the table's
  afterwards.
- **The shell must never touch the program's pages through a mapping of
  its own.** A changed page faulted in by the shell kills the shell's
  thread, not the program. Read `wants` with `vmo_read` (a changed page is
  `ERR_IO`: "changed since it was allowed"), not through the read-only
  mapping the plan's step 2 describes. The same holds for libos's `spawn`:
  `map_image` maps the image into the caller and `load_elf` reads the ELF
  header, the program headers and the writable segments' bytes through
  that mapping (`user/lib/spawn.c`), so `spawn` of a verified VMO needs
  those reads done with `vmo_read` (or the shell must read them first and
  accept that an evicted page fetched again could still kill it). The
  read-only and executable segments are mapped into the child straight
  from the VMO: a changed page there kills the program, as it should.
- The fallback for an approval with no table: read the file whole (the
  `FILE_MAP_READ` VMO or `file_read`), check its SHA-256 against the
  allow line, write the table, then go on as above with a fresh
  `file.map(EXEC)`.
- `pager_supply`'s `ERR_IO` for a verified VMO tells fat the disk's bytes
  aren't the approved ones: fat should log it once and not retry; the
  requests are already failed.
- Programs bigger than `VMO_VERIFIED_MAX` (64 MiB; 1 GiB since CR's
  CP1) are refused, as the shell's `PROGRAM_MAX` refuses them.

## PF1 notes

Choices PF1 made where the plan left room, and what it leaves to PF2, PX,
M13's F1b and M13.6's U5. The code is `user/services/fat/pager.c` (its
header is the model); `fileops.c`'s `op_map` and lock, `adopt.c`'s
checks and remakes, `main.c`'s binding.

- **Slots and keys.** Each VMO fat makes is a slot of `maps[]` in the
  state (layout 6; `FAT_MAX_MAPS` 32): its file (an entry of `opens[]`,
  which grew to `FAT_OPENS`, 64, and which a slot of `maps[]` holds open
  as a slot of `files[]` does), its kind, its key and the VMO's size. A
  key is `FAT_MAP_KEY(seq, slot)`: `seq` counts up from the clock (ns
  since boot) at the first map of a state set up empty, so no key is ever
  used twice for a pager, not even by an instance that started fresh
  while the VMOs of the one before still live. A request for a key the
  state doesn't know is answered with `PAGER_OP_DETACH` (one log line an
  instance).
- **`FILE_MAP_READ`'s sharing.** fat holds a handle of a file's shared
  VMO (and the keeper a copy, keep slot `FAT_KEEP_MAP(i)`) while the file
  is open through `fs.open`, and lets go when its last `fs.open` closes;
  then the VMO is its mappers' alone and `PAGER_REQ_GONE` can come. So
  every map of a file while it is open shares one VMO and one set of
  pages, but libos's `file_map_path` (open, map, close) gets a new VMO
  each time: **the page cache lives as long as some mapping or open**,
  not across processes that map a file one after another. A cache that
  outlives its mappers needs fat to keep VMOs it can drop under pressure
  and a way to tell "only fat holds it" (a handle count, or a pager op
  that drops fat's VMOs and their keys at once): for M13's `mmap` or the
  review to weigh, not done here.
- **`PAGER_REQ_GONE`**: the slot forgotten (one store, as a view's drop),
  then the detach that frees the key; a death between them leaves a GONE
  for a key nobody knows, detached by the successor. fat logs one line a
  VMO when it goes: `fat /usb0: mapped file <key> gone: N page requests,
  M pages supplied` (this instance's counts): pager-test.sh counts on it.
  PX may want it quieter for programs run from `/data` (one line a run).
- **Reads on copies.** A page request is read with FatFs on copies in
  fat's own memory: a cursor `FIL` per slot (made from the file's `FIL`,
  `FA_WRITE` off) on a copy of the volume whose window is never written
  back (`wflag` 0). Nothing of the state changes, so a death in the middle
  of a read needs no undo, and a read never writes the FAT sector an
  `FS_GATHER` file's write left in the window. Each request is one
  `pager_supply` of its range clipped to the VMO, zero past the end of the
  file in its last page; pages past the file's end are failed
  `ERR_OUT_OF_RANGE`; a read error fails the request `ERR_IO`; a supply's
  `ERR_IO` (a verified VMO's mismatch) is logged once a slot and not
  retried; other supply errors fail the range `ERR_IO`. No read-ahead
  beyond the kernel's 16 pages: a sequential reader's requests are 64 KiB
  each already.
- **Serving.** The pager's binding is `PORT_BIND_ONCE` (key
  `FAT_KEY_PAGER`), one request a turn and bound again, so the read-loop
  rule holds without `port_again`. Before each `fs` request (`files_reap`)
  fat serves what is queued (up to 16): a mapping let go and then the file
  removed are seen in that order (`fat_restart_pager` removes a file right
  after its last mapping and the keeper's copy go). The reply waiting for
  fat's next system call goes before each disk read (`reply_flush`).
- **Restarts.** The pager handle is read at startup
  (`startup_handle(FAT_SR_PAGER)`; none: `file.map` is
  `ERR_NOT_SUPPORTED`, as for utest's own fats and init's test mode).
  After the adopt (or the fresh mount), `pager_start` binds the pager and
  calls `pager_next(PAGER_NEXT_AGAIN)` once, serving what it returns. A
  `file.map` is an operation like any file request: its slot goes in the
  undo copy (`undo_map`) and its shared VMO's keeper put comes before the
  state records it; an undone map's VMO dies with the process and the
  keeper's copy is refused at the restore, so its key is detached. A map
  whose reply never went out is answered again: the shared VMO from fat's
  handle (back from the keeper), or for `FILE_MAP_EXEC` a new VMO under a
  new key (the old key's GONE then finds nobody). `maps_adopt` makes fat's
  handles agree with the rule (held while the file is open) after the
  successor's closes. Test powers `die=map:<n>` and `die=supply:<n>`
  (test.c) end fat after a map made its VMO and between reading a request
  and supplying it.
- **A fresh start** (a state given up on) forgets every slot; the old
  VMOs stay attached under keys the new state doesn't know, so their
  present pages stay readable until their next request is detached. A
  pager op that detaches every key (or volumes making a new pager when
  fat starts fresh) would close that gap: for the review.
- **Writes and mapped files, until PF2.** A file open for writing isn't
  mapped (`file.map` is `ERR_BUSY`), and while a file is mapped it can't
  be opened for writing, removed or renamed (`ERR_BUSY`, the open-file
  lock, since the slot holds the file open). So nothing changes a mapped
  file, and Q7's rule for `EXEC` keys already holds.
- **Outside the files listed** (small): `abi/idl/file.idl`'s comment on
  `map` (and the generated header), `keeper.c` (the drop bits grew to two
  words for the map slots), `undo.c` (`undo_map`, the opens' bits a
  64-bit word), `test.c` (the two powers), init's `TEST_ROOT` (the pager
  power, so utest's own fat gets a pager in the init run),
  `user/tests/pagertest/main.c` (`xhash`: a `FILE_MAP_EXEC` VMO read with
  `vmo_read`; short result lines, a long one is cut in two in the log),
  utest's `fat_restart.c` (`fat_restart_pager`).

**What PF2 needs:**
- Lift the two `ERR_BUSY`s above: `op_map`'s `written()` check and the
  lock (`open_at` counts a mapped file as open: `files_open_used`). For a
  `READ` key then: after a write's sectors are in fat's cache,
  `PAGER_OP_INVALIDATE` the written range of every `READ` slot of that
  file (`maps[]` with its `open`; there may be several: one per time the
  file was mapped while not open), never with a supply of the range in
  between (fat's one loop gives that); `PAGER_OP_SET_SIZE` and the slot's
  `size` after a truncate or growth; **reset the slot's cursor**
  (`mh[i].cur_ok = false`: its cluster may be freed) and read the file's
  size from its `FIL` as `read_request` does. A writer's `FIL` may be
  dirty (`FA_DIRTY`): `read_pages` refuses one today (`ERR_BAD_STATE`);
  sync it first or overlay its buffer.
- Keep `ERR_BUSY` for `EXEC` slots (Q7); unlink of a `READ`-mapped file:
  detach its keys first (`PAGER_OP_DETACH`, then the slot forgotten as a
  GONE does), then unlink.
- The disk going: volumes closes the pager (PU), which detaches every key;
  fat's slots go with the mount.

**What PX needs:** `fs_map_file(&f, FILE_MAP_EXEC, ...)` gives a VMO the
shell holds alone (fat holds no handle of an `EXEC` VMO, ever), its pages
the last one zero past the file's end (what `allow.d`'s table hashes). A
supply that doesn't match is logged once by fat (`the disk's pages don't
match the approved program's`) and not retried. The file can't be written,
removed or renamed while that VMO lives.

**What M13's F1b needs** (`MAP_PRIVATE` of files): a copy-on-write child
of the shared `FILE_MAP_READ` VMO; fat changes nothing for it. The VMO is
shared only while the file is open in fat (above): F1b's `mmap` should
keep its `fs.open` until `munmap` if it wants mappers of one file to
share pages, and should expect `ERR_BUSY` from `file.map` on a file it
opened for writing until PF2.

**What M13.6's U5 needs:** `file.idl` method 6 is taken (`map`); fat's
state layout is 6 (bump it again with U5's changes); `fileops.c`'s
`fat_file_ops` has `.map`, and `struct fat_open` is shared by slots of
`files[]` and `maps[]` (`files_open_used`).

## PF2 notes

Choices PF2 made where the plan left room, and what it leaves to PX, M13's
`mmap` and the review. The rules and the ordering argument are in
`user/services/fat/pager.c`'s header ("A mapped file that changes", "The
ordering").

- **The lock.** A mapping no longer counts as an open for fat's lock: a file
  mapped to read may be opened for writing (its shared FIL, opened to read
  by the first open, gets `FA_WRITE` after FatFs's own read-only check:
  `open_to_write`, which also does `FS_TRUNCATE`), written, truncated,
  renamed, removed or renamed over, and a file open for writing may be
  mapped to read. A file mapped to run (`FILE_MAP_EXEC`) refuses all of
  these with `ERR_BUSY` while that VMO lives (Q7), renaming it included,
  and a file open for writing is never mapped to run. An open file is
  still never removed or renamed (`files_may_change`, which replaces
  `files_is_open`).
- **Where the invalidate goes:** inside the change's operation, after
  FatFs changed the file, before the commit: first `ffx_flush` (new, in
  `ffx.c`: the FIL's sector buffer and FatFs's window written into the
  hold, so a cursor copy reads through `disk_read` what the FIL has), then
  `PAGER_OP_SET_SIZE` and `PAGER_OP_INVALIDATE` of the changed pages on
  every `FILE_MAP_READ` VMO of the file, and every slot's cursor reset.
  Not after the send: an `FS_GATHER` file's writes stay held across
  requests, and fat's reads see them all the while. Both ops are
  idempotent, so a successor's re-run does them again; an undo with no
  re-run (two crashes) can leave a VMO's size off, and `pager_start` sets
  every `READ` VMO's size to its slot's at each start (`sizes_again`).
  A pager op the kernel refuses (other than a VMO gone) cuts the VMO off
  (fails closed). A flush that fails is the write's failure.
- **Rename of a mapped file** keeps its mappings (no byte changes): its
  open entry's place and its FIL's entry pointer follow the new entry
  (`files_moved`), so a later open of the new name finds the same FIL.
- **Removal, and rename over,** cut the file's VMOs off (detach, then the
  slot forgotten, one log line each: `fat /data: mapped file <key> cut
  off: its file was removed`), after FatFs's unlink succeeded, inside its
  operation. POSIX's "an unlinked file stays readable through its
  mapping" is not done (the plan's rule; M13 to weigh).
- **The stick:** volumes' disk-gone path already retires the mounts, which
  closes their pagers (PU's `fs_kept_release`): only a comment in
  `disk_key`. fat itself cuts off the key of a request it was reading when
  its disk went (`read_request`), so a mapper sees one reason, "the file's
  pager is gone", not sometimes "couldn't read it".
- **Not done:** after a lost hold (`hold_failed`), pages supplied from a
  gathered write that then never reached the disk stay until evicted (fat
  writes nothing more then, and its own reads disagree with its answers
  too). A cut-off VMO whose removal was undone without a re-run keeps its
  slot until fat starts fresh.
- **Tests:** utest `fat_map_coherent` (new, `fat_coherent.c`: every class
  of write and truncate seen by two VMOs and a copy from a mapping,
  rename, `FS_TRUNCATE` open, `EXEC` refusals, rename over and unlink cut
  off); `fat_restart_pager`'s "open for writing" now maps to read, not to
  run. pager-test.sh cases `write` and `pull` (new); `map` lost its
  "removing a mapped file is refused" step (no longer true). pagertest
  gained `write` and `pull` and its list is `mount * rw`.
