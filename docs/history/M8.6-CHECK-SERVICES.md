# M8.6 code check: the system services and their protocols

The last step of [M8.6-PLAN.md](../M8.6-PLAN.md): a check, by an agent
that did not write the code, of `user/services/` (init, devmgr, fat,
logd, console, shell, mixer, music, bootfs, serialin) and `abi/idl/`
against [CODING-GUIDE.md](../../CODING-GUIDE.md) and
[ARCHITECTURE.md](../../ARCHITECTURE.md), main at febd124. The
permission model of [M8.6-SVC.md](M8.6-SVC.md) first, then bugs, then the
known items, then the guide.

Every finding was written here before any fix. Outcome: **fixed** (with
the commit), **design question** (for the owner), or **left** (why).

## Findings

### High

**S1. A program on `/data` can be granted the trusted services, and with
them everything the views keep from it.**
`user/services/shell/sh_allow.c:161` (`sh_program_file`) takes any list
`wants_read` (`user/lib/wants.c:66`) accepts, and `want_svc` accepts any
name. So a program on `/data` may ask for `svc devmgr-ctl`, `svc devmgr`
or `svc init`, and `allow` shows only the bare name ("allow u: devmgr,
devmgr-ctl, ...? y/n"; tools/shell-tests/allow.txt approves exactly such a
list, a copy of utest). Once approved:
- `devmgr-ctl`: `DEVMGR_MOUNTS` hands out the filesystems' own channels,
  unguarded, so the program can rewrite `/data/etc/allow` and approve
  anything, itself included; `DRIVER_VIEW` hands out any PCI function's
  BARs; `KILL`, `REBIND`, `RELEASE`, `REMOUNT`.
- `devmgr` (the query channel): `GET_SERVICE` of usb-bus, whose
  `open_interface` gives a `usb` channel to any interface of any device but
  a hub (`drivers/usb-bus/serve.c:305`): control requests to the boot
  stick and the keyboard, reports. `<devmgr.h>` already says "even QUERY
  is for trusted programs only".
- `init`: kill any service, reboot, `mount -w`, `kernel load`.
The build refuses `devmgr-ctl` and `init` outside `user/tests/`
(tools/checkwants.py, `TESTS_ONLY`), but nothing refuses them at run time,
and nothing refuses `devmgr` at all. A program on `/data` is by definition
not a test of the tree. **Outcome:** fixed: the shell refuses to allow or
run a program from `/data` whose list names a service only the system's own
programs may have (`devmgr`, `devmgr-ctl`, `init`), and says which.

### Medium

**S2. Names from another stick reach the console as they are.**
`user/services/fat/fsops.c:87` (readdir) and `:177` (statfs's label) pass
FAT names through unchanged; a crafted stick's long names can hold any
UTF-16 code unit, controls included (ESC, `\r`, `\b`). `ls`, `find`,
`df`/`mount`, `music status` and jamjar's library print them, so a file
name can move the cursor, clear the screen, switch to the alternate screen
or write over the line above (a fake `allow ...? y/n`, a fake prompt)
(candidate 15, M8-REVIEW item 18). Such a name can't be opened through fat
anyway (`path_resolve` refuses control characters in a path), so showing
it differently costs nothing. The label is also cut at 15 bytes, which
can split a UTF-8 character. **Outcome:** fixed in fat, the one place every
reader goes through: in names and labels it hands out, each control
character (below 0x20, 0x7f) becomes `?`, which fat refuses in a path, and
the label is cut at a character's start.

**S3. The mixer's one thread waits in `audioctl.device` and `stream_levels`
for up to seconds while it should be mixing.**
`user/services/mixer/output.c:450` (`out_query`) walks devmgr's services
with a `GET_SERVICE` and an `hda.query` each, 2 s deadlines (`FIND_WAIT`),
up to 32 of them; `:436` (`out_device_gain`, from `stream_levels`) calls
`out_find`, which does the same walk with `hda.info`, until a driver was
found. Any of devmgr's services that is slow to answer (usb-bus inside a
bulk transfer: up to 5 s reads, 10 s writes; a driver devmgr is restarting)
holds the loop that must mix a period every 42.7 ms with 128 ms of lead:
the shell's `hda` while music plays is enough on the PC. **Outcome:**
fixed: `device` is answered by a thread of its own (the walk needs only
devmgr's channel; the answer is written to the control channel with the
request's txid), so the loop goes on; `stream_levels` says 0 for the
device gain until the output has found its driver instead of looking for
it.

**S4. The console replays the whole kernel log ring when it starts.**
`user/services/console/main.c:173-183`: `klog_pos` starts at 0, so a
console started again (a crash, `kill console`) reads all of the ring (4
MiB now) and puts every line through `kernel_line` and into the
scrollback, which keeps 4000 lines: tens of thousands of lines drawn into
a scrollback that keeps the last few, before it serves a client.
**Outcome:** fixed: the catch-up still reads the ring for the notices'
state (which mounts there are), but only its last 256 KiB go on the screen.

### Low

**S5. `mount -w`/`-r` says nothing about how long it took.** The remount
path (shell `mount.c` -> initctl.mount -> devmgr `disk_remount`,
`user/services/devmgr/fsvc.c:255`) has no fixed 10 s wait left: fsctl.stop
(at most `SYNC_WAIT`), the service's exit (at most `STOP_WAIT`, which only
a service that ignores the stop reaches), a new `block` channel, the start;
the shell polls statfs every 50 ms for at most 10 s (`BACK_WAIT`, a bound,
not a wait). The old 10.2 s steps were the volume's own work before the
block cache. **Outcome:** fixed: devmgr's line says how long the remount
took.

**S6. Comments that describe the old rights and handles.** The root's
`RIGHT_READ`/`RIGHT_MANAGE` in console `main.c:22-24`, logd `main.c:4` and
`:164`, serialin `main.c:11`, shell `sh_handles.c:3`, `sh_sysinfo.c:2`,
`sh_kernel.c:2`; initctl.idl's header gives the shell's channel as
startup role `SR_USER + 3` (it is `/svc/init`); logd's `serve_ctl` comment
says it returns what a flush failed with (it always returns OK); init
`main.c:391-395` has three comments in a row that belong to the code after
them. **Outcome:** fixed (one cleanup commit).

**S7. A milestone tag.** `abi/idl/usb.idl:43` "(M8: mass storage)".
**Outcome:** fixed.

**S8. `kill` reports through `sh_say` and returns 0.**
`user/services/shell/cmd/kill.c:12-40` (candidate 20): its usage and
failures go to the output, not the terminal, and `$?` is 0 for all of
them (the guide: `sh_tty`, 2 for usage, 1 for a failure). **Outcome:**
fixed.

**S9. Dead code.** `sh_devmgr_ctl()` (`user/services/shell/sh_handles.c:97`,
`sh.h:139`): nothing calls it; test programs get `/svc/devmgr-ctl` from
their list. **Outcome:** fixed (removed).

**S10. The notices trust a line's process name more than they should.**
`user/services/console/notices.c:30-32` says "a process can't choose the
name the kernel puts in front of its lines". It can: the name is the one
its creator gave `process_create`, and every program holds its own job
(`SR_JOB`), so any program can start a process called `init` or `devmgr`
and write lines that become notices ("the Jam OS stick was pulled out").
Only the notices' yellow lines can be faked this way; nothing acts on
them. **Outcome:** the comment says what holds; a real fix needs the
kernel to mark lines from processes outside the system's own jobs:
design question D3.

**S11. The music player serves one channel until it is empty.**
`user/services/music/main.c:268`: `while (svc_serve_request(...) == OK)`,
on the shared channel and on each opener's, with no budget, before it
decodes the next piece; a client that keeps writing requests holds up
playback (its own music, and every other opener's calls). **Outcome:**
fixed: a budget per channel per turn, as the mixer and fat have.

**S12. A program can use up fat's shared tables.** `FAT_VIEWS` (32) and
`FAT_MAX_FILES` (32) are per volume, shared by every client
(`user/services/fat/fat.h:26,36`): a program with any view of `/data` can
open files or views until both are full, and then logd can't reopen its
file and the next program's `/data` view fails (fail closed: no mount).
It lasts until the program ends (the shell kills its job). **Outcome:**
left: per-client quotas are design question D4.

**S13. `ls` and `find` show a directory's first 256 entries and say
nothing of the rest.** `user/services/shell/sh_vfs.c:137` reads at most
`SH_DIR_MAX`; `ls.c` and `find.c` print what came (candidate 22, M8-REVIEW
item 19). **Outcome:** fixed: both say on the terminal that there are more
than 256 and only 256 are shown.

**S14. `allow` takes a key typed before its question as the answer.**
`user/services/shell/cmd/allow.c` (`ask`) reads the first key in the
keys channel, which may have been typed before the question was on the
screen (a `y` typed ahead with the command). **Outcome:** fixed: keys
queued before the question are thrown away first (a Ctrl+C among them
says no).

**S15. Three protocols don't say what a client does after
`ERR_PEER_CLOSED`.** `abi/idl/fs.idl`, `file.idl`, `block.idl` (the
guide's IDL recipe asks for the reconnect rule in every header).
**Outcome:** fixed.

**S16. A client can grow its stream's ring at the mixer's cost.**
`user/services/mixer/streams.c:20`: the ring goes to the client with
`RIGHT_WRITE`, which also allows `vmo_set_size`, and pages the client
commits in it are the mixer's; one shared `audio` channel means the mixer
can't count streams per client either (candidate 16, AUDIO-REVIEW items
10 and 11). The mixer only ever reads a ring with `vmo_read`, so a ring
that shrinks costs the client its own sound, nothing more. **Outcome:**
left: it needs the kernel (a VMO whose size its client can't change)
and per-opener `audio` channels: design questions D5 and D6.

### Design questions (for the owner)

- **D1. The shell's `/svc/devmgr-ctl`.** The brief asked whether the shell
  could hold a control channel without the exclusive drivers. It can't
  cleanly: the shell holds devmgr-ctl only to pass it on, and the one
  program that needs it for hda is `hdatest`, which the shell runs
  (tools/hda-stream-test.sh) and which takes the output stream on
  purpose. A narrowed channel would need a fourth channel kind in devmgr
  and would break `hdatest` from the shell; and it buys nothing against a
  shell gone wrong, which holds more than hda already (every mount
  unguarded, `RIGHT_ROOT_VMEX`, `DRIVER_VIEW` through the same channel).
  Recommendation: keep it; S1 keeps it from programs on `/data`.
- **D2. `right debug` for programs on `/data`.** `debug_command` runs
  `panic`, the crash tests and `stress`: an approved program can stop the
  machine. No program in the boot image asks for it. Refuse it from `/data`
  as S1 does the trusted services, or keep it as the owner's choice?
- **D3. Notices from processes that only borrow a system name** (S10): the
  kernel could prefix lines from processes outside init's service jobs
  differently, or the console could match only lines whose process it knows
  by koid. Both need kernel work.
- **D4. Per-client limits in fat** (S12): views and open files per client
  channel, so one program can't take what logd and the shell need.
- **D5. Shared service channels.** `audio`, `audioctl`, `devmgr`, `logd`
  are one channel shared by every holder: a reply that arrives after its
  caller's deadline is queued where any holder can read it (a stream's ring
  and channel, for `audio`). `music` hands out a channel per opener
  (`svc.connect`); the others could do the same.
- **D6. A ring the client can't resize** (S16): a right of its own for
  `vmo_set_size` (or a VMO made with a fixed size), so the mixer can hand
  out a ring its client can write but not grow; then a stream cap per
  client, once each has a channel of its own (D5).
- **D7. Giving up on the console or the shell.** init gives up on any
  service that ends more than 10 times in a minute
  (`user/services/init/shell.c:192`). For the console and the shell that
  leaves a machine nobody can use until a reset (11 `kill shell` in a
  minute is enough). They could be started again for good at the 5 s
  backoff instead.
