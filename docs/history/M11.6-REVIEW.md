# M11.6 review: services that outlive their process

An independent read of milestone M11.6 at local main 80c7086 (every stage
and the join merged), by an agent that wrote none of it, against
CODING-GUIDE.md, ARCHITECTURE.md ("Services that outlive their process",
IPC, Storage, Audio) and docs/M11.6-PLAN.md (the owner's answers, "As
built", the list for the review, X).

Reviewed: the keep protocol (`user/include/keep.h`, `user/lib/keep.c`); the
state VMO and standby (`user/include/svcstate.h`, `user/lib/svcstate.c`,
`user/lib/start.c`, `kernel/include/jam/startup.h`, the kernel's
`channel_reply_wait` mark); fat's state, hold, commit, undo and adopt
(`user/services/fat/`: state.c, request.c, undo.c, hold.c, adopt.c,
keeper.c, fileops.c, views.c, main.c, test.c) against FatFs R0.16's
`f_truncate`, `f_unlink` and `remove_chain`; the mixer's state and adopt
(`user/services/mixer/`: state.c, adopt.c, device.c, output.c's header);
devmgr's and init's supervision and spares (`user/services/devmgr/spare.c`,
supervise.c, fsvc.c, request.c's kill, main.c's stop; `user/services/init/
spare.c`, shell.c, services.c's mixer start and reboot path); usb-storage's
fence (`drivers/usb-storage/block.c`); `storm`; and the join's
found-not-fixed list.

Severity, as in the earlier reviews: **High** lets a client gain authority,
forge a service's state or corrupt memory; **Medium** is damage or a loss
of service a client or an ordinary death can cause; **Low** is a narrow
case, a wart, a gap in a check or a test.

**Nothing High was found.** What held up under a careful read:

- **The keeper** takes only what passes three side-effect-free probes
  (a VMO's size, an event signalled with nothing, a channel's writable or
  peer-closed bit: signal bits are disjoint across object types,
  `kernel/include/jam/abi.h`), and only handles it can duplicate; it never
  widens rights (`RIGHT_SAME` both ways), caps slots and handles at 256,
  refuses a put whole, and hands a slot only to the next keep channel of
  the same binding. The successor's `keep_restore` checks every message
  (sizes, counts, no slot twice, the totals in `KEEP_DONE`) and every
  handle ends up taken, handed on or closed. The successor's authority is
  a fresh start's: devmgr and init mint the role handles again; the state
  VMO goes with `SVCSTATE_SERVICE_RIGHTS` only (the transfer right comes
  off in transit), so it can't be passed on.
- **The state VMO.** The layout is computed from what the service expects,
  never read from the VMO, so a bad header can only fail a check; every
  slot field and the commit word are checked together (`check_slots`), and
  fat's and the mixer's own areas are checked index by index before use
  (`adopt.c` `check_*`, `state_check`). Nothing a client can write is
  authority: view and open flags come from the state, a re-run request's
  data from its slot (`op_data_in`), the mixer's `read` from the state.
  The `replied` mark is written by the kernel in the same system call that
  sent the reply (`rw_reply`, `kernel/abi/channel_sys.c`), so a successor
  never answers twice what went out.
- **Exactly once in fat.** Every point a death can fall on was traced: a
  slot set up and not read, read and not begun, begun (undo copy whole or
  not: `op` is stored last), run, committed and `ops_done` not yet moved
  (adopt moves it), sent in part, sent, answered and the mark not set. Each
  maps to one of svcstate's four cases and the right action. A close of a
  file whose client left is an operation with `ops_done` as its commit
  word; the bad-request rule counts only crashes, per slot (`runs`), and a
  committed request that crashes its send twice starts fresh. The undo log
  can't overflow with today's sizes (fs.sync's worst is about 28 KiB of
  32), and a spent undo starts fresh.
- **Standby.** Only the supervisor holds the other end of `SR_STANDBY`;
  `parse_promotion` checks magic, version, the reserved word, counts and
  strings, refuses a second `SR_STANDBY`, and the handle table has room for
  a full promotion (16 + 64).
- **The fence.** usb-storage drops a request whose client end is closed
  before it touches the disk, and its single loop finishes a started one
  before the successor's; devmgr's pre-opened `/data` channel is a new one,
  so the fence still separates a dead fat from its successor.
- **The reboot path.** init releases the mixer's keeper and spare before
  it asks devmgr to stop (`shell_stop_devmgr`), and devmgr drops its spare
  and the pre-opened `block` channel first (`stop_all`); kexec-reboot's
  "stopping: ... ended N ms" lines are all a few ms (run below).

### Design questions for the owner

- **A (finding 2). How should a service's kept server end stay sendable?**
  The kernel's cycle rule refuses to send a channel end whose queue holds
  a channel end, and a client can always put one there. Options:
  1. *A kernel flag "this end receives no handles"*, set on a server end
     by whoever creates it (devmgr's `fs` channel, init's `/svc/audio` and
     `/svc/audioctl`, fat's file and view channels, the mixer's stream and
     opener channels: no IDL request carries handles), checked in the send
     path before a message carrying handles is queued to that end. Then
     no queue a supervisor sends from can ever hold a channel end. An ABI
     addition, so M12's (the interface review); small in the kernel.
     **Recommended.**
  2. *In user space, until then:* when a start fails `ERR_NOT_SUPPORTED`,
     the supervisor (it holds both ends of these channels) reads every
     queued message off the server end, answers the ones carrying handles
     `ERR_INVALID_ARGS` as the service would, writes the rest back on its
     client end (same bytes, same txid, so each caller still gets its own
     reply) and tries again at once. A program that writes such messages
     in a tight loop can still win the race between the drain and the send,
     so it narrows the attack (from one message at a death to a program
     spinning during the restart) rather than closing it, and it reorders
     queued requests of different callers.
  3. Leave it: only a program that already has the sound permission can
     do it, and a reboot clears it.
- **B. The tight-loop trade-off** (stage C: a copy 7.5 -> 5.5 system calls
  a request, a tight cached-read loop 3.2 -> 4.0). The proposed fix, a batch
  of requests per port packet with each reply going out with the next take,
  **does not win the loop back**, so it was not built. Why: today a cached
  `file.read` costs fat the port wait (which carries the last reply), the
  take, the `vmo_write` of the data and the port binding again: 4. The old
  batch loop reached 3.2 because its reply was a write of its own, after
  which its next read often found the client's next request already
  queued (the client, on another CPU, had a few microseconds to send it).
  Now the reply goes out *in* the system call that reads, so that read
  comes microseconds after the reply, before any sync client can have sent
  again: a batch's second take finds nothing, and a request would cost 5
  (wait, take, `vmo_write`, the empty take carrying the reply, the binding).
  Every libos file call is synchronous, so batching only helps a channel
  with several requests queued at once, which no client makes today.
  What would win the loop back, all kernel or ABI work (M12): a
  `channel_reply_wait` that re-arms a `ONCE` port binding in the same call
  (3 a request); a read that says whether more is queued (so a
  `PERSISTENT` binding needs no empty take); or file data in the reply for
  small reads (no `vmo_write`). Recommendation: keep one request per
  packet; take the re-arm option to M12's kernel track if the PC's `perop`
  shows the 4th call matters.

- **C. `update -w`'s renames** (the plan's review list: about 1-2 s each on
  the PC). Each `fs.rename` ends in FatFs's `sync_fs`, whose `CTRL_SYNC`
  fat turns into a `block.sync` (a SCSI SYNCHRONIZE CACHE) in the
  operation's send, then marks the volume clean: a cheap stick's cache
  flush per rename. Batching them is a durability decision, so it is
  left to the owner: (1) fat skips the `block.sync` that FatFs's own
  `sync_fs` asks for inside a metadata request (rename, unlink, mkdir) and
  leaves the volume marked dirty until the next `fs.sync`, file sync or
  close, which flush and mark it clean (a rename answered but not yet
  flushed can be lost to a power cut, never half done: the dirty mark goes
  first); or (2) init's update does its renames and then one `fs.sync`,
  which needs (1) to save anything. Recommendation: (1), measured on the PC
  with `update -w` before and after.
