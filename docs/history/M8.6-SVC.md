# M8.6 track B: `/svc`, per-program views, `allow` and the splits

The design for track B of [M8.6-PLAN.md](../M8.6-PLAN.md) (the owner's
decisions 1, 3, 4 and 11), written before the code. What changes for
each program is the table at the end.

## The namespace: mounts and services

A program's namespace (libos's `ns.c`, given by its starter on `SR_NS`)
holds two kinds of entry:

- **mounts**, as today: `/boot`, `/esp`, `/data`, `/usbN`, each an `fs`
  channel;
- **services**, new: `/svc/<name>`, each a channel to a service (names of
  at most 10 bytes, `[a-z0-9-]`, listed in `user/include/svc.h`).

Both travel in the same `ns_msg` messages (`NS_MOUNT`, `NS_UNMOUNT`,
`NS_SET`), so following a running program (`ns_update`) works for
services exactly as for mounts: when devmgr restarts, init replaces
`/svc/devmgr` in its table and sends its followers the new set. The
message grows to 24 entries (8 mounts and 16 services at most); its
`reserved` word becomes a bit mask of the entries that hand out a
channel per opener (below).

A program reaches a service by name, as it opens a file:

- `svc_open(name, &ch)`: a channel of its own (closed by the caller);
- `svc_get(name)`: libos keeps one per name, opened on first use and
  opened again once its peer is gone (the reconnect rule for free), so
  code that used `startup_handle(SR_X)` becomes `svc_get(SVC_X)`.

`/` lists `svc` next to the mounts when there is a service, `ls /svc`
lists the names, `fs_stat` of one says it is not a file or directory, and
`file_open` of one is `ERR_WRONG_TYPE`.

**A channel per opener.** A service that supports it serves the generic
`svc` protocol (`abi/idl/svc.idl`, one method: `connect () -> (handle
channel)`) on its shared channel next to its own; the namespace entry is
marked, and `svc_open` calls `connect` and returns the new channel
instead of a duplicate. The music player does (each opener gets its own
`music` channel, so jamjar no longer shares the shell's endpoint, and a
call cut short leaves its late answer in jamjar's channel, which goes
with jamjar). The others hand out duplicates of one channel, as today:
`audio`, `audioctl`, `devmgr`, `devmgr-ctl`, `init`, `logd`.

**What init publishes** (in its own namespace, so its followers get
them): `audio` and `audioctl` (the mixer's, made once), `music` (the
player's, made once), `devmgr` and `devmgr-ctl` (each devmgr's; replaced
on a restart), `init` (the shell's control channel, `initctl`) and
`logd` (`logctl`). The shell's startup message then holds only its
console, its root resource, `RES_PCI` and the note channel from init:
the spawn limit (16 startup handles) is far away again, and a new
service costs no startup slot. init's own services (devmgr, the mixer,
logd, ...) keep their startup roles for the channels they serve.

## Views: what each program is given

A program started by the shell gets **exactly what it was granted**:
the services and mounts on its list (below), each mount read-only or
writable as the list says, and nothing else of the shell's. A program
whose list is empty, or that has none, gets its terminal only (its
PROGRAM-level console channel, its stdout channel in a pipe, and the
handles every process has: itself, its job, the boot image to start
programs from).

**Read-only and guarded mounts.** A mount's service hands out narrower
channels onto the same volume: a new `fs` method, `view (u32 flags) ->
(handle fs)`, with two flags:

- `FS_VIEW_READ_ONLY`: every request that would change the volume is
  `ERR_ACCESS_DENIED` (open with a write flag, mkdir, unlink, rename), and
  `statfs` says read-only;
- `FS_VIEW_GUARD_ETC`: the same for anything at or under the volume's
  top-level `etc` directory (the name compared without case and without
  the trailing dots and spaces FAT ignores; a rename is refused if either
  name is there). This is what protects `/data/etc/allow` (below).

A view of a view keeps both sets of flags. The check runs in the server
(fat, and libos's fsserver for the bootfs server and the tests' RAM
filesystem), on the path after `.` and `..` are resolved, through one
libos function (`fs_view_check`). Every mount the shell gives a program
is a view: read-only when the list says so, else guarded. Only init and
the shell it starts hold unguarded channels (logd's `/data` is guarded,
the music player's mounts are read-only).

## The program's list

A program declares what it wants in its own source, once:

```c
JAM_WANTS("svc music\n"
          "mount /data r\n"
          "mount /usb* r\n");
```

`<wants.h>` turns that into an ELF note (`JamOS`, type 1) in the section
`.jamos.wants`, which `user/linker.ld` keeps in the read-only segment and
covers with a `PT_NOTE` program header, so a loader finds it without
section headers. The text is one want per line:

| Line | Means |
|---|---|
| `svc <name>` | the service `/svc/<name>` |
| `mount <point> r` / `mount <point> rw` | that mount, read-only or writable (guarded); `<point>` is `/boot`, `/esp`, `/data`, `/usb*` (every other stick) or `/*` (every mount) |
| `right <name>` | a power on the root resource: `klog`, `sysinfo`, `clock` or `debug` (below) |

**Checked at build time**: `tools/checkwants.py` reads each built
program's note (the Makefile runs it before packing the boot image) and
fails the build on a malformed line, an unknown service or right, a
mount point it doesn't know, or a test-only want (`svc devmgr-ctl`, `svc
init`: they kill drivers and services) in a program outside
`user/tests/`. Rights that are never granted to a program (`reboot`,
`kexec`, `vmex`) are not in the language at all.

**Granted by the build.** A program in the boot image gets its list as
it stands: the build checked it, and the image can't change. A program on
`/data` gets its list only once the owner approved it (below).

## `allow`: marking a program on `/data`

`allow <file>` (the interactive shell only) reads the file's list and
asks:

```
allow hello: audio, /data (write), /usb* (read)? y/n
```

A `y` writes one line to `/data/etc/allow` (made if missing): the
file's SHA-256, its path and its list as text. `allow -l` lists the
lines, `allow -r <name>` removes the ones whose path or file name is
`<name>`. Only a file on `/data` can be allowed.

**Why no program can mark a file.** Writing `/data/etc/allow` needs an
unguarded `/data`, which only init and the shell hold (every program's
`/data` is guarded or read-only). Running the file needs the root
resource's `RIGHT_ROOT_VMEX`, which only init and the shell hold. A
program that changes an allowed file changes its hash, and the file no
longer runs. Decision 11 stands: whoever holds the stick can edit the
file on another computer, as they could replace the kernel; ARCHITECTURE
says so.

## Running a program from `/data`

The kernel gives `RIGHT_EXEC` to no VMO a process makes, and that stays
the rule but for one call: `vmo_make_exec(vmo, root, &out)` (new) replaces
a VMO handle with one that has `RIGHT_EXEC` and no `RIGHT_WRITE`, if the
caller holds `RIGHT_ROOT_VMEX` on the root resource, the handle is the
VMO's only one, and the VMO is a paged one with no mapping and no pin
anywhere. Nobody can change the bytes after that (writing, mapping
writable and resizing all need `RIGHT_WRITE`), so the shell's check
can't be raced:

1. read the whole file into a new VMO (`file_read_vmo`: only the shell
   has a handle to it);
2. `vmo_make_exec` on it;
3. map it read-only, hash it, find the line in `/data/etc/allow` with
   that path and hash (none: "not allowed: `allow <file>` first"; a line
   for the path with another hash: "changed since it was allowed");
4. read the list from the same bytes, give the program its views, and
   start it from that VMO (`spawn_args.vmo`).

## The root resource's rights

`RIGHT_READ` and `RIGHT_MANAGE` on the root stop meaning "everything a
program might read" and "reboot, kexec and debug". The powers become
rights of their own, meaningful on a `RES_ROOT` handle only (bits 11 to
18; a slice never has them):

| Right | Calls | Held by |
|---|---|---|
| `RIGHT_ROOT_KLOG` | `klog_open` | console, logd, shell |
| `RIGHT_ROOT_SERIAL` | `serial_open` | serialin |
| `RIGHT_ROOT_SYSINFO` | `sys_info`, `cpu_stat`, `proc_list` | shell (and `ps`/`top`), init (`kill` finds names) |
| `RIGHT_ROOT_CLOCK` | `rtc_read` (and track C's clock) | shell (`date`) |
| `RIGHT_ROOT_REBOOT` | `reboot`, `kexec_reboot` | init, console (Ctrl+Alt+Del's fallback), shell (`reboot -f`'s fallback) |
| `RIGHT_ROOT_KEXEC` | `kexec_load` | init only (`reboot` after a flash, track C's `kernel load`) |
| `RIGHT_ROOT_DEBUG` | `debug_command` | shell (ktest, crash, stress, ...) |
| `RIGHT_ROOT_VMEX` | `vmo_make_exec` | shell (programs from `/data`) |

`RIGHT_WRITE` on the root keeps `framebuffer_take` and `serial_write`
(the console's). init holds every right (userboot gives the root
`ROOT_RIGHTS`). A program granted `right sysinfo` gets a duplicate of the
shell's root with that right only, without `RIGHT_DUPLICATE` and
`RIGHT_TRANSFER`.

## The hda driver and the mixer

devmgr's match table marks the hda driver **exclusive**: its channel is
handed out (`GET_SERVICE`) only on devmgr's control channel and on a third
channel init makes for the mixer (role `SR_DEVMGR_AUDIO`, the query
methods plus the exclusive drivers); the plain query channel gets
`ERR_ACCESS_DENIED`. So the mixer is the driver's only client outside the
tests (`hdatest` holds the control channel). The shell's `hda` keeps its
queries through the mixer: `audioctl.device` hands out a channel the
driver makes with a new `hda.query`, which answers everything but
`open_output` (dump, info, jacks, gain and bits: the owner's knobs), so
nothing the shell does can take the one output stream.

## The splits

- **`bin/play`** (`user/apps/play`): the shell's `play` resolves and opens
  the file, then starts `bin/play` with the open file (its `file` channel
  and transfer buffer, `SR_USER + 0` and `+ 1`, the size as an argument),
  a stdout channel (its lines are the shell's) and its list (`svc
  audio`). It has no namespace: a crafted file can reach the mixer and
  nothing else. Ctrl+C first asks it to stop (a message on `SR_USER + 2`:
  it fades out and says where it stopped, as before), and kills its job
  if it hasn't ended a second later.
- **jamjar's covers**: jamjar still reads the tag and finds the picture
  (its bounded ID3 parser); the picture's bytes go to `bin/jamcover`,
  which it starts with nothing but a channel and two VMOs (the picture,
  read-only; the pixels, for it to write) and asks to decode, crop and
  scale (stb_image and the 40 MiB arena move there). A picture that
  crashes or hangs it (5 s) costs that album its cover and the helper a
  restart; jamjar never maps what the helper writes (it reads it with
  `vmo_read`).

## init waits for the splash with a deadline

The shell waits for `SPLASH_PLAYED` at most the video's length plus a
margin (20 s from the splash's start); then init starts it anyway and
says why in the log.

## What changes for each program

| Program | Before | After |
|---|---|---|
| shell | 15 startup handles; root READ + MANAGE | console, root (KLOG, SYSINFO, CLOCK, REBOOT, DEBUG, VMEX), RES_PCI, init's note channel; everything else in its namespace (`*`): every mount unguarded, every service |
| programs the shell runs | every mount read-write, `audio`; tests more by command | their list: views and services; `run jamjar` = `jamjar`; `run sysmon` works (`right sysinfo`) |
| jamjar | the shell's `music` end, every mount read-write, covers decoded in-process | `music` (its own channel), `/data` and `/usb*` read-only; covers in `bin/jamcover` |
| play | in the shell's process | `bin/play`: the file and `audio` only |
| music | init's whole namespace read-write, `SR_AUDIO` | every mount read-only, `/svc/audio` |
| logd | `/data`, root READ | `/data` guarded, root KLOG |
| splash | `SR_AUDIO` | `/svc/audio` |
| console | root READ, WRITE, MANAGE | root KLOG, WRITE, REBOOT |
| serialin | root READ | root SERIAL |
| mixer | devmgr's query channel | devmgr's audio channel (reaches hda) |
| utest, usbtest (init's run) | root READ, devmgr's channels as roles | root KLOG, SYSINFO, CLOCK, KEXEC, VMEX (the refusal tests), devmgr's channels in `/svc` |
| hdatest, mixtest, utest, usbtest (from the shell) | test handles by command | their lists (`svc devmgr-ctl`, `svc init`, ...) |

## Tests

utest: the namespace with services (open, list, a per-opener channel, a
service gone and replaced), views (read-only and guarded refusals on fat
over a RAM disk, `..` and case and trailing-dot tricks, views of views),
a child given a list gets exactly it and can't open the rest, the root
rights (each call refused without its right), `vmo_make_exec` (refused
without the right, with a second handle, on a writable mapping; a program
started from a made-executable VMO runs), the hash. ktest: the root
rights at the handle layer. Shell scripts: `allow` (asked, approved,
listed, run, revoked, a changed file refused, a program can't write
`/data/etc`), `play` and jamjar as before, a cover that kills the helper.

## Open questions (for the owner)

- `run sysmon` and `run jamjar` now get what their lists say: the
  `sysmon` and `jamjar` commands stay as names for them.
- The shell's `hda gain` and `hda bits` still change the codec (they are
  not read-only, but they can't starve the mixer).
- A program on another stick (`/usbN`) can't be allowed; copy it to
  `/data` first.
