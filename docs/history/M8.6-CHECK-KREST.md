# M8.6 code check: the rest of the kernel

The last step of M8.6 ([M8.6-PLAN.md](../M8.6-PLAN.md), "Last: the code
check"): a read of `kernel/kexec`, `kernel/boot`, `kernel/debug` (panic,
klog, selftest, stress, dbgcmd, report, lockdep), `kernel/dev` (fbcon,
serial, rtc, wallclock, pci, reboot), `kernel/acpi`, `kernel/abi` (every
`sysc_*` and its argument checks, the root rights through
`sysinfo_check_root`), `kernel/main.c` and their headers and tests,
against [CODING-GUIDE.md](../../CODING-GUIDE.md) and
[ARCHITECTURE.md](../../ARCHITECTURE.md), at main febd124. The kexec
findings of [M8.5-REVIEW.md](M8.5-REVIEW.md) are not repeated; its
unfixed Lows are looked at again at the end. Findings first; each one's
outcome is filled in as it is fixed.

Severity: **High** a bug the system will meet, or a hole a program can
use; **Medium** wrong behaviour a user can meet, or a guide rule broken
in a way that matters; **Low** a wart, a rare race, a note.

Before any change, on febd124: ktest at 4 CPUs, 248 passed.

## What was checked and holds

- Every system call with hostile arguments: user pointers only through
  `copy_*_user` (ranges checked, faults are `ERR_INVALID_ARGS`), copied
  once (the `@struct` calls by the dispatcher, the rest into kernel
  buffers before use); sizes capped before any allocation
  (`CHANNEL_MAX_*`, `VMO_PIN_SYS_MAX_PAGES`, `PROC_LIST_MAX`,
  `SERIAL_IO_MAX`, `KLOG_READ_MAX`, `KEXEC_CMDLINE`, the 64-byte debug
  command); range checks written so they can't wrap (`vmo_rw`,
  `vmo_create_physical`); reserved fields and unknown flags refused; new
  handles closed again when their value can't be copied out; received
  channel handles closed when the message can't be delivered; the
  syscall number bounds-checked with a speculation-safe index.
- Wrong handle types and rights: each `sys_*` / `sysc_*` asks
  `handle_get` for the type and the narrowest right; every root power
  (`RIGHT_ROOT_*`) is checked by `sysinfo_check_root`, which also wants
  `RES_ROOT`; a slice of the root can never carry a root power
  (`publish_res` masks with `RES_RIGHTS`, and `resource_create` never
  makes a `RES_ROOT`).
- The panic path: after `kexec_panic_begin` decides, nothing allocates and
  the only locks taken (klog, fbcon, serial tx) were force-unlocked first;
  the backtrace reads only frames `vmm_translate` (lock-free) says are
  mapped; lockdep is off.
- The klog ring at 4 MiB: page-aligned static array, as kexec needs;
  readers copy 512 bytes per step under the lock, never a user copy under
  it; a gap between steps stops the read; the crash record's ring check
  (16 MiB at most) passes this kernel's own ring (static assert).
- The wall clock: the base and offset under one lock, `wallclock_set`'s
  argument checked whole (flags, reserved, zone, range); a reader racing a
  set gets a time on one side of it.

## Outcomes

- **1 (Medium): fixed** (b1c6fe9). Every synchronous drain (`serial_panic`,
  `serial_set_async(false)`, the broken-interrupt path) goes through one
  helper that keeps only the ring's newest 4 KiB (`SYNC_DRAIN_MAX`, 0.36 s
  at 115200 baud) and counts the rest in `serial_dropped`; the klog ring
  still has it. Test: ktest `serial_ring_keeps_newest` (the cut, near the
  32-bit wrap); the time itself can't be shown in QEMU, whose UART has no
  baud delay. The PC shows it: `reboot` right after `ktest` (whose flood
  test fills the ring) no longer risks "spinlock serial tx stuck".
- **2 (Medium): fixed** (35c5764, docs only): each call's root power named
  in syscalls.def and abi.h, klog_read's 4 MiB ring and `cap` 0, the
  debug words as dbgcmd.c has them.
- **3 (Medium): fixed** (a5df16a, a refactor): `kmain_stage2` is a short
  sequence of `boot_disk_init`, `clocks_init`, `cpus_init`, `run_tests`,
  `run_user_space` (with `init_words`) and `finish`; the same calls in the
  same order.
- **4 (Medium): fixed** (4d6cb1c, a refactor): the walk takes buses from a
  list, each bus put on it once. Checked in QEMU: the same `pci:` lines
  as before, and with a root port, a PCI bridge behind it and a second
  root port (`QEMU_EXTRA`) all four buses and their functions found.
- **5 (Low): fixed** (ec06b13): `pci_dev_info.reserved` at offset 14 (the
  layout is unchanged; the kernel writes 0), and layout asserts for
  `pci_dev_info`, `job_info`, `process_info`, `fb_info`.
- **6 (Low): kernel side done** (35c5764, 8b1125e): the read past the end
  with `cap` 0 is documented and tested (ktest
  `console_klog_end_then_recent`). The console's change is the services
  agent's (the note above).
- **7 (Low): fixed** (93fc385): `seen` stored and loaded atomically. No
  test: a race x86 forgives; a stale value only raises a spurious
  `SIG_READABLE`.
- **8 (Low): fixed** (f14dcd6): `dbgcmd_run_from` is gone (the syscall
  calls `dbgcmd_run`); `busy` is touched only atomically.
- **9 (Low): fixed** (cf70272): the wait has a 10 ms deadline in time, a
  chip that never settles fails `rtc_read` at once instead of after five
  tries, and the timeout is logged once with status A. No test: QEMU's RTC
  never stays in an update.
- **10 (Low): fixed** (e32a027): `glyph_locked`, no recursion.
- **11 (Low): fixed** (fd46a83): pitch >= width * bpp / 8, bpp 8..32 in
  whole bytes. ktest `kexec_handoff_check` gains a good framebuffer and
  two bad ones; the pitch-in-pixels case was accepted before the fix
  ("corruption 14 was accepted").
- **12 (Low): fixed** (92039ed): `on` above 1 is `ERR_INVALID_ARGS`, before
  the cap is looked at. ktest `dma_cap_bus_master_refuses_other_values`
  (failed before: 2 was taken as on). Every driver passes 1.
- **13 (Low): fixed** (52851d0), but for `font_8x16`, whose file is
  generated (tools/bdf2c.py): its extern stays in fbcon.c. The one line
  outside this area: `kernel/arch/x86_64/ipi.c` loses its local extern
  (panic.h declares `panic_in_progress`).
- **14 (Low): fixed** (52851d0, f14dcd6, a5df16a).
- **15, 18, 19 (Low): not changed** (notes). 18: `machine_reboot` can run
  before the TSC is calibrated (an early panic's reset), where the guide
  allows an iteration bound.
- **16, 17: design questions** (below).

## Design questions

- 16: should `vmo_make_exec` seal the VMO itself (a flag `vmo_write`,
  `vmo_set_size`, `vmo_decommit` and a writable map check under the VMO's
  lock), so the guarantee doesn't rest on handles alone?
- 17: should the screen and the serial port's output get root powers of
  their own (`RIGHT_ROOT_SCREEN`, `RIGHT_ROOT_SERIAL_OUT`), as the rest of
  the root's uses did?
