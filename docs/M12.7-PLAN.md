# M12.7 plan: NVMe and installing

Status (2026-10-09): a plan, nothing built. Written against main ae859bee
(M12's S2a merged; S2b, D and P6 still running). **Waiting for the owner's
answers to the questions below; stage 1's driver tracks can start as soon
as S2b merges** (the standing order: "NVMe stage 1 after S2b"). M12.7 is in
wave 5 ([ROADMAP.md](ROADMAP.md#now)),
beside M12.5 and M13.

Goal ([roadmap](ROADMAP.md#later)): **a user-space NVMe driver behind the
IOMMU, on the block interface M12 reviewed, in three stages, because the
PC's only NVMe drive holds Windows: (1) read-only, (2) writes to a Jam OS
disk only, (3) an installer, so the PC boots Jam OS from an internal disk
and `update` writes there.**

The owner's choice (2026-10-09): **stages 2 and 3 run on a second NVMe
drive he is buying, which Jam OS owns whole.** The driver refuses every
write to any other drive. A partition carved from Windows' drive is a
rejected alternative ([below](#rejected-alternatives)).

**Done when** (the roadmap's row, made concrete):
1. **Stage 1.** On the PC: the Windows drive is found, its four GPT
   partitions are listed with their names and types, and its ESP is
   mounted read-only and a file on it read (its SHA-256 the same as Linux
   reads). Windows' drive is untouched: a whole-disk SHA-256 taken from a
   Linux live stick before the Jam OS session matches the one taken after
   it, and the drive's own "host write commands" counter doesn't move
   while Jam OS runs. In QEMU: no write opcode ever reaches the emulated
   drive, and the image's hash is unchanged.
2. **Stage 2.** On the PC: the new, blank drive is made a Jam OS disk,
   written and read back; a power cut (the power button held) in the middle
   of a file storm loses no file that was synced; every write to Windows'
   drive is refused by volumes and, separately, by the driver.
3. **Stage 3.** On the PC: Jam OS is installed on the new drive, the PC
   boots it with the stick out, `update` writes a new build there with the
   stick's power-cut-safe steps, and Windows still boots from the firmware's
   boot menu.
4. As for every milestone: an independent review-and-fix before each
   stage's PC check, then All tests and `soak 10` on the PC with the NVMe
   driver bound (sign-off tier, [TESTING.md](TESTING.md#the-tiers)).

## What M12.7 is not

- **No other storage drivers.** No AHCI (SATA), no UAS, no RAID or VMD
  ([Later](#later)).
- **No other filesystem.** The Jam OS disk is FAT32 like the stick (Q5).
  NTFS is never read: Windows' C: is listed, not mounted.
- **No changes to Windows' drive. Ever, at any stage.** No partition
  table edits, no files on its ESP, no Limine on it, no firmware boot
  entry written by Jam OS.
- **No UEFI runtime services.** The installed disk boots through the
  firmware's default path (Q3); Jam OS writes no NVRAM variable.
- **No pagers** (M12.5) and nothing of POSIX (M13). M12.5's pagers get
  faster from a fast disk, and don't wait for it.
- **No drivers that outlive their process.** drv/nvme keeps nothing
  across a restart, as usb-storage doesn't; fat outlives its process above
  it as today.
- **No NVMe extras**: one namespace served per controller, one I/O queue
  pair, one interrupt vector, PRPs only (no SGLs), no Host Memory Buffer,
  no power states, no TRIM. Each is an addition for later.

## The hardware

- **The PC** (ASUS TUF GAMING B760-PLUS WIFI, i7-14700): one NVMe drive
  today, a Crucial P3 Plus 2 TB (CT2000P3PSSD8) at 02:00.0, c0a9:5421, MSI-X
  with 9 vectors ([HARDWARE.md](HARDWARE.md#other-devices)). It holds
  Windows 11: GPT with EFI System, Microsoft reserved, C: (NTFS) and
  Recovery. It is a DRAM-less drive that uses a Host Memory Buffer under
  Windows; it works without one (slower), and Jam OS gives it none.
- **The second drive** (stages 2-3): any M.2 2280 NVMe drive, 250 GB or
  more. The board's manual lists more M.2 slots than the one Windows uses;
  the owner checks which one is free and what it shares lanes with (some
  slots turn SATA ports off; nothing is on SATA today). It must arrive
  blank, and stay blank until Jam OS prepares it: **don't initialise it in
  Windows' Disk Management** (Windows would write its own GPT and a
  Microsoft reserved partition, and Jam OS would treat it as Windows' disk
  from then on: read-only).
- **Intel VMD** (00:0e.0) must stay off for the M.2 slots, as now: a drive
  behind VMD is hidden from PCI enumeration.
- **The IOMMU** is on by default (since 2026-10-07): every pin the driver
  makes is in its own domain ([ARCHITECTURE.md](../ARCHITECTURE.md#the-iommu)).
  Each NVMe controller is its own PCI function, so each drive gets its own
  driver process, its own `dma_cap` and its own domain: the process that
  drives Windows' drive never holds the Jam OS drive's handles, and the
  other way round.
- **QEMU** for the tests: `-device nvme` (MSI-X, PRPs, the admin and I/O
  command sets, `nvme-ns` for several namespaces and a 4096-byte
  `logical_block_size`), behind `-device intel-iommu` in the IOMMU runs.
  OVMF boots from an NVMe drive (stage 3's tests). QEMU's trace events
  `pci_nvme_admin_cmd` and `pci_nvme_io_cmd` log every command's opcode:
  stage 1's test reads them.

## The design

### The NVMe driver (drv/nvme)

A new driver, drivers/nvme/, started by devmgr for every PCI function of
class 01 08 02 (NVM Express): one new row in devmgr's match table
(`user/services/devmgr/main.c`). It gets the handles every PCI driver gets:
DR_PCIDEV, DR_DMA (bus mastering off), DR_BAR(0), DR_IRQ(0) (devmgr makes
one interrupt object, MSI-X vector 0) and DR_SERVE. It uses
`<jam/driver.h>` and nothing else, as every driver (`tools/checkdriver.py`).

Files (new): main.c (start, the loop, ending), ctrl.c (registers, enable
and disable, identify, the queues' creation, reset), queue.c (submission
and completion queues, command ids, PRPs, timeouts), cmd.c (the one place
a submission entry's opcode is written: [the guarantee](#the-read-only-guarantee-stage-1)),
serve.c (`storage` and `block`), nvme.h.

**Start.**
1. Map BAR0's registers and doorbells: the first page (CAP, VS, CC, CSTS,
   AQA, ASQ, ACQ) and the doorbells from 0x1000 for queues 0 and 1 (stride
   `4 << CAP.DSTRD`). The kernel never maps the MSI-X table's page into a
   driver; if a doorbell shares that page, the driver says so and exits 3.
2. **Quiesce before bus mastering**: the firmware's UEFI driver leaves
   the controller enabled with queues in firmware memory. Clear CC.EN and
   wait for CSTS.RDY to drop, up to CAP.TO (in 500 ms units; at most 60 s).
   Only then `drv_dma_bus_master(dma, 1)`: nothing the firmware queued can
   run against Jam OS memory (the [safe rebind](../ARCHITECTURE.md#drivers-and-services)).
3. **The admin queue**: one 4 KiB page for 64 submission entries (64 bytes
   each) and one for 64 completion entries (16 bytes each), from a
   contiguous VMO. The submission page is pinned **read-only**
   (`drv_vmo_pin_read_only`: the device only reads it, M12's Q13), the
   completion page writable. AQA, ASQ, ACQ; CC with CSS 0 (the NVM command
   set), MPS 0 (4 KiB pages: refused with a log line if CAP.MPSMIN is
   larger), round robin, IOSQES 6, IOCQES 4, then EN; wait for RDY, up to
   CAP.TO. CSTS.CFS at any point: a reset (below).
4. **Identify** (opcode 06h) into a writable-pinned page: the controller
   (CNS 1: model, serial, firmware, MDTS, NN, VWC, ONCS, SQES/CQES), the
   active namespace list (CNS 2), each namespace (CNS 0: size, the LBA
   format in use and its block size, metadata). **One namespace is
   served**: the first active one whose format has no metadata and a
   block size of 512 or 4096 (consumer drives have one namespace); any
   other is logged ("namespace 2: not served") and never read.
5. **Number of queues** (Set Features, FID 07h): one I/O pair. Then Create
   I/O Completion Queue (05h; 64 entries, interrupts on vector 0) and
   Create I/O Submission Queue (01h; 64 entries, read-only pin, on
   completion queue 1).
6. Bring the namespace's partition table in (a few reads:
   [Partition tables](#partition-tables)), then serve DR_SERVE.

The boot log has one line per controller and one per namespace, and a
RESULTS line, e.g. `nvme 02:00.0: CT2000P3PSSD8 (serial ..., firmware
...), NVMe 1.4, 1 namespace: 3907029168 blocks of 512 bytes, GPT, 4
partitions, read-only`.

**Interrupts.** One vector for the admin queue and the I/O queue (devmgr
makes one interrupt object; a vector per queue is an addition for later).
The loop binds it to its port as every driver does, acks before scanning,
then walks both completion queues by their phase bit and writes each
queue's head doorbell once per scan. While commands are in flight the loop
also wakes at the nearest command deadline, so a lost interrupt costs
time, never an answer.

**PRPs and the IOMMU.** Every buffer the device reaches is pinned once,
when it is made, never per transfer (pins cost an invalidation:
[the IOMMU](../ARCHITECTURE.md#the-iommu)):
- the queues and the identify page (above);
- **each `block` channel's buffer**: `block.map_buffer` makes the VMO in
  the driver (as usb-storage does), pins it writable (a read makes the
  device write it; stage 2's writes make it read the same pages, and a
  page is pinned one way at a time) and keeps its page addresses. The
  client's handle has no RIGHT_RESIZE, so the pages under the pin can't
  go. Up to 1 MiB a channel (`buffer_max`), 8 channels at once: 2048
  pages at most, inside a domain's limits;
- **PRP lists**: one 4 KiB page per command slot (512 entries: 2 MiB),
  pinned read-only, filled by the driver.

A request becomes commands of at most MDTS (`2^MDTS` pages; 0: no limit)
and at most the PRP list's reach. PRP1 is the first page's address plus the
offset in it, PRP2 the second page or the list. The PRP rule needs `offset`
to be a multiple of 4 (block.idl gains the note; fat's offsets are whole
sectors). No SGLs: optional in NVMe and absent on many consumer drives.

**Serving `block` with several requests in flight.** `block.read`,
`block.write` and `block.sync` are marked `later` in block.idl ([New
interfaces](#new-interfaces-for-m14)): the server's handler gets the
request's `struct idl_txn` and returns `IDL_LATER`, and the driver answers
with `block_reply_read(txn, status)` when the last of its commands
completes. Nothing changes for clients or on the wire; usb-storage's three
handlers take the txn and answer as now. So:
- answers come by txid, in completion order;
- `queue_depth` is 32 (half the submission queue: the rest keeps room for
  the other channels and a split request); more requests wait unread on the
  channel, never refused;
- a request split into several commands is answered once, with the first
  failure;
- each command slot remembers its channel, its txn and its deadline; the
  command id is the slot index with a generation (a late completion of a
  slot reused after a reset is ignored);
- the fence of usb-storage carries over: before a request's first command
  is submitted the driver looks at the channel's peer, and drops the
  request if the client has gone. And because NVMe may complete commands
  in any order, a write a dead client left in flight could land after its
  successor's write to the same block: **a partition whose closed channel
  still has commands in flight gets no new command from any channel until
  they complete** (milliseconds). Stage 1 has no writes, but the rule is
  built then, with its test, so stage 2 only adds the opcodes.

**Timeouts, abort and reset.** Admin commands get 10 s, I/O commands 30 s
(as Linux). A command past its deadline is aborted (Abort, 08h, naming its
id); if the abort itself gets no answer in 5 s, or the controller reports a
fatal status (CSTS.CFS), or a queue looks corrupt (a completion for a free
slot of the current generation), the controller is **reset**: CC.EN off,
wait, the admin queue and the I/O pair made again, bus mastering left on
(the device is the driver's and quiet once disabled). Commands in flight
are failed with ERR_IO, except reads, which are submitted once more after
the reset (`idempotent`). Three resets within 60 s: the driver exits 3 and
devmgr restarts it with backoff, as for any driver; volumes sees the disk's
channel close and mounts it again when devmgr announces it again.

**Ending.** DR_SERVE closed (devmgr stops it: a reboot or a kill): every
channel closed, then the controller's **normal shutdown notification**
(CC.SHN 01b, wait for CSTS.SHST 10b, up to 10 s): the drive saves its own
state, as Windows' shutdown does, and its "unsafe shutdowns" counter
doesn't grow. Then unpin and exit 0. A kexec turns bus mastering off on
every function as today.

**Announcing the disk.** devmgr's disks.c learns PCI disks: a function
bound to drv/nvme is a disk, asked for a `storage` channel of volumes' own
with `svc.connect` like a usb-storage driver, and announced with
`disks.attach(id, BUS_NVME, storage)`, where `id` is `0x40000000 | bus <<
8 | dev << 3 | fn` (its own range, never the top bit, which test disks
use).

### The read-only guarantee (stage 1)

Stage 1's driver has **no write path at all**, and this is checked three
ways, so a mistake in one doesn't reach the drive:

1. **Structure.** cmd.c is the only file that writes a submission
   entry's opcode, through two functions: `sqe_admin(enum admin_op, ...)`
   and `sqe_read(...)`. The enum lists the stage's admin commands and no
   others: Identify (06h, CNS 0, 1, 2 only), Get Log Page (02h, log pages
   01h and 02h only), Set Features (09h, FID 07h only), Create and Delete
   I/O Completion and Submission Queue (05h, 01h, 04h, 00h), Abort (08h).
   The one I/O command is Read (02h). Each function checks its arguments
   against that list again at run time and ends the driver (exit 1, a
   RESULTS line) on anything else: fail closed. **There is no code for**
   Write, Write Zeroes, Write Uncorrectable, Dataset Management (TRIM),
   Copy, Flush, Format NVM, Sanitize, Security Send, Firmware Download or
   Commit, Namespace Management or Attachment, Directive Send, or any
   other Set Features: nothing to call by mistake.
2. **A build check** (new: tools/checknvme.py, run by `make check`): the
   opcode constants in drivers/nvme/ are exactly the stage's list (stage 1:
   the list above; stage 2 adds Write and Flush, [below](#stage-2-writes-to-a-jam-os-disk-only));
   no other file of drivers/nvme/ stores to a submission entry's first
   byte; the I/O opcode names of the list's complement appear nowhere. A
   later change that adds a command must change the check, which a review
   sees.
3. **The protocol.** `storage.open_partition(index, 0)` (writable) answers
   ERR_ACCESS_DENIED on every disk in stage 1; `block.info` says
   `read_only` 1; `block.write` answers ERR_ACCESS_DENIED before looking at
   anything; `block.sync` answers OK with no command (nothing was written).
   volumes, separately, never asks for a writable channel on BUS_NVME in
   stage 1, and `mount -w` refuses NVMe mounts.

**How a test proves it in QEMU** (new: tools/nvme-test.sh): the drive
image's SHA-256 is taken on the host before and after the run, which reads
every partition, mounts the ESP-like partition, reads files, runs `disk
digest` and kills the driver mid-read; QEMU logs every admin and I/O command
(`-trace pci_nvme_admin_cmd -trace pci_nvme_io_cmd`), and the script fails
on any I/O opcode but 02h or any admin opcode outside the list. The image
is opened writable (a read-only `-drive` would hide a write as an error
instead of showing it).

**How the PC proves it**: [P1](#p1-stage-1-read-only-on-windows-drive).

### Partition tables

**Where they are read.** In the driver, through a library both disk
drivers can link: drivers/lib/parttable.c with its header in
drivers/include/jam/ (new), linked as DRV_LIB like `drivers/lib/netserver.c`.
Not in volumes: `storage.idl` (shaped by M12 for GPT) has the driver list
the partitions and open a `block` channel limited to one, and the limit is
the driver's to enforce, so the driver must know the bounds from a table
it read itself; giving volumes the whole disk to parse would break
storage.idl's rule that nothing is given the whole disk. volumes applies
the policy (what to mount, and how) on what `storage.partition` answers,
and checks the Jam OS mark again with its own code ([stage 2](#stage-2-writes-to-a-jam-os-disk-only)).
usb-storage moves onto the library later (a stick or USB SSD with GPT then
gets its partitions too): after M12.1 has reviewed usb-storage, so the two
don't edit it at once.

**The library**: `pt_read(block_size, blocks, read_fn, ctx, &table)`, where
`read_fn` reads blocks into a buffer of the caller's, and the table holds
the scheme, the MBR disk id, the GPT disk GUID, which GPT headers were good,
whether the disk is blank, and up to 16 used partitions (type byte, type
GUID, unique GUID, start, length, attributes, name in UTF-8). It reads LBA
0, LBA 1, the entry array, the last LBA and the backup entry array: at most
2 x 32 KiB. The MBR rules move over unchanged from
`drivers/usb-storage/block.c` (a table looked for before a FAT boot
sector; entries inside the disk and not overlapping).

**GPT, checked as UEFI says (2.10, section 5.3)**, every field read with
bounds checked before use:
- LBA 0 is a protective MBR (an entry of type EEh); a hybrid one (EEh beside
  other entries) is read as GPT and logged; a GPT header without a
  protective MBR is ignored, as UEFI does.
- **Each header** (primary at LBA 1, backup at the last LBA): signature
  "EFI PART", revision 1.0, header size 92 up to the block size, the
  header's CRC32 (computed with its own field as zero), the reserved field
  zero, MyLBA right (1, or the last LBA), AlternateLBA the other one,
  FirstUsableLBA <= LastUsableLBA, both inside the disk and clear of both
  headers and entry arrays, the entry array inside the disk and outside the
  usable range, 128 to 1024 entries of 128 bytes times a power of two (at
  most 32 KiB read), and the entry array's CRC32.
- **Both headers good**: they must agree (disk GUID, usable range, entry
  count and size, the entry array's CRC); then the table is read. **One
  good**: the table is read from it, the disk is listed with "primary (or
  backup) GPT damaged", and it can never be written (stage 2's mark
  needs both). **Neither**: the disk is listed as having no readable table
  and nothing on it is mounted.
- **Entries**: a type GUID of zeros is unused; a used entry needs
  FirstUsableLBA <= start <= end <= LastUsableLBA, no overlap with an
  earlier used entry (left out and logged otherwise, as MBR entries are);
  more than 16 used: the rest listed in the log, not served. Names: 36
  UTF-16LE units to at most 108 bytes of UTF-8 (`storage.partition`'s
  `str[<=108]`), stopping at the first zero; a unit that isn't valid UTF-16
  becomes '?'.
- GUIDs are kept as the 16 bytes on disk (the first three fields
  little-endian); the printed form is made only for the log and the shell.
- **Blank**: LBA 0, LBAs 1 to 33 and the last 33 LBAs (or the same 64 KiB
  at each end at 4096 bytes a block) are all zeros. A new drive reads as
  zeros. Stage 2's `create_table` writes only to a blank disk.

**Host tests** (new: tools/gptcheck.c, built and run on the Mac by `make
check`, as menucheck is): the library compiled for the host against
images made by a new tools/mkgpt.py: a Windows-like disk (protective MBR,
ESP, MSR, basic data, recovery: the PC's layout), each header's CRC broken
in turn, the entry array's CRC broken, headers that disagree,
out-of-range and overlapping entries, 4096-byte blocks, 129 and 1024
entries, a hybrid MBR, GPT without a protective MBR, a name with odd
UTF-16, a blank disk and an almost blank one; plus a few thousand
mutated tables (seeded, deterministic) that must neither crash nor list a
partition outside the disk.

### volumes and the shell (stage 1)

- volumes takes `disks.attach` with BUS_NVME like a stick, with a few
  differences: it never asks for a writable channel (stage 1); a GPT
  partition counts as FAT when its type is the ESP's
  (C12A7328-F81F-11D2-BA4B-00A0C93EC93B) or Microsoft's basic data
  (EBD0A0A2-B9E5-4433-87C0-68B6B72699C7, which is also NTFS's: fat looks at
  the boot sector, finds no FAT and exits FAT_EXIT_NO_VOLUME, having read
  one block); MSR, recovery and anything else is listed, never started.
  FAT partitions are mounted read-only as **`/nvme0`, `/nvme1`, ...** (Q6),
  numbered in the order found, apart from `/usbN`. On the PC: Windows' ESP
  is `/nvme0`.
- volumes' MAX_PARTS grows from 4 to 16 (`user/services/volumes/disk.h`).
- **Listing** (new `volumes` methods, read-only, on any volumes channel):
  each disk (its id, bus, model, serial, size, block size, scheme, which
  GPT headers are good, its kind: Jam OS, blank or other) and each
  partition (type by name where known, else the GUID; GPT name; start and
  size; its mount, if any). volumes asks the driver (`storage.info`,
  `storage.partition`, the new `storage.ident`).
- **The shell's `disks`**: one block per disk, e.g.

```
nvme0  CT2000P3PSSD8  serial 2324E6E2xxxx  2000.4 GB  GPT (both headers good)  read-only
   1  EFI system         100 MiB   "EFI system partition"           /nvme0
   2  Microsoft reserved  16 MiB   "Microsoft reserved partition"
   3  Microsoft basic data 1.8 TB  "Basic data partition"           (no FAT volume)
   4  Windows recovery    750 MiB  ""
usb0   SanDisk Cruzer  ...
```

- **`disk digest <disk> [<lba> <count>]`**: SHA-256s computed in the
  driver (the new `storage.digest`: the data never leaves the driver, and
  no channel to the whole disk exists). Without a range: the **region
  list** below, one line each, also written to the boot log (so the main
  session reads them from `/data/logs` on the Mac).
- **`disk smart <disk>`**: the drive's health log (Get Log Page 02h, the
  new `storage.health`): data units read and written, host read and write
  commands, power cycles, unsafe shutdowns, percentage used, critical
  warning. The driver also logs it once when it starts.

**The region list**, made from the partition table alone so that Linux
can make the same one: the first 34 blocks (protective MBR, primary GPT);
each partition under 1 GiB whole (the ESP, MSR and recovery); for larger
ones (C:) the first and last 64 MiB and 32 samples of 1 MiB at
`start + k * (size / 32)`; the last 33 blocks (backup GPT). A few GiB in
all: about ten seconds at the driver's software SHA-256. The same list,
read by Linux (new: tools/disk-regions.py, which opens the device
`O_RDONLY` and refuses a path that isn't a block device), must print the
same lines; that proves the read path at every region.

### Proving Windows' disk untouched

(Superseded on 2026-10-09: the owner's revised Q2 answer, at the end,
keeps only witness 2, the drive's own counter. The rest is kept for the
record.)

Three independent witnesses (Q2):
1. **A whole-disk SHA-256 from a Linux live stick**, before and after the
   Jam OS session (`sha256sum /dev/nvme0n1` after `blockdev --setro`), with
   Windows fully shut down before the first and not started until after
   the second. It doesn't trust any Jam OS code. About 15 to 30 minutes
   each for 2 TB.
2. **The drive's own counter**: "host write commands" in its health log
   counts every write command the controller completed. Read by the Jam OS
   driver when it starts and by `disk smart` at the end of the session: the
   same number.
3. **Jam OS's region digests** equal Linux's (both runs): the reads are
   right, not just harmless.

For every later build that touches the driver (after stage 1's sign-off),
witness 2 alone is enough on every boot, and an optional Windows-side check
of the regions Windows doesn't change while it runs (GPT areas, MSR,
recovery) can be run from an administrator PowerShell (new:
tools/disk-regions.ps1, which opens `\\.\PhysicalDrive0` for reading only).

### Stage 2: writes to a Jam OS disk only

**What makes a disk Jam OS's** (Q1): Jam OS owns the whole drive, and the
mark is its partition table:
- GPT, **both headers good and agreeing**;
- exactly two used entries: entry 1 of the ESP's type with the GPT name
  "Jam OS ESP", entry 2 of **Jam OS's data type,
  71bae565-d4a8-4315-8c81-9b35462cc158** (made for this plan; Windows
  doesn't mount a type it doesn't know, so it never writes "System Volume
  Information" there) with the name "Jam OS data";
- nothing else. A disk with any other partition, a damaged header, or MBR
  is **other**: read-only, whatever it holds.

**The driver's mode, per drive**, decided from the table it read itself
when it starts, and again only after its own `create_table`:
- **other** (Windows' drive): exactly stage 1. Every write and every
  writable `open_partition` is refused (ERR_ACCESS_DENIED) before any
  command is built; `create_table` refused, unless the owner confirmed
  the drive's erase (the serial's last four and `erase`: [NV-warn
  notes](#nv-warn-notes)), which arms **erase** for that `create_table`
  alone: the table's blocks and the zeros at the blank rule's two spots.
- **blank**: reads, and `storage.create_table` (below). Nothing else
  writes.
- **Jam OS**: writable `block` channels on its two partitions; writes only
  inside a partition (the range check as usb-storage's, against the
  driver's own table); the GPT areas, the protective MBR and the gaps are
  out of every channel's reach.

The write opcodes (Write 01h, Flush 00h) are reachable only through one
function, `sqe_write`, which takes the channel and checks the drive's mode
and the range itself before it builds anything; tools/checknvme.py's stage
2 list says so (Write and Flush, only in cmd.c, only from `sqe_write` and
`sqe_flush`). **A boot word `diskro`** makes every drive "other" (a
Developer entry, "Jam OS (internal disks read-only)"; devmgr passes `ro` to
drv/nvme): the way out if a stage-2 build misbehaves.

**volumes checks the mark again with its own code** (not the library's:
a bug in one isn't a bug in both): it asks for a writable channel only on
a disk its own check calls Jam OS's, and refuses `mount -w` elsewhere
("mount: /nvme0 is not on a Jam OS disk: it stays read-only"). Below it, the
driver refuses anyway; the stage 2 test proves each refusal separately
(a test word makes volumes skip its own check once, and the driver must
still refuse).

**Durability.** Every write is sent with FUA (Force Unit Access): its
answer means it is on the medium, as fat's write order (data, both FATs,
the directory entry) and `update`'s renames assume. The drive's volatile
cache would otherwise let a later write reach the flash before an earlier
one. `block.sync` sends Flush as well (a drive without a volatile cache:
answered at once). FUA costs speed on a drive without power-loss
protection; Jam OS writes little, and the bench line says how much.

**Preparing a blank disk** (`disk prepare <disk>`, new): the shell asks
init (a new `initctl` method), which asks volumes on a channel init alone
holds (a new protocol, `volinstall`, as `volesp` is: nothing the shell or
the tests hold can ask it). The shell shows the drive's model, serial and
size and asks the owner to type the serial's last four characters. volumes
makes three random GUIDs and asks the driver's `storage.create_table`,
which **refuses unless the drive is blank** and writes, all with FUA: the
backup entry array, the backup header, the primary entry array, the
primary header, a Flush, then the protective MBR last. A cut before the MBR
leaves LBA 0 zero and the rest a Jam OS table: the blank rule counts such a
disk as blank-in-progress (LBA 0 zero and every header present a Jam OS
one), so `disk prepare` simply runs again. The layout: the ESP from 1 MiB,
512 MiB; the data partition from there to the end of the disk, at most 2
TiB (FAT32 with FatFs's 32-bit sector numbers), 1 MiB aligned; 128 entries.
The driver reads its table back and changes mode; volumes formats both with
fat (FAT_ARG_FORMAT, given only to the two partitions of a disk it has just
prepared) and mounts them read-only like any other disk's; `mount -w` then
works on them.

**Preparing a disk that isn't empty** (the owner, 2026-10-14: "leave it
to the user, they're the ones choosing what drive to install it on, just
warn using the empty rules"; built by NV-warn, [its notes](#nv-warn-notes)):
the empty rules (block 0, the first and last 64 KiB, and the first MiB at
1 MiB and at 513 MiB, all zeros) no longer refuse, they decide which
confirmation is asked. An empty drive: the one above, unchanged. Any other
(not the boot disk, nothing on it mounted read-write, not `diskro`): the
shell shows what is on it (its partition table, each partition's type,
size and name, any FAT volume Jam OS mounted from it, or "data Jam OS
doesn't recognise"), says everything on it will be lost, and asks for the
serial's last four characters and then `erase`; anything else stops, and
nothing is written. volumes and then the driver check both answers again;
the driver zeros the first MiB at each spot (where the ESP and the data
partition will start) before it writes the table, so fat formats both.

**A power cut** loses at most what wasn't answered: the stick's rules
hold, with FUA making "answered" mean "on the medium". The FAT clean bit
says whether a volume was cut; a dirty one is mounted and logged as on the
stick (there is no fsck).

### Stage 3: the installer and the boot path

**`install <disk>`** (new; shell, then init, then volumes' `volinstall`):
1. A blank disk is prepared first (stage 2); a Jam OS disk is reused: its
   data partition is kept, its ESP's files replaced. Any other: refused.
2. init writes the ESP through the writable `fs` channel volinstall hands
   it (the disk's ESP stopped and started writable, in no namespace, as
   `volesp` does for the stick), on update.c's worker thread like
   `user/services/init/espwrite.c`, with the same deadlines: Limine's
   EFI/BOOT/BOOTX64.EFI (copied from the stick's ESP, read back and
   compared), the boot menu (the stick's `boot/limine.conf`: its `boot():`
   paths name whatever partition Limine was loaded from, so it works
   unchanged), boot/jamos.elf and boot/bootfs.img (init's checked copies
   of the running build, as an update's), each synced and read back against
   its SHA-256; the boot menu last, so a cut before it leaves a disk the
   firmware can't boot rather than one that boots half a build.
3. The data partition gets the stick's `/data/etc` (the settings, the
   update key's trust, the network address): Q7.
4. The shell says which firmware entry to pick and how to make it the
   default (Q3).

**Booting it** (Q3): the firmware finds `\EFI\BOOT\BOOTX64.EFI` on the
ESP of any disk by itself (the removable-media path) and lists the drive
in its boot menu (F8) and boot order. Jam OS writes no NVRAM variable and
needs no UEFI runtime services. Windows keeps its own "Windows Boot
Manager" entry, untouched; the owner picks the order in the firmware.

**Knowing the boot disk.** Limine names the disk it loaded the kernel from:
an MBR disk id for the stick, and for a GPT disk its disk GUID (its
`limine_file`'s `gpt_disk_uuid`; the MBR id is then 0). The kernel reads the
GUID beside the MBR id (`kernel/boot/limine.c`), passes it on as
`bootdisk=gpt:<GUID>` (to init, to volumes, and on the kexec command line,
as `bootdisk=` is today), and volumes' boot-disk check gains the GPT form:
the disk whose `storage.info` disk GUID matches, with the Jam OS layout and
boot/jamos.elf on its ESP, is the boot disk: `/esp` (read-only) and
`/data`. The stick, if it is in, is then just another disk: `/usb0`,
`/usb1` read-only (Q8).

**`update` on the installed disk**: no change. init's ESP write already
goes to "the boot disk's ESP" through `volesp`; the boot disk is now the
NVMe one, and the same steps run (new build under `*.new` names, read
back, the four renames each synced, the menu last with its spare): a
power cut at any point leaves one of the menu's two entries booting a whole
build ([Storage](../ARCHITECTURE.md#storage)). With FUA and Flush the
"synced" in those steps is the medium's, not the drive's cache.

### Rejected alternatives

- **A partition carved from Windows' drive** (shrink C: in Windows, give
  Jam OS the space). Rejected (the owner, 2026-10-09):
  - Jam OS would have to write Windows' partition table (both headers and
    entry arrays, CRCs recomputed) to add its partitions: the one write
    that can make Windows unbootable, on the one disk the plan exists to
    protect. Letting Windows' diskpart make them instead can't set GPT
    names, so the ESP can't be marked.
  - The "refuse every write to this drive" rule would become "refuse
    writes outside these ranges on this drive": a range check, not a
    structural one, inside the driver process that drives Windows' disk.
  - Booting it: the firmware's removable path on that disk is Windows'
    `\EFI\Boot\bootx64.efi`, so Jam OS would need a firmware entry written
    from Windows (`bcdedit` on `{fwbootmgr}`) or Limine on Windows' ESP (a
    write to Windows' disk).
  - The whole-disk hash check of stage 1 couldn't be repeated: Jam OS's
    own writes would change it.
- **A USB SSD.** Nothing new to build for stage 2 once usb-storage reads
  GPT, but it doesn't meet stage 3's "boots from the internal disk", and
  it is a bigger stick.
- **NVMe namespace write protection** (Set Features 84h, "write protect
  until power cycle") on Windows' drive: optional in NVMe and likely absent
  on the P3 Plus, and itself a state-changing command sent to the drive
  Jam OS must not touch.
- **GPT parsing in volumes**: [Partition tables](#partition-tables).
- **The partition mark in a GPT attribute bit**: type-specific bits mean
  something else to each type, and Windows reads bits 60 to 63; the name
  and the type GUID are what tools show.

## Questions for the owner

Each stands on its own and ends with a recommendation; the plan assumes
the recommendation until you say otherwise. Q1, Q2 and Q3 shape the
tracks; the rest are smaller.

### Q1. What marks a drive as Jam OS's

- **(A)** Its partition table: GPT with both headers good, exactly Jam
  OS's two partitions (the ESP named "Jam OS ESP", the data partition of
  Jam OS's own type named "Jam OS data"), nothing else. Jam OS writes a
  table only onto a blank drive, after you type the last four characters
  of its serial. Checked by the driver and, with other code, by volumes.
- **(B)** A list of serial numbers in the settings (`disk.jamos = ...`):
  a drive is writable only if listed. Independent of what's on it, but a
  setting that can be wrong, and the installed system's list lives on the
  disk it protects.
- **(C)** Both.

*Recommendation: (A).* The mark travels with the drive, needs no setting,
and Windows' drive can never match it (it has four partitions of
Microsoft's types). The typed serial guards the one moment a blank drive
becomes Jam OS's.

### Q2. How to prove Windows' drive untouched in stage 1

- **(A)** A Linux live stick (Ubuntu, on the second stick: it erases
  it): a whole-disk SHA-256 before and after the Jam OS session, plus the
  drive's host-write counter, plus Jam OS's region digests compared with
  Linux's. About an hour of the owner's time, once.
- **(B)** No Linux: the drive's counter, and the regions Windows doesn't
  change while it runs, hashed from PowerShell before and after.
- **(C)** The counter alone.

*Recommendation: (A) once, for stage 1's sign-off*; afterwards (C) on every
boot, and (B) whenever a build changes the driver's core. (A) is the only
witness that trusts no Jam OS code.

### Q3. How the installed disk boots

- **(A)** The firmware's own path: Limine as `\EFI\BOOT\BOOTX64.EFI` on
  Jam OS's ESP; the firmware lists the drive by itself; you set it first in
  the boot order (or pick it with F8). Jam OS writes no NVRAM variable.
- **(B)** Jam OS writes a firmware boot entry: needs UEFI runtime services
  in the kernel (new kernel work, M10-sized), and a bug there writes NVRAM.
- **(C)** Limine stays on the stick and gets an entry that boots the
  internal disk's build: fails "boots without the stick".

*Recommendation: (A).* Nothing to build in the kernel, nothing written
outside Jam OS's own drive, and the firmware's menu stays the way back to
Windows.

### Q4. Windows in Jam OS's boot menu

- **(A)** No Windows entry: Windows is picked from the firmware (F8, or
  the boot order).
- **(B)** A Limine entry that chainloads Windows' boot manager from
  Windows' ESP (`protocol: efi`): convenient, but BitLocker (if on, with
  Secure Boot off as Jam OS needs) measures the loader that started Windows'
  boot manager and asks for the recovery key.

*Recommendation: (A)*, at least until you know whether BitLocker is on
(`manage-bde -status C:`: P0 asks).

### Q5. The Jam OS drive's filesystem

- **(A)** FAT32, like the stick: the data partition up to 2 TiB, the 4 GiB
  file limit, everything fat has (outliving its process, the hold, the
  fence) as tested.
- **(B)** exFAT (FatFs has it): files over 4 GiB; a new mode of fat to test
  and review.
- **(C)** A filesystem of Jam OS's own: a milestone of its own.

*Recommendation: (A).* M12.7 is about the drive; a filesystem change is
its own milestone when 4 GiB files matter.

### Q6. Mount names for internal drives

- **(A)** `/nvme0`, `/nvme1`, ... per FAT partition, numbered apart from
  `/usbN` (Windows' ESP is `/nvme0`).
- **(B)** `/disk0`, `/disk1`, ... for every internal drive, whatever its bus.

*Recommendation: (A)*: the name says which hardware, as `/usbN` does.

### Q7. What the installer copies to the new `/data`

- **(A)** The build, and the stick's `/data/etc` (settings, network
  address, update trust): the installed system starts as the stick does.
- **(B)** The whole stick's `/data` (logs, music, everything).
- **(C)** The build only: a fresh `/data`.

*Recommendation: (A)*; copy music by hand with `cp` if wanted.

### Q8. The stick after the install

- **(A)** It stays a working stick: picked with F8 it boots Jam OS from
  itself as now (the NVMe disk then mounts as `/nvmeN` read-only), and
  `update` writes only the disk the PC booted from.
- **(B)** `update` writes both the boot disk and the stick when both are in.

*Recommendation: (A)*: one write path, already power-cut tested; the stick
is the way back if the internal disk's build breaks.

## Risks

- **Windows' drive.** The worst outcome of the milestone. Defences, in
  order: no write code in stage 1 (structure, the build check, the
  protocol); in stage 2 a driver process per drive whose mode for Windows'
  drive is decided from its table and refuses before building a command,
  volumes' own check with other code, the `diskro` word; independent
  reviews before each PC check; the whole-disk hash and the drive's own
  counter. What none of these covers: an admin command that isn't a write
  but changes the drive (a format, a sanitize, a firmware commit): they
  have no code, and the build check keeps it so.
- **The firmware's controller state.** UEFI leaves the controller running
  with queues in its memory; the driver disables it before bus mastering
  goes on. A controller that doesn't come back after the disable gets one
  reset and then the driver gives up (exit 3); the drive is unchanged
  either way.
- **The P3 Plus without its Host Memory Buffer.** Slower reads under heavy
  load; no correctness effect. A later addition if `bench` shows it.
- **BitLocker.** Nothing in the plan changes what Windows measures at its
  boot (no Limine entry for Windows, no changes to its ESP, the firmware
  starts Windows Boot Manager itself). P0 has the recovery key ready in
  case the firmware's boot-order change matters on this board.
- **Windows initialising the new drive.** If Disk Management is opened
  first it offers to; then the drive is "other" to Jam OS for good. The way
  back is Windows' `diskpart` `clean` on that drive only, which risks
  picking the wrong one: P2 says not to open it.
- **Write ordering on NVMe.** Completion order isn't submission order and
  the drive caches writes: FUA on every write, Flush on sync, and the
  drain-on-close rule for a dead client's writes. Tested with kills in
  QEMU and a real power cut on the PC.
- **FAT32 on a big partition.** fat mounts by reading the FSINFO sector;
  a dirty volume makes FatFs count free clusters by reading the whole FAT
  (128 MiB at 1 TB): seconds, once. The data partition stops at 2 TiB.
- **Two QEMU traces differ**: QEMU's trace event names may change between
  versions; N5's test pins the PC's QEMU 10.0.2 and fails loudly if no
  command was traced at all (rather than passing on silence).

## Later

## N3 notes

Choices the plan left open, made the safe way (track N3, serving storage
and block):
- **block.write has no handler in drv/nvme.** tools/checknvme.py forbids
  any identifier naming a write in drivers/nvme/, so there is no
  `.write`: the generated dispatch answers ERR_NOT_SUPPORTED, not
  ERR_ACCESS_DENIED (block.idl says so). Every channel says `read_only`
  1, and `open_partition(i, 0)` is ERR_ACCESS_DENIED on every disk
  (checked right after `read_only > 1`, before the index). W1 adds the
  handler with the opcodes and the check's stage-2 list.
- **storage.idl**: `health` is `later idempotent` (it sends Get Log Page
  with ctrl_admin_send and answers from its completion; every request
  waiting meanwhile gets that answer); `digest` is `later`, at most
  DIGEST_MAX (1 GiB: the region list's largest is a partition under 1
  GiB) and DIGEST_QUEUE (8) waiting. `info`'s vendor is "NVMe" and its
  product the model's first 16 characters; `ident` has the whole model,
  the serial and the firmware revision.
- **Buffers and pins**: a channel's buffer is 64 KiB by default, 1 MiB
  at most, pinned writable when map_buffer makes it and unpinned when
  nothing of the channel's is out; 8 channels, 32 reads each in flight.
  The digest buffer (1 MiB, two halves: one hashed while the other is
  read) is pinned once at the start and also carries the partition
  table's reads. About 600 + 2048 + 256 pages at most, inside the job's
  4096.
- **The drain rule is per partition** (the table's index). A draining
  partition's channels are not read; a request read in the moment its
  predecessor died (the race between the fence and the read) is held and
  sent when the partition is quiet. A gone client's reads not yet sent to
  the drive are taken back (queue.c's new io_cancel). For W1: a write
  must still be fenced when it is read, as reads are; the rule then keeps
  a successor's writes behind every write the dead client had out.
- **The table**: read once at the start, waited for (no client yet). A
  disk whose table can't be read is served with no partitions; a read
  that gets no answer, or a controller that fails meanwhile, ends the
  driver (exit 3). The RESULTS line: `nvme 02:00.0: <model>, <n> MiB,
  GPT, 4 partitions, read-only` (`..., GPT, 4 partitions, primary GPT
  damaged (<why>), read-only` when one header is bad).
- **A test's storage channel**: devmgr refuses get_service for a disk's
  driver, so utest's NVMe cases get theirs from a new
  `devmgrctl.disk_storage` (13, `later`: devmgr asks the driver's
  svc.connect for the caller, as for volumes). Only the control channel
  (init's, the tests') has it, and that channel can already hand every
  disk to anyone with set_volumes: no new authority.
- **The drain rule's test**: QEMU's drive completes reads in
  microseconds, so a client that leaves almost never has any out. The
  test word `nvmetest=slow` answers a channel's reads 20 ms apart
  (block.c), so utest's `nvme_fence` client leaves with 31 out and the
  log shows the partition held and released;
  `tools/nvme-test.sh`'s new `block` case runs utest's NVMe cases with it.
- **tools/nvme-test.sh's level 3** is now "the shell has `disks`" (N4),
  not "storage.idl has digest" (N3 adds digest).
- **Until N4**: volumes takes a BUS_NVME disk like a stick. A GPT
  partition's MBR type is 0, which volumes counts as FAT, so fat is
  started read-only on each partition and the ESP becomes `/usb0`
  (read-only at the driver too); N4 replaces this with `/nvme0`.

## N4 notes

Choices the plan left open, made the safe way (track N4, volumes and the
shell):
- **The shell reaches volumes through init, not by `svc volumes`.** The
  plan says the listing is "on any volumes channel", but the only volumes
  channel a program may hold is its control channel (kill, test_disk,
  release_disk, set_disks), which tools/checkwants.py keeps from every
  program but a test. So the listing is a protocol of its own, `voldisks`
  (74, abi/idl/volumes.idl), spoken on a new kind of channel (chans.c's
  LEVEL_LIST) that answers voldisks alone (anything else is
  ERR_ACCESS_DENIED), made by a new control method `volumes.list_channel`.
  init holds the control channel and hands the shell one list channel per
  call: `initctl.disks` (11, admin: the shell's channel only). The shell
  gains no authority; the list channel can list, hash and read the health
  log, and nothing else. Control channels also speak voldisks (for tests).
  Costs outside the plan's file list: abi/idl/initctl.idl, init/ctl.c
  (one op), user/services/shell/sh.h (the two declarations).
- **voldisks**: `disk(index)` (id, bus, ready, kind, scheme, read_only,
  block size, blocks, partitions, name, model, serial, firmware),
  `partition(id, index)` (MBR type, type GUID, start, blocks, fs state, GPT
  name, mount), and the two `later` questions `digest(id, lba, count)` and
  `health(id)`, which volumes forwards to the driver's storage.digest and
  .health from a task (the loop goes on; 60 s and 10 s). The shell
  computes the region list itself from `disk` and `partition` (the same
  rule as tools/disk-regions.py, no more state in volumes).
- **Names**: a disk is `nvme0`, `usb0`, ... numbered per bus in the order
  attached, the lowest free one (kept across its driver's restart; a gone
  disk's number is free again). A mount is numbered separately, in the
  order its FAT partitions are found: a disk named nvme1 can hold /nvme0 if
  the first drive has none. The log names an NVMe disk "nvme0", a stick
  still "disk N".
- **FAT or not**: on a GPT disk by the type GUID (ESP,
  Microsoft basic data), on an MBR disk by the type byte as before. Basic
  data is also NTFS's: fat starts, reads one block, exits
  FAT_EXIT_NO_VOLUME, and volumes remembers it (`nofat`; the listing says
  "no FAT volume"; nothing is written). A disk whose block size is not 512
  starts no service at all (fat would exit 1 and be restarted until given
  up on): the partitions say "no FAT: 4096-byte blocks". This applies to
  sticks too.
- **Read-only**: NVMe mounts are `other` mounts with a `nvme` flag, so
  everything about /usbN holds (read-only `block` channel, no format
  argument), and `volumes.remount` with writable on one is
  ERR_ACCESS_DENIED. init's `mount` already refuses anything but /usbN;
  the shell's mount.c answers "not on a Jam OS disk" first. No desktop
  notice for an internal drive's mounts.
- **What the listing does not have**: "which GPT headers are good" (the
  plan's example) is not in storage.info, so `disks` says only GPT; the
  driver logs "primary GPT damaged". The `kind` is Jam OS (an MBR disk with
  the ESP, FAT32 layout, or the boot disk), "nothing found" (no table: not
  proof of blank; the driver's strict blank rule is stage 2's), or other.
  Stage 2's W1/W2 add the GPT mark.
- **Limits**: MAX_PARTS 16 (every table the library lists); at most 4
  `/nvmeN` mounts beside 4 `/usbN`, and a namespace holds 8 mounts in all
  (NS_MAX_MOUNTS: /boot /esp /data and five more); a ninth fails with
  init's "can't mount".
- **The boot log**: `disk digest` prints each line to the screen in the
  plan's exact form and to the log as `disk digest: nvme0 part1
  2048+204800 <hash>`, a different form on purpose: a test that reads the
  serial output (tools/nvme-test.sh) sees both streams, and the same line
  twice would not equal tools/disk-regions.py's. `disk smart` logs one
  line of its counters the same way.
- **The gate is gone**: devmgr's nvme row has no word; every boot binds
  drv/nvme. `nvmetest=on` still means no test words.
- **tools/nvme-test.sh**: `ls` prints BCD before bootmgfw.efi, so the
  script waits in that order; its L3 patterns otherwise held.

## W1 notes

Choices the plan left open, made the safe way (track W1, the write path
in the driver), and what W2, W3 and R3 should know:
- **The gate is cmd.c's.** The drive's mode (`enum nvme_mode`: other,
  blank, Jam OS) and the blocks a write may reach live in cmd.c's static
  `gate`, set only by `cmd_arm` from the table the driver read itself (the
  library's `pt_kind`): at the start, after `create_table`'s read-back, and
  nowhere else. It starts from MODE_OTHER every time; `ro` (from `diskro`)
  and a table that can't be read leave it there. MODE_JAMOS: the two
  partitions' blocks, copied from the table. MODE_BLANK: only the blocks
  Jam OS's table takes (`pt_jamos_plan`: the first 2 + 32 and the last
  1 + 32 at 512 bytes), which lie inside the blank rule's zeros, so a
  prepare overwrites only blocks seen to be zeros (or a cut prepare's own
  table).
- **sqe_write** refuses (exit 1) a write whose target doesn't fit the mode
  (a partition: MODE_JAMOS; `PART_TABLE`: MODE_BLANK) before it looks at
  the blocks, then one outside its target; every Write has FUA. `allowed()`
  in sqe_put lets Write and Flush onto the I/O queue only while the mode
  isn't MODE_OTHER, a second check of the same gate. `sqe_flush` refuses a
  MODE_OTHER drive. The protocol refuses first, so these are never reached
  by a well-behaved path: `open_partition(i, 0)` is ERR_ACCESS_DENIED on
  any drive that isn't MODE_JAMOS before the index is looked at (and
  `blk_open` checks the mode again); `block.write` on a read-only channel
  is ERR_ACCESS_DENIED before anything (it was ERR_NOT_SUPPORTED in stage
  1: utest's nvme_block now expects ERR_ACCESS_DENIED); `create_table` is
  ERR_ACCESS_DENIED unless MODE_BLANK, before its GUIDs are looked at.
- **tools/checknvme.py, stage 2** (the owner's replacement for R1/R2): its
  rule 5 fails the build unless OPC_WRITE is named only in sqe_write and
  allowed() and handed to sqe_put once; sqe_write checks `gate.mode ==
  MODE_JAMOS` and refuses before `in_gate` and its refusal, before it
  builds; the Write carries RW_FUA; sqe_flush refuses MODE_OTHER first;
  the gate is assigned in cmd_arm alone, which starts from MODE_OTHER,
  returns on `c->ro`, and sets MODE_JAMOS / MODE_BLANK only after
  `pt_kind`'s PT_KIND_JAMOS / PT_KIND_BLANK; the gate and the write
  opcodes are named in no other file. Rule 2's "write" and "flush" names
  are a closed list. Its self-test feeds it a clean stage-2 driver and 12
  bad ones (the range checked before the mode, no mode check, a mode looked
  at but not refused, a second function building a Write, the gate set
  elsewhere, cmd_arm without `ro`, a mode set by hand, allowed() without
  the mode, no FUA, an ungated Flush, a wrong opcode, and another file
  naming a raw write, the opcode, the gate or a second sqe_flush), and the
  stage-1 rules a stage-2 driver: each must fail.
- **create_table** is drivers/nvme/table.c's (the table code moved out of
  serve.c, which passed 800 lines): the library makes the bytes
  (`pt_jamos_make`, drivers/lib/parttable_make.c, checked on the Mac by
  tools/gptmake.c in gptcheck: read back as Jam OS's, blank-in-progress
  after each write but the first, the same partitions as tools/mkgpt.py's
  jamos layout), into a 64 KiB buffer of the driver's, pinned writable once;
  one write at a time, each after the last one's answer, in the plan's
  order. The read-back happens from the loop (`table_work`), not inside a
  completion (pt_read waits, and a wait inside a completion would reap the
  queue it is reaping); it is a bounded wait on the loop's own drive, as
  the start's is. The answer is OK only when the read-back is Jam OS's;
  ERR_BAD_STATE while one runs; ERR_NO_SPACE under about 580 MiB (64 MiB of
  data at least); ERR_INVALID_ARGS for GUIDs all zeros or the same. A
  closed channel's create_table runs to its end, unanswered. The RESULTS
  box gets a line either way.
- **Writes after a reset** are failed with ERR_IO, not sent again (the
  plan: reads only): the client sees the failure and writes again.
  `block.sync` on a writable channel sends a Flush when the drive has a
  volatile write cache (VWC), else answers at once.
- **`diskro`**: the word goes kernel to init to devmgr to every drv/nvme
  as `ro` (kernel/main.c, kernel/include/jam/userboot.h's

## NV-warn notes

The owner's decision (2026-10-14): `disk prepare` works on any drive he
picks; "leave it to the user, they're the ones choosing what drive to
install it on, just warn using the empty rules", with "warn, then a strong
confirm". What was built (track NV-warn), the choices it made, and what
the next review should look at:
- **The empty rules** (the library's blank rule, `pt_read`): block 0, the
  first and last 64 KiB, and now also the first MiB at 1 MiB and at
  513 MiB (`PT_BLANK_SPOT_ESP`, `PT_BLANK_SPOT_DATA`: where pt_jamos_plan
  starts the ESP and the data partition on every disk, gptmake checks it
  at both block sizes), all zeros. This is R3's design question 1 (a
  drive whose table was wiped and its filesystem left is not empty), with
  R3's "first MiB" at each start. Blank-in-progress needs the spots zero
  as well (create_table writes nothing there). The spots are read last in
  each test, so a disk the other rules reject costs nothing more;
  gptcheck has 7 new cases (a byte in each spot, at both block sizes,
  just before the first and just past the second, a cut prepare with one).
- **The rules decide the confirmation, not whether.** `voldisks`'
  new `prepare_check(id) -> (plan, refused)` (volumes' `plan_of`, which
  asks the driver the new `storage.mode`: MODE_OTHER / BLANK / JAMOS, the
  `ro` word, and whether its table was read whole) tells the shell what it
  would do before the owner is asked anything: PLAN_TABLE (empty: today's
  confirmation, unchanged), PLAN_FINISH (a Jam OS disk a prepare was cut
  short on, unchanged), PLAN_ERASE (anything else), or a refusal.
- **Refused, as before or newly said before anything is typed**: the disk
  Jam OS booted from (DISK_BOOT, or one that was and whose driver is
  restarting); not NVMe; not 512-byte blocks; `diskro`; a Jam OS disk with
  both partitions mounted ("a Jam OS disk already"); a drive under about
  580 MiB; a volume on it mounted read-write; a drive whose table its
  driver couldn't read (a read failed: never erased). **Decided here**: a
  drive whose volumes are mounted read-only is not refused. Every FAT
  volume on a drive that isn't Jam OS's is mounted read-only by volumes on
  its own, and nothing unmounts one (there is no `umount`), so refusing
  any mounted volume would refuse every such drive, Windows' among them.
  Instead the warning lists each mount ("mounted read-only at /nvme0
  (unmounted first)"), and the erase drops those services
  (`drop_services`: read-only, nothing to write back) before the table is
  written; if create_table then fails, the disk is read again and mounted
  as it now is. A volume mounted read-write (only a Jam OS disk's can be)
  is refused.
- **The strong confirmation** (the shell): the drive's model, serial and
  size; "It is NOT empty"; what is on it (its MBR or GPT and each
  partition's type, size and GPT name; a FAT volume's label and mount,
  from `fs_statfs`; "no FAT volume: data Jam OS doesn't read" for a FAT- or
  basic-data-typed partition fat found nothing on; "no partition table, but
  data Jam OS doesn't recognise" when there is no table); "EVERYTHING ON
  nvme1 WILL BE LOST"; then the serial's last four characters (as for an
  empty drive) and then exactly `erase` (lower case). Anything else, Enter
  alone, Ctrl+C or two minutes' silence stops, and nothing is written.
- **Where the answers come from** (today's guarantees kept, and two
  added): both are read from the shell's console's keys (`sh_poll_key`),
  never from stdin, a pipe or the command line; **keys already waiting
  when a question is shown are dropped** (typed ahead, or pasted with the
  command: they can't answer a question they were typed before); and a
  shell running one command line for SSH (`cmd=`: `ssh pc 'disk prepare
  nvme1'`, whose keys may be the remote side's pipe) refuses an erase.
  The shell has no script files; `runlines` only says a program's start
  and end.
- **The IPC path needs the same proof.** `initctl.prepare_disk(id, tail,
  word)` and `volinstall.prepare(id, tail, word)` carry the typed answers;
  volumes checks them against the serial its driver gave (`confirmed`)
  before it unmounts or asks anything, and passes them to
  `storage.create_table(..., tail, word)`, where the driver checks them a
  third time against its own Identify serial (`erase_ok`, table.c). For an
  empty drive they aren't looked at (W1's and W3's tests call
  create_table with none).
- **In the driver** a confirmed erase arms a new mode, **MODE_ERASE**,
  through cmd_arm (`erase && kind == PT_KIND_OTHER`, a table read without
  error, no `ro`, a plan that fits) for that create_table alone: the
  table's blocks as for a blank drive, plus the first MiB at each spot,
  never a partition. create_table then writes zeros over both spots first
  (16 writes of 64 KiB from the second half of its buffer, now 128 KiB),
  then the table in the plan's order. The read-back arms the gate from the
  drive again: MODE_JAMOS once it worked; a cut erase leaves a drive that
  is someone else's, which the next `disk prepare` shows and asks about
  again (also when the cut left Jam OS's backup table, which volumes' mark
  reads as Jam OS's: R3 stage 3's S2). The zeros are why fat formats: a Windows ESP (FAT, at 1 MiB on
  most drives) would otherwise be mounted as the new ESP. tools/checknvme.py's

  self-test offences (an erased drive's partitions writable, MODE_ERASE

- **Not changed**: a Jam OS disk can't be erased by `disk prepare` (it

- **volinstall** (`abi/idl/volumes.idl`, protocol 75, init's alone) gained
  `open_esp(id)`, `close_esp(id)`, `open_data(id)` and `close_data(id)`
  (the plan listed three; the data partition needs its own close). They
  are `user/services/volumes/install.c`'s `disk_install_hold`, in a task:
  the disk must be Jam OS's by volumes' own check (mark.c) and by its
  driver's (storage.mode asked: R3 stage 3's S3), not the boot disk, not
  `diskro`, with both partitions mounted
  and settled (it waits up to 20 s for a partition just made read-only
  again to answer its first probe). The partition's service stops in order
  and starts again read-write (`fs_restart`), `vol.held` is set and
  `disk_mounts` leaves it out, so it is no mount for anyone while init
  writes it (the same as `volesp` does for the stick's ESP); the reply
  carries a channel to it, init's alone. `close_*` makes it read-only again
  and a mount again. A partition `mount -w` made writable for everyone is
  ERR_BUSY; `volumes.remount` of a held one is ERR_BUSY.
- **initctl.install** (13, `later`, the shell's channel only): `(id, tail,
  word)` as `prepare_disk`'s. `user/services/init/install.c` runs it on a
  thread of its own (a 96 KiB static stack, like update.c's worker; not
  update.c's thread itself, so a check or a stick write could be refused
  with a plain flag: `install_busy()`/`update_busy()` exclude each other
  and `prepare_disk` is refused while an install runs) and answers the
  shell from that thread when done (20 minutes at most).
- **The steps** (each logs `init: install: step n/6 ...`): 1 `volinstall.
  prepare` (ERR_ALREADY_EXISTS = a Jam OS disk: reused, its `/data` kept);
  2 the sources read into VMOs and hashed (the boot disk's
  `/esp/EFI/BOOT/BOOTX64.EFI`, its boot menu `/boot/limine/limine.conf` or
  the spare `/boot/limine.conf`, `/boot/jamos.elf`, `/boot/bootfs.img`: the
  build the stick runs, which is the running build except after an
  `update -m` and a `reboot`); 3 `/data/etc` of the boot disk copied to
  the new `/data/etc.new` (files up to 1 MiB, 256 entries, 4 levels; the
  host key included, as Q7 (A) says), synced, read back against SHA-256,
  renamed to `/etc`, only when the disk has none (a leftover `etc.new` is
  removed first); 4 the ESP: the menu, a menu at Limine's other places
  (`/EFI/BOOT/limine.conf` is read first: R3 stage 3's S11) and an
  update's leftovers removed first (a reinstall), room checked, `/EFI/BOOT`, `/boot`, `/boot/limine`
  made, Limine, `/boot/jamos.elf` and `/boot/bootfs.img` and the same two as
  `prev-*` (so the menu's "previous build" entry boots too), each written
  with FS_GATHER, synced and read back against its SHA-256; 5 the boot menu
  last (espwrite.c's helpers are reused, so the same deadlines: 300 s for
  the ESP, 120 s for `/data`, their log lines say `update: write:`); both
  partitions read-only again at the end, failed or not. A failure answers
  the shell with the error and leaves the disk with no boot menu: the
  firmware lists it and Limine finds nothing to boot, never half a build;
  `install` again finishes it.
- **The boot menu** is copied as it is (it is the one this boot's loader
  read). `bootmenu_check` (update's rules) is only run and logged: the
  tests' one-entry `timeout: 0` menu fails it and must install too. The
  stick's cmdline words ride in the copied menu, so an installed QEMU disk
  boots with the test's words.
- **The shell** (`user/services/shell/cmd/disks.c`, `install <disk>`): the
  same prompts as `disk prepare` (`write_cmd(install)`): the drive's model,
  serial, size; for a drive that isn't empty what is on it and `erase`;
  the serial's last four typed; a Jam OS disk is installed on again (the
  prepare check's REFUSED_JAMOS is accepted for `install` only, so `disk
  prepare` still refuses it, as decided). It ends with `Jam OS <version>
  installed on nvme1: choose "UEFI OS (<model>)" (or the drive's name)
  first in the firmware's boot order (F8 at power-on picks it once), then
  pull the stick out`.
- **The data partition's filesystem** is chosen in one place, volumes':
  `volinstall.prepare` formats both partitions with the service `FAT_PATH`
  (`user/services/volumes/disk.h`) and `fs_format_arg` (`fsvc.c`; prepare.c
  sets `fresh`). The installer (install.c and `disk_install_hold`) names
  no filesystem: it copies through the generic fs calls on the channel
  `open_data` returns, so U7b/U11a switch it by changing that choice in
  volumes (the mark check's GUID types and `mount_others` are the other
  FAT-aware spots there). The ESP stays FAT (the firmware reads it).
- **Not built / decided**: no utest case (nothing a test program holds can
  reach `volinstall` or `initctl.install`: both are init's); the new calls
  are covered by the QEMU runs below. `reboot` during an install is not
  refused (a kexec mid-write leaves a disk without its menu, which a new
  install finishes). The installed build is the stick's files, not a
  separately verified copy of the running kernel.
- **Tests** (PC, QEMU 10.0.2, tools/pc-batch.sh; scripts the track did not
  commit): a smoke run on a stick boot with a blank 1 GiB NVMe image:
  `install` with a wrong serial end (stops, nothing written), then the
  right one (`installed on nvme0`, 1.1 s), `install` again (a Jam OS
  disk, `/etc` kept, 0.9 s), `disk prepare` still says "a Jam OS disk
  already"; on the host (mtools) the ESP's `jamos.elf`, `bootfs.img` and
  their `prev-*` copies have the build's SHA-256, `limine/limine.conf` and
  `BOOTX64.EFI` are there, `/etc` has the files, the subdirectory and the
  empty file; then a second boot of that image alone (`QEMU_BOOT_NVME=1`,
  no stick) names the drive's GPT GUID as the boot disk, mounts `/esp` and
  `/data`, and `/data/etc/probe.txt` reads back. A drive with a Windows-like
  table (`tools/nvme-img.py windows`): `install` shows "It is NOT empty",
  the serial end and `erase` typed, installed, the old table gone. Also:
  `tools/init-test.sh` (all three parts), ktest at 4 CPUs, shell scripts
  basic, cmds, commands, files, `tools/kdump-test.sh save`,
  `tools/update-write-test.sh` (wfail first; the whole script), and
  `tools/nvme-test.sh` prepare, erase and erasestop (the shell's
  `disk prepare` was reshaped): all PASS.
- **For I3**: install on a blank NVMe (`QEMU_NVME=<image>` made by `python3
  tools/mkgpt.py <img> --layout blank --size 1G`; its serial is
  `jamos-nvme0`, so the typed answer is `vme0`); the shell lines to wait
  for are `Type the last 4 characters`, `installed on nvme<N>` (the disk
  number: `seen re:nvme(?P<n>[0-9]+) +QEMU NVMe Ctrl +serial jamos-nvme0 `
  after `disks`, as nvme-test.sh's `s3_names` does) and `a Jam OS disk
  already` for the second run; then boot the image alone with
  `QEMU_BOOT_NVME=1 QEMU_IMAGE=<img>` (the installed image is already
  GPT: booted as it is). The log has numbered progress lines for the cut
  cases: `init: install: step 1/6` (prepare) through `6/6` (done), plus
  `the ESP is writable`, one `... KiB written ... synced` line per file
  (`update: write:` prefix) and `step 5/6: the boot menu, last`: kill QEMU
  after the wanted line (the sync after each file is the next one; there is
  no stop-after-change hook like `update`'s UPDATE_OFFER_STOP, add one in
  install.c if exact points are wanted). After a cut the disk has no menu
  (mtools: `::/boot/limine/limine.conf` missing), and `install` again
  prints `the disk is a Jam OS disk already` and finishes. `/data/etc` in
  the stick image must hold a file (the stick has `settings` and `history`
  once booted). The stick-and-NVMe `both` case: the installed drive's
  `/esp` and `/data` become `/nvmeN` read-only on a stick boot (I1).
- **Open for the hardware night**: the firmware's name for the entry

## I3 notes

Built in QEMU before P3 (the installer's tests; hardware untouched). Run on
the PC with `tools/pc-batch.sh`, one shard for each case.
- **`tools/install-test.sh <outdir> [case...]`** ([TESTING.md](TESTING.md)
  has the row): cases `install`, `again`, `cut`, `both` as the I3 row above
  says, and `erase` (a Windows-like drive: `install` asks for its erase
  after the serial's end, `no` stops with nothing written and no install
  started, `erase` goes on; the boot disk is refused). Each case makes its
  own stick (the image with a file, one in a subdirectory and an empty one
  in `/data/etc`, a file on `/data`'s root only the stick has) and drive
  (`tools/mkgpt.py --layout blank --size 1G`, QEMU's serial `jamos-nvme0`:
  `vme0` typed), installs from a stick boot and checks the drive on the
  host with mtools, `tools/fatcheck.py` and `tools/nvme-written.py`. The
  cold boot of the installed drive is `QEMU_BOOT_NVME=1` with the new
  `QEMU_MENU_AT=keep`, so Limine reads the menu `install` wrote (the stick
  run's one-entry test menu, with that run's cmdline words), not a test's;
  the kernel's `loader:` command line is compared with the stick run's.
- **The cut hook** (the one edit in init for the tests,
  `user/services/init/install.c`'s `cut_after`): the boot word
  `nvmetest=` already reaches init as a comma-separated list that only
  drv/nvme read, and drv/nvme ignores words it doesn't know, so the hook is
  a word in that list, `instcut<point>`; no kernel or `main.c` change (the
  kernel sanitises `nvmetest=`: lower-case letters and commas only, under 48
  characters). Points: `prepared`, `etcnew`, `etc`, `cleared`, `limine`,
  `kernel`, `prevkernel`, `bootfs`, `prevbootfs`, `menu` (each right after
  that change was synced; the worker then sleeps for good and logs
  `init: install: cut after <point>, as the test asked`, and the test ends
  QEMU with `monitor quit` on that line). A point that is not reached (the
  etc ones on a drive that has a /etc) never stops. A kill on a log line was
  tried first for the plan and dropped: the menu's write follows the line
  before it within milliseconds, so "no menu yet" could not be asserted.
- **What `cut` found**: nothing wrong. After a cut at any point before the
  last the drive has no `/boot/limine/limine.conf` and no spare, the files
  so far are whole and the later ones not there, `/etc.new` is whole or
  `/etc` is renamed as the point says, both FAT volumes pass `fatcheck`
  (a cut leaves them dirty, not damaged), the table is Jam OS's and nothing
  lies outside it; the points are tried in turn on one drive, each install
  over what the one before left (the disk is a Jam OS disk from `prepared`
  on, "a Jam OS disk already"). A drive with Limine and no menu starts
  Limine (the firmware says it started Boot0001) and no kernel; with no
  Limine yet the firmware says it failed to load Boot0001 and falls to its
  shell. Then a stick boot installs over the cut drive, and it cold-boots.
- **The stage-3 power-cut points on NVMe**: `tools/update-write-test.sh`
  (`wstop`) and `tools/update-menu-test.sh` (`stops`) run unchanged with
  `QEMU_BOOT_NVME=1` in their environment (qemu-test.sh makes the stick
  image Jam OS's GPT layout on NVMe; the ESP is at 1M in both layouts, so
  their mtools checks hold). The scripts gained a switch each for it:
  `update-write-test.sh` a `WRITE_RUNS` (like the menu script's
  `MENU_RUNS`; `wstop` alone starts from the stick as `wfail` leaves it),
  `update-menu-test.sh`'s own boots (`boot_entry`, for `cut` and `entries`)
  attach the image as NVMe when `QEMU_BOOT_NVME=1`. Both also stopped
  prompting on a rerun into an output directory that is still there
  (`mcopy -n`; a batch's rerun copies the old directory over first).
- **Decided**: the cut test is one chain on one drive, three shards for the
  points; one `cut` case's boots are about 12 stick boots, so the shards
  split them. `INSTALL_CUTS` in another order than the plan's has no
  meaning (the expectations assume each point sits after the one before).
