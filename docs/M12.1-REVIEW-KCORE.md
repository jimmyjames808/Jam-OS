# M12.1 code check: the kernel core

Part 3b of M12.1's check ([ROADMAP.md](ROADMAP.md), M12.1's row): every
line of the kernel core changed since M8.6 (`git diff 2079f350` at main
ae859bee), read in full context: `kernel/object/` (channels, handles and
`handle_info`, ports, VMOs), `kernel/sched/` (the futex, `thread_yield`,
the direct hand-off), `kernel/mm/`, `kernel/abi/` (every system call's
argument checks), `kernel/arch/` (the FS base, the system call rule for the
FPU, PCID hints), `kernel/proc/`, `kernel/lib/`, `kernel/main.c`, their
headers in `kernel/include/jam/` and `abi/syscalls.def`; about 6,800
lines. Read against M12's intent: [M12-REVIEW-KERNEL.md](M12-REVIEW-KERNEL.md)
and [M12-PLAN.md](M12-PLAN.md)'s answers K-A to K-F, and the format of
[M8.6-CHECK-KCORE.md](history/M8.6-CHECK-KCORE.md). Devices, the IOMMU,
kexec and debug are the kernel-devices reviewer's; what crosses into them
is noted. Findings first; each one's outcome is filled in as it is fixed.

Severity: **High** is a crash, a hole, or a hang or breakage that a
program can cause for others with hostile arguments; **Medium** is wrong
behaviour the system or a test tier will meet; **Low** is a wart, a guide
violation, or a hole only a holder of a power can use on itself.

Before any change, on ae859bee: the full ktest at 4 CPUs on the PC:
418 passed (the RESULTS box's stress line is a test's faked failure, as
always).

## Findings

| # | Sev | Where | What is wrong | Failure scenario | Fix | Outcome |
|---|---|---|---|---|---|---|
| 1 | High | `kernel/object/channel.c:639` (channel_set_flags), `kernel/abi/channel_sys.c:181` | Any holder of a channel end with RIGHT_READ can set `CHANNEL_NO_HANDLES` on it, and the mark is one-way and per end, not per handle. Ends are shared: every program's namespace holds a duplicate (RIGHT_SAME) of init's published service ends (`/svc/wayland`, `/svc/audio`, `/svc/music`, `/svc/serve`, ...) and of the mounts that have no view. `svc.connect` answers with a handle (`connect () -> (handle channel)`), and so do a mount's `open`s. | A hostile program calls `jam_channel_set_flags(<its /svc/wayland handle>, CHANNEL_NO_HANDLES)`. From then on, for the rest of the boot, every reply carrying a handle to that shared end is refused (ERR_NOT_SUPPORTED at the compositor's reply, the caller's call times out): no program can open a window again; the same for sound, music, serve, and file opens on a shared mount. One call, no power needed. | Only the end's sole holder may mark it: ERR_BAD_STATE while the end has more than one handle (a duplicate anywhere, or one in transit). Every setter today (init's `kept_end_mark`, volumes' fs, control, watch and ESP ends) marks an end it made a moment ago and holds alone. | see below |
| 2 | Medium (design) | `kernel/object/channel.c:313-376` (charge_reader), M12's Q2 / K-A | Once a writer closes, everything it left queued is charged to the reader's job, whoever wrote it and however much: up to `CHANNEL_MAX_QUEUED` messages of up to 64 KiB each per end (64 MiB), bounded only by the writer's own limit while it wrote. Before Q2 a client's unread messages stayed the client's. | A client connects to a server (svc.connect: the server holds the new end alone, so it is that end's reader), writes up to its own message limit, closes, and repeats on new connections: each close moves its whole backlog onto the server's job, freeing the client's quota for the next round. The server's job reaches its `JOB_LIMIT_MSG_BYTES` (the excess is dropped, as Q2 says), and from then until it has read the backlog every message the server writes to any client (its replies, events) fails with ERR_NO_RESOURCES. A server that reads promptly recovers; one that reads a connection only when it handles it (the compositor's per-client ordering) stays stuck. | Design question for the owner, not decided here (Q2 was the owner's answer). Options: (a) move to the reader only what was written after the reader received the end (a sequence mark at channel_received), the rest dropped at the close; (b) cap what one close may move (e.g. the queue's first N KiB), the rest dropped; (c) as now. | Reported (design) |
| 3 | Low | `kernel/arch/x86_64/uentry.c:109-118` (thread_set_fs_base, fs_load) | `thread_set_fs_base(base)` skips the MSR write when `base` equals the CPU's last loaded value and the caller is the thread that last ran there. But user code can change the CPU's FS base itself by loading a selector into FS (every descriptor's base is 0): the skip assumes "whatever it did to FS since is its own doing", which holds for a switch, not for the call that exists to set the base again. `abi/syscalls.def` promises "undefined until it calls this again". | A thread (musl's `__set_thread_area` path, or code that saved and restored FS) loads `%fs` with the user data selector, then calls `thread_set_fs_base(X)` with the value it had: the call returns OK, the base stays 0, and the thread's next TLS access (`%fs:0`) reads address 0 and the process is killed. Only the thread itself is hurt. | thread_set_fs_base always writes the MSR (it is no hot path); the switch keeps the skip. | see below |
| 4 | Low | `kernel/abi/vmo_sys.c:139-163` (sys_vmo_make_exec) | The new executable handle is inserted into the caller's table before the "one handle, no mapping" check and the seal. A sibling thread can duplicate it (its value is predictable: the FIFO free list) in that window; the check then fails (another handle exists), the call closes its handle and returns ERR_BAD_STATE, but the duplicate keeps RIGHT_EXEC on a VMO that was never sealed, while the caller still holds a writable handle to it. | A holder of RIGHT_ROOT_VMEX (init and the shell only) gets a mapping of code it can still change: W^X undone for a VMO of its own. No gain of authority (the power already makes any VMO executable), so Low. | Check and seal while the VMO's one handle is out of the table (the khandle handle_remove gave), then insert the sealed handle; a duplicate made after that is of a sealed VMO. | see below |
| 5 | Low | `kernel/object/channel.c:669-689` (channel_get_info), `kernel/object/handle.c:398` (handle_info) | `handle_info` on a channel end walks the peer's whole queue (up to 1024 messages) with the pair lock and the peer's lock held and interrupts off, to sum `peer_queued_bytes`; no right is needed and the compositor calls it per flush (W-DQ3's flow control). | Many threads of a program spin on `handle_info` of an end whose peer holds 1024 small messages: each call is about 1024 list steps with interrupts off on its CPU, and the pair lock is contended against the end's real writers and readers. A latency wart, not a hang. | Keep the queued bytes as a counter beside `nqueued` (updated where nqueued is). Not fixed here: no failure, and channel.c's counters are K1's design. | Reported |
| 6 | Low (design, cross-boundary) | `kernel/abi/sysc_hw.c:343-352` (pin), `kernel/object/vmo.c` (vmo_pin_flags) | A read-only pin through an IOMMU domain needs only RIGHT_READ on the VMO (Q13), but a pin also commits the pages (charged to the VMO's job, not the pinner's) and stops the VMO's owner from decommitting or shrinking over them (ERR_BAD_STATE). Before M12 both needed RIGHT_WRITE, which already allowed commit. | A driver handed a read-only view of a client's buffer (a sound stream) pins all of it: the client's job pays for every page of a sparse VMO, and the client can no longer shrink its own buffer until the driver unpins. Needs a bound dma_cap (a driver). | For the owner / the devices reviewer: a read-only pin of uncommitted pages could be refused (ERR_BAD_STATE) instead of committing them, or need RIGHT_WRITE to commit. | Reported |
| 7 | Low (design) | `kernel/object/channel.c:290-307` (channel_received), K-A's refinement | The reader is the job of the last table that received the end as its *only* handle. The common pattern "keep a duplicate, send one, then close mine" leaves the reader with the sender's job: the receiver never becomes the reader, and the end holds a reference on the sender's job for as long as the end lives. | A spawner duplicates an end, hands the copy to a child, closes its own: when the writer later closes, the child's backlog is charged to the spawner's job (kept alive by the reference) instead of the child's. Accounting goes to the wrong job; nothing leaks. | Design note: the reader could also move when the end's handle count drops back to 1 (the remaining handle's table), which needs the handle table to report closes of channel ends. | Reported |
| 8 | Low | `kernel/sched/futex.c:151-166` (wake_locked), `:199-209` (requeue) | Waiters of every process share 256 buckets, and a wake or requeue walks its bucket's whole list with interrupts off. A process can park its whole thread limit on addresses that hash to one bucket (it knows the hash and its own address space pointer is fixed). | Another process whose futex hashes there pays O(threads) per wake with interrupts off. Linux has the same property; bounded by the job's thread limit. | Note (a per-address-space salt in the hash would make the bucket unpredictable). | Reported |

Not findings (checked and correct):
- Channels (K1): the per-pair txid counter (bit 31, never 0, both ends
  drawing from one counter); handles consumed on every outcome in
  `channel_sys.c` (`take_all` with a refused value, a value twice, the
  channel's own end; `finish_taken`'s commit-then-release; `close_list`
  only for lists the kernel could read); the reserved receive slots
  (`handle_untake` of a reserved slot can't fail: a user close or take
  never matches an in-transit slot, and the table outlives the call);
  D5's dropped late replies (the gave-up ring under the caller end's lock,
  forgotten once used, only for bit-31 txids); the slot exchange (a slot
  is taken only from a listed waiter under its end's lock, published last
  with release, read with acquire); `charge_reader`'s rounds (progress,
  the job references dropped unlocked, a dropped tail freed unlocked) and
  its races with readers and the peer's own close; the mark against a
  queue that already holds handles; the "only handle" rule of
  `channel_received` under concurrent inserts.
- Handles and ports (K3): `handle_replace`'s refused path (slot, charge and
  release as `handle_remove`'s); `handle_info` (no padding in the struct,
  no right needed, the object referenced while read); bindings ending with
  the object's last handle (`port_object_closed` takes port and binding
  references under the object's lock, a port that is dying detaches its
  own; `port_bind_held` checks the count under the same lock, so a bind
  either precedes the scan or is refused; a fired ONCE binding is retired
  by its dequeue, as before); every `khandle_release` runs with no lock
  held, so the new scan's "port bindings" -> object order holds.
- Threads (K4): the entry and FS base checks in `start_thread` (before
  anything changes); the FS base across switches and migration (`fs_load`'s
  skip is sound for switches: user code can only make the base 0, and
  thread ids are never reused); the futex (queued before the word is read
  with a full fence, the waker's bucket lock as the other fence; a waiter
  never returns while a waker touches it; cancel, deadline and requeue
  each re-find the bucket under its lock; a wake during a page fault in
  the read is kept by `woken`); `thread_yield`.
- The system call rule for the FPU: `in_syscall` is set and cleared with
  interrupts off; the saved area is a clean XSAVE state (or zeroed FXSAVE
  area) with the thread's MXCSR and control word, so nothing of another
  thread's is ever restored; XSAVEOPT never runs on a modified area
  without an XRSTOR in between (`fpu_cpu` is reset); the two inline
  `syscall`s in utest list the vector registers.
- The direct hand-off: the wakee is READY on no queue only on the waker's
  CPU, which alone touches the slot with interrupts off; a waker that is
  preempted, migrates, runs out of slice or never blocks queues it
  (`take_handoff`, `sched_handoff_done`); a kill or second wake of the
  wakee finds it READY and does nothing.
- Kept VMOs and `VMAR_KEPT_ONLY`: decommit and shrink refused for every
  holder, growth committed past the size before it shows, the mapping's
  entries filled under the region lock and never zapped (protect refuses
  any change), a failed fill taken back whole.
- Arguments: every new system call's lengths, flags, reserved words,
  pointers and handle lists (`read_list` first, then `refuse` closes),
  names (`PROCESS_NAME_MAX` + 1 buffers), `random_get`'s bound and
  zeroing, `debug_command`'s and `klog_name`'s and `kexec_load`'s lengths.
