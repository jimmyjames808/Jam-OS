# M13.6 plan: a Unix filesystem

Status (2026-10-14): U1 (the format's read side) built: [U1
notes](#u1-notes); U2b: [U2b notes](#u2b-notes); U5 (the protocols):
[U5 notes](#u5-notes); the rest a plan. Written against main fcc39f93
(M13's B1-B5, S1, K1, K2 merged; M12.5's PK1, PK2, PK4 merged, PK3 and PU
running; M12.7's stage 1 merged, W1 running in QEMU). **Waiting for the
owner's answers to the questions below.** The format tracks (U1 to U3)
touch only new files and can start as soon as Q1 is answered. M13.7 (the
ports system) is planned beside it, in docs/M13.7-PLAN.md; what it can
count on from this milestone, and when, is [below](#what-m137-can-assume).

Goal ([roadmap](ROADMAP.md#now), "porting first", the owner, 2026-10-11):
**a filesystem that ported software can live on.** FAT32 has no symbolic
links, no permission bits, no owners, no hard links, a 4 GiB file limit and
names that ignore case, and Unix software breaks on each: package layouts
(`libfoo.so -> libfoo.so.1`), build systems (`ln -s`, `install -m 755`,
`test -x`), archives that carry links and modes, `Makefile` beside
`makefile`, files over 4 GiB, a rename that replaces atomically, a file
unlinked while it is open. The decision of 2026-09-30 (FAT32 only; ext2,
littlefs and an own copy-on-write filesystem declined:
[HISTORY's decisions](HISTORY.md#decisions)) is reopened for this, and only for this
([Not planned](ROADMAP.md#not-planned)).

**Done when** (made concrete):
1. **In QEMU**, on a volume Jam OS formatted: posixtest's new `links`
   section passes (symlink, readlink, lstat, link, chmod and fchmod,
   chown to the one user, real `st_mode`, `st_ino` unchanged by a rename,
   `st_nlink`, rename replacing atomically, `O_EXCL` against a dangling
   link, `O_NOFOLLOW`, fsync, unlink of an open file, `Makefile` and
   `makefile` side by side); a 6 GiB file is written and read back with
   its SHA-256 the host's; a sparse file with a block at 5 GiB reads zeros
   before it.
2. **Cut tests**: QEMU killed (`kill -9`) at 20 points of a storm of
   writes, renames, links and unlinks: after the next boot every file
   synced before the cut is whole, and the image passes Linux's `e2fsck
   -fn` (on the test PC's WSL) both after Jam OS's own recovery and after
   Linux's recovery of the image as the cut left it.
3. **The service outlives its process**, as fat does: `storm` copying
   onto the new filesystem while its service is killed 10 and 100 times a
   second, the copy matching and no client seeing an error.
4. **Linux reads it**: a volume Jam OS made passes `e2fsck -fn`, and
   Linux's tools list the same files with the same bytes, modes and link
   targets; a volume made by Linux's `mke2fs` with Jam OS's feature list
   is read and written by Jam OS.
5. **A port that needs it works**: one of M13.7's first ports whose
   install makes symbolic links and executable files installs and runs
   from the new filesystem.
6. **On the PC**: the Jam OS drive's data partition (M12.7 stage 2) holds
   the new filesystem at `/jam`; the power button held during a write
   storm loses no synced file.
7. As every milestone: an independent review-and-fix, then All tests and
   `soak 10` on the PC with the new filesystem mounted
   ([TESTING.md](TESTING.md#the-tiers)).

## What M13.6 is not

- **FAT32 stays.** The stick's ESP and `/data`, every ESP (UEFI reads
  only FAT), `make flash`, the Mac's Finder copies onto the stick, logd's
  logs, `/data/etc` and `update`'s power-cut-safe writes are untouched.
  The new filesystem is added beside FAT, not instead of it.
- **No users.** One user, `jam`, uid and gid 1000 (M13's Q7); owners are
  stored, but every file Jam OS makes belongs to 1000 and `chown` to anyone
  else is `EPERM`, as for an ordinary user on Unix. No ACLs, no quotas.
- **Permission bits are not authority.** Handles and namespaces stay the
  only authority ([ARCHITECTURE.md](../ARCHITECTURE.md#goals)). The bits
  are what ported programs expect to see and set (Q4); any program with a
  writable view of a file can `chmod` it back.
- **No extended attributes, no FIFOs, sockets or device nodes on disk**:
  `mknod` and `mkfifo` stay `EPERM`; extended attributes found on a
  volume Linux wrote are kept and never read or written (freed with their
  file).
- **No indexed directories written**: a directory is a list of blocks
  (fine to tens of thousands of entries); an index is a later addition.
- **No fsck that repairs** (Q10): the journal's replay at mount, a
  checksum on every metadata block, read-only on an error, and a
  read-only checker. Repairs are Linux's `e2fsck`.
- **No writable shared mappings** (M12.5's Q1 stands); the new filesystem
  is a pager for read and exec mappings like fat (track U10).
  **Superseded for ext** (the owner, 2026-10-16): writable shared
  mappings come on ext only, planned in
  [HISTORY](HISTORY.md#writable-file-mappings-on-ext); FAT keeps M12.5's answer.
- **No installer, no booting from it** (M12.7 stage 3 is deferred); no
  TRIM, no online resize, no encryption, compression or case folding.
- **No read-only package images** (erofs or squashfs): weighed below as
  an option; M13.7 may add them later on top of this.

### A. Own code, ext4's on-disk format

Write Jam OS's own implementation of a subset of the ext4 format: the
layout Linux, e2fsprogs and every rescue system know, with code written
for Jam OS's restart model. Nothing is copied from Linux or e2fsprogs
(GPL and LGPL). The format is documented independently of the code, and
BSD-licensed implementations exist to read beside the documents: FreeBSD's
sys/fs/ext2fs (13,684 lines: BSD-2-Clause, BSD-3-Clause, MIT-CMU, and the
RSA-MD notice on its MD4-derived directory hash; reads and writes ext4
with extents and checksums, no journal) and lwext4's BSD-3 files (its
journal code included). Code taken from either goes into third_party with
its licence, as FatFs did; written fresh is the default.

**The subset** (what Jam OS's `mkfs` sets, and what it accepts on a volume
someone else made):

| Feature | Jam OS | Someone else's volume with it |
|---|---|---|
| `filetype`, `extents`, `flex_bg`, `64bit`, `sparse_super`, `large_file`, `huge_file`, `dir_nlink`, `extra_isize`, `metadata_csum` (CRC32C on every metadata block), `has_journal` (jbd2, checksum v3) | made and maintained | read and written |
| `ext_attr` | not made | read and written; attribute blocks kept, freed with their inode |
| `dir_index` (hashed directories) | not made | read (an indexed directory reads as a plain one: its index blocks look like empty entries to a reader that doesn't know them; with `metadata_csum` they carry the index's checksum tail, not an entry block's, so U1 tells them apart by the inode's index flag); a write to one rewrites its index blocks as empty plain blocks and clears the flag (`e2fsck -D` can index it again) |
| `resize_inode` | not made | left alone (its blocks are allocated) |
| anything else incompatible (`inline_data`, `encrypt`, `casefold`, `meta_bg`, `mmp`, `bigalloc`, `ea_inode`, `orphan_file`, `largedir`, `journal_dev`, unknown bits) | | not mounted |
| anything else read-only compatible (`quota`, `project`, `verity`, unknown bits) | | mounted read-only |

**For it:**
- **An independent checker on every test.** Linux's `e2fsck -fn` reads
  every image a cut test leaves, and Linux's own journal replay recovers
  it as a second opinion: code we didn't write judges code we did. The
  test PC's WSL2 has e2fsprogs; nothing new to install.
- **Rescue and inspection**: a Linux live stick, or WSL on the PC (`wsl
  --mount --bare`, then `e2fsck -fn` or a read-only mount), reads the Jam
  OS drive. On the Mac, Homebrew's e2fsprogs (`debugfs`, `mke2fs`,
  `e2fsck`) works on image files and on a raw device (*unsure*: to be
  checked on the owner's Mac; macOS has no ext driver of its own).
- **Linux's USB sticks** become readable in Jam OS as a side effect (Q9).
- The format is proven at every size the PC has: 4 KiB blocks, 64-bit
  block numbers, files to 16 TiB, nanosecond times to 2446, 255-byte
  names, extents that make a 6 GiB file a few metadata blocks.

**Against it:**
- **The format's weight.** Group descriptors of two sizes, flex groups,
  CRC32C seeds per structure (superblock, descriptors, bitmaps, inodes,
  extent blocks, directory leaves' tails, the journal), the journal's own
  checksums, extra inode fields: about 2,000 lines more than B, and every
  field a chance to disagree with Linux. The checker on every test is what
  makes that safe to write.
- **Linux may change a volume** if the owner mounts it read-write there
  (a new feature bit, an orphan file): Jam OS then mounts it read-only or
  not at all, by the table above; it never writes what it doesn't know.

### B. Own simple format

The same service and the same restart model on a format of our own:
inodes in fixed tables, extents in the inode spilling into one tree level,
directories as lists of blocks, a write-ahead journal of metadata blocks.
About 2,000 lines smaller than A, and every choice ours.

What it costs against A: nothing outside Jam OS reads it (a host tool
built from the same core is the only way in from the Mac or Linux), and
the only checker is our own, built from the same core: a bug in the core
can be a bug in the checker, so the cut tests prove less. A format of our
own also has to earn the trust ext4 has from twenty years of power cuts.

### C. lwext4

lwext4 (github.com/gkostka/lwext4, last commit 2022-09, 28 open issues)
is a portable C ext2/3/4 library for microcontrollers, the obvious port.
Its licence is **not** simply BSD: the repository's LICENSE is the GPL-2.0
text with a note that "some files ... contain a different license
statement"; 45 of its 47 C files and headers carry BSD-3-Clause, but **`src/ext4_extent.c`
(2,140 lines) and `src/ext4_xattr.c` (1,564 lines) are GPL-2.0-or-later.**

- **With the GPL files** (full ext4): the service binary linking them is a
  combined work under GPL-2.0+: every image Jam OS ships must carry or
  offer the complete source of that program (its libos parts included,
  which BSD allows), the repository holds GPL code against
  `CONTRIBUTING.md`'s rule and the 2026-09-30 decision ("no GPL code may be
  copied"), and anyone reusing Jam OS under BSD terms must strip it. A
  separate process keeps the GPL out of the kernel and the other services
  (mere aggregation), but the rule is the project's, not only the law's.
  **Excluded.**
- **Without them** (`CONFIG_EXTENTS_ENABLE 0`, `CONFIG_XATTR_ENABLE 0`):
  ext2/ext3 with indirect blocks (a 6 GiB file needs about 6 MiB of
  indirect blocks, each journaled as it changes), 19,333 lines vendored.
- **Quality**: unmaintained for three years; open issues include journal
  replay failures (86), large-file write failures (67), over-allocation in
  its mkfs (72), heap leaks (68) and several out-of-bounds reads and
  overflows on crafted images (89-93, 100-101). Jam OS would own fixing
  them in code it didn't write, and a crafted stick reaches that parser.
- **Restarts**: lwext4 keeps its state in its own heap (block cache trees,
  mount structures, transactions). fat's way (the library's memory at a
  fixed address in the state VMO, an undo copy of what a request changes)
  doesn't extend to a heap that changes anywhere; the other way (the disk
  as the state, below) needs a transaction per request and a replay that
  works, which is issue 86.

### D. FAT32 with emulation

Keep FAT32 and store what it lacks beside it: symbolic links as small
files with a marker and the system attribute (Cygwin's way), modes and
owners in a hidden file per directory (Linux's UMSDOS did exactly this,
1994-2004). About 2,500 lines in fat and libc, and the Mac still reads the
files.

What still breaks: **names ignore case** (`Makefile` and `makefile`
collide; a source tree with both can't be unpacked); **4 GiB files**;
**hard links** (UMSDOS faked them with hidden files; tools that count
links or detect them by `st_ino` are confused); **`st_ino` changes on a
rename** (fat's id is the directory entry's place); **rename can't
replace atomically** (FAT has no such operation: an unlink and a rename,
with a moment when the name holds nothing); **unlink of an open file**
stays `EBUSY`; names with `: * ? " < > | \`, trailing dots or spaces
can't exist; and **the sidecar can disagree with its directory**
after a cut or after the Mac or Windows edits the stick (they don't know
it), with no fsck to reconcile them. It is a stopgap that leaves most of
the goal undone.

### E. Read-only images for installed ports

Ports built on the Mac are packed into an image (`mkfs.erofs` or
`mksquashfs` on the Mac: GPL tools there cost the system nothing) and
served read-only in Jam OS by a small reader: erofs's liberofs is dual
GPL-2.0+ OR MIT (taken as MIT), about 1,700 lines for uncompressed images;
squashfuse is BSD-2, 2,687 lines. Links, modes, hard links, case and big
files are all in the image. No state, so it restarts like bootfs; an
uncompressed erofs image's 4 KiB blocks are pages, so it is the best
pager of all; and an image's page hashes could be approved once, as PK4's
tables are. A real fit **for installed packages** (Fuchsia's packages,
Android's system image and macOS's sealed system volume work this way).

It is **not** a filesystem ported software can live on: a program's
configuration, `$HOME`'s dotfiles, `/tmp`, a build tree, a port's install step,
`tar x`, `ln -s` at run time all need a writable Unix filesystem, and with
E those still land on FAT. So E is an addition M13.7 can choose later on
top of A or B, not instead of them.

### F. NetBSD's FFS through a rump kernel

A rump kernel runs NetBSD's own kernel code (VFS, FFS, WAPBL's journal)
unmodified in a user process over a small host layer (threads, locks,
memory, block I/O). Mature crash safety and all of Unix's features, under
BSD licences. But it brings a whole NetBSD kernel's worth of code into one
service (far beyond anything else Jam OS vendors), its state is that
kernel's heap (restart is a remount, with a journal replay that only
covers what WAPBL committed, and per-request durability would mean an
fsync per request through a VFS built for caching), Linux writes UFS only
experimentally, and macOS not at all.

### The recommendation: A

A gives Jam OS everything on the goal's list with code that is ours (BSD,
built around the restart model from the first line), a format other
systems read, and an independent checker for every crash test. B is
smaller and simpler but proves less; C's licence and state rule it out;
D leaves most of the goal undone; E is a later addition for packages; F
is far too big. **Q1** asks.

## The design

The rest of the plan assumes A. Names: the format library is **ext**
(no Jam OS calls: built into the service and, unchanged, into the host
tools and tests), the service **extfs** (one per volume, as fat).

### The disk is the state

fat outlives its process by keeping FatFs's memory in the state VMO and
an undo copy of what each request changes, with the request's disk writes
held until it commits ([Services that outlive their
process](../ARCHITECTURE.md#services-that-outlive-their-process)). extfs
does it the other way round: **every request is one journal transaction,
committed on the disk before its answer, so the disk is always whole and
the successor's start is the same recovery a power cut needs.**

1. **Run**: the request changes metadata blocks in extfs's cache only
   (a transaction records each block it changed). File data for new blocks
   goes to the disk first, to blocks the committed bitmaps still call free
   (ordered mode: data before the metadata that points at it).
   Overwrites of a file's existing blocks go in place (POSIX promises
   nothing about a torn overwrite; a re-run writes the same bytes from the
   slot's bounce buffer, as fat's does).
2. **Commit**: the transaction's descriptor block, the changed blocks and
   a commit block, in **one** write to the journal (two where the journal
   wraps; jbd2's checksum v3 and asynchronous commit: the commit block
   counts only if its checksum covers the rest, so no flush is needed
   between them), with FUA (M12.7: an answered write is on the medium).
   The transaction's id (jbd2's, one per request that writes) is recorded
   in the request's slot before the commit. On a USB stick
   (only with Q2's B) usb-storage would need FUA writes or a SYNCHRONIZE
   CACHE after each commit (*unsure* which cheap sticks honour FUA; U3
   and the stick's track decide, with a test that a cut can't reorder
   them).
3. **Checkpoint**: the changed blocks written to their home places. The
   journal superblock's tail moves every 64 transactions or after a second
   idle, so a replay never has more than 64 transactions to read.
4. **Answer**, through the slot as fat does (the reply into the slot, the
   commit word, the kernel's replied mark).

**A successor** (or a boot after a power cut) mounts the volume: the
superblock and group descriptors, then the journal replay from its tail
(at most 64 transactions, a few hundred blocks: milliseconds on NVMe), then
the orphan list. Then it looks at the request slot: if the journal's
next transaction id after the replay has passed the slot's (the journal
superblock keeps the counter when the tail moves, so a checkpointed
transaction still counts), it was committed: send the reply; if not,
nothing of it is on the disk but data written to free blocks and
overwrites that a re-run writes again: run it again from the slot. **No
undo copy and no hold**: one recovery path, exercised by every restart in
`storm` and every cut test. What stays in the state VMO is small: the
slots, the open files (inode number and generation, flags; a few dozen
bytes each), the views. The block
cache and the directory index are rebuilt.

**Journal hazards, named for U3**: a metadata block freed and then reused
for file data must not be overwritten by a replay of an older transaction
(jbd2's revoke records, or no reuse of a freed metadata block until the
tail passes it: U3 chooses, with a test either way); a transaction larger
than the journal's quarter (a truncate of a huge file) is split into
steps that each leave the volume whole (a truncate shortens the extent
tree from its end, a step at a time, the inode's size first); the
journal's size is 64 MiB on volumes over 8 GiB (`mkfs`), 1/128 of smaller
ones.

**Cost.** A write of 64 KiB is its data write plus one journal write of
two to four blocks plus the checkpoint's few blocks, all FUA. On the
NVMe drive that is tens of microseconds; on a USB stick (Q2's option B)
about what fat costs today, since fat's write-through also writes the FAT
and the entry each request. Batching several queued requests into one
transaction is a later speed-up that changes no rule (Q6).

### What extfs holds and serves

- **One thread, one port**, like fat: the `fs` channel and its views,
  every open file's channel, the block channel, the keeper. One request
  at a time.
- **Opens**: any number per inode (no one-writer rule: that was FatFs's),
  keyed by inode number and generation. `FS_APPEND` writes at the end in
  the server, exact across processes. **Unlink of an open file
  succeeds**: the inode goes on the orphan list (on disk, so a cut frees
  it at the next mount) and is freed at its last close, or by the
  successor when the state shows no open of it.
- **`st_ino` is the inode number**, unchanged by a rename (fs.stat's `id`
  already promises "the same for every path that reaches it while it stays
  where it is"; on extfs it stays across a rename too).
- **Rename** is one transaction: replacing, moving a directory (with the
  check that it isn't moved into itself), and swapping two names
  (`RENAME_EXCHANGE`, a new flag: Linux's `renameat2`).
- **Directories**: entries in a list of blocks; extfs keeps an in-memory
  hash of each directory it has looked into (bounded, rebuilt by a
  successor), so a lookup in a directory of 10,000 entries is a hash probe
  after the first. `readdir`'s cookie is the entry's byte offset, stable
  while the directory changes (entries never move; a removed one becomes
  part of the one before it), so no entry is skipped or repeated.
- **Symbolic links**: targets up to 60 bytes in the inode, longer ones
  (to 4095) in a block. Resolution: [below](#paths-and-links).
- **Permission checks** for the one user (Q4): the owner bits for files
  of uid 1000, the other bits for anything else (a volume Linux made);
  directories' write and search bits; no root bypass.
- **Errors**: a metadata block whose checksum fails is `ERR_IO` for that
  request, the volume is marked as having errors (the superblock's state)
  and remounted read-only, and the log says what (ext4's
  `errors=remount-ro`). Nothing is repaired in place.
- **Views** as fat's (`fs.view`), with two changes. `FS_VIEW_GUARD_ETC` is
  judged on where a path **resolves**, not the string asked for: a symbolic
  link into `etc` is refused like `etc` itself; a hard link whose source
  resolves under `etc` is refused (a link would let a guarded file be
  written from outside `etc`). And a view can be **rooted at a
  subdirectory** (`fs.subview`, new): `..` stops at the view's root, so a
  mount of `/jam/usr` as `/usr` reaches nothing above it.
- **The pager** (U10): `file.map` as fat's after M12.5's PF1 and PF2
  (read and exec mappings, invalidation on write, the size on truncate,
  `ERR_BUSY` for a file a program runs from: M12.5's Q7). A 4 KiB block is
  a page, so a fetch is one block read, and a run of a file's extent can
  be read ahead. An unlinked file that is still mapped keeps its inode on
  the orphan list until the mapping goes, instead of being detached
  (M12.5's "detach on unlink" was FAT's limit).

### Paths and links

Today libc cleans a path (`.` and `..` lexically, `..` stopping at a
mount's root), finds the mount by its first name and sends the rest to
the service. Symbolic links change two things: `..` must be resolved
after a link is followed (physically), and a link's target may lead out
of the mount (Q8).

- **libc** joins a relative path to the current directory, finds the mount
  by the first name, and sends the rest **uncleaned** to a service whose
  `statfs` says it has links (FAT's mounts keep today's lexical cleaning).
- **extfs resolves inside its mount**: each name, `..` physically, and
  each relative link whose target stays inside the view. It never follows
  an absolute link and never climbs above the view's root: either answers
  the request with the new status **`ERR_LINK_OUT`**, and libc asks
  `fs.resolve(path)`, which answers how much of the path it consumed and
  what to continue with (the link's target and the rest, or "above the
  root" and the rest). libc continues from there **in its own namespace**,
  counting links to 40 (`ELOOP`).
- **`..` above a mount's root** then goes to the namespace's `/`, as POSIX
  says (`/jam/..` is `/`); today it stays at the mount's root. The service
  still never goes above its view's root.
- **This widens nothing.** A link is a string; following it reaches only
  what the caller's own namespace and views reach. A service never follows
  an absolute link (it doesn't know the caller's namespace), so a link on
  a shared volume can't make one program's open reach another program's
  mounts.
- **`O_NOFOLLOW`, `AT_SYMLINK_NOFOLLOW`, `O_DIRECTORY`** go to the server
  as flags; `O_EXCL | O_CREAT` on a name that is a dangling link is
  `EEXIST` (POSIX), never a file made at the link's target.
- **The current directory** is kept as the resolved path (`chdir` through
  a link stores where it leads: `pwd -P` and `getcwd` agree, as on Linux).

On extfs mounts (FAT's stay as B1 left them):

### The executable bit and approvals

The executable bit is **necessary, not sufficient** (Q5):
- `posix_spawn`, `execve` and the shell refuse a file on extfs without an
  execute bit (`EACCES`), before anything else.
- **Approval is unchanged**: a program on disk runs only after `allow` (its
  path and SHA-256 in `/data/etc/allow`, its page table in
  `/data/etc/allow.d/<sha-256>`, the pages checked by the kernel as they
  arrive: M12.5's PK4 and PX). `chmod +x` by a program approves nothing:
  any program with a writable view can set the bit.
- **Links**: `allow` resolves a path's links first and records where it
  leads; a run through a link is checked against the resolved path and the
  file's hash. A hard link to an approved file is another path (approve
  it too, or run the approved one); the hash and the page table are the
  same, so a hard link can never run changed bytes (the kernel's page check
  refuses them).
- `/data/etc` stays where approvals live (it is on the stick, and every
  program's `/data` view leaves it alone); nothing about approvals moves
  to the new filesystem in this milestone. PX's `/data`-only test
  (`sh_on_data`) is widened to the new mount (U8, after PX).
- **Scripts** (`#!/bin/sh` with the execute bit): the interpreter is the
  program that must be approved; the script is its data, as on Unix.
  Whether libc's `execve` runs a `#!` line is M13.5's and M13.7's (no
  POSIX shell yet).
- Who seals a program a POSIX program starts from disk (today only the
  shell holds `RIGHT_ROOT_VMEX`) is PX's and M13.7's question; M13.6 only
  adds the bit's check in front of it.

### Which disks, and the namespace

- **The Jam OS drive** (M12.7 stage 2's): its data partition ("Jam OS
  data", type 71bae565-...) holds the new filesystem. **The mark doesn't
  change**: the type GUID says the partition is Jam OS's, the superblock
  says which filesystem it holds (FAT32 or ext), and volumes starts fat or
  extfs by what it finds (Q7). It is mounted read-write as **`/jam`**
  (Q3), the one exception to "internal drives mount read-only", made by
  the same mark check M12.7's W2 builds for `mount -w`.
- **The stick** keeps FAT32 (Q2); a third partition for the new
  filesystem is an option the owner can take later (a new stick layout from
  `make usb`, which erases the stick).
- **Other disks** with an ext volume (a Linux stick: MBR type 0x83, or
  GPT's Linux filesystem type 0FC63DAF-8483-4772-8E79-3D69D8477DE4) mount
  read-only as `/usbN` or `/nvmeN` (Q9).
- **Subtree mounts** (Q3): init gives POSIX programs mounts of parts of
  `/jam` under the names ported software expects (`/usr`, `/var`, `/tmp`,
  `/home`), each an `fs.subview`; `NS_MAX_MOUNTS` goes from 8 to 16.
  Which names, and what lives under `/usr`, is M13.7's; M13.6 builds the
  mechanism and a default table. `/tmp` is a directory on `/jam` emptied
  by init at boot (U7b: or `/data/tmp`, or a volume in memory, when there
  is no writable `/jam`: [U7b notes](#u7b-notes)). Booted from the Jam OS
  drive, its data partition is `/data` and `/jam` both, and `/pkg` is a
  read-only view of the package area ([DB1 notes](#db1-notes)).
- **Tests** in QEMU use a second disk image (an NVMe drive with Jam OS's
  layout, `QEMU_NVME`, or a test stick), so M13.6's work doesn't wait for
  the real drive; the PC check waits for M12.7's P2.

### Q1. Which filesystem

- **(A)** Jam OS's own code for a subset of ext4's on-disk format: Linux
  reads it, `e2fsck` checks every crash test, a journal transaction per
  request (about 10,500 lines of ours in all).
- **(B)** Jam OS's own simple format: the same design, about 2,000 lines
  smaller; only our own tools read or check it.
- **(C)** Port lwext4's BSD files (ext2/ext3 without extents); its two

- **(E)** Read-only images (erofs) for installed ports and FAT32 for

*Recommendation: (A).* It is the only option that gives the whole list
with code that is ours and BSD, fits the restart model from the start, and
has a checker we didn't write. (E) is worth adding later for packages, on
top of (A).

- **(A)** The Jam OS drive's data partition only. The stick stays as it

- **(B)** (A), and a third partition on the stick for the new filesystem

- **(C)** (A), and a file on `/data` holding a volume (no new layout, but

### Q3. Where it appears

- **(A)** The whole volume at `/jam`, and for POSIX programs subtree mounts
  of it under the names ported software expects (`/usr`, `/var`, `/tmp`,
  `/home`; `HOME=/home/jam` when it exists), a namespace holding 16 mounts.
- **(B)** The whole volume at `/jam` only; ports use `/jam/...` paths and

- **(C)** The volume becomes `/data` when present, and the stick's FAT data

*Recommendation: (A).* Ported software and `#!` lines name `/usr/bin` and
`/tmp`; subtree views give them those names without one root filesystem,

### Q4. What the permission bits do

- **(A)** Stored and reported only: `chmod 000` changes `ls -l`, nothing
  else.
- **(B)** Stored, reported and checked for the one user as for an ordinary
  (not root) user on Unix: no write bit, no write; no search bit on a
  directory, no lookup through it. Not authority: any program with a
  writable view can `chmod` back.
- **(C)** (B) for POSIX programs only; Jam OS's own programs ignore them.

*Recommendation: (B).* Ported programs and their test suites (libc-test,
`install`, `make`, git's tests) expect a file without a write bit to
refuse a write; one rule in the service keeps every client the same.

### Q5. The executable bit and approval

- **(A)** Both needed: no execute bit, `EACCES`; then `allow`'s approval
  (path and hash, the page table) as for `/data` today.
- **(B)** (A), with M13.7's installer writing approvals for what it
  installs (through init, as the shell's `allow` does): M13.7's to ask.
- **(C)** The bit alone, under `/jam`: rejected (any program could make
  anything it wrote runnable).

*Recommendation: (A)* for M13.6; (B) is M13.7's question on top of it.

### Q6. When a write is on the disk

- **(A)** Every request is committed in the journal, with FUA, before its
  answer: the restart and the power cut have one recovery, `fsync` is free.
- **(B)** Requests commit into memory (the state VMO) and the journal is
  written every 5 seconds or at `fsync`: faster for many small writes,
  needs fat's hold and undo copy as well, and a power cut loses up to 5
  seconds of answered writes (POSIX allows it).

*Recommendation: (A).* One recovery path tested by every restart; a speed-up
(several queued requests in one transaction) can come later with no change
to the rule.

### Q7. The Jam OS drive's data partition

M12.7's W2 formats it FAT32 (its Q5) when `disk prepare` runs.

- **(A)** W2 as planned; this milestone's U7b makes `disk prepare` format it

- **(B)** Hold W2's format step until U7b.
- **(C)** Three partitions on the drive (ESP, FAT data, ext data): the

*Recommendation: (A).* Nothing waits, the mark stays two partitions, and

### Q8. Where links are followed

- **(A)** In the service, inside its view; a link that leads out (absolute,
  or `..` above the root) comes back to libc (`ERR_LINK_OUT`, `fs.resolve`),
  which continues in the program's own namespace; `..` above a mount's root
  goes to `/` (POSIX).
- **(B)** In libc, a name at a time: a `getattr` per component of every
  path (a path of 6 names costs 6 calls before the open).
- **(C)** In the service, absolute links included, read against the
  volume's own root: wrong for subtree mounts and blind to the caller's

*Recommendation: (A).* One call for the usual path, POSIX's answers, and no
service ever reads a link against a namespace it doesn't know.

### Q9. Other people's ext volumes

- **(A)** Mount them like FAT ones (`/usbN`, `/nvmeN`), `mount -w` allowed

- **(B)** Never mount them.
- **(C)** Mount them read-only, always.

*Recommendation: (C).* Reading a Linux stick is useful and only reads;
writing someone else's volume with a young implementation isn't worth the

### Q10. Checking a volume in Jam OS

- **(A)** Nothing beyond the journal's replay, the checksums and read-only

- **(B)** (A), and a read-only checker (`disk check /jam`) from the host

- **(C)** A repairing fsck of our own.

*Recommendation: (B).* The host tool needs the checker anyway (U8), and you

## Risks

- **Getting ext4's format exactly right.** A field written wrong is a
  volume Linux calls damaged. Defence: `e2fsck -fn` on every image every
  test leaves, fixtures made by `mke2fs`, and Jam OS writing only the
  features it knows (others refused or read-only).
- **The journal.** The worst outcome of the milestone is a cut that loses
  a synced file, or a replay that writes old metadata over new data.
  Defence: the cut shim at every write of every transaction in `make
  check`, Linux's replay as a second opinion, QEMU cuts, a real power cut
  on the PC, and the review reading the journal first.
- **Crafted volumes.** A stick from anywhere reaches the parser (Q9: read
  only). Defence: every metadata block's checksum checked before use,
  bounds on every field, the fuzzed images in `make check`, and the parser
  in its own process (a crash restarts it; it holds one partition's
  channel and nothing else).
- **Licence hygiene.** Agents must not read Linux's or e2fsprogs' code
  while writing (the format's documentation, FreeBSD's ext2fs and lwext4's
  BSD files only); the brief says so and the review checks for copied
  shapes.
- **Directories as lists.** A directory of 100,000 entries is slow to read
  the first time (the hash comes after); a written index is a later
  addition behind its own feature bit.
- **A journal write per request.** Many small writes cost a journal write
  each; fine on NVMe, slower on a stick (Q2's B). Batching is a later
  speed-up.
- **Linux changing the volume.** If the owner mounts `/jam`'s partition
  read-write in Linux, Linux may set feature bits Jam OS doesn't know:
  Jam OS then mounts it read-only and says why. P1 step 5 uses `--bare`
  and `-n` for this reason.
- **Restart time.** A successor mounts and replays (up to 64
  transactions) instead of mapping its state: slower than fat's restart.
  Measured (the bench line); the tail can move more often if it matters.
- **Paths change for every POSIX program.** U6 moves `..` handling and
  link resolution; posixtest's existing sections on FAT, the shell
  scripts and libc-test must stay as they are on FAT.
- **Size creep**: indexed directories, extended attributes, FIFOs on disk,
  writable mappings, package images and a repairing fsck are all later
  additions; a finding that needs one becomes a question, not a track.

**The subset as built** (super.c's table): read and written: `has_journal`,
`ext_attr`, `resize_inode`, `dir_index`, `filetype`, `extent`, `64bit`,
`flex_bg`, `metadata_csum_seed`, `sparse_super`, `large_file`,
`huge_file`, `dir_nlink`, `extra_isize`, `metadata_csum`. Read only:
`uninit_bg` (its CRC16 descriptors are checked), `dir_prealloc`,
`imagic_inodes`, `lazy_bg`, `exclude_*`, `sparse_super2`, `fast_commit`,
`stable_inodes`, `btree_dir`, `snapshot`, `quota`, `replica`,
`read-only`, `project`, `shared_blocks`, `verity`, and any unknown
compatible or read-only-compatible bit. Refused: `orphan_file`,
`orphan_present`, `bigalloc`, every incompatible bit not in the first
list, revision 0, an external journal. Beyond the plan's table:
`metadata_csum_seed` is read and written (it only moves where the seed
comes from: `tune2fs -U` sets it); `fast_commit` is read-only (a replay
that doesn't know fast commits must not write); `needs_recovery` mounts
read-only (`EXT_RO_RECOVER`) until U3's replay clears it. A volume is
written only if it also has `has_journal`, `filetype`, `extent`,
`sparse_super`, `large_file` and `metadata_csum` (`EXT_RW_NEEDS_*`,
else `EXT_RO_LACKS`): ext2/ext3 volumes, and their block-mapped files on
ext4 volumes, are read, never written. Block sizes 1, 2 and 4 KiB are
tested; 64 KiB is handled (its rec_len encoding) but has no fixture.

**The verdict** is `fs->ro`, bits saying why a volume may only be read
(asked, features, lacks, errors in the superblock, needs recovery,
damaged since the mount). Damage is `ERR_IO` with `fs->why` (a few
words: "extent block checksum", "directory entry: name"), `why_ino` and
`why_blk`, for the log, and adds `EXT_RO_DAMAGED`; marking the
superblock's error state on the disk is a write, so U4's.

**The shared header, for U2a, U2b and U3:**
- *The cache* is where a transaction collects. `ext_bread` (pinned) and
  `ext_bnew` (zeros, for a block written whole), `ext_brelse`; a writer
  changes the bytes, sets the structure's checksum with its `_set`
  function, then `ext_bdirty` (which forgets the buffer's "checked"
  mark, so a block dirtied without its checksum set fails its next
  read). Dirty buffers are never evicted (`ERR_NO_RESOURCES` when every
  buffer is pinned or dirty: size the cache for the largest transaction).
  `ext_sync` writes every dirty block home in block order and refuses a
  read-only volume (`ERR_ACCESS_DENIED`); `ext_discard` forgets them.
  **U3**: commit = the journal write of the dirty buffers, then
  `ext_sync` as the checkpoint; abort = `ext_discard`. The device's write
  is FUA (M12.7); the contract says writes come only from `ext_sync`: U3
  widens it to its journal writes (several blocks in one call are fine).
  Data written around the cache (U2a's file data) must `ext_binval` its
  blocks.
- *Checksums*: `ext_super_csum`, `ext_group_csum` (metadata_csum's and
  uninit_bg's), `ext_inode_seed` / `ext_inode_csum_{ok,set}`,
  `ext_extent_csum_{ok,set}`, `ext_dirleaf_csum_{ok,set}` (`_set` writes
  the whole tail), `ext_dx_csum_{ok,set}`, `ext_xattr_csum`,
  `ext_bitmap_csum`; `ext_crc32c` for U3's jbd2 checksums. Found against
  Linux's images: an index block's checksum covers its tail's reserved
  word *and* its checksum field as zeros; a descriptor's metadata_csum
  CRC counts its checksum field as zeros, uninit_bg's CRC16 skips it.
- *Groups* (**U2a**): `ext_group_get`/`ext_group_put` (a descriptor's
  halves joined; put sets its checksum; flags and itable_unused kept as
  they are without group checksums), `ext_group_first`,
  `ext_group_blocks`, `ext_group_has_super` (sparse_super and
  sparse_super2), `ext_bitmap_read` (checked; `ERR_BAD_STATE` when the
  group's `*_UNINIT` flag says it was never written: U2a builds it and
  clears the flag). A bitmap's checksum lives in its descriptor: set it
  there, then put the descriptor.
- *Inodes*: `ext_iget` copies only the fields `i_extra_isize` covers
  (128 + up to 32 bytes; the rest of the inode is attributes) and
  `ext_iput` writes back exactly those bytes, so **U2b** gives a new
  inode `extra_isize` 32 (the whole `struct ext_disk_inode`) and never
  grows it on an old one; `EXT_IGET_UNLINKED` reads inodes with no links
  (orphans, files open after unlink). Times: `ext_itime` /
  `ext_itime_set` (seconds to 2446, nanoseconds; int64 nanoseconds end
  in 2262, so U4 clamps when it fills `getattr`). `ext_xattr_block`
  checks an inode's attribute block (magic, one block, checksum): its
  `refcount` is what freeing needs (blocks are shared).
- *Extents* (**U2a**): `ext_extent_find` fills a `struct ext_path` with
  every node pinned: at an index level `at` is the entry followed (the
  first one when the block is before every entry, so a path always
  reaches a leaf), at the leaf the last extent starting at or before the
  block (-1: none); `bound` is the first block past the leaf's range (the
  next index entry's start at any level, 0 for none). The root lives in
  the caller's `struct ext_inode`, so a change to it is an `ext_iput`.
  Every node is checked as it is reached (checksum, magic, room, depth
  one less than its parent's, entries in order, extents inside the
  volume and ending by 2^32 without overlapping): a writer keeps those
  true. `ext_map` answers whole runs (data, hole, unwritten).
- *Directories* (**U2b**): `ext_dir_block` reads and checks a block as
  what it is (`EXT_DIRBLK_LEAF`, `_DX_ROOT`, `_DX_NODE`); an indexed
  directory's root and nodes are told apart by the index flag and the
  block's shape (block 0, and a first entry that is empty and the
  block's whole length). Entries' names never hold '/' or NUL (damage
  otherwise). `ext_rec_len`, `ext_dirent_size`. The plan's rule for a
  write to an indexed directory (index blocks become empty leaves, the
  flag cleared) needs a leaf tail on each of them with metadata_csum.
- *The orphan list* is read by `ext_orphans` (bounded; a loop is
  `ERR_NO_RESOURCES`).

**For U4**: `ext_dir_next` returns "." and ".."; a ".." entry is a block
number like any other, never proof of where it leads; lookups are a
linear walk (U2b's in-memory hash comes on top); the device's reads are
in multiples of 1 KiB, so a volume whose block size is smaller than the
device's sector needs a read-modify-write in the block adapter, or
refusing (Linux's mkfs never makes one). The library is single-threaded
per `struct ext_fs` (one thread in extfs).

**The fixtures** (tools/extfix/): `jam4k` (Jam OS's own feature set,
4 KiB blocks, 4 groups with flex_bg), `linux1k` (Linux's default ext4,
1 KiB blocks: an indexed directory, attributes in the inode and in a
block, an extent tree two deep, two orphans) and `old2k` (ext3 with
uninit_bg, 2 KiB blocks, block maps to triple indirect). Each holds
directories, empty and multi-block files, holes and a sparse file past
5 GiB, fast, slow and dangling links, hard links, setuid, setgid and
sticky bits, a FIFO, device nodes (old and new number encodings), owners
past 65535, times past 2038 with nanoseconds, a 255-byte name, UTF-8,
`Makefile` beside `makefile`. Made on the test PC's WSL (Ubuntu 24.04,
e2fsprogs 1.47.0) by `tools/remote-test.sh tools/extfix/make.sh
build/extfix`, which records every command; each `e2fsck -fn` clean
before the orphans were added. The Mac has no e2fsprogs (checked with
`brew list`; nothing installed). Gzipped they are 25 to 55 KiB each, not
the "few KiB" the plan said: the extent tree two levels deep needs over
336 one-block extents.

**Tests**: `make check` runs `build/host/extcheck`: the CRCs' check
values; each fixture listed by the library exactly as debugfs listed it
(path, inode, mode, owner, links, size, blocks, three times, the file's
bytes as a hash, link targets, device numbers) with a 512-buffer cache
and a 16-buffer one, every run of every file agreeing with its blocks,
entries' types agreeing with their inodes, the orphans, every bitmap and
attribute block checked, the shapes the fixtures are there for; every
checksum broken alone (superblock, a descriptor of each kind of
checksum, an inode, an extent node, a directory leaf, an index root, an
attribute block, both bitmaps), refused with its reason and taken once
the library's `_set` function sealed it again; every feature bit set
alone on `jam4k`, judged against the plan's table as written out again
in the test; every inode, descriptor and the superblock written back
unchanged through `ext_sync` with not one byte changed; and 3,000
mutated volumes (about 3 seconds on the Mac). Before the merge, four
long passes of 150,000 runs each (`--fuzz 150000 --seed S`) found
nothing; about 7% of runs aren't mounted (a damaged superblock or

mounted ones on the checksummed fixtures find damage on the walk.

**What the plan said that changed**: the fixtures' size (above); "U1
tells them apart by the inode's index flag" needs the block's shape too
(the flag says the directory has an index, not which of its blocks are
the index's).

## U2b notes

What U2b built (names and links, and mkfs), on U1's read side and U2a's
allocator. Written fresh from the format's documentation; nothing read
from Linux or e2fsprogs.

**The files** (user/services/extfs/ext/): `ext_names.h` (the API),
`names_int.h`, `dirent.c` (entries in a directory's blocks), `names.c`
(the directory hash), `links.c` (create, mkdir, symlink, link, unlink,
link counts), `rename.c`, `orphan.c` (the list written, drops,
recovery), `ext_mkfs.h` and `mkfs.c`. The shared header gained
`struct ext_fs`'s `names` (the hash, NULL for none) and `struct
ext_cache`'s `discards` (ext_discard counts, so the hash starts over
after a transaction is given up).

**For U3 and U4**:
- Every call is one step of a transaction in the cache; refusals (a name
  taken, missing, a directory not empty, a bad name) change nothing; any
  other error means `ext_discard`. **`ext_discard` does not undo `fs->sb`**
  (free counts, `last_orphan`, changed in memory by the writers): an
  abort must restore the superblock it had at the transaction's start (the
  tests do; U3's abort must).
- The library has no clock and no idea what is open: the caller passes
  the time and a random generation for new inodes (`struct ext_attrs`);
  an inode whose last name goes is put on the orphan list and its number
  handed back (`out_orphan`), and the caller drops it
  (`ext_orphan_drop`) at once or at its last close. A drop of a file
  bigger than about 1,000 extents is `ERR_SHOULD_WAIT`: commit and drop
  again (it stays on the list). `ext_orphans_recover` at a mount, with a
  keep function for what the successor's state holds open, `max` per
  transaction.
- The hash (`ext_names_init`, caller's memory) is optional: lookups go
  through `ext_lookup`.
- Link counts stop at `EXT_LINK_MAX` (65000): `ERR_NO_RESOURCES`
  (POSIX's `EMLINK`). A link to a directory is `ERR_IS_DIR` (POSIX:
  `EPERM`). Moving a directory below itself is `ERR_INVALID_ARGS`.
- An indexed directory (Linux's) is made plain by its first change.
- mkfs: Jam OS's feature set, 256-byte inodes, flex groups of 16, the
  journal by the plan's size (at least jbd2's 1,024 blocks, at most a
  quarter of the volume; it may run on through groups that hold no
  metadata), the journal superblock clean with no features (as mke2fs
  makes it: U3 sets checksum v3 when it first writes), groups past 0
  `INODE_UNINIT` (no tables to zero), every block bitmap written,
  `s_errors` remount-ro, the root and lost+found owned by the caller's
  uid and gid. Compared field by field with mke2fs's jam4k.

**Tests**: `make check`'s extcheck (tools/extnames.c, extmkfs.c,
extbig.c on tools/extvol.c's volumes, each step checked by
tools/extinv.c's invariants and U2a's tools/extverify.c): 10,000 entries
in one directory, renames of every kind, links, symbolic links, orphans

## U5 notes

What U5 built: the protocol changes of [the table](#the-interfaces-that-change-for-m14),
fat's and the boot image's answers to them, and libos's wrappers. The IDL
was committed first, alone ("U5 IDL:"), for U4.

**Where it differs from the table, and why**:
- The constants are named by the generator (`<PROTOCOL>_<NAME>`):
  `FS_FEAT_LINKS`, `FS_FEAT_MODES`, `FS_FEAT_CASE`, `FS_FEAT_BIG`,
  `FS_FEAT_MULTI_WRITER` (the table's `FSF_*`), `FS_DT_*` (readdir's
  `type`), `FS_MODE_FMT/DIR/REG/LNK` (getattr's `mode` is POSIX's whole
  `st_mode`: the kind in its top bits), `FS_ATTR_*` (setattr's mask),
  `FS_RESOLVE_INSIDE/ABSOLUTE/ABOVE` (resolve's `kind`), `FS_ONE_USER`
  (1000), `FS_RENAME_EXCHANGE`. The open flags stay in `<os.h>` beside
  the others: `FS_NOFOLLOW` 128, `FS_DIRECTORY` 256, and `FS_FLAGS` is 511.
  Any code that used 0x100 as "a bit nobody knows" now uses 0x200.
- `file.setattr (mask, mode, uid, gid, atime_ns, mtime_ns)` has no path
  or flags; `file.getattr` is `fs.getattr`'s results.
- `resolve`: `used` is how many bytes of the path the service took (up to
  the end of the link's name, or of the `..` that climbed out), `next` the
  path to go on with, already joined to the rest. `ABSOLUTE`: walk it from
  the caller's `/`. `ABOVE`: walk it from the directory the mount point
  is in. `INSIDE` (kind 0): nothing leads out, and `next` is the path's
  physical form (links followed, `..` resolved) relative to the view's
  root: that is what `chdir` stores. A joined path of 4,095 bytes or more is
  `ERR_NAME_TOO_LONG`. U6 and U4 build on this reading.
- `subview` is `ERR_NOT_SUPPORTED` on **fat too**, not "a prefix" as the
  table has it (the track row and the brief say the rest is
  `ERR_NOT_SUPPORTED`; nothing mounts a part of `/data` yet). The views'
  checks (below) already refuse a root at or under `etc` where it would
  hide where `etc` is.
- fat's `setattr` is OK for a path that is there (the table), after the
  checks it shares with `file.setattr` (`fat_attr_check`): an unknown mask
  bit is `ERR_INVALID_ARGS`, a read-only volume, or a uid or gid other
  than `FS_ONE_USER` in the mask, is `ERR_ACCESS_DENIED` (libc's old
  rules, moved here). The boot image: `ERR_ACCESS_DENIED` for a path that
  is there.
- The made-up modes are libc's: a directory 0755, a file 0644, a file
  directly in a `bin` or `sbin` of the boot image 0755, the write bits off
  on a read-only volume (the boot image is always: 0555 and 0444); one
  link, owner and group 1000, `blocks` in 512-byte units, all three times
  the modification time (0 for the root and the boot image). On a
  read-only **view** the shared view code also takes the write bits off
  getattr's reply, as it sets `read_only` in statfs's.
- readdir's `type`: fat and the boot image fill `FS_DT_DIR` and
  `FS_DT_REG`; `fs_dirent_get` refuses a type that is not one of those
  or `FS_DT_LNK`/`FS_DT_UNKNOWN`, or that says the opposite of `is_dir`.
- `statfs`: fat's magic is 0x4d44 (MSDOS), the boot image's 0x858458f6,
  both 255 and no features. (libc still picks the magic from the label
  until U6 reads these.)
- The fat state layout is 7. fat and bootfs leave `symlink`, `readlink`,
  `link`, `resolve` and `subview` out of their ops tables: the generated
  dispatch answers `ERR_NOT_SUPPORTED` for a method with no handler,
  after it has checked the request (so a malformed one is still
  `ERR_INVALID_ARGS`), and after the view's check.

**Views** (user/lib/fsview.c, not in the track's list, but a new call that
takes a path has to be judged like the old ones): `setattr`, `symlink`
(the new name is the change; the target is only text), `link` (both
names: a link to a guarded file would write it from outside) and rename's
exchange are changes (read-only, `etc`); every new call that takes a path
is checked for `etc/ssh` (`FS_VIEW_HIDE_KEYS`), the target of a symlink
not; a `subview` rooted at or under `etc` is refused on a view that hides
the keys, and on one that guards `etc` unless the new view is read-only.
extfs judges a path by where it **resolves** (the plan, above); these checks
are the lexical first line it keeps.

**libos** (user/lib/fs.c, `<os.h>`): `file_open_mode`, `fs_mkdir_mode`
(`file_open` and `fs_mkdir` pass 0644 and 0755); `fs_getattr`,
`fs_setattr`, `fs_symlink`, `fs_readlink`, `fs_link`, `fs_resolve`,
`fs_subview`, `fs_statfs_kind` (magic, longest name, features) by path
through the namespace, `file_getattr`, `file_setattr` on an open file;
`struct fs_attr`, `struct fs_attr_set`; `struct fs_entry` has `type`. They
send the path as it is and hand `ERR_LINK_OUT` on: the loop is libc's (U6).
The generated stubs whose names clash got the `idl_` prefix in
`<fs_idl.h>`: `idl_fs_getattr`, ..., `idl_file_getattr`, `idl_file_setattr`.

**Edits outside the track's files** (the signatures changed under them):
every caller of the generated `open`, `mkdir` and `statfs` stubs passes
the new arguments (`user/posix/sys/{fobj,dir,meta,path}.c` pass the
default mode and ignore the features: U6 reads them), init's espwrite,
logd's store_fs, volumes' spare, the shell's storm; `user/tests/ramfs/ram.c`
(a test filesystem) gained the signatures and readdir's `type`;
`user/lib/status.c`, `kernel/object/object.c` and two tests name
`ERR_LINK_OUT`; CODING-GUIDE's status table has it.

**Tests**: utest `dirent_types`, `fat_attrs`, `fat_attrs_read_only`,
`fat_attr_views`, `fs_attr_ns` (user/tests/utest/fs_attr.c): every new
call against fat over a RAM disk (made-up attributes, the setattr
rules, open's mode and flags, the exchange refused, the link calls
`ERR_NOT_SUPPORTED`, readdir's type, statfs), read-only, guarded and

and on `/boot`.


## U4 notes

What U4 built: bin/extfs (user/services/extfs/, beside ext/), the `fs`
and `file` protocols on the ext core, and its startup header
`<extfssvc.h>`. About 3,600 lines with their comments (and 1,100 of
tests); the Makefile builds ext/ into it as the program's own
subdirectory (no new lines but a comment).

**The files**: `extfs.h` (the map), `main.c` (the start, the mount, the
format, the loop, the journal's idle checkpoint), `disk.c` (ext's device
over `block`), `state.c`, `request.c` (a transaction per request, the work
left for after an answer), `adopt.c` (every start, a successor's
carrying on), `keeper.c`, `walk.c` (paths, links, permission bits, the
views' judgment where a path resolves), `fsops.c`, `files.c`, `views.c`,
`test.c`.

**The rule as built** (request.c's header):
- A request is begun (`ext_jnl_begin`), run, and committed in the
  journal if its answer is OK (aborted otherwise: a method that fails half
  way leaves nothing); `on_commit` records the transaction's id in the
  slot's record just before the commit block goes; then the slot is
  committed and answered. A successor that finds the slot not committed
  asks `ext_jnl_committed` of the recorded id: committed, the reply
  already in the slot is the answer (handles it carried made again);
  not, the slot it made (an fs.open's file, a view) is forgotten and the
  request runs again from its slot (a write's bytes from the slot's
  bounce buffer). No undo copy, no held writes.
- **One transaction per request.** What may outgrow one does its first
  step in the request with the inode on the on-disk orphan list, and the
  rest after the answer, a transaction a step (`defer_run`): a truncate
  that shrinks (up to 8 steps of `EXT_TRUNCATE_STEP` in the request while
  `ext_jnl_room` allows, the rest after), and every orphan drop (an unlink
  or a replacing rename answers at once; the inode is dropped after, or
  at its last close if it is open). `defer_run` finishes before the next
  request is read; a death in it is finished by the next mount's orphan
  recovery (`ext_orphans_recover`, with the state's open files kept).
- Every start mounts from the disk: the journal's replay is the
  recovery, the same after a kill as after a cut; a state is carried on
  from only if it names the volume's UUID and its open files' inodes are
  there with their generations.
- The journal's tail moves after a second idle (`ext_jnl_checkpoint`).
- Writes are FUA by the block driver's rule (drv/nvme); usb-storage
  writes aren't, so an ext volume on a stick would need a sync per
  commit: none is written (Q2, Q9), and disk.c says so.

**Decided here**:
- **A link loop** (more than 40 links in one walk) is `ERR_OUT_OF_RANGE`
  from every method, resolve too: the status table has no ELOOP, and
  libc's own count is to 40 across services. **U6** maps it to `ELOOP` for
  a path call. (U6 replaced it with a status of its own, `ERR_LINK_LOOP`.)
- **Views and subviews.** The shared code (`fs_view_dispatch`) stays the
  first line, on the path as written; walk.c then judges every flag on
  the place the path resolves to (`phys`: the names from the volume's
  root), with `fs_view_hides` and `fs_view_in_etc` themselves. A directory
  the view hides wholly can't be walked through (so `x/../y` through
  `etc/ssh` learns nothing); readdir leaves out what the view hides
  wholly wherever the listing was reached (a link to `.`); a hard link
  whose source resolves into a guarded `etc` is refused; a file opened
  through a view that may not change it can't be `file.setattr`ed. A
  subview's root is held by inode and generation and its place (up to
  1,023 bytes) is kept for the judgment; the shared code is given only the
  read-only bit for a subview (its paths are relative to its root, so
  `usr/etc` would look like `etc`), and fs.view on a subview ORs the
  parent's flags back in. A subview rooted in `etc` is refused as the
  shared code refuses it, where it resolves. The place is fixed when the
  subview is made: a root renamed into `etc` afterwards (only a view that
  may change `etc` can) is still judged by its old place.
- **getattr on a read-only view** loses the write bits in the shared code
  (U5's choice, kept): extfs answers the real mode, and a read-only view
  shows it without write bits, as `statfs` says read-only.
- **subview on fat** stays `ERR_NOT_SUPPORTED` (U5's); extfs's is real.
- **Format**: `EXTFS_ARG_FORMAT` formats a writable partition whose first
  4 KiB are zeros (ext's mkfs writes block 0, the superblock's, last, so a
  format cut short is blank still and is made again: utest checks it).
  The label is `jam`.
- **Errors**: an `ERR_IO` with the volume newly damaged gives the
  transaction up, marks the superblock's state as having errors through
  one transaction of its own (not when the journal itself failed, nor for
  a disk error), and serves read-only from then on; the next mount reads
  the mark and mounts read-only (until e2fsck).
- **Permission bits** as Q4's B, checked in walk.c and the methods: search
  for every lookup, write and search to add or remove a name, read to
  list, the file's bits at its open; setattr by the owner only (uid 1000),
  a uid or gid other than 1000 refused.
- **file.map** is `ERR_NOT_SUPPORTED` until U10; `EXTFS_SR_PAGER` is taken
  and kept.
- Devices and FIFOs on a Linux volume: listed (type unknown), stat'd, not
  opened (`ERR_NOT_SUPPORTED`).

**Not done, for others**: volumes starting extfs (U7a, [done](#u7a-notes):
the roles are fat's numbers, `EXTFS_STATE_SIZE` 1 MiB, the same limits as
fat's job fit: about 4 MiB of heap for the cache, the journal's region and
the directory hash); libc's loop (U6).

**Tests**: utest's `extfs_*` cases (user/tests/utest/extfs.c,
extfs_restart.c), each over a RAM disk extfs formats, started directly as
fat's own tests start fat (not through volumes' `test_disk`, which needs
U7a's start by kind): `extfs_basic`, `_links`, `_perms`, `_writers`,
`_views` (a link into etc refused through a view, subviews), `_error`
(a spoilt directory block: ERR_IO, read-only, the mark on the disk);
`extfs_restart_steps` (a script of every kind of request, undisturbed
and with extfs ended at device writes, the journal's commit, the slot's
commit and the answer, 19 deaths in four runs plus two during a format:
the same answers, the same files and the same free space as the
undisturbed run), `_handles` (fs.open's and fs.view's replies remade),
`_bad` (ERR_IO after two crashes; two kills don't count), `extfs_spare`
(a spare promoted twice, the open file carried on).
`tools/extfs-svc-test.sh` runs them from the shell and Linux's `e2fsck
-fn` on every disk they leave: all clean.


## U6 notes

What U6 built: libc (user/posix/sys/) on a mount whose `statfs` says
`FS_FEAT_LINKS` (extfs), FAT's mounts and the boot image as B1 left them;
`ERR_LINK_LOOP`; posixtest's `links` section.

**Paths** (files.h's header, path.c):
- The names up to the mount are cleaned as before; on a mount with links
  the rest goes as written. A call that gets `ERR_LINK_OUT` asks
  `fs.resolve` and starts again from where it said, in our own namespace
  (an absolute target from our `/`, a `..` above the mount from `/`), the
  `/dev`, `/etc` and `/proc` trees judged again there: every path call
  runs `do r = op(&p); while (path_again(&p, &r))`. Each step out counts
  as a link; past 40, `ELOOP`. A loop inside one walk is extfs's: the new
  status `ERR_LINK_LOOP` (-28, `kernel/include/jam/status.h`, the names in
  `kernel/object/object.c` and `user/lib/status.c`, extfs's walk, utest's
  status loop and `extfs_links`), `ELOOP` in libc's `lx_err`.
- `..` above the root of a mount **with links** is `/` (`/u6/..` is `/`);
  FAT's mounts keep B1's rule (`/data/..` is `/data`: posixtest's files
  section says so), as the table's "FAT's stay as B1 left them" reads.
- Kept **physical** (fs.resolve's `INSIDE` answer, `path_place`): the
  current directory (`chdir` through a link stores where it led), a
  directory descriptor's path, both names of a `rename` and a `link`
  (placed before the call, so a two-path call never needs the loop). A
  **file** descriptor keeps its path as resolved (the mount's part as
  written): no extra call per open; it is used only to open the file
  again for a child.
- The features and the read-only flag come from one `fs.statfs`,
  remembered per mount (the flag a second, the features a minute).
- Symbolic links into `etc` (U4's "judge where they resolve"): a link out
  of a mount is followed by libc in the caller's own namespace, so what it
  reaches is judged by that mount's own view (fat's for `/data/etc`, which
  hides it), and a target under libc's `/etc` is libc's; a relative link
  inside extfs is extfs's to judge (U4). Nothing in libc widens a view.

**The calls** (meta.c, dir.c, file.c, fobj.c): stat by `fs.getattr`
(`lstat`, `AT_SYMLINK_NOFOLLOW`: `FS_NOFOLLOW`), fstat by
`file.getattr`; chmod, chown and utimensat by `fs.setattr`, or
`file.setattr` on a descriptor's open (a directory's or an `O_PATH`
one's by its path), "now" read from `CLOCK_REALTIME`, a refusal `EPERM`
(`EROFS` on a read-only mount), a uid or gid other than 1000 `EPERM`
before asking; access by the bits that count for the one user (owner's
for uid 1000, others' else: `path_perm`, extfs's rule); symlink,
readlink (cut to the buffer, no NUL), link (`linkat` follows no link
unless `AT_SYMLINK_FOLLOW`; a directory `EPERM`; `EXDEV` between two
mounts, two mounts of one volume too); `renameat2`'s `RENAME_EXCHANGE`
(`EINVAL` on FAT, as before) and `RENAME_NOREPLACE`; the umask on every
`open(O_CREAT)` and `mkdir`; `O_NOFOLLOW` on a link `ELOOP` (extfs says
`ERR_INVALID_ARGS`), `O_PATH | O_NOFOLLOW` the link itself (fstat
`S_IFLNK`); `O_CREAT | O_EXCL`, `mkdir`, `unlink`, `rename` never follow
the last name; `statfs` gives the service's magic and name length (FAT's
label check is gone); getdents' `d_type` is readdir's `type`.

**Many writers** (`FS_FEAT_MULTI_WRITER`): one open per file per process
still (extfs serves 32 opens in all), and one more per file for the
`O_APPEND` descriptions, opened `FS_APPEND`: the service appends, and
the offset after is the size it then reports (one `file.stat` per
append). A writable descriptor given to a child is opened again for it
(nothing lent); the size is always the service's. **Left as it is**: an
`O_APPEND` set later by `F_SETFL` on a description of a file opened
without it writes at the size asked just before (not exact against
another process); clearing `O_APPEND` on an `FS_APPEND` description
still appends.

**The execute bit** (spawn.c, its own commit, CS1's file): `program()`
calls `path_program`: the path with its links followed (approvals are
by that path, `allow`'s rule) and, on a mount with modes, `EACCES` for a
file without the execute bit that counts, before `/svc/exec` is asked.

**Not done**:
- libc-test's expected failures (M13's P2): it runs on `/data`, FAT, so
  nothing of FAT's comes off its list until `/data` is ext (U7a, U8).
- `spawnfd.c` (posix_spawn's file actions, `addchdir`) still cleans
  paths lexically (`spawn_absolute`, CS1's file): on a mount with links
  `a/link/..` there means `a`, not the link's parent.
- `/proc/self/fd/N` of a file on a mount with links names the path as
  resolved, not its physical form (a readlink there would need a call).
- `readlinkat(fd, "")` and `linkat(fd, "", AT_EMPTY_PATH)` of an `O_PATH`
  descriptor are as before (ENOENT, and B1's descriptor case).

## U8 notes

What U8 built: the host tool `tools/jamext/`, the checker as library code,
the shell's file commands for links and modes, `disk check`, and `allow`
and the run path widened to `/jam`. About 1,900 lines (jamext 1,300, the
checker 600 with its comments, the shell's commands 450), and the tests
below.

**The checker** is `user/services/extfs/ext/check.c` (`ext_check.h`): the
invariants `tools/extinv.c` already checked for the writing tests (the
tree, link counts, the inode and block bitmaps, who owns each block, the
free counts, the orphan list), moved into the library so one checker
serves three places: `extinv.c` (now a wrapper that fails on the first
problem), `jamext check` and the shell's `disk check`. It reports every
problem, one line each, up to 50 (then says it stopped), polls a cancel
(Ctrl+C), never writes, and takes its memory from the caller's `alloc`
(about 13 bytes an inode, a bit a block, 8 bytes an entry of the
largest directory: a 256 GB volume at the default ratio asks for about
200 MB). `tools/extdetect.c` spoils a good volume six ways (a link count,
a block used but free, a nameless inode, the superblock's count, a block
owned twice, a directory size) and wants each said, and a good volume
silent; `extcheck --image <file>...` mounts images another tool made.
Not checked (e2fsck's, or the library's own checksums as each block is
read): extent trees' ordering beyond what `ext_extent_find` verifies,
directory index blocks, extended attributes' contents, the journal.

**jamext** (`build/host/jamext`; `make check` builds it and runs
`tools/jamext-test.sh`): `mkfs`, `mkimage <image> <size|auto> <dir>`,
`import`, `put`, `get`, `ls [-lR]`, `ln [-s]`, `mkdir [-p]`, `rm [-r]`,
`chmod`, `info`, `check [--replay]`. A volume is a file, or part of one
(`--offset`/`--size`, or `--part N` of a GPT or MBR, 512-byte sectors;
a raw device works the same, its size read from the superblock).
Decided here:
- **Writes go through the library's journal**, a transaction per change
  or per megabyte of a file's data, as extfs does: a tool killed
  half way leaves a volume the next mount (jamext's or Jam OS's) replays,
  and a volume that needs replay is replayed when it is opened for
  writing (read-only commands read it as it lies and say so; `--replay`
  replays it first). The file is `fsync`ed once at the end, not at each
  commit: the host tool is not a power-cut-safe writer of a raw device.
- **Reproducible images**: `--seed` (the uuid and every inode's
  generation) and `--time` (every time written; `SOURCE_DATE_EPOCH` too)
  make the same bytes from the same directory (the test makes one twice and
  compares).
- **`mkimage`/`import` modes**: a directory 0755, a file 0644 or, with any
  host execute bit, 0755 (so two people get the same image); `--keep-modes`
  copies the host's bits, `--keep-times` the mtimes. One owner (1000).
  Symbolic links are kept as they are, hard links (one host inode) stay
  one file, sockets and devices are skipped with a line on stderr.
  Zero blocks of a file are not written (a hole), so a sparse host file
  stays sparse. `size auto` is the tree's data, a tenth, 24 MiB for the
  journal and the first groups, and inodes for every name.
- `put` makes the missing directories above its name and replaces a file
  that is there; a `put` that runs out of space removes its half file.
- **The smallest volume** mkfs makes is about 16 MiB (a journal of 1,024
  blocks at least): 12 MiB says "no space".

**The shell**: `ls -l` is now `mode links owner group size name` with
` -> target` after a symbolic link (the old `<dir>` column is the mode's
`d`; the size column and its two spaces before the name are as they were,
so a test that matches `KiB  init` still does); `ls -l link` shows the link
itself. `stat [-L]`, `ln [-s] <target> <name>` (into a directory: under the
target's name), `chmod <octal|symbolic> <path>...` (u+x, go-w, a=r; a
volume that keeps no bits, such as FAT, says so instead of accepting and

modes, so `ls -l /data` shows `-rw-r--r--  1 jam  jam`. Two shell-side
facts: libos's `printf` has no `%o` (stat prints the octal by hand), and
the shell's `grep` has no bracket expressions.
- **Not done: following a link that leads out of its volume.** extfs
  follows relative links inside the volume; an absolute target (or a `..`
  above the mount) comes back `ERR_LINK_OUT`, which libc follows
  (`path_again`) and libos does not. The shell's commands show it as "a
  symbolic link that leads out of its volume (readlink shows it)". A
  follower in libos's path calls (user/lib/fs.c) would give the shell
  every link; sbase's `cat`, `ls` and the POSIX programs have it already.
- `sh_on_data` (the shell's path test: `allow`, `run`, the pages' check)
  accepts `/jam/...` beside `/data/...`; approvals stay in `/data/etc/allow`.
  **init's `/svc/exec` has its own `dp_on_data` check (init/exec.c) that is
  still `/data` only**: a program on `/jam` can't yet start a child by path
  through `/svc/exec`. Not widened here (init's file; PO13 widened
  `dp_on_data`, `<dataprog.h>`, to `/jam/`); `/usr` and the other
  views of `/jam` are not program mounts yet (M13.7 decides).
  A program on `/jam` runs from its pages (U10's `file.map`), as one on

**`disk check <mount>`** (`user/services/shell/sh_extcheck.c`): the same

## U10 notes

What U10 built: extfs as a pager, `user/services/extfs/pager.c` (its
header is the model, fat's pager.c the pattern), about 600 lines, and
`file.map` in files.c; the rest is small hooks (files.c, fsops.c,

**As built:**
- **`file.map`** (read and exec) as fat's: `FILE_MAP_READ` the file's one
  shared VMO while some `fs.open` holds the file (extfs's handle with the
  keeper), `FILE_MAP_EXEC` a VMO of the caller's own every time. Slots in
  the state (`maps[]`, `XF_MAX_MAPS` 64, twice fat's: the keeper and the
  job's 256 handles have room) name the inode and its generation, so the
  pager needs no open file of its own. Keys `XF_MAP_KEY(seq, slot)`, seq
  from the clock, as fat's.
- **Page requests** read with `ext_read` on the inode as it is now (whole
  blocks straight from the device, holes and unwritten extents zeros) and
  supplied whole, clipped to the file and to the VMO; no read-ahead past
  the kernel's 16 pages (a sequential mapper's requests are 64 KiB each). A
  VMO holds at most the file's first `VMO_SMALL_MAX_SIZE` (64 GiB).
- **Coherence**: a write (`op_write`, failed ones too: data over the
  file's own blocks is on the disk whatever the answer) and a truncate
  (`files_truncate`, so an `FS_TRUNCATE` open too) drop the changed pages
  and set the size inside the request, before its commit; a request given
  up (`maps_settle`) and every start set the VMOs' sizes again from the
  inodes. The ordering argument is pager.c's header.
- **Q7 on ext**: a file mapped to run refuses an open for writing (or
  truncating), an unlink of any of its names and a rename over it
  (`ERR_BUSY`); a file open for writing isn't mapped to run. **Decided**:
  a rename *of* a running program's file, and an exchange, are allowed
  (fat refused them; on ext no byte or inode changes: Linux's rule).
- **Unlinked mapped files** (and files renamed over) stay readable: a
  slot holds its inode as an open does (`files_held`), so the orphan is
  dropped at its last close or GONE, and a successor's orphan recovery
  keeps it. No more "cut off: its file was removed" on ext.
- **Restarts**: the slots carried on (keeper slot `XF_KEEP_MAP(i)`), a
  map's reply made again (`XF_MADE_MAP`, or `XF_MADE_MAP_SHARED` for one
  that shared a slot, which a re-run never forgets), `PAGER_NEXT_AGAIN`
  at every start; test powers `die=map:<n>` and `die=supply:<n>`.
- **volumes**: the hand-off already reached extfs (the same role number,
  U7a); now said for both kinds (`EXTFS_SR_PAGER` for an ext mount, a
  static assert that the roles agree, the comments).
- **Outside the track's files** (small): init's ctl.c sends `kill
  extfs-<mount>` to volumes as it does `fat-<mount>` (it went to devmgr
  and failed: storm couldn't kill an ext mount's service); posixtest's
  `spawn-data` makes its copy executable (a mount with modes wants the
  bit; the shell has no `chmod` until U8).

- **Why volumes and not init**: volumes alone knows the boot disk is the
  drive (the loader named it by its GUID: `disk_booted_from_drive`) and that
  its data partition holds ext. init mounting a duplicate of `/data`'s channel
  (U7b's sketch) would need that fact in the `mounted` event (a new flag, an
  IDL change) and would leave volumes' list without the `/jam` every
  namespace has. A view of `/data`'s root as `/jam` was not taken either: it
  is a second channel with view flags for no gain.
- **The names**: `/data` stays the data partition's name on a drive boot, so
  settings, logs, approvals (`/data/etc/allow`), `update` and kdump's saves
  are where they were, and the installer's wording ("a Jam OS disk is
  installed on again (its /data is kept)", "your /data/etc") is right on
  both boots. `/jam` is the same volume under the name a stick's boot gives
  the drive, so what is put in `/jam` (packages, `/usr`) is found under the
  same path whichever way the PC started.
- volumes says `volumes: nvme0: the machine booted from this Jam OS drive:
  its data partition is /jam too`, after the `-> bin/extfs at /data (OK)`
  line (kept as it was). The vol's `jam` flag is set for it (`choose_ext`),
  so `jam_taken` counts it; booted from a drive, **no other Jam OS drive's
  data partition is `/jam`**: it is `/nvmeN`, read-only, as its ESP is
  (M12.7's Q8; U7a gave a second drive `/jam` read-write when the boot
  drive's data wasn't). A boot drive whose data partition is still FAT
  (made before U7b) has no `/jam`; `disk format <disk> data` from a stick
  boot makes it ext.
- Not changed: `disks` lists the partition as `/data (ext)` (the listing
  has one mount path, 15 bytes); `mount -w /jam`, `kill extfs-jam` and
  volumes' requests by the path `/jam` don't name it on such a boot (it is
  `/data`'s service, `extfs-data`).
- **A stick's boot** is as before: the stick's `/data`, and a Jam OS drive's
  data partition `/jam` beside it (layout-test `both`, nvme-test `jam`). U7b's
  (D), the stick's ext `/data` as `/jam` too when no drive is in, is not

- **For the owner** (packages across the two boots): approvals stay
  `/data`'s (PO13's rule), so a package installed from a stick's boot onto
  the drive's `/jam/pkg` is approved in the *stick's* `/data/etc/allow`; on

**`/tmp`'s pager** (tmp.c's `ram_pager`). The memory volume gets a pager as
volumes makes a mount's (spare.c): `jam_pager_create` on init's root
(`RIGHT_ROOT_PAGER`), a budget of a sixteenth of the memory (4,096 pages if
it is unknown), page requests answered within `FS_CALL_TIMEOUT`, handed to
bin/extfs as `EXTFS_SR_PAGER` with READ WRITE WAIT only. extfs's pager (U10)
supplies pages from its RAM disk as from a block one: nothing in extfs
changed. The pager and its pages are charged to init's job, as the volume's
VMO already was. A memory `/tmp` that goes (replaced by a volume's, or its
service ended) takes its pager with it: mappings of its files are cut off,
as a pulled stick's are. The log line says it: `init: /tmp: in memory (128
MiB at most, a pager of 8192 pages)`. mmap of a `/tmp` file now works on
every kind of `/tmp`: `MAP_SHARED` read, `MAP_PRIVATE` read and written
(posixtest `mmap-tmp`); writable shared mappings are WK3's, ext only, on
`/tmp` as on any extfs mount.

**`/pkg`** (tmp.c, the same thread as `/tmp`). A read-only view
(`fs.subview` with `FS_VIEW_READ_ONLY`) of `/jam/pkg` while `/jam` is mounted
read-write, else of `/data/pkg` while `/data` is read-write and can give views
(ext), else none; the directory is made if it isn't there. It is looked at
again whenever `/jam` or `/data` comes or goes (a new channel is a new view),
so it follows `/jam` through the installer's hold: to `/data/pkg` meanwhile
(none on a FAT `/data`) and back (nvme-test `jam`). The log says `init: /pkg:
a view of /jam/pkg, read-only`, `init: no /pkg: /data/pkg can't be a view
(its volume is FAT)` or `init: /pkg is gone: ...`. bin/pkg's `pick_prefix`
now takes `/jam` only when it is read-write too (a read-only `/jam`, R3's
damaged-header case, was chosen and then failed every write), so the two
rules are one.

**What PO14 can rely on** (the ports' compiled-in prefix `/pkg`, the shell's
`PATH` `/pkg/bin`):
1. In shell mode init's namespace, and so every follower's (the shell, the
   sessions), has `/pkg` whenever there is a package area on a volume that
   can give views, and it is the directory bin/pkg installs to: `/jam/pkg`
   when `/jam` is in the namespace and read-write (always on a drive boot,
   where it is the data partition; a stick's boot beside the drive), else
   `/data/pkg` (a stick's boot with an ext `/data`). `/pkg/<path>` is
   `<prefix>/<path>`, byte for byte the same file.
2. No `/pkg` on a stick with a FAT `/data` and no drive (FAT has no views of
   directories; bin/pkg still installs to `/data/pkg` there): after U11b's
   ext default, only an old stick not made again. Program mode (the `init`
   run) has no `/pkg`, as it has no `/tmp`.
3. `/pkg` is read-only: every change through it is refused, statfs says
   read-only, `mount` lists it so. bin/pkg changes the area through its own
   grants (`mount /jam rw pkg`, `mount /data rw pkg`) under the prefix's own
   name, never through `/pkg`.
4. It moves only when `/jam` or `/data` comes or goes (an install's hold, a
   drive's `disk format`, a stick pulled), within a second or so (the
   thread), and the followers get the new mount with the change, as for
   `/usr`. Files opened through a view whose volume's channel closed (the
   installer's hold restarts `/jam` on a new one) see it close, as `/tmp`'s
   do.
5. Like `/usr`, `/pkg` reaches a **program** only through a grant: a
   program's namespace is its list's grants, and no word gives `/pkg` today
   (`mount <point>` knows `/boot`, `/esp`, `/data`, `/jam`, `/usb*` and `*`;
   `mount * r` does take it). A port that bakes `/pkg` in needs PO14 to add
   one: `posix` granting `/pkg:r` as it grants `/tmp:w` (wants.c,
   checkwants.py and its fuzz copy, utest `wants_posix` and
   `pkgctl_other_version`), or a `mount /pkg r` want. And a program run as
   `/pkg/bin/<name>` needs the approvals and the run path to know `/pkg/`
   (`dp_on_data` takes `/data/` and `/jam/`, approval lines name
   `/data/pkg/...` or `/jam/pkg/...`): map `/pkg/` to the prefix there, or
   run by the prefix's own path.
6. Untouched, PO14's (done: [M13.7's PO14 notes](M13.7-PLAN.md#po14-notes)): `PATH` (`/data/pkg/bin` still, no `/jam/pkg/bin`),
