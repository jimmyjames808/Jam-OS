### Q1. Is the 600 ns target with the lock checker on or off?

**What it is about.** Every spinlock in Jam OS goes through the lock-order
checker (`kernel/debug/lockdep.c`), on every boot. It found real bugs on
the PC, and BENCH.md has always been measured with it on. Stage 0 counted
the locks: **one process-to-process call takes 20 spinlocks** (a kernel
channel_call 14, a context switch 1). BENCH.md's `spin_lock +
spin_unlock` line is 26.7 ns with the checker; the bare ticket lock is a
locked add and a store, about 5 ns on this CPU (an estimate: the PC will
measure it). So the checker is probably **about 400 ns of today's
1533 ns**, more than any other single piece. The roadmap already asks for
a column with the checker off; nobody has decided which column the
target is on.

**Options.**
- (a) **Target on the checker-on column** (what runs every day), and make
  the checker's fast path cheap in this pass: no `pushf`/`cli` pairs when
  interrupts are already off, the held-lock list kept without a search,
  the class cached in the lock (it already is). Aim: under 5 ns added per
  lock. Nothing is given up.
- (b) Target on the checker-off column; the checker stays on in every
  boot. The everyday system would stay a few hundred ns slower than the
  headline number.
- (c) Checker off in the everyday boot, on in every test boot (All tests,
  soak, stress, the init run), as Linux keeps lockdep for debug kernels.
  The headline number is then the everyday one, but bugs that only show
  in normal use on the PC would no longer panic at the first bad order.

**Recommendation: (a).** Print both columns (stage 1 adds the boot word
`nolockdep` for the second), hold the target on the checker-on column,
and make the checker cheap (track P). If the checker-on column still
misses 600 ns after the pass while the checker-off one makes it, decide
between (b) and (c) then, with both numbers in front of you.

### Q2. May a system call clobber the vector registers?

**What it is about.** Each switch between two user threads today saves the
outgoing thread's FPU/SSE/AVX state (XSAVEOPT, 832 bytes) and restores the
incoming one's (XRSTOR): 2 saves and 2 restores per call, about 80 ns on
the PC (BENCH.md: 39 ns per pair). A thread that blocks inside a system
call has **no live vector registers**, if a system call counts as a
function call: Jam OS's system call wrappers are out-of-line functions
(`user/lib/syscalls.S`), and under the x86-64 C calling convention every
XMM/YMM register is the caller's to save across a call. Only the MXCSR
and the x87 control word must survive a call. So for a thread that
switched out from inside a system call, the kernel could save just those
two words, and give it back clean registers (zeros) with its own MXCSR
and control word. Nothing leaks between processes: the incoming
thread always gets either its own saved state or zeros.

What it costs: the rule becomes part of the system call ABI ("a system
call may clobber the vector registers and the x87 stack; it keeps MXCSR
and the x87 control word"). Linux keeps every register across a system
call, so a program that issues the `syscall` instruction itself (inline
assembly) and keeps a vector value live across it would break. Today only
utest's benchmark does that, and it keeps nothing live. M13's POSIX layer
calls through C functions, so ported programs are safe; a port that
inlines raw system calls would need its wrapper to say "clobbers
xmm0-15".

**Options.** (a) the rule, and the drop on a voluntary switch (about
60 ns a call saved); (b) keep every register (today), and gain only what
XSAVEOPT's init and modified tracking already gives; (c) the old lazy FPU
(CR0.TS and a trap on first use): **not offered**, it leaked FPU state
across processes on Intel CPUs (LazyFP, CVE-2018-3665) and its trap costs
more than it saves.

**Recommendation: (a)**, with the rule in ARCHITECTURE and in the
generated wrapper header's comment, and a utest that MXCSR and the
control word survive a call that blocks while the vector registers come
back as zeros (never another thread's values). An exception from ring 3
(a page fault) is not a call: its full state is always saved. PKRU (if
protection keys are ever used) and CET state (if shadow stacks are ever
turned on) are never dropped: see [FPU](#fpu-no-save-on-a-voluntary-switch).

### Q3. How is a reply addressed?

**What it is about.** Fast-IPC kernels like seL4 give the right to answer
a call to the server **thread** that received it (a reply object or reply
capability): if that thread dies, the call fails. Jam OS today addresses a
reply by **(channel end, txid)**: any thread holding the server's end may
answer, with the txid the kernel stamped on the request. M11.6 needs the
second: a successor process that holds the same channel end must be able
to answer a call its dead predecessor had already taken. M11.6 also asks
for two small extras: the receive half may copy the next request into a
buffer the server chooses (its state VMO), and the kernel may write
"the reply went out" into the server's memory before it waits.

**Options.** (a) keep (channel end, txid) and add both extras; (b) reply
objects bound to the receiving thread (what seL4 does). Speed does not
depend on it: the hand-off finds the waiting caller through the channel
end's list of callers by txid, as a reply does today, and switches
straight to that thread.

**Recommendation: (a).** The buffer choice is free (the receive half's
destination is the system call's own argument; a server points it into
its state VMO). The mark is one optional 8-byte user write per reply,
only when the server asks for it (a few ns). Both are in the interface
below; M12 reviews it.

### Q4. How should deadlines get cheaper?

**What it is about.** libos gives every file call a deadline
(`FS_CALL_TIMEOUT`), fat every block call. Stage 0 measured what one costs
(`bench-dcall`, counts): **one more system call** (libos reads the clock
with `clock_get` to compute `now() + timeout`, about 45 ns), **one
sleeper-queue insert and removal** (two more spinlocks), and **one
one-shot timer re-arm** (a write of the TSC-deadline MSR) on every call,
because a call's 5-second deadline becomes the earliest sleeper on an
otherwise quiet CPU. The re-arm is wasted: every CPU's timer is re-armed
at every 100 Hz tick anyway, and a deadline seconds away only needs the
tick.

**Options.**
- (a) Kernel only: a deadline later than the CPU's next tick never
  re-arms the timer (the tick looks at the queue); and a flag in
  `struct channel_call_args` (its `reserved` word becomes `flags`) to
  give the timeout relative, so the kernel reads the TSC itself and libos
  makes no `clock_get` call. genidl's `_until` stubs gain a `_within`
  twin (a timeout instead of a deadline).
- (b) A read-only time page mapped into every process (the TSC-to-ns
  scale and offset), so `now()` in user space is a TSC read and no system
  call at all. More ABI (a new mapping every process gets), and M13's
  `clock_gettime` will want it anyway.
- (c) Both.

**Recommendation: (a) now**, (b) at M13 or for M12 to place: (a) removes
the system call and the MSR write from every file and block call with a
small, local change; (b) is a bigger interface that is better designed
with the POSIX clock calls in view.

### Q6. What does "one copy of the message" mean?

**What it is about.** The roadmap asks for "one copy of the message".
Today a message's bytes are copied four times on their way (user memory
to a stack buffer in the kernel, to the message, to the reader's stack
buffer, to the reader's memory): 8 copies a round trip. Two levels are
possible:
- (a) **one copy in, one copy out**: straight from the sender's memory
  into the message, and from the message straight into the reader's
  memory. 4 copies a round trip; the kernel's own two per message are
  gone. A small, local change.
- (b) **one copy, full stop**: straight from the sender's memory into
  the reader's buffer, through the kernel's map of the reader's pages
  (the reader named its buffer when it started waiting). Saves one more
  small copy a message (about 5 to 10 ns for a 16-byte message), more for
  big ones; costs a walk of the reader's page tables and holding its
  pages against an unmap while the copy runs, on every message.

**Recommendation: (a)** in M11.5. Big data already moves through shared
VMOs and rings, not messages, so (b) saves little on real calls; it can
come back with M12.5's pagers if a bulk path wants it.

## What a call costs today

### Counted (stage 0, QEMU, exact)

The full table is in [BENCH.md](BENCH.md#path-breakdown-m115-stage-0-qemu-2026-10-02)
(counts, so QEMU's are the PC's). For one process-to-process round trip
on one CPU (utest's `bench-call` against `bench-echo`, the line the
target is about): **5 system calls** (the call; the server's read,
write, a read that finds nothing, and its wait), **10 user copies** (5
in, 208 bytes; 5 out, 44 bytes), **4 message copies in the kernel**
(64 bytes), **2 kmallocs and 2 kfrees**, **4 job-counter updates**,
**5 handle-table operations**, **20 spinlocks**, **2 scheduler passes
and 2 switches**, 2 wakes, **2 FPU saves and 2 restores**, **2 CR3
loads**, 1 observer callback. One context switch between two kernel
threads: **1 scheduler pass, 1 spinlock**, nothing else. A call with a
deadline adds a `clock_get` system call, 2 spinlocks, a sleeper-queue
entry and a timer re-arm.

This confirms the research report's reading of the 1407 ns call
(research-arch, 01-architecture-survey.md section 1.1: 5 kernel entries,
8 copies of the message bytes, 2 kmallocs, 5 handle lookups, 2 scheduler
passes) and adds what it couldn't count: **20 spinlocks**, 4 job-counter
updates, and per switch one FPU save, one restore and one CR3 load. The
8 copies are the user copies of the bytes (request in, request out,
reply in, reply out) plus the 4 in the kernel (into the message and out
of it, each way); the other user copies are the argument structs and
the lengths.

### Timed (the PC, to come)

The same run prints a timeline per case on the PC: a TSC mark at each
point of the path, the median of each step over 64 round trips. Each
step includes one mark's own cost, printed with it. The shape of a
process-to-process round trip (34 steps; QEMU's TSC can't time them):

```
client  call -> msg_made -> sent -> block -> sched_in -> sched_locked
        -> sched_picked -> arch_fpu -> arch_done
server  sched_done -> wait_out -> sys_exit(wait_one) -> sys_enter(read)
        -> read(0) -> sys_exit(read) -> sys_enter(write) -> msg_made
        -> sent -> sys_exit(write) -> sys_enter(read) -> read(1)
        -> sys_exit(read) -> sys_enter(wait_one) -> wait_in -> block
        -> sched_in -> sched_locked -> sched_picked -> arch_fpu -> arch_done
client  sched_done -> reply -> sys_exit(call) -> (user) -> sys_enter(call)
        -> call
```

## The switch regression, first

At M8.6 every line through a context switch got slower than at M5.5:
the switch 30 -> 92 ns, each wake-and-switch line about +120 ns
([BENCH.md](BENCH.md#m86-pc-2026-10-02)). Every M11.5 number is built on
the switch, so it is found first.

**What is known.** The code of the switch grew a little since M5.5
(`account_switch`'s TSC read and CPU-time sums, the busy flag before the
dequeue, one more test hook, `enqueue`/`dequeue` no longer inlined): by
reading it, 10 to 15 ns, not 60. The per-switch extra of the M8.6 run is
close to **one cache line fetched from another core per switch** (the
M8.6 run measured 105 ns for a cache line round trip P->P2, so about
50 ns one way). Two candidate kinds:

- **the environment**: M5.5's run was the boot menu's Benchmark entry
  (nothing else running); M8.6's was `bench` from the shell with user
  space live; and since M8.5 the kernel starts the other CPUs itself
  (INIT-SIPI-SIPI, the APs take the BSP's MTRRs and APIC mode) where
  Limine did before;
- **a line shared with another CPU** on the switch path (struct
  fields or arrays packed across CPUs: `trace_pos[]` in `kernel/sched/sched.c`
  is 4-byte entries, 16 CPUs to a cache line; the run queues are 560-byte
  entries, not cache-aligned, so neighbours share a line), which only
  costs when another CPU writes it between two switches.

**Step 0 (one flash of this branch, no more builds).** Three boots, the
same build:
1. Tests > Benchmark (as M5.5 ran it): the `context switch` line and the
   `path: context switch` block;
2. a normal boot, `bench` from the shell (as M8.6 ran it): the same lines;
3. Tests > Benchmark with `smp=loader` typed into the entry (E in Limine's
   menu: Limine starts the APs, as before M8.5): the same lines.

If 1 is near 30 ns and 2 near 92, it is the live system: the timeline of
2 shows which step grew and the next stage finds what writes that line.
If 3 is near 30, it is the AP start-up. If all three are near 92, it is
the code: the timeline names the step.

**The timeline's switch steps** (`path: context switch`, 14 steps for a
round trip of two switches) and what each holds, so a step that grew
names its code:

| Step | Code (kernel/sched/sched.c unless named) |
|---|---|
| `yield -> sched_in` | `thread_yield`'s call |
| `sched_in -> sched_locked` | `irq_save`, the run queue's `spin_lock` with the lock checker (`kernel/debug/lockdep.c`) |
| `sched_locked -> sched_picked` | enqueue prev, the busy flag, `pick_best`/dequeue, the `on_cpu` wait, state and slice, `account_switch` (TSC read), `trace[]` and `trace_pos[]` |
| `sched_picked -> arch_fpu` | `arch_thread_switch` (`kernel/arch/x86_64/uentry.c`): the TSS and `kernel_rsp`, FPU (none for kernel threads) |
| `arch_fpu -> arch_done` | `aspace_switch` (nothing between kernel threads) and the test hook |

## The design

### The pieces, and what each removes

From the counts above, for the same-CPU process-to-process round trip:

| Piece | Today | After | Where |
|---|---|---|---|
| reply-and-wait (server) | read, write, read (fails), wait_one: 4 system calls | 1 | new system call |
| system calls a round trip | 5 | **2** | |
| handle lookups | 5 | 2 (the reply and the next read share one when it is the same channel) | |
| failed reads | 1 | **0** (the receive half reads in the kernel before it would block) | |
| message bytes copied | 8 | **4** (user to message and message to user, each way; no stack bounce buffer) | `kernel/abi/sysc_channel.c`, `kernel/object/channel.c` |
| kmalloc + job charge per message | 2 + 4 | **0** when the reader is waiting (the message goes into the waiting thread's slot); as today when it has to be queued | |
| scheduler passes | 2 full | 2 direct hand-offs (no enqueue, no pick, no placement) | `kernel/sched/sched.c` |
| FPU saves + restores | 2 + 2 | 0 + 2 cheap (control words only, Q2) | `kernel/arch/x86_64/fpu.c` |
| spinlocks | 20 | about 8 to 10 (per side: the handle table, the channel pair and an endpoint, the run queue), each cheaper (Q1) | |
| CR3 loads | 2 | 2 (isolation keeps them), with `pcid_load`'s bookkeeping trimmed | `kernel/arch/x86_64/pcid.c` |

A budget for the PC (estimates; stage 0's timeline replaces them): 2
kernel entries 60 ns, argument and data copies 80, 2 handle lookups 20,
2 messages without allocation 20, 2 address-space switches 90 (68 each
today), FPU 20, 2 switch cores 60 (if the regression is fixed), the
channel locks and hand-off checks 60: **about 410 to 500 ns**, with the
checker cheap. With the checker as it is, add about 150.

### Reply-and-wait

One new system call, `channel_reply_wait`, with an argument struct (more
than six arguments: `@struct` in `abi/syscalls.def`):

- **the reply**: a channel end, its bytes (the txid first, as every reply
  today) and handles. `HANDLE_INVALID`: no reply (a server's first wait).
  The reply is a normal write: it goes to the caller waiting for that
  txid on the peer end, or is queued as any message is.
- **the next request**: read one message from a channel end into the
  caller's buffers (the server's choice of buffer: M11.6's state VMO
  slot). If none is queued, wait for one; with a port given, wait on the
  port instead and return its packet (a server with many channels, like
  fat), and the next call reads from the channel the packet names. The
  read happens in the kernel before it would block, so a server never
  makes a read that finds nothing.
- **the mark** (optional, M11.6): a user address; the kernel writes 1
  there (8 bytes) after the reply is sent and before it reads or waits.
- a deadline, as every wait has.

Errors: those of a write for the reply half (then nothing is read), those
of a read or a wait for the second. `ERR_PEER_CLOSED` from the reply
half doesn't stop the read (a client that went away is not the server's
problem), and the result says which half failed.

**Replies stay addressed by (channel end, txid)** (Q3). Nothing in the
kernel remembers which thread read a request. A successor holding the same
channel end answers its predecessor's calls exactly as today.

genidl: `<proto>_serve` (single-channel servers) becomes a loop of
reply-and-wait calls; the handlers and `<proto>_reply_<method>` are
unchanged. A port-based server's loop (fat, the mixer, devmgr) moves when
its owner moves it: fat and the mixer in M11.6, the rest in their own
time. The old calls stay: a server may still read, write and wait.

### Direct hand-off

When a thread wakes another and then blocks at once (the client's
request, the server's reply-and-wait), today it queues the wakee on its
own CPU (wake-affine), blocks, and `schedule()` takes the wakee back off
the queue. The hand-off does the same in one step: the waker records the
wakee as this CPU's next thread (`rq->handoff`) instead of queueing it,
and the `schedule()` that follows switches to it without touching the
run queues or placement. It is how every wake-affine wake ends, not a
path of its own for one system call: a request that wakes a server
waiting on a channel, on a port, or in reply-and-wait, and a reply that
wakes its caller, all go through `thread_wake_sync`. A server on another
CPU (pinned there, or busy) is woken as today: no hand-off across CPUs.
Conditions, else the normal wake:

- the wakee may run on this CPU (its affinity) and nothing of higher
  priority than the wakee is queued here;
- the waker really blocks right after (it is inside `channel_call` or
  `channel_reply_wait`); if it doesn't (the wait is satisfied at once),
  the recorded wakee is queued normally before the waker returns;
- the wakee keeps its own priority, and the CPU time is charged to
  whoever runs; the slice continues (it is not refreshed), so a
  ping-pong pair can't hold a CPU from others past one slice.

It uses `switch_context` as every switch does, so nothing about the
switch's safety rules changes (the run queue lock held across the
switch, `on_cpu`), and kernel shadow stacks, if they come, are still one
change in one place.

With replies addressed by txid the hand-off on the reply side finds the
caller the way a reply does now: `hand_over_locked` looks up the waiter
by txid on the caller's end; the hand-off just switches to that waiter's
thread instead of queueing it.

### One copy

Per Q6 (a). `sys_channel_call`, `sys_channel_write` and the read side copy the bytes
user to a 512-byte stack buffer to the message (2 copies) and back
(2 more). After: the message is allocated first and the bytes are copied
from user memory straight into it (`copy_from_user`, no lock held), and
out of it straight to the reader's buffer. When the reader is already
waiting (reply-and-wait, or a `channel_call` waiting for its reply) the
message goes into a slot of that thread's (one per thread, sized for the
common small message, e.g. 256 bytes; bigger ones are allocated as
today) and is never queued: no kmalloc, no job charge (nothing is held
that a sender could pile up: one slot per waiting thread). Charging
stays exactly as today for every queued message.

A message in registers (seL4's short IPC, no memory copy at all for up to
a few words) is a different system call ABI; it is left to M12 to weigh,
with this pass's numbers.

### FPU: no save on a voluntary switch

Per Q2. Each user thread gets a state: **live** (its registers matter:
it was switched out from user mode, by an interrupt, or from an
exception) or **called** (it was switched out anywhere inside a system
call: blocked, or preempted while the kernel ran the call for it; its
user registers are not live in either case). A switch out of a
called thread saves MXCSR and the x87 control word only; a switch into a
called thread restores a clean state with those two (one XRSTOR from a
per-CPU template, or none when this CPU's registers already belong to
the same process and hold the same control words). A live thread is
saved and restored in full, with XSAVEOPT as today. The fpu_owner
optimisation (no restore when the CPU still holds the thread's state)
stays.

On this CPU: **PKU** (user protection keys) is present but not enabled
(XCR0 is 7); if a later milestone uses it, PKRU is per-thread state
that is never dropped (it is part of what memory the thread may touch,
not a scratch register). **PKS** (supervisor keys) is present and not
used; it lives in an MSR, not in the XSAVE area. **CET** (shadow stacks,
branch tracking) is present and not enabled; turning it on later moves
the save to XSAVES/XRSTORS with IA32_XSS (CET's user state is a
supervisor XSAVE component) and adds the shadow stack switch to
`switch_context`; its state is never dropped either. M11.5 enables none
of them and keeps XSAVEOPT.

### Cheaper deadlines

Per Q4 (a): in `kernel/sched/wait.c`, a new earliest sleeper whose
deadline is after this CPU's next tick doesn't re-arm the timer (the tick
re-arms it and looks at the queue); and `channel_call_args.flags` gets
`CHANNEL_CALL_TIMEOUT` (the deadline field is a timeout from now), so a
call with a timeout needs no `clock_get`. genidl adds `_within` stubs;
libos's file calls and fat's block calls use them. The sleeper queue
insert and removal stay (two locks): a call that may wait must be
findable by its deadline.

### Smaller items

- **`pcid_load`'s bookkeeping**: the address-space switch went 46 ->
  68 ns with PCIDs (BENCH.md M5.5): the epoch check, the slot search and a
  sequentially consistent generation read on every load. A per-address
  space hint of the slot it last had on this CPU skips the search.
- **The lock checker's fast path** (Q1): no `irq_save`/`irq_restore`
  when interrupts are already off (the scheduler, every `_irqsave`
  caller), the held list as a stack (release is almost always the top).
- **No clock read in a wait with no deadline**: `channel_call` and
  `object_wait_one` call `uptime_ns()` on every pass of their wait loop
  even for `DEADLINE_NEVER`.
- **`nolockdep`**, a boot word for the checker-off column.

### What is given up

Nothing in isolation: every call still crosses into the kernel and
switches address spaces; every server is still its own process. Nothing
in restart: replies stay addressed by channel end and txid (Q3); a
killed server thread inside reply-and-wait finishes the call it is in,
as every thread does, so a request is either still queued or wholly in
the server's buffer. Accounting: a message handed to a waiting thread is
not charged to the sender's job, because it can't accumulate (one per
waiting thread).

## Stage 0, built: the per-call breakdown

**What it is** (branch `m11.5-perf`):

- `kernel/include/jam/pathstat.h`: probes `PATH_COUNT`/`PATH_ADD` (a
  counter) and `PATH_MARK` (a TSC timestamp at a named point), plus forms
  for inside a switch (`PATH_SW_*`, counted for prev or next) and for
  system calls by number. Disarmed, a probe is one load and a branch not
  taken; `make KTESTS=0` removes them. They sit on the system call entry
  and exit, user copies, message copies, kmalloc/kfree, the handle table,
  every spinlock, the scheduler (pass, switch, wake, IPI), the FPU,
  CR3 loads and PCID flushes, job charges, the sleeper queue and timer
  re-arms, channel reads that find nothing, observer callbacks, and the
  marks of the call and switch paths.
- `kernel/test/pathstat.c`: the trace. It follows up to four member
  threads or processes, counts only between two boundaries of the lead
  member (a call or a yield: so warm-up, start-up and exit never count),
  leaves interrupt handlers out (the interrupt itself is counted), keeps
  up to 8192 timestamps.
- `kernel/test/bench_path.c`: `bench` ends with a breakdown of six cases
  (switch, kernel call, user call, user call with a deadline,
  thread->thread, user call P->P2): counts per call over 1024 calls after
  256, and a timeline from 64 of them (the round trips of the usual
  shape, each step's median). `path:` lines in the log, one `bench: path`
  summary line per case in the RESULTS box.
- `kernel/test/test_pathstat.c`: the trace's rules (members only, the
  window, interrupt handlers left out, one trace at a time) and today's
  counts per call, pinned.
- `user/tests/utest/bench.c`: `bench-dcall` (a call with a deadline per
  call, as libos makes them), timed as a new `bench` line too; the call
  benchmarks' warm-up reads the clock once every 64 calls (it read it
  every call, which the trace would have counted).
