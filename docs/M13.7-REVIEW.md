M13.7's independent review ([M13.7's plan](M13.7-PLAN.md), the PR row): the
trust path that `pkg install chromium` goes through, from the bytes the
network sends to a program that runs. **Findings only**: this track changed
no code (each fix needs its own tests, so each is a track of its own).

Looked at hardest, as the row asks: what is signed and by which key, and
whether an old signed index or package comes back; every parser of
repository bytes (HTTP, INDEX, VULNS, manifests, the archive, ELF notes, the
journal); whether a program can run with grants its approval didn't cover;
what `bin/pkg` holds while it parses the network; and what a cut at any
point, or a hostile journal, leaves.

Severity, as in the earlier checks: **High** loses or corrupts what was
answered, or is a hole a program can use; **Medium** is wrong behaviour the
system will meet; **Low** is a wart, a limit, or a hole only the shell, a
compromised `bin/pkg` or a crafted disk can reach.

Counts: **2 High, 5 Medium, 11 Low.** None is fixed here.

## Looked at and found sound

- **The signed texts.** `pkg_signed_text` reads in the order PO3 asked: the
  size bound, the exact first line, the bytes, the last line's shape, the
  Ed25519 signature over every byte before it (Monocypher's check, which
  refuses a non-canonical S), and only then a field; a bare `signature`
  line is refused with a key. The first lines (`jamos-pkg 1`, `jamos-ports 1`,
  `jamos-vulns 1`, update's `jamos-update 2` under its own key) keep any
  signature from being read as another format's. The replay rule keys on
  the SHA-256 of the whole text, signature included, so two texts with one
  serial are refused.
- **The grammars.** Every line in its fixed place, every count checked
  before its slot is written (the one exception is PR8), sizes bounded
  (4 MiB a manifest, 1 MiB an index or VULNS, 1 GiB a file, 2 GiB a
  package's files, 4 GiB an archive), orders strict, the rules across lines
  (every `runs` resolves inside the index, every package has its `src`).
  Paths: 1 to 255 bytes of 0x21..0x7e without FAT's bad bytes, no empty,
  `.` or `..` part (so no absolute path), no part ending in `.`, no `+`
  first; no two equal by FAT's names and no file where another needs a
  directory, inside one manifest. A list's one escape is `\x0a`.
- **The archive.** No ustar header is parsed: each is rebuilt from the
  signed (path, mode, size) and compared whole, so links, directories,
  devices, pax and GNU headers, owners and times can't pass; padding and
  the two end blocks are checked and nothing may follow. The stream and the
  whole-package readers share the member rules; a table is compared with
  the one its program's bytes made. The whole package is held to the
  index's size and SHA-256 before init sees it, and the second fetch to the
  manifest the question showed.
- **The network.** No redirect, `200` only, a head of at most
  `HTTP_HEAD_MAX` bytes and a bounded number of lines, Content-Length
  agreeing with itself and with the index, Transfer-Encoding winning, a
  chunked decoder bounded at each part, and deadlines on everything
  (resolve, connect, head, an idle body, the whole at a floor of 16 KiB a
  second), each ended by Ctrl+C. The repository's file names are derived
  from the index, never read from it.
- **init's approve.** The manifest is copied out of bin/pkg's VMO before it
  is read; each program is read once, in 128 KiB pieces, and the SHA-256
  and the page table made together; the table written is init's own; the
  list is read from the notes through `checked_read`, every page checked
  against that table, so it is the list of the bytes hashed; the refusals
  are judged on the parsed list; nothing is written unless every program
  passed. At run time `/svc/exec` and the shell seal the file against its
  table and read the list from the sealed VMO, so a file changed after its
  approval can't run with any list, and `dp_path_same`'s aliases change only
  which line is the key, never which bytes run.
- **The guard.** `FS_VIEW_GUARD_PKG` folds `pkg` as FAT does, covers
  opens that write, makes, removals, renames and links by either name, and
  writable subviews at or under it; extfs judges it where a path resolves,
  directory channels too (their place found by climbing to the volume's
  root). Every `:w` grant has it, on every mount.
- **The journal and the settle.** The journal is strict and canonical,
  ends with its own SHA-256, and moves by `journal.new`; init and bin/pkg
  give each step the same meaning and run the same order, every step can
  be done twice, and every file they touch is named by a signed manifest
  whose SHA-256 the journal names (by the text of its path: PR9). A cut
  journal, or one written by a hostile hand, can make the settle revoke
  lines or remove a record, which bin/pkg could do anyway; it can't add an
  approval.
- **The question.** Only the shell asks, one key, keys typed ahead
  dropped; bin/pkg has no `-y`, and what it shows is printable ASCII from a
  signed manifest. PATH has `/pkg/bin` last, so a package can't take a
  boot image program's name.

## Questions for the owner

1. **PR5, what bin/pkg holds.** (a) Split bin/pkg: a fetcher with the
   network and no mounts, an installer with the mounts and no network; or
   (b) init checks every file's hash at approve and makes the moves itself,
   so bin/pkg writes only a staging area. **Recommended: (a)**; (b) alone
   still leaves the live prefix to the process that read the network.
2. **PR2, raised starts.** (a) A program says in its list that it may be
   started by a caller with less (a want word), and `/svc/exec` refuses a
   raised start of one that doesn't; or (b) leave `/svc/exec` as it is and
   make each deputy check AT_SECURE. **Recommended: (a)**, safe by default
   for the interpreters and shells to come; Chromium then needs neither
   (the owner's `chrome` isn't raised once the launcher's list is the
   browser's, and the browser's children are its own).
3. **PR3, a program that runs during its upgrade.** (a) Refuse the upgrade
   before the commit point while a program of the package runs; or (b)
   versioned directories (`lib/chromium-<version>/`, a pointer moved last)
   so the old version keeps working until it quits. **Recommended: (a)
   now**, (b) when Chromium updates often enough to need it.
4. **PR6, the rollback floor.** Where the floor lives: init's own record in
   /data/etc of the highest version it approved per package, a minimum
   serial or date in the image, and an expiry on INDEX and VULNS.
   **Recommended: all three**, the expiry 30 days, `pkg update -f` the way
   past it.
5. **PR1, writable boot media.** (a) Refuse `/esp` writable (and a writable
   `*` that includes it) to every program from /data, whatever the owner
   says; or (b) allow it with a question of its own. And `/usb* rw`, which
   reaches another stick's ESP? **Recommended: (a)**, and a writable view
   of any partition of the ESP's type refused the same way.
6. **PR16, changing the ports key.** Let `/boot/ports.pub` hold more than
   one key (the first signs what is installed from now on, the others are
   kept for records and removal)? **Recommended: yes**, with `pkg` saying
   which packages are under an old key.
7. **PR18, the browser's files.** Add a `mount /home rw` want (init's view
   of /jam/home) so the browser's list can name its home and no more?
   **Recommended: yes**, before CR-d ships the browser.
