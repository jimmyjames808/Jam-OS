approvals) built: [PO5 notes](#po5-notes). PO6 (bin/pkg) built: [PO6 notes](#po6-notes). PO7 (the shell and `update`) built:
[PO7 notes](#po7-notes). PO9 (zlib, bzip2, xz and libarchive, installed through `pkg`) built: [PO9 notes](#po9-notes). PO13 (packages on
`/jam`, and big ones) built: [PO13 notes](#po13-notes). Written against main fcc39f93
(the ROADMAP commit that put porting first), with M13's P1 (sbase and Lua)
and P2 (libc-test) running on their branches and X2 (tinyssh) not started.
**Waiting for the owner's answers to the questions below.** M13.6 (the
Unix filesystem) is being planned beside this one by another agent; where
this plan needs it, it says exactly what, and works on FAT32 until then.

Goal ([roadmap](ROADMAP.md#now), "porting first", the owner, 2026-10-11):
**porting a program becomes routine.** A recipe per program (its source,
version, hash, licence, patches, dependencies and build steps), a tool
that builds recipes in dependency order, packages, and `pkg` on Jam OS to
install, upgrade and remove them. Jam OS writes only its system's own
programs; everything else is ported ([ROADMAP: Not planned](ROADMAP.md#not-planned)),
so this is the road every other app takes.

**Done when:**
- the four ports of M13 (sbase, Lua, libc-test, tinyssh) are recipes in the
  new format, the boot image is built through it, and every test they had
  still passes;
- a new port is a directory with a recipe in it (no Makefile edit), and a
  porter's guide says how to write one;
- on the PC, `pkg install vim` fetches from the Mac's repository: ncurses'
  terminfo first (its dependency), each program's list shown and approved
  with one answer, `vim` runs from the shell in a terminal window and over
  SSH; `pkg upgrade` takes a new revision, `pkg remove` takes it all back
  (files and approvals); `pkg audit` reports a planted advisory;
- a package or index that is changed, rolled back, or signed by another
  key is refused, by `pkg` and again by init; QEMU killed at every step of
  an install or upgrade leaves the old version or the new one, never a
  mix, and the next `pkg` finishes or undoes it;
- the first ladder of ports (zlib, bzip2, xz, libarchive, make, ncurses,
  vim) is built, packaged and tested on the PC through `tools/remote-test.sh`;
- every package carries its licence text; the boot image carries the
  notices of the ports in it; a GPL package's source is served beside it;
- and, as every milestone: All tests and `soak 10` on the PC.

## What M13.7 is not

- **No new POSIX.** What a port needs from the layer (signals, sockets,
  ptys, `fork`) is M13's, M13.5's or a follow-up's; a rung of the ladder
  that needs one waits for it (the table in [The first ports](#16-the-first-ports)).
- **No building on Jam OS.** Ports are cross-built on the Mac with
  `tools/jamos-cc` until M15; this plan keeps the formats readable there and
  says what M15 needs ([After M15](#15-after-m15-building-on-jam-os)), nothing more.
- **No dynamic linking** (M14.5): every port is static. Libraries are
  build-time only.
- **No public package repository.** The owner's Mac serves the owner's PC.
  The formats allow a public one later; its key, hosting and policy are
  not decided here.
- **No Linux binaries**, no binary packages from other systems: every
  package is built from source by the recipe ([ROADMAP: Not planned](ROADMAP.md#not-planned)).
- **No config-file merging** (Debian's conffiles): a package never ships a
  file the owner edits; programs read the owner's own files from `/data`.
- **No new filesystem work.** FAT32 now; M13.6's filesystem when it lands.

Two facts found while reading, both of which shape this plan:

- **The boot image is nearly full.** On P1's branch, bootfs is 31.8 MB
  (13.9 MB on main): its 63 sbase programs take 16 MB, about 250 KB each,
  and Lua 0.57 MB. `update` refuses a boot image over 32 MiB
  (`UPDATE_FILE_MAX` in `user/include/update.h`, the kexec region's share).
  So **ports can't keep going into the boot image**: one more port of
  sbase's size and `update` stops working. Packages on `/data` are not a
  convenience but the only room there is (and sbase itself should be one
  multi-call program: track PO2, with upstream's own sbase-box).
- **A static POSIX program costs about 250 KB at least.** sbase's `true`
  is 253 KB, its `ls` 301 KB, its `sed` 348 KB. The likely cause is the call layer's table
  (`[SYS_x] = lx_x` in user/posix/sys/calls.c), which makes every handler
  and all it calls reachable, so `--gc-sections` keeps the whole layer in
  every program. Not M13.7's to fix (a follow-up for M13's R1 review), but
  every package size below includes it. *Unsure*: measured only by the
  sizes; nobody has looked at a link map yet.

Eight systems, read for what Jam OS can use. None fits whole: none
targets a capability kernel whose programs need approval, and none

**What we take**, in one list: a short declarative recipe with build
hooks (Alpine, Void, Serenity); the source's hash and size (FreeBSD);
build styles (Void, Redox); host tools apart from target libraries (Void,
Redox); a reason on every patch, checked by a lint (pkgsrc, Serenity);
only declared dependencies visible to a build (pkgsrc's buildlink3,
poudriere); a revision for rebuilds of one version (FreeBSD, Alpine); a
test in every recipe (Homebrew); per-file hashes under one signature
(pkgar, FreeBSD, Void); CVEs fixed listed in the recipe (Alpine) and a
signed vulnerability list checked on the machine (FreeBSD, pkgsrc); a
package area only the installer writes and one state file for what is
installed (Haiku). What is our own: approval by the owner's key and the
program's list, the page-hash tables, and everything FAT32 forces.

## The design

### 1. Two places a port goes

| | System ports | Packages |
|---|---|---|
| What | what the system needs before `/data` is there, what a test entry runs, and what needs a grant `allow` refuses (`svc session`, `svc net listen low`, `svc init`, ...) | everything else |
| Today's | sbase, libc-test, tinyssh (bin/sshd needs `svc session` and port 22); M13.5's mksh later | Lua moves here (Q4) |
| Built by | `make`, every build, through the same tool | the tool, on demand (make ports, a new target) |
| Sources | vendored in `third_party/` (a build never touches the network) | fetched by hash into a cache (Q2) |
| Lands in | the boot image (`/boot/usr/bin`) | the package prefix on `/data` ([section 9](#9-installing-upgrading-removing)) |
| Approved by | the build (`tools/checkwants.py`) | the ports key's signature and the owner's one answer at install (Q7) |
| Updated by | `update` | `pkg upgrade` |

One recipe format serves both; a recipe's `place` line says which. The
boot image stays small: a system port is the exception, chosen per port
(Q4).

### 2. The recipe

**Where**: a new top-level directory, **ports/**, one directory per port
(flat, as Serenity's Ports/; a `category` line for listing only):

```
ports/zlib/
    recipe            the recipe (below)
    patches/          NNNN-<what>.patch, applied in order, each with a header
    override/         whole files that replace upstream's (OVERRIDES lists them)
    OVERRIDES         as user/posix/musl/OVERRIDES
    wants/<program>   a program's list, when it isn't the default `posix`
    test              what to run on Jam OS to test it (section 14)
    build.sh          only for `style custom`: the build's shell functions
ports/config.site     autoconf's answers for cross builds (section 5)
ports/jamos.cmake     CMake's toolchain file
ports/jamos.meson     Meson's cross file
ports/keys/           the public halves of signing keys a public build may carry (none yet)
```

**The format**: lines of `<key> <value>`, `#` comments, no quoting, no
variables but the few the builder defines (`$version`, `$name`); a parser
is 150 lines of C, so the M15 builder (or a C reader of recipes on Jam OS)
needs no TOML or shell. Build commands are not in it: they are the build
style's, or build.sh's functions. zlib's whole recipe:

```
name        zlib
version     1.3.1
revision    1
summary     the deflate compression library, and minigzip
homepage    https://zlib.net/
licence     Zlib
licence-file LICENSE
source      https://zlib.net/zlib-1.3.1.tar.xz 1265724 38ef96b8dfe510d42707d9c781877914792541133e1870841463bfa73f883e32
mirror      zlib-1.3.1.tar.xz
place       package
style       configure-plain       # zlib's own configure, not autoconf: CHOST, CC, --static
configure   --static --prefix=$prefix
program     bin/minigzip          # wants/minigzip, or the default `posix`
library     lib/libz.a include/zlib.h include/zconf.h
cpe         cpe:2.3:a:zlib:zlib
fixed       CVE-2022-37434 1.2.13 # (secfixes: what this or an earlier version fixed)
```

(The size and hash above are placeholders of the right shape; the track
that writes the recipe fills in the real ones.)

The keys:

| Key | Meaning |
|---|---|
| `name`, `version`, `revision` | `revision` counts rebuilds of one version (a patch, a dependency's fix, a new sysroot) and resets to 1 with a new version |
| `summary`, `homepage`, `category` | for `pkg info` and the generated list of ports |
| `licence`, `licence-file` | an SPDX expression (the builder knows the list of identifiers it accepts); the file(s) in the source that hold the text, copied into the package (section 12) |
| `source <url> <size> <sha256>` | a tarball; several lines for several files. `source git <url> <commit>` for a project with no tarballs (a commit hash, never a branch or tag) |
| `mirror <file>` | the copy kept in the owner's distfiles mirror (section 3) |
| `vendored <dir>` | a system port's source in `third_party/<dir>` instead of `source` (its hash is the tarball's, in `third_party/VERSIONS.md`) |
| `local <dir>` | a port of Jam OS's own code (a test program such as `ports/cr-hello`): its source is the port's own `files/` directory, instead of `source` or `vendored` (added by CR's CT1) |
| `place boot` / `place package` | section 1 |
| `style` | `configure` (autotools), `configure-plain` (a hand-written configure), `make`, `cmake`, `meson`, `custom` (build.sh's `build` and `install`) |
| `toolchain clang` | built by `tools/jamos-clang` and `tools/jamos-clang++` (clang and lld, C++ with LLVM's libc++) instead of `tools/jamos-cc`, under the same tool names; the port must `needs llvm-runtimes` (CR's CT1, [CR-PLAN](CR-PLAN.md#1-the-toolchain)). `toolchain clang rust` adds Chromium's pinned Rust: the build gets `$JAMOS_RUST` (the directory with `bin/cargo` and `bin/rustc`; `tools/cr/toolchain.sh rust` unpacks it) and its `build.sh` runs cargo, linking by the port's clang wrapper (CR's CT2, [CT2 as built](CR-PLAN.md#ct2-as-built-2026-10-14)) |
| `configure`, `make`, `cmake`, `meson` | the style's extra arguments |
| `needs <port> [>= <version>]` | a library this port links (its staged headers and `.a` are visible to the build: section 5) |
| `runs <port> [>= <version>]` | a package that must be installed for this one to run (data, or a program it starts) |
| `host <tool>` | a tool the Mac must have (`cmake`, `pkgconf`, `gmake`, `perl`); the builder checks before starting and names what is missing |
| `program <path> [<wants file>]` | an executable in the package and its list; the builder links every program with its list (`jamos-cc --jamos-wants`); an executable the install made with no `program` line is dropped and named, so nothing is packaged as a program without a list chosen for it |
| `library`, `files <glob>` | what else is kept from the staged install; anything not named is left out, and the builder says what it dropped |
| `subpackage <name> <glob>...` | a second package from the same build (ncurses' terminfo data apart from its programs) |
| `multicall <program> <name>...` | one program run under several names (sbase: track PO2) |
| `cpe`, `fixed`, `not-affected` | section 13 |

**A lint** (`ports.py lint`, in `make check` for every recipe): every key
known, the licence an SPDX identifier, every patch with its header, every
override hash current, every `needs` and `runs` a recipe, no cycle, the
size and hash present, no `program` without a list it can pass.

### 3. Sources: vendored or fetched

Vendoring every port's source in git does not scale: vim's tarball is
about 17 MB, ncurses 3.6 MB, a Python 27 MB, and each version change is a
commit of the whole tree. Fetching does not need it: a source named by
its size and SHA-256 is as fixed as a vendored one.

- **Packages** (Q2's recommendation): the builder downloads each
  `source` into a cache on the Mac (`~/.cache/jamos/distfiles/`), checks
  size and SHA-256 before anything opens it, and never uses a file that
  fails. A distfile that has vanished upstream (URLs rot) comes from the
  owner's **mirror**: a directory (`~/jamos-distfiles/`, copied to the PC
  host and backed up) that the builder fills with every distfile it
  fetches. A public mirror is a later decision.
- **System ports** stay vendored in `third_party/`, so `make` never needs
  the network and a public build is made from the git tree alone.
- `source git` checks out the named commit into the cache (as a tarball
  of it, hashed: a later fetch of the same commit must give the same
  hash, or the builder stops).

### 4. Patches and overrides

Two ways to change upstream's code, both kept:

- **Patches** (`patches/NNNN-<what>.patch`, unified diffs, applied in order
  with `patch -p1 --fuzz=0`): for small changes across files (a
  configure check, a Makefile line, an `#ifdef __linux__`). Fuzz 0 means a
  patch that no longer applies exactly stops the build: a new version is
  read, not guessed at. **Every patch starts with a header** (the DEP-3
  fields Debian uses, a subset): `Description:` (what and why),
  `Forwarded:` (sent upstream, where, or `not-needed` with the reason: "Jam
  OS has no fork"), and the lint refuses a patch without them.
- **Overrides** (`OVERRIDES` and `override/`, the musl format and
  `tools/checkoverrides.py`'s check): for a file we rewrite whole or in
  its heart, where a patch would be most of the file (sbase's three `fork`
  sites, tinyssh's three). Their advantage is the check: an upstream
  release that changes the file at all stops the build, even where a
  patch would still apply.
- **musl stays on overrides** (`user/posix/musl/OVERRIDES`): it is the
  system's C library, built by `user/posix/posix.mk`, not a port. Its
  overrides need one addition this plan uses (section 13): a **new file**
  (upstream's iconv fix adds `src/locale/gb18030utf.h`), which the format
  can't say today; a line with `-` for the upstream hash means "a file
  upstream doesn't have".
- **The rule** (Q3): a patch by default; an override when the change is
  more than about half of a file, or a fork replaced; never both on one
  file.

### 5. The builder

**tools/ports.py** (Python, as the rest of tools/: Q12), run on the Mac
(and on the test host: "Two build hosts" below):

```
ports.py build <port>...      build, in dependency order, what is out of date
ports.py package <port>...    build, then make the packages (section 6)
ports.py repo                 the repository: every package, the index, signed (section 7)
ports.py lint [<port>...]     section 2's lint
ports.py audit                section 13
ports.py fetch <port>...      only download (for the mirror)
ports.py graph                the dependency order, printed
```

and make ports = `ports.py repo` for every `place package` recipe; the
Makefile calls `ports.py build` for `place boot` ones as part of `make`.

**A build, step by step**, in build/ports/<name>/:

1. **Order.** The recipes' `needs` and `runs` form a graph; the builder
   refuses a cycle (with the cycle printed) and builds a port only after
   everything it `needs`.
2. **Out of date** is decided by a stamp: the SHA-256 of the recipe, its
   patches, overrides, lists and build.sh, the distfiles' hashes, the
   sysroot's stamp (`build/sysroot` changes with musl and the call layer),
   and each `needs` port's own stamp. Same stamp, no build.
3. **A clean tree every time**: the source unpacked afresh into work/,
   patches applied, overrides copied in (after their check). No build
   reuses another's tree (poudriere's rule): a port that builds only on a
   second try is caught.
4. **What the build sees** (pkgsrc's buildlink3, Void's split): a sysroot
   made for this port, build/ports/<name>/sysroot/: `build/sysroot`'s
   files plus the staged headers and `.a` of exactly the ports it
   `needs`, nothing else. `jamos-cc` gets it as `JAMOS_SYSROOT`.
   pkg-config is the Mac's `pkgconf` with `PKG_CONFIG_SYSROOT_DIR` and
   `PKG_CONFIG_LIBDIR` pointed into it, so a library the port didn't
   declare is not found even if the Mac has it.
5. **The build style** runs the upstream build:
   - `configure`: `./configure --host=x86_64-linux-musl --build=<the Mac's>
     --prefix=$prefix --disable-shared --enable-static` with
     `CC=jamos-cc`, `AR`, `RANLIB`, `STRIP` the cross tools', and
     **`CONFIG_SITE=ports/config.site`**: the answers configure can't find
     by running a test program on the Mac (`ac_cv_func_fork=no`,
     `ac_cv_func_vfork_works=no`, `ac_cv_func_mmap_fixed_mapped=yes`,
     `ac_cv_file__dev_zero=yes`, the `sizeof`s, ...), in one place for every
     port (pkgsrc's platform file, cut down). The triplet stays
     `x86_64-linux-musl` (M13's Q10): a `jamos` triplet in GNU's
     `config.sub` would be cleaner but means patching `config.sub` in every
     port until upstream takes it. `jamos-cc` defines `__jamos__` and not
     `__linux__`, so a port's Linux-only code (`/proc`, `epoll`'s
     Linux-isms, `inotify`) is not taken by `#ifdef __linux__`; configure's
     link tests find what musl and the layer really have.
   - `cmake`: `-DCMAKE_TOOLCHAIN_FILE=ports/jamos.cmake` (system name
     `Linux` with the cross compiler and the port's sysroot, static, no
     try-run: answers in the file).
   - `meson`: `--cross-file ports/jamos.meson`.
   - `make`: `make CC=... AR=... PREFIX=... DESTDIR=...` with the Mac's
     GNU make (`gmake`; the Mac's own make is 3.81).
   - `custom`: build.sh's `build` and `install` functions, run by `/bin/sh`
     with the same variables.
   Each runs with `SOURCE_DATE_EPOCH` set from the recipe's commit, so
   timestamps baked into a program are the same on every build.
6. **Install** into build/ports/<name>/stage/ (`DESTDIR`), then **keep only
   what the recipe names** (`program`, `library`, `files`, the licence):
   upstream's make install drops man pages, info files, `.la` files and
   locale data a port may not want.
7. **Check what was made**: every `program` is a static ELF64 with its
   list (`tools/checkwants.py`, with the rules for its place: a package's
   lists are refused what `allow` refuses for `/data`, so a package can't
   ask for `svc session` or `svc init` and be installed anyway); the
   **FAT32 rules** on every staged file (section 10); the size of each
   program.
8. **Library ports** stage their headers and `.a` for the ports that need
   them; nothing of a library goes into a package before M15 (static
   linking: there is no use for it on Jam OS without a compiler), except
   its programs and data.

**Static linking's cost, said plainly**: a library's code is copied into
every program that links it. A fix in zlib is a rebuild (a revision bump)
of every port that `needs` zlib, and of their packages; a fix in musl or
the call layer is a rebuild of every port. The builder does the first by
itself (a `needs` port's new stamp makes its dependents out of date), and
each package records what it was built with (section 6), which is how
`pkg audit` sees a vulnerable zlib inside vim.

**Reproducible**: the same recipe, distfiles and sysroot give the same
package bytes (sorted archive members, fixed times, no host paths in
programs: `-ffile-prefix-map`). Checked by building zlib twice in the
self-test. On one host: the Mac and the PC's WSL have different versions
of CMake and the rest, so the same bytes across the two are not promised.

**Two build hosts.** The owner's packages are built on the Mac (`make
ports`, served by the Mac). But every QEMU test runs on the PC's WSL
Ubuntu, and `tools/remote-test.sh` copies the checkout there without
build/ and builds it there; so a port's test builds the port there too,
and the builder runs on Linux as well as macOS (no macOS-only tool in it,
the host triplet found at run time, `gmake` or `make` whichever is GNU
make 4). Its distfile cache there is its own (`~/.cache/jamos/distfiles/`
on the PC, filled from upstream or from the Mac's mirror over the LAN),
and the host tools a recipe names (`cmake`, `meson`, `pkgconf`, `perl`)
must be installed in WSL once: the join adds the one `apt` line to
TESTING.md beside the Mac's `brew` line.

### 6. The package

**Format** (Q5): a ustar archive, `<name>-<version>-r<revision>.jpk`,
uncompressed:

1. `+MANIFEST`, first: the signed text below;
2. the files, under paths relative to the prefix;
3. `+TABLES/<program path>`: each program's page-hash table, in
   `/data/etc/allow.d/`'s format (PK4's: a header with the magic, the
   file's size and SHA-256, then the SHA-256 of each 4 KiB page, the last
   zero-padded).

ustar because it is simple (a reader of fixed 512-byte headers is a
couple of hundred lines of C with every bound checked), every tool on the
Mac can look inside one, and it carries a mode and a time. No compression
in format 1: the packages are a few MB (static programs, little data), the
network is local, and a decompressor would have to be a boot-image port
before `pkg` could read anything. Compression comes later as a
must-understand manifest line (`!compress zstd`), the way `update`'s
manifest grows ([update.h](../user/include/update.h)).

**The manifest** (a strict line grammar in the style of `update`'s, so the
same kind of parser reads both):

```
jamos-pkg 1
name vim
version 9.1.0
revision 1
abi 3f2a9c0e71d4b6a2
licence Vim
summary the vim editor
runs ncurses-terminfo 6.5
built-with musl 1.2.6 1
built-with jamos-posix 3f2a9c0e71d4b6a2
built-with ncurses 6.5 1
file bin/vim 755 3801224 <sha256>
file share/vim/vim91/defaults.vim 644 4402 <sha256>
...
program bin/vim <the list's text, with \n written as \x0a>
table bin/vim 29728 <sha256 of +TABLES/bin/vim>
signature <128 hex digits>
```

- `file`: every file of the package, its mode (kept for M13.6; ignored on
  FAT32), size and SHA-256. Nothing in the archive that isn't listed is
  ever written, and a listed file that isn't in the archive fails the
  package.
- `program`: which files may run, and the list each asks for: what the
  owner is shown and what init writes as the approval (section 9).
- `table`: the program's page-hash table, so a program on `/data` runs from
  the pager with every page checked (M12.5 PX) from the first run, with no
  full read to build the table. init also makes the table itself from
  the file it reads back, and the two must match (section 9): the shipped
  table is a check of the write, not trusted alone.
- `built-with`: the components inside the package (musl, the call layer by
  its stamp, every `needs` port with its revision): for `pkg audit`.
- `abi`: section 11.
- The signature: Ed25519 over every byte before its line, as `update`'s,
  with the ports key (Q6). The first line's `jamos-pkg` keeps a package's
  signature from ever being read as an update manifest's or an index's,
  whatever key signs them.

**Limits**, fixed in the format: 4,096 files, a path of at most 255 bytes,
1 GiB a file (`VMO_VERIFIED_MAX`, the biggest program the kernel verifies),
2 GiB a package (PO13 raised them from 64 MiB and 512 MiB, for Chromium's
300 MB program). A port that needs more says so in review.

### 7. Signing and the repository

**The key** (Q6): a **ports key** of its own, made once on the Mac
(`build/host/jamos-sign keygen` into `~/.config/jamos/ports.key` and
`ports.pub`), its public half built into bootfs as `/boot/ports.pub` the
way `update.pub` is (the Makefile's `PORTS_KEY`, beside `UPDATE_KEY`).
Why not the update key: the update key replaces the kernel; the ports key
can only install programs that still run inside their lists. Keeping them
apart means the ports key can live on a build host, or later be a
project's key, without that host being able to replace anyone's kernel.

**A public build** (no local.mk, no keys): no `ports.pub` in its bootfs, so
`pkg` refuses every repository ("this build has no ports key"), as
`update` refuses every update. A public repository later would add its
key's public half under ports/keys/ (public by nature) and a setting to
choose it: not in M13.7.

**The repository** is static files, made by `ports.py repo` in build/repo/:

```
build/repo/
    INDEX              the signed index (below)
    VULNS              the signed vulnerability list (section 13)
    pkg/<name>-<version>-r<rev>.jpk
    src/<name>-<version>-r<rev>.src.tar   the distfiles, the port's directory, the git commit (section 12)
```

The index:

```
jamos-ports 1
serial 412
made 2026-10-12T09:14:03Z
abi 3f2a9c0e71d4b6a2
package vim 9.1.0 1 <size> <sha256 of the .jpk> runs=ncurses-terminfo
package ncurses-terminfo 6.5 1 <size> <sha256>
...
signature <128 hex digits>
```

- **`serial`** grows with every `repo` run; `pkg` keeps the highest it has
  accepted (`/data/pkg/db/serial`) and refuses a lower one (a replayed old
  index would offer old, vulnerable packages: TUF's rollback rule, in its
  simplest form). `-f` overrides, for a repository rebuilt from scratch.
- The index names each package's hash, so a package from the repository is
  checked twice: its hash against the signed index, and its own signed
  manifest. A package copied by hand (`pkg install /usb0/x.jpk`) has only
  the second, which is enough.

### 8. Delivery: `pkg` and the Mac's server

**Transport** (Q5): HTTP from the Mac. **tools/ports-server.py** (new)
serves build/repo/ read-only on port 8080 of the address `update`'s server
uses, the files snapshotted per request as update-server.py snapshots
(a make ports running meanwhile can't give half a package). HTTP because
Jam OS already speaks it (`<http.h>`: `fetch`), any web host could serve a
public repository later, and the signatures, not the transport, are what
is trusted (as apt and FreeBSD's pkg trust theirs over plain HTTP). The
setting **`pkg.repo`** (`http://<host>:8080/`, default from `net.host`)
names it.

**bin/pkg** (new, user/services/pkg/, a native libos program like
`bin/update`, not a POSIX one: it must work before any port does):

```
pkg update                 fetch the index (the catalogue), show what is new
pkg install <name>...      with its `runs` dependencies, in order
pkg install <file.jpk>     a package from a mount (a stick)
pkg upgrade [<name>...]    everything with a newer version or revision
pkg remove [-r] <name>...  -r: also what `runs` it; else refused while something does
pkg list [-u]              installed (-u: with upgrades waiting)
pkg info <name>            the manifest's summary, licence, programs and their lists
pkg files <name>           its files
pkg audit                  installed packages against VULNS (section 13)
pkg check                  every installed file against its manifest's hash
```

Its grants: `/svc/net` and `/svc/dns` (the repository), `/data` writable
with only `etc` guarded (the new want word of section 9: the package area
is its to write), the boot image read-only (`/boot/ports.pub`), and a
`pkgctl` channel to init (section 9), which the shell gets from init and
hands to `bin/pkg` when the owner types `pkg`, as it does for `update`.
It parses what the network sends, so it holds nothing else: no `/esp`, no
root powers.

### 9. Installing, upgrading, removing

**The prefix** (Q8): **`/data/pkg`**, laid out as a Unix prefix (a
package's paths are relative to it):

```
/data/pkg/bin/           programs (on the shell's PATH, after /boot/bin and /boot/usr/bin)
/data/pkg/share/<name>/  data (vim's runtime, terminfo)
/data/pkg/share/licences/<name>/   every package's licence texts
/data/pkg/db/<name>      the installed manifest (signed: `pkg check` re-verifies it)
/data/pkg/db/serial      the highest index serial accepted
/data/pkg/db/journal     the transaction in progress, if any
```

Ports are built with `--prefix=/data/pkg`, so a program finds its data
where it was put (vim's `$VIM`). Moving the prefix means rebuilding: one
constant in the builder and in `pkg`.

**The guard.** Today every program's writable `/data` is a view that
refuses changes under the top-level `etc`. The package area gets the
same: a new view flag, **`FS_VIEW_GUARD_PKG`** (`<fsview.h>`, checked by
fat's views and libos's fsserver exactly as `FS_VIEW_GUARD_ETC` is), set on
every program's writable `/data` view; a program can read `/data/pkg` but
not change, replace or remove anything in it. Only init, the shell and
`bin/pkg` (by a new want, `mount /data rw pkg`, which `tools/checkwants.py`
allows only to programs under user/services/) hold a view without it.
Without the guard nothing worse than today could run (a changed program
fails its hash), but any program with `/data` writable could delete or
corrupt every package's data: Haiku's read-only package area is the model.

**Approval** (Q7). A program on `/data` runs only with an approval line
in `/data/etc/allow`, which only init and the shell can write. For a
package:

1. `bin/pkg` shows, for the whole install (dependencies included), each
   package's name, version and licence, and each program with the list it
   asks for, then asks once: `Install 3 packages, 2 programs? [y/N]`.
2. It writes the files (below), then calls **`pkgctl.approve`** on its
   channel to init with the package's manifest.
3. init, on the worker thread its `update` check uses (a program of
   several MB takes a moment to hash; init's loop goes on), checks the
   manifest's signature against `/boot/ports.pub` itself (it trusts
   nothing `bin/pkg` says), and for each `program` line reads the file
   from `/data/pkg`, hashes it (and makes its page table), and
   compares both with the manifest's `file` and `table` lines. Only then
   does it append the approval line (`<sha-256>\t/data/pkg/bin/vim\t<list>`,
   with a tag field `pkg=vim-9.1.0-r1` the shell's `allow -l` shows and
   `allow -r` refuses to remove: `pkg remove` does) and write the table to
   `/data/etc/allow.d/<sha-256>`. init applies the same refusals `allow`
   does (no `svc init`, `svc session`, `devmgr`, `right debug`, ...), so a
   signed package still can't get a refused grant.

So the trust is: the ports key signed it (the owner's build), and the
owner said yes at the terminal. `bin/pkg` could only fake the yes if it
were compromised by what it parses, and even then only for packages the
owner's key signed. init parses only the manifest (a strict line parser
like `update`'s), never the archive: the archive is `bin/pkg`'s to read.

**The journal** (all or nothing on a disk that can lose power, FAT32 with
no rename-over):

- **Install**: the journal names the package and step; each file is written
  as `<path>.new`, synced, read back against its hash; then `approve`
  (init reads the programs at their `.new` names: the call says the files
  are staged); then each `.new` renamed to its path; then the manifest
  into db/; then the journal goes. A file at its final name is always an
  approved one.
- **Upgrade**: the new version's files as `.new`; `approve` the new
  hashes, staged as for an install (the old lines stay: either version's
  file may run during the swap); for each file, the old removed and the
  `.new` renamed (FAT can't
  rename over a file; the same order as init's ESP write, each pair synced);
  then **`pkgctl.revoke`** of the old version's lines; then db/; then the
  journal goes.
- **Remove**: refused while another installed package `runs` it (unless
  `-r`); `revoke` first (nothing of it can start again), then the files,
  then db/, then the journal.
- **After a cut**, the next `pkg` (and init once `/data` is mounted, so
  nothing runs from a half-swapped package after a boot) reads the journal
  and finishes the step it names, or undoes it if its files aren't all
  there and checked. QEMU killed at each step is the test (PO8).
- **A running program's file** can't be removed once M12.5's Q7 is in
  (`ERR_BUSY` for a file a program runs from). The upgrade then leaves
  that file's `.new` in the journal and says "vim is running: the new
  version takes its place when it ends; run `pkg upgrade` again"; init's
  settle at the next boot finishes it.

**Conflicts**: a file owned by another installed package is refused
(`pkg files` knows who owns what from db/); a program named as a boot-image
program is installed but warned about ("`/boot/usr/bin/ls` is found first
on PATH").

### 10. FAT32 now, M13.6 later: exactly what needs the new filesystem

The builder checks every staged file of a package against FAT32's rules
and refuses (with the file named) or applies a recorded rule, so a
package that installs is one that works on FAT32:

| What a port may install | On FAT32 (now) | Needs M13.6 |
|---|---|---|
| **Names that differ only in case** (`Makefile` and `makefile`; terminfo's `a/` and `A/` directories), within a package or against one already installed | refused; a recipe may rename (ncurses can be configured to name terminfo directories by hex: *unsure* whether its configure picks that by itself when cross-built, so the recipe says so explicitly) | case-sensitive names |
| **Characters FAT forbids** (`: * ? " < > \|`, a trailing dot or space) | refused | names with them |
| **Symlinks** (vim's `ex` and `view` → `vim`; `libfoo.so` names; terminfo's aliases) | turned into a copy (a program: a second approval line, same hash) or, for a program, a `multicall` name; recorded in the manifest as a copy | symlinks: one file, many names; the versioned layout below |
| **Hard links** (terminfo's aliases, some archives) | copies | hard links (*unsure* M13.6 has them) |
| **Execute bits** | ignored: the approval line is Jam OS's exec bit | kept and shown (`ls -l`); still not the authority |
| **Scripts with `#!`** (configure-made wrappers, a package's shell scripts) | installed, but run only as `sh <script>` (Jam OS runs static ELF; `#!` needs M13.5's shell and a loader rule) | nothing new: that is M13.5's |
| **Files over 4 GiB** | refused | large files |
| **Times** | FAT keeps 2-second times; packages carry fixed times anyway | 1 ns times (matters to `make` at M15, not to installing) |
| **Owners, modes like 0600** | single user; a program that checks its key file's mode (OpenSSH-style) needs a patch | modes kept (still one user) |

**With M13.6** the prefix moves to the new filesystem's mount (its name is
M13.6's plan's to choose), and the layout can become Homebrew's: each
version in its own directory (`store/vim-9.1.0-r1/`) and the prefix's
`bin/` and `share/` made of symlinks into it, so an upgrade is one rename
of a symlink (atomic, no journal swap per file) and the old version stays
until `pkg clean` (a rollback by switching back). Section 9's journal is
what FAT32 gets until then; the manifest and `pkg`'s commands don't change
between the two layouts.

### 11. Packages across system updates (before M14)

A ported program carries the call layer and libjam inside it (static), so
it speaks the `fs`, `file`, `net`, `tty`, `signal` protocols and the
system calls of the build it was made with. Until M14 freezes them
([M13-PLAN](M13-PLAN.md), "What M13 must not block"), an `update` can
break every installed package.

So (Q10): the build computes an **ABI stamp**: the SHA-256 (first 16 hex
digits) of `abi/syscalls.def`, the `abi/idl/*.idl` files the POSIX layer
and libjam speak, and `user/include/posixfds.h`. It goes into `build.txt`,
into `update`'s manifest (an extension line, `abi <stamp>`: an older
build skips it), into the sysroot, and into every package's manifest and
the index.

- `pkg install` refuses a package whose `abi` isn't the running build's
  (`-f` takes it, at the owner's risk).
- After an `update` whose stamp differs, `bin/update`'s last line says
  "3 installed packages were built for the old system: `pkg upgrade` once
  the Mac has rebuilt them"; make ports rebuilds every package when the
  sysroot's stamp moves (section 5's stamps do it), and `pkg upgrade` takes
  the new revisions.
- The stamp is coarse (any change to those files moves it, also one no
  package uses). Finer is M14's versioning, which replaces it.

The honest cost: until M14, most updates that touch the POSIX layer or a
protocol mean a full rebuild of the packages (minutes on the Mac for the
first ladder) and a `pkg upgrade` on the PC.

### 12. Licences

- **Every recipe names its licence** (SPDX) and its licence file(s); the
  lint refuses one without. The package carries the text in
  `share/licences/<name>/`, and `pkg info` shows the licence. The
  generated list of ports has a licence column.
- **The boot image needs notices too, today.** musl, sbase and Lua are MIT:
  a copy of the program must carry the copyright notice. The boot image
  ships their programs and none of their notices. PO2 adds
  `/boot/share/licences/<port>/` for every system port (and for the other
  third_party/ code in the boot image: FatFs, lwIP, Monocypher, dr_mp3,
  pl_mpeg, stb, the fonts), and a shell command `licences` that lists
  them.
- **GPL ports** (Q9). CODING-GUIDE's rule (permissive licences only in the
  tree) is about Jam OS's own code and what it links. A ported GPL program
  is a separate program; recipes and patches for it may live in ports/
  (a patch to GPL code is under the GPL: the port's directory says so in
  a `LICENSE` note, as FreeBSD's ports tree carries GPL patches beside BSD
  code). What changes is what a distributor must give:
  - a GPL program linked statically with musl (MIT) and libjam (BSD-2) is
    fine for the GPL (both are compatible), and its "complete source"
    includes the program's source, our patches, the recipe and build
    scripts, and the source of what it links: the Jam OS tree at the
    commit it was built from;
  - so **every package's source goes beside it in the repository**
    (`src/<name>-<version>-r<rev>.src.tar`: the distfiles, the port's
    directory, and the commit of the Jam OS tree; GPLv2's section 3 and
    GPLv3's 6(d) accept source offered from the same place as the
    binary). Done for every package, not just GPL ones: one rule;
  - **the boot image and the public release image carry no GPL port**
    (Q9's recommendation), so the image stays redistributable with only
    the permissive notices above; GPL programs are packages.
- **LGPL libraries** linked statically oblige the distributor to give
  object files that let the user relink with a changed library. Simplest:
  no LGPL library before M14.5's dynamic linking (configure with
  `--disable-nls`, no gettext or libiconv; musl has `iconv`). The lint
  refuses an LGPL `needs` unless the recipe says how it is met.

### 13. Security updates

- **In the recipe** (Alpine's secfixes): `cpe <CPE name>` (how
  vulnerability databases name the product), `fixed <CVE> <version or
  revision>` (fixed upstream in that version, or by our patch in that
  revision), `not-affected <CVE> <reason>` (it doesn't apply: a code path
  we don't build, a 32-bit-only bug).
- **`ports.py audit`** on the Mac: for each recipe (and for musl and the
  other `third_party/` code: their entries in `third_party/VERSIONS.md` get
  the same three fields), asks the NVD's CVE API by CPE and version (and
  OSV.dev where it has the project), drops what `fixed` and `not-affected`
  cover, and prints the rest: the owner's to-do list. It needs the network
  and the NVD's rate limit (*unsure* of the API's terms for unattended
  use; run by hand, weekly, not in `make check`).
- **VULNS**: the repository's signed list (FreeBSD's VuXML, pkgsrc's
  pkg-vulnerabilities): `vuln <component> <affected range> <CVE>
  <summary>`, made from the audit's open items the owner confirms.
  `pkg audit` on the PC checks every installed package's `built-with`
  lines against it, so a zlib bug shows in vim, and musl's in every
  package.
- **The worked example: musl's CVE-2026-6042.** musl is in every package.
  The fix (upstream's patch to `src/locale/iconv.c` and a new header) goes
  in as an override (section 4's new-file form); musl's entry gets `fixed
  CVE-2026-6042 1.2.6-jam1`; the sysroot's stamp moves, so make ports
  rebuilds every package with a new revision, and `pkg upgrade` takes them.
  Until that fix lands, VULNS lists it and `pkg audit` names every
  installed package (the honest answer: they all contain it, though none
  converts GB18030).
- **Response time** is the owner's: nothing is automatic beyond the
  rebuild. `pkg update` says when installed packages are listed in VULNS.

### 14. Testing a port

- **`test`** in each port's directory (Homebrew's `test do`): commands and
  their expected output, in the shell tests' format (`tools/shell-tests/`),
  run on Jam OS. zlib's: `minigzip` round trips of a few files and the
  compressed size of one; Lua's: its portable test set; vim's: `vim -es`
  scripts that edit a file and write it, and `vim --version`.
- **tools/ports-test.sh <port>** (new, run on the PC through
  `tools/remote-test.sh` as every QEMU test is): builds the port and its
  `runs` closure, makes a test image whose data partition already has the
  packages installed (written by the Mac with mtools: the files, db/, the
  approval lines and tables, as `pkg` and init would have made them; a
  test image only), boots it and runs the `test` through the serial
  shell. One QEMU run per port, a few minutes; ports run in parallel shards
  as other tests do.
- **Upstream's own test suites** run on Jam OS only (the Mac can't run a
  Jam OS program): where a port's suite is a program (zlib's `example`),
  the recipe packages it as a test program (in a `-test` subpackage, never
  in the repository); a suite that needs a shell, Perl or make (most
  autotools `make check`s) waits for M13.5 and M15.
- **tools/pkg-test.sh** (new): `pkg` itself, against a repository the test
  host serves into QEMU: install with dependencies, upgrade, remove, the
  refusals (a changed byte in a package, in the index, a lower serial, a
  package signed with another key, a manifest naming a file the archive
  lacks, a refused grant in a signed list, a wrong `abi`), and QEMU killed
  at each step of an install, an upgrade and a removal, then booted again
  (the journal settles it, `pkg check` passes).
- **The builder's self-test** (in `make check`, on the Mac, no network,
  no QEMU): fixture recipes and a fixture distfile in the tree: the order,
  a cycle refused, a patch with fuzz refused, a missing hash refused, a
  stamp unchanged after a no-op, two builds byte-identical, the FAT rules
  on a staged tree with every bad case, the manifest and index written and
  read back by the C parser (built for the Mac, as menucheck is).

### 15. After M15: building on Jam OS

Nothing here builds on Jam OS, but nothing should have to be thrown away
when M15 does:

- **The formats** (recipe, manifest, index, VULNS) are line-based and parsed
  in C already on Jam OS (all but the recipe); a C reader of recipes is
  small.
- **The builder** is Python; M15's "build tools rewritten in C" includes it,
  or a ported Python runs it (Python is a port of its own, later).
- **What a native build needs**, as ports: a POSIX shell (M13.5's mksh),
  make (this plan's rung 4), sed, grep, sort and the rest (sbase), `awk`
  (onetrue awk), `patch` (*unsure* whether sbase has a `patch`; a port of
  OpenBSD's or a small one otherwise), `tar` and the decompressors
  (rungs 2 and 3), a C compiler (tcc or cproc first, then GCC: M15's own
  question), and pkg-config. Each is on the ladder or in M15.
- **The order** is Haiku's bootstrap: every one of those is first built
  cross on the Mac and installed as a package; then each is rebuilt on Jam
  OS by itself, and the two results compared.

## Questions for the owner

**Answered 2026-10-11:** every question as recommended, except Q9, which
follows the owner's licence decision of the same day (CONTRIBUTING.md):
GPL and LGPL code is allowed in any separate program, a package or a
program in the boot image, with its complete source shipped beside it
(the boot image's then in the image or on the same release page) and its
changed files marked; nothing GPL in the kernel or a BSD library. The
boot image stays small anyway (Q4), so in practice GPL ports are packages.

Each stands alone and ends with a recommendation; the plan assumes the
recommendation until you say otherwise.

### Q1. The recipe format

- **(A)** Make fragments, as P1 wrote them (user/ports/<name>/<name>.mk,
  included by the Makefile): no new tool, but every port is make code, a
  new port edits the Makefile's includes, and nothing knows the port's
  licence, dependencies or source hash as data.
- **(B)** A short file of `key value` lines per port (section 2), the build
  steps given by a build style or a port's build.sh, read by one builder
  (tools/ports.py). Alpine's, Void's and Serenity's model.
- **(C)** TOML as Redox's `recipe.toml`: richer, but a TOML parser in C on
  Jam OS at M15.
- **(D)** pkgsrc, with Jam OS as a platform: its recipes, but its framework
  (bmake, its bootstrap) to port and its 20,000 recipes still each to port.

*Recommendation: (B).* Data where data is enough, shell where a build
needs it, and a format a C program reads in 150 lines when Jam OS builds
its own ports.

### Q2. Where the sources come from

- **(A)** Vendored in `third_party/` as today, for every port.
- **(B)** Fetched by URL, size and SHA-256 into a cache, with the owner's
  mirror of every file, for every port.
- **(C)** (B) for packages; system ports (the boot image's) stay vendored,
  so `make` never needs the network and a public build is made from git
  alone.

*Recommendation: (C).* Vendoring vim, ncurses and Python's sources would
put tens of MB into git per version; a hashed tarball is as fixed. The
boot image keeps building offline.

### Q3. Patches or overrides

- **(A)** Overrides only (whole files, upstream's hash checked), as musl and
  sbase do today.
- **(B)** Patches only (unified diffs, fuzz 0, a header with the reason).
- **(C)** Both: a patch by default; an override when the change is most of
  a file or replaces a `fork`; musl stays on overrides.

*Recommendation: (C).* A one-line configure fix as a whole-file override
hides what changed and carries a copy of upstream's file; a rewritten fork
site as a patch can apply cleanly to a changed file. Each has its place,
and the lint keeps both explained.

### Q4. Which ports stay in the boot image

- **(A)** All of them, as M13 started: no install step, but the boot image
  is already at 31.8 MB of `update`'s 32 MiB limit with sbase and Lua.
- **(B)** Only what the system needs before `/data`, what a test entry runs,
  or what needs a grant `allow` refuses: sbase (as one multi-call program),
  libc-test, tinyssh, later mksh. Lua and every new port are packages.
- **(C)** None: even sbase a package.

*Recommendation: (B).* The boot image is full, and a port that is a
package costs nothing at boot. (C) would leave a fresh stick with no `sed`
or `find` before `pkg` has run, and sshd can't be a package at all.

### Q5. The package format and how it travels

- **(A)** An uncompressed ustar archive with a signed manifest first
  (section 6), fetched over HTTP from a static repository the Mac serves
  (section 8).
- **(B)** The same package, fetched over `update`'s UDP protocol (extended
  from three fixed files to a repository).
- **(C)** Packages only copied by stick (`pkg install /usb0/x.jpk`), no
  network.

*Recommendation: (A)*, with (C)'s command kept for a stick. HTTP is
already in Jam OS, needs no new protocol, and could be served by any host
later; trust comes from the signatures, not the wire. Compression is a
later manifest line.

### Q6. The signing key

- **(A)** The update key: one key to keep.
- **(B)** A ports key of its own (`~/.config/jamos/ports.key`,
  `/boot/ports.pub`), made the same way.
- **(C)** No signature: the hash in the index, fetched from the Mac.

*Recommendation: (B).* The update key can replace the kernel; the ports
key can only install programs that still live inside their lists. Apart,
the ports key can later sit on a build host or become a project's key
without that power. (C) trusts every device on the network that answers
as the Mac.

### Q7. How a package's programs are approved

- **(A)** As today: `pkg` installs the files, and the owner runs `allow` on
  each program.
- **(B)** The ports key's signature plus one answer at install: `pkg` shows
  every package and every program's list and asks once; init checks the
  signature and the files itself and writes the approval lines, tagged
  with the package, and `pkg remove` takes them back.
- **(C)** The signature alone: a signed package is approved without a
  question.

*Recommendation: (B).* (A) is ten `allow`s for a package with ten programs,
and the lines would outlive `pkg remove`. (C) drops the moment the owner
sees what a program will be given. Either way the refusals `allow` makes
still hold.

### Q8. Where packages go, and who may change them

- **(A)** `/data/pkg`, guarded as `etc` is: every program reads it, only
  init, the shell and `bin/pkg` change it (a new view flag).
- **(B)** `/data/etc/pkg`: guarded today, no new flag; an odd place for
  programs and their data, and the shell's PATH gains a path under `etc`.
- **(C)** `/data/pkg` unguarded: a changed program still can't run (its
  hash), but any program with `/data` writable can delete or spoil every
  package's data.

*Recommendation: (A).* One small flag beside an existing one, and
packages that only `pkg` touches. With M13.6 the prefix moves to its
filesystem, the guard with it.

### Q9. GPL ports

- **(A)** Permissive licences only, as for the tree: no make, no git, no
  bash, no GCC.
- **(B)** GPL programs as packages only, each package's source (distfiles,
  patches, recipe, the tree's commit) served beside it; the boot image and
  the public image carry none.
- **(C)** GPL programs anywhere, the boot image included, with the source
  obligation then on the image too.

*Recommendation: (B).* M15 needs make and GCC, and much of what is worth
porting is GPL. (B) keeps the image's licence story the permissive one it
is now and makes the source rule one mechanical step for every package.
LGPL libraries wait for M14.5 (section 12).

### Q10. Packages across `update`, before M14 freezes the ABI

- **(A)** An ABI stamp in every build and package: `pkg` refuses a package
  built for another stamp; after an `update` that moved it, `pkg upgrade`
  takes the Mac's rebuilt packages.
- **(B)** No check: an old package may fail in odd ways after an `update`.
- **(C)** Packages shipped inside `update`: the server sends the build and
  the matching packages, and `update` upgrades the installed ones in the
  same step.

*Recommendation: (A).* It is cheap, and it turns a silent breakage into a
message with the fix in it. (C) is attractive but ties two delivery paths
together for a problem M14 removes.

### Q11. The first real editor

- **(A)** vim, with ncurses: what most people reach for; the hardest test
  of the terminal; `:!` waits for M13.5.
- **(B)** mg (public domain, OpenBSD's small Emacs) with ncurses: smaller,
  fewer gaps.
- **(C)** nano (GPL-3) with ncurses.

*Recommendation: (A).* An editor is the first thing anyone opens over
SSH, vim is the one most people expect, and its demands on the terminal
are the ones every later full-screen port makes. mg is a good second if
vim stalls.

### Q12. The builder's language

- **(A)** Python, as every tool in tools/ (genidl, mkbootfs,
  update-server); rewritten in C (or run by a ported Python) at M15.
- **(B)** C from the start, built for the Mac and later for Jam OS: one
  program in both places, but several times the code to write now.

*Recommendation: (A).* The builder runs only on the Mac until M15, and
the formats it shares with Jam OS (the manifest, the index) are already
read in C by `pkg`; the recipe format is chosen so the M15 rewrite is
small.

**Changed by the owner, 2026-10-11:** at M15 the builder is not rewritten
in C; CPython is ported and runs it, with the rest of tools/ (ROADMAP's
M15 row). So ports.py keeps to Python's standard library and runs other
programs only through `subprocess`. What Jam OS itself reads (recipes in
`pkg`'s case, manifests, indexes) is still parsed in C (PO4).

## Risks

- **The boot image's 32 MiB.** Already at 31.8 MB on P1's branch. PO2's
  multi-call sbase takes it back, and the build's new size check stops the
  next surprise; until PO2 merges, a port added to the boot image (X2's
  tinyssh) could push it over and stop `update`. Raising
  `UPDATE_FILE_MAX` is possible (the kexec region is 48 MiB) but not this
  plan's.
- **Static programs are big** (about 300 KB each, section "Where M13.7
  starts"); vim and its runtime make a 30 MB package. Fine on the LAN and a
  stick; the call layer's size is worth a look in M13's R1.
- **The ABI stamp moves often** before M14: every such `update` needs a
  rebuild and `pkg upgrade`. Annoying, never silent (Q10).
- **Ports find gaps in the layer.** Each ladder rung is also a test of
  M13: a missing call or a wrong errno is reported as a finding for M13's
  follow-ups, not patched around in the port (a port's patch for a layer
  bug would hide it from every other port).
- **Cross-configure's wrong answers.** configure can't run test programs on
  the Mac; a wrong cache answer in config.site builds a program that
  fails at run time on Jam OS. Each answer in config.site has a comment
  saying why it is right for the layer, and a port's `test` is the net.
- **Who can install.** A program runs from `/data/pkg` only after the owner
  said yes to a package the ports key signed, with the same refusals as
  `allow`; init checks the signature and every program's bytes itself.
  The ports key on the Mac is now a second key to keep safe (anyone with it
  can offer the owner programs; they still need his yes). bin/pkg parses
  the network's data and holds the package area writable: a bug there can
  spoil packages (not run anything unapproved). PR reads exactly this.
- **FAT32's limits** keep some ports out until M13.6 (case, symlinks,
  names): the builder says which rule refused which file, so the list of
  "waits for M13.6" ports is known, not discovered on the PC.
- **Licences**: a recipe's licence is the porter's reading of upstream; the
  lint checks the field is there, not that it is right. The review reads
  each new port's licence file against its recipe. The boot image's
  missing notices (section 12) are a gap today, fixed by PO2.
- **The audit's data sources** (NVD, OSV) change their APIs and limits;
  the audit is a helper for the owner, not a guarantee, and runs by hand.
- **Upstream URLs rot**: the mirror holds every distfile the builder ever
  fetched; it must be backed up like the keys.

## PO1 notes

What track PO1 (the recipe format and the builder) built, the choices it
made where the plan left them open, and what PO2 and PO3 need to know.

**What there is.** `tools/ports.py` (the commands) on `tools/portslib/`,
a module per job: `recipe.py` (the format and one recipe's lint),
`licence.py` (the SPDX identifiers the builder accepts), `tree.py` (the
ports tree, the checks across recipes, the order), `fetch.py`,
`source.py` (unpacking, overrides), `patch.py`, `toolchain.py` (the
port's sysroot and tools), `build.py`, `stage.py` (keep, check, the FAT
rules), and the self-test (`selftest.py` on `fixtures.py`'s fake ports).
`ports/config.site`, `ports/jamos.cmake` and `ports/jamos.meson` are the
shared files; `ports/zlib/recipe` and `ports/xz/recipe` the first two
ports. `make check` runs `ports.py lint` and `ports.py selftest` (about
3 s on the Mac, offline).

```
ports.py build [-f] [-v] [-j N] <port>...   build what is out of date, in order
ports.py lint [<port>...]                   every recipe's checks
ports.py fetch <port>...                    only download (fills the mirror)
ports.py graph [<port>...]                  the order, with needs and runs
ports.py selftest                           the builder's own tests
ports.py --out DIR --ports DIR --offline    (before the command)
```

`package`, `repo` and `audit` answer "not built yet" (PO3, PO12).

**The format as built** (section 2's keys, with these differences):
- No `mirror` key: a recipe has several `source` lines, so the file's name
  in the cache and the mirror is an optional fourth word of each (default:
  the URL's last part). The mirror is a directory, JAMOS_DISTFILES_MIRROR
  (default ~/jamos-distfiles, `none` for none), and JAMOS_MIRROR_URL
  names mirrors served over HTTP (the PC fetching the Mac's); the cache is
  JAMOS_DISTFILES (default ~/.cache/jamos/distfiles).
- `$name` and `$version` work in source URLs and file names too; `$prefix`
  only in a style's arguments; `$$` is a dollar; any other `$word` is a
  lint error.
- A `make` line's arguments go to every make run of the styles configure,
  configure-plain and make (the build and the install).
- A `program` without a second word takes `wants/<its name>` if the port
  has one, else the default list `posix`. Every list must hold `posix`.
- `lgpl-relink <how>` is section 12's "says how it is met": a port that
  `needs` an LGPL library (one whose licence leaves no non-LGPL choice) is
  refused without it.
- `subpackage <name> <glob>...`: the name is `<port>-<what>`; a file both
  a subpackage and `files` name is the subpackage's.
- `multicall` and `subpackage` are parsed, linted and recorded; the names
  and the second package are PO2's and PO3's to make.
- `source git <url> <commit>` works (a 40-digit commit; `git archive` into
  the cache, its hash recorded beside it as `<file>.sha256`, a later
  archive that differs refused).
- A port's directory may hold only `recipe`, `patches/`, `OVERRIDES`,
  `override/`, `wants/`, the custom style's shell file, `files/` (PO2:
  below), `test` and `LICENSE`; the lint refuses anything else (a misspelt `patch/` would
  otherwise be silently ignored). ports/ itself holds the ports, the
  three shared files and `keys/`.
- The licences accepted are the list in `tools/portslib/licence.py`
  (permissive, plus GPL-2.0, GPL-3.0, LGPL-2.1, LGPL-3.0 and MPL-2.0 for
  separate programs); `LicenseRef-` names, the old `+` suffix and anything
  not listed are refused: adding a licence is a reviewed one-line change.
  AGPL is not on it (CONTRIBUTING.md names GPL and LGPL only).
- The custom style's `build` and `install` functions run under `sh -e` in
  the source directory, with the build's variables (`name`, `version`,
  `revision`, `prefix`, `destdir`, `srcdir`, `portdir`, `jobs`, `make`,
  and CC, AR and the rest). Inside `install()` the `install` program is
  `command install` (the function's name shadows it), and a failure in the
  middle of an `a && b` line doesn't stop `sh -e`: the porter's guide
  (PJ) should say both.

**The builder's choices.**
- **Patches** are applied by the builder's own applier (`patch.py`), not
  the host's `patch`: the Mac's is BSD's and the PC's GNU's, and ours
  refuses any path out of the tree (absolute, `..`, through a symlink).
  Fuzz 0 as GNU's `--fuzz=0`: the context must match byte for byte, at
  the hunk's line or nearest it. New and deleted files are taken; renames,
  mode changes and binary diffs are refused (an override does those). A
  patch's header needs `Description:` and `Forwarded:` (`not-needed`
  with its reason).
- **Overrides**: a port's `OVERRIDES` is musl's format, our files relative
  to the port's directory, checked by `tools/checkoverrides.py` against
  the freshly unpacked source before they are copied in. Its new-file
  form (`-` for the hash: a file upstream must not have) is in, with its
  self-test cases. **For PO12**: `user/posix/posix.mk` makes every
  OVERRIDES line's upstream file a prerequisite of its check; a `-` line
  there would stop the build ("no rule to make"), so the musl fix must
  also filter `-` lines out of `MUSL_OVR_UP` (awk `$2 != "-"`).
- **The sysroot** of a port is build/sysroot plus the `library` files of
  the ports it needs and of what they need, transitively (a static
  library's own libraries must be linked too: the plan said "exactly the
  ports it needs"). They go at the sysroot's top (include/, lib/, where
  jamos-cc looks), and their pkg-config files' `prefix=` is emptied on
  the way in, so pkg-config's sysroot rule puts `-I` and `-L` inside it.
  Two ports giving one file is an error.
- **The tools** are in build/ports/<name>/bin under the
  `x86_64-linux-musl-` names (CC and the rest point there, and CMake and
  Meson find them by those names). The `gcc` is jamos-cc with the
  port's sysroot, `-ffile-prefix-map` for the source's path, and on a
  link the list of the `program` whose name the output has; the stage's
  check catches a program linked under another name and renamed
  (selftest: "a program linked with another list"). `ar` and `ranlib`
  add `D` (zero times and owners): found on the PC, where a plain
  `ar rc` (zlib's) wrote the build user's uid, so libz.a differed between
  the Mac and the PC. The `g++` refuses, so a port that wants C++ fails
  instead of finding the Mac's.
- **The environment** is made from nothing but PATH, HOME and a few
  others: the host's CFLAGS, CPATH, PKG_CONFIG_PATH and an outer make's
  MAKEFLAGS never reach a build. CFLAGS is `-O2`; TZ, LANG and LC_ALL are
  fixed; SOURCE_DATE_EPOCH is the port directory's last commit (or, in a
  copy without git such as the test host's, its newest file).
- **The stamp** (out of date or not) hashes the builder's format line,
  every file of the port's directory, the shared files, `tools/jamos-cc`,
  the whole sysroot, the cross prefix, SOURCE_DATE_EPOCH, a vendored
  source's tree and every needed port's stamp. One run at a time per
  output directory (a lock).
- **The stage** keeps what the recipe names, programs stripped of debug
  information (as the boot image's are), modes 0755 and 0644, times the
  epoch; it lists everything else in dropped.txt and on the terminal (an
  executable with no `program` line is named as one). A symlink the
  install made becomes a copy of its target (a `copy` line); one leaving
  the install is refused.
- **The checks per place**: every program a static x86-64 executable
  whose note is the list its recipe chose; the list allowed by
  `tools/checkwants.py`'s rules for a program outside user/services/ and
  user/tests/, and for a package also not one `allow` refuses (svc
  devmgr, right debug, and what checkwants already refuses there: svc
  session, svc init, the low ports, ...). The FAT32 rules (section 10,
  plus the package format's 255-byte path) apply to every file a package
  would carry, in both places for now (a name FAT can't hold is no
  portable name for the boot image either); `library` files are exempt
  (they never go into a package).
- **Unpacking** refuses absolute paths, `..`, members through a symlink
  the archive made, links out of the tree, devices; tar (gz, bz2, xz) and
  zip; Python 3.12's `data` filter on top where there is one.
- The builder runs on the Mac's own Python (3.9) and the PC's (3.12).

**The stage list** (build/ports/<name>/stage/stage.txt, `jamos-stage 1`,
described in `tools/portslib/stage.py`) is the seam for PO3: `port`,
`built-with` (musl's version, the sysroot's stamp, each needed port's
version and revision: the manifest's `built-with` lines), `program` with
its list file, `library`, `file`, `licence` (in share/licences/<name>/),
`sub` and `copy` lines, each file with its size and SHA-256.

**What it proved** (2026-10-11, the Mac and the PC's WSL through
`tools/remote-test.sh`): zlib 1.3.2 (configure-plain, a patch, a list;
about 2 s on the Mac, 1 s on the PC) and xz 5.8.4 (autotools with
config.site and threads; about 20 s on the Mac, 6 s on the PC) build
into their stages; a second run finds both up to date; a forced rebuild

file of xz's stage and zlib's. They are packages, built only into
build/ports/: nothing goes into the boot image. Neither has run on Jam OS

**The self-test** (`selftest.py`): licence expressions; the lint (no
licence, an unknown one, no licence file, an unknown key, a needs of
nothing, a cycle, another style's arguments, no size, no hash, a list
that isn't there, a package asking for svc session, a list without
`posix`, a patch without its header); the patch applier (clean, at an
offset, fuzz refused, `..` refused, a new file, the last newline, a mode
change refused); hostile archives; the FAT rules; fetching (a bad hash and
a bad size refused and not kept, the mirror filled, a vanished upstream
served by the mirror); a git source; and real builds of five fake ports
with the real compiler (the order; a library's patch seen by its user;
the transitive link; a program's list; the dropped executable; a symlink

**Not done here**: packages, the index and signing (PO3); the audit

### The signed texts (all three formats)

As `update`'s manifest (`<update.h>`): bytes 0x20..0x7e and `\n` only;
every line ends in one `\n`; fields are split by single spaces (no
leading, trailing or double space); no blank line. The first line names
the format, the last is `signature <128 lower-case hex digits>`: the
Ed25519 signature (RFC 8032, Monocypher's `crypto_ed25519_check`, as
`updsig.c`) by the ports key of every byte before that line. A bare
`signature` line is unsigned and refused. **Domain separation**: the
first lines are `jamos-pkg 1`, `jamos-ports 1` and `jamos-vulns 1` (and
`update`'s `jamos-update 2`, under its own key); the first line is
signed with the rest and every reader demands exactly its own, so a
signature made for one format never verifies as another's, whatever key
made it. Read in this order: the size bound, the first line, the bytes,
the signature line's shape, **the signature**, and only then any field.

**Extension lines**, as `update`'s: in one place per format (named
below), lines `<key>` or `<key> <value>`, the key 1..32 of `a-z 0-9 -`
(not one of the format's keywords), the value 1..200 bytes of 0x20..0x7e
with no space at either end; a reader skips them. A key starting with
`!` (then 1..31 of `a-z 0-9 -`) is must-understand: a reader that
doesn't know it refuses the text. None is written yet.

**Fields** (`pkgformat.py`):

| Field | Grammar |
|---|---|
| name | `[a-z0-9][a-z0-9+._-]{0,62}` |
| version | `[0-9A-Za-z][0-9A-Za-z._+~-]{0,62}` |
| revision | `[1-9][0-9]{0,8}` |
| size | decimal, no leading zero (`0` alone), at most the line's limit |
| sha256 | 64 lower-case hex digits |
| abi | 16 lower-case hex digits |
| serial | `[1-9][0-9]{0,18}`, at most 2^63-1 |
| made | `YYYY-MM-DDTHH:MM:SSZ` (UTC) |
| licence | 1..200 bytes: words of `A-Z a-z 0-9 . + ( ) -` split by single spaces (an SPDX expression) |
| text (a summary) | 1..200 bytes of 0x20..0x7e, no space at either end |
| path | 1..255 bytes of 0x21..0x7e except `" * : < > ? \` and the bar; parts split by single `/`, none empty, `.` or `..`, none ending in `.`; the first part doesn't start with `+` |
| id (a vuln's) | `[A-Za-z][A-Za-z0-9-]{0,62}` |

**The version order** (`vcmp`, the same as tree.py's `vkey`): a version
is the list of its maximal runs of ASCII digits and of ASCII letters
(other bytes only separate); two lists compare item by item, a digit run
with a digit run as numbers (leading zeros ignored: by length after
them, then bytewise), a letter run with a letter run bytewise, a digit
run before a letter run; when one list is the start of the other, the
shorter comes first; equal lists are equal versions (`1.0` = `1_0`).

### The package (`<name>-<version>-r<rev>.jpk`)

**`+MANIFEST`**, lines in exactly this order:

```
jamos-pkg 1
name <name>
version <version>
revision <revision>
abi <abi>
licence <licence>
summary <text>
<extension lines>*
runs <name> [<least version>]*         sorted by name, strictly; at most 64; never the package's own
built-with <name> <version> [<revision>]*   sorted by name, strictly; at most 64
file <path> <644|755> <size> <sha256>+ sorted by path bytewise, strictly; 1..4096; 0..1 GiB each, 2 GiB in all
program <path> <list>*                 sorted by path, strictly; at most 256
table <path> <size> <sha256>*          one per program, in the programs' order
signature <hex>
```

- The manifest is at most 4 MiB (4,194,304 bytes), its signature line
  included.
- Paths: no two equal ignoring ASCII case, and no file where another
  path needs a directory (`a` and `a/b`): FAT32's rules.
- A `program` path is a `file` of mode 755 and size above 0, and every
  file of mode 755 has a `program` line (mode 755 means exactly "a
  program").
- `<list>` is the rest of the line: the program's list (its ELF note's
  text, `<wants.h>`) with each `\n` written as the four bytes `\x0a`;
  any other backslash is refused. Decoded: 1..1023 bytes, lines of
  0x20..0x7e without a backslash, each ended by `\n`. The program's one
  JamOS note must be exactly that text, and a list `allow` would refuse
  is refused (`svc session`, `svc init`, `svc devmgr`, `right debug`, the
  low ports: tree.py's `list_problems` for place `package`).
- A `table` line's size is 64 + 32 x ceil(file size / 4096).
- `built-with`: `musl <version>` (no revision: 0 when matched),
  `sysroot <16 hex digits>` (`sysrootid.py`: the sysroot as `strip
  --strip-debug -D` leaves its objects and archives, so the Mac and the
  PC agree) and `<port> <version> <revision>` for each port it needs,
  transitively. Only a package with programs has them.
- Extension lines: after `summary`.

**The archive**: members in exactly this order and nothing else:
`+MANIFEST` (mode 644), each `file` in the manifest's order (its mode),
`+TABLES/<path>` for each program in order (mode 644); then two blocks of
512 NULs and the end of the file. At most 4 GiB. The ustar form
(`ustar.py`): each header is a function of (path, mode, size) alone:

| Bytes | Field | Value |
|---|---|---|
| 0..99 | name | the path, NUL-padded (exactly 100 bytes: no NUL), or its part after the split |
| 100..107 | mode | `0000644\0` or `0000755\0` |
| 108..123 | uid, gid | `0000000\0` each |
| 124..135 | size | 11 octal digits, `\0` |
| 136..147 | mtime | `00000000000\0` |
| 148..155 | chksum | 6 octal digits, `\0`, space: the sum of the 512 bytes as unsigned, this field counted as 8 spaces |
| 156 | type | `0` |
| 157..256 | linkname | NUL |
| 257..264 | magic, version | `ustar\0` then `00` |
| 265..328 | uname, gname | NUL |
| 329..344 | devmajor, devminor | `0000000\0` each |
| 345..499 | prefix | the part before the split, NUL-padded, or NUL |
| 500..511 | | NUL |

A path over 100 bytes is split at its last `/` within its first 156
bytes (the prefix at most 155); the rest must be 1..100 bytes, or the
path can't be packaged (the packager refuses it). Data is NUL-padded to a
multiple of 512. **A reader rebuilds each header from the path, mode and
size it read and compares all 512 bytes**: what another writer would vary
(owners, times, pax or GNU headers, links, directories, devices, the
checksum's other spellings) is refused by that one comparison.

**Reading a package** (`pkgverify.verify_package`, and PO4's reader):
the first header is `+MANIFEST`, mode 644, size 1..4 MiB; its bytes are
checked as a signed text and parsed, nothing else read before; the ABI
stamp must be the running build's (pkg's `-f` aside); then the members
one by one are exactly the manifest's (path, mode, size, in order), each
file's SHA-256 its line's, each table's SHA-256 its line's **and** the
table computed from the file just read; padding NUL; the two end blocks;
nothing after them.

**The page-hash table** (`+TABLES/<path>`; proposed as allow.d's format
for PX, so init can compare its own table with the shipped one byte for
byte): a 64-byte header, little-endian, then the hashes:

| Bytes | Field |
|---|---|
| 0..7 | magic `JAMPAGES` |
| 8..11 | version: 1 |
| 12..15 | the page size: 4096 |
| 16..23 | the file's size (1..1 GiB) |
| 24..31 | pages: ceil(size / 4096) |
| 32..63 | the SHA-256 of the whole file |
| 64.. | pages x 32 bytes: the SHA-256 of each 4 KiB page, page 0 first, the last zero-padded to 4096 bytes |

`vmo_make_exec_verified` takes the bytes from 64 on. `make check` builds
`tools/pagetable.c` twice, with `user/lib/sha256.c` and with
`kernel/lib/sha256.c` (each compiled as it is, against a stand-in
`<os.h>` or `<jam/string.h>` for memcpy), and compares their tables with
the packager's on eleven sizes around the page and padding edges and on a
real staged program: equal.

**What goes in**: the main package `<port>` has the stage's programs,
its `files` no `subpackage` claims, and the licence texts in
`share/licences/<port>/`; each `subpackage <name>` makes a package
`<name>` of the files it claims and the licence texts again, in
`share/licences/<name>/` (two packages never own one path), summary
`<the port's summary> (<name>)`, no `runs`, no `built-with`. A
`multicall <program> <name>...` name is a copy of the program beside it
(`bin/unxz` for xz) with its own `file`, `program` and `table` lines:
FAT32 has no links (a line naming two paths for one stored file is a
possible later extension; xz's package is 1.7 MB for it). A port with
only `library` lines makes no package. A staged symlink (`copy` in
stage.txt) is an ordinary file.

### The index (`INDEX`)

```
jamos-ports 1
serial <serial>
made <made>
abi <abi>
<extension lines>*
package <name> <version> <revision> <size> <sha256> <port>    sorted by name, strictly; at most 4096
runs <name> <dep> [<least version>]*   right after its package line; <name> is that package's; deps sorted, strictly, at most 64
src <port> <version> <revision> <size> <sha256>*   after all packages; sorted by port, strictly
signature <hex>
```

At most 1 MiB. A package's size is 1,536 bytes..4 GiB, a source's
0..4 GiB. Across lines: every `runs` dep is a package of this index of
at least the version named; every package's (port, version, revision)
has its `src` line, and every `src` line is some package's. Every
package has the index's `abi`. **The repository's paths are derived,
never read**: `pkg/<name>-<version>-r<revision>-<the first 16 hex digits
of its sha256>.jpk` and `src/<port>-<version>-r<revision>-<16 hex>.src.tar`,
so a rebuild of one version and revision (a new sysroot, a needed
library's fix) is a new file, never a file changed under a reader.

**The serial**: `ports.py repo` writes the larger of the last INDEX's
serial + 1 and the time (seconds since 1970), so it grows with every run
and still grows after `build/repo` is deleted and made afresh. pkg keeps
the last accepted (serial, SHA-256 of the index's text): a lower serial
is a replay, refused; the same serial is taken only with the same bytes
(two indexes with one serial: refused). Overriding it (a repository made
afresh with the Mac's clock wrong) is pkg's `-f`.

**Upgrades** (for PO6): a package is newer when its (version by the
order above, revision) is above the installed one's, **or** both are
equal and its SHA-256 differs from the installed package's (a rebuild:
the signed, fresh index says which bytes are current). So pkg records
each installed package's SHA-256 beside its manifest in db/.

### VULNS

```
jamos-vulns 1
serial <serial>                 the index's of the same run
made <made>
<extension lines>*
vuln <component> <first> <fixed> <fixrev> <id> <summary>*   sorted by "<component> <id>" bytewise, strictly; at most 4096
signature <hex>
```

At most 1 MiB. `<component>` is a name; `<first>` a version or `-`
(from the start); `<fixed>` a version or `-` (no fix yet); `<fixrev>` a
revision or `-`, and `-` when `<fixed>` is; `<summary>` the rest of the
line, a text. A component at version V and revision R (0 for a
`built-with` line without one) is **affected** when (`first` is `-` or
V >= first) and (`fixed` is `-`, or V < fixed, or V = fixed and
`fixrev` is a number above R). `pkg audit` checks each installed package
by its own name, version and revision and by each of its `built-with`
lines (`pkgverify.affected`). Replays are refused as for the index, with
VULNS's own last (serial, SHA-256).

`ports.py repo` makes VULNS from **`ports/vulns`**: `vuln` lines in
exactly this grammar (blank lines and lines starting with `#` dropped:
the owner's confirmed items), sorted on the way in. `ports/vulns` holds
only its comment so far, so VULNS has no entries.

### Source tarballs

`src/<port>-<version>-r<rev>-<hash16>.src.tar`, the same ustar form,
members under `<port>-<version>-r<rev>/`, sorted: `README`,
`distfiles/<file>` (each source as fetched), `vendored/<dir>/...` (a
vendored source), `port/...` (the port's directory), `shared/...`
(config.site, jamos.cmake, jamos.meson), and `jamos-tree`: one line,
`jamos-tree <commit> <file> <size> <sha256>`, or `jamos-tree unknown - -
-` without git. The tree is `src/jamos-<12 hex of the commit>.tar`, `git
archive` of HEAD, or of a `git stash create` commit when tracked files
have changes (no stash entry is made), shared by every port built from
it (about 42 MB). Every port has one (one rule), so a GPL package's
complete source (its sources, patches, recipe, build files and the Jam
OS tree it links) is always in the same repository.

### The repository and its server

`ports.py repo` builds the ports named (default: every `place package`
recipe) and every package they `runs`, transitively; packages each and
checks each with the reference verifier; writes the packages and sources
(whole files, by rename), then VULNS, then INDEX, so an index never
names a missing file; then deletes what neither the new index nor the
one before names (a client that fetched the old index a moment ago still
finds its files), keeping the tree tarballs those sources name. Only
jamos-sign reads the secret key.

`tools/ports-server.py` serves `build/repo` on port 8080 (`--bind`
0.0.0.0; `--client` answers only that address): GET and HEAD of
`/INDEX`, `/VULNS`, `/pkg/<file>`, `/src/<file>`; no listing, query,
`%`, part starting with `.`, symlink or non-regular file (400, 404, 405).
Each answer is one snapshot: read whole, checked unchanged (size, times,
inode) from open to the end, read again if it changed, 503 after five
tries (a file growing while read is caught at its size + 1), with
Content-Length and `Connection: close`. Its self-test runs a real server
against Python's client: the files, HEAD, every refused path, a file
rewritten in place mid-read (the answer is the new version whole, never
a mix), one that keeps growing (503), one replaced by rename.

**The Makefile**: `PORTS_KEY ?= ~/.config/jamos/ports.pub`, copied into
bootfs as `/boot/ports.pub` (the same `ed25519 <64 hex>` line as
`update.pub`: `update_key_parse` reads it) when the file is there;
`PORTS_KEY=`, or a machine without the key, builds an image without it
(a public build: pkg refuses every repository). `make ports` runs
`ports.py repo`. `make check` builds `build/host/pagetable-libos` and
`-kernel` and runs `ports.py vectors` and `ports-server.py --self-test`
beside the self-test. `*.key` is in .gitignore.

## PO4 notes

What track PO4 (the formats on Jam OS) built: the C readers of PO3's
formats, the journal's format, and the tests that hold the C and the
Python readers to each other. Written against main 29ebfe1a.

**What there is.** `user/include/pkgfmt.h` (the whole API and its
contracts) and, in libos, `user/lib/pkgfmt.c` (the common rules: the
signed-text prologue, fields, extension lines, the serial's replay rule,
the version order, the path grammar), `pkglist.c` (a program's list: its
encoded field, what a package may not ask for, the ELF note finder),
`pkgmanifest.c`, `pkgtar.c` (the ustar header, the page-hash table, the
package whole and as a stream), `pkgindex.c` (INDEX, VULNS, `pkg audit`'s
range rule, the repository's derived file names), `pkgjournal.c`.
`pkgint.h` is theirs alone. None calls an allocator or a system call, so
`tools/pkgcheck.c` builds the same files on the Mac (`make check`,
ASan and UBSan). Only `pkgfmt.c` links Monocypher (the rule is in the
Makefile beside `updsig.c`'s, and `user/posix/posix.mk` leaves the file as
libjam.a has it); a program that does not call a pkg function links none
of it. Big structures (a manifest 275 KB, an index 800 KB) go on the
heap; readers keep pointers into the text, which must outlive them.

**How it reads** (the order PO3 asked for): the size bound, the first
line, the bytes, the signature line's shape, **the signature**, then the
grammar line by line in its fixed place, then the rules across lines. A
reader returns `OK`, `ERR_INVALID_ARGS` (a grammar rule), `ERR_OUT_OF_RANGE`
(a size bound), `ERR_NOT_SUPPORTED` (a must-understand line, or another
version of the format's first line), `ERR_ACCESS_DENIED` (no signature, a
signature that is not the key's, bytes that are not the signed ones, a
list a package may not ask for), `ERR_BAD_STATE` (a replayed serial) and a
static `why` string. `pkg_manifest_parse_unchecked` and the index and
VULNS twins skip the signature for tests and the host check; nothing else
may call them.

**The archive.** A reader does not parse ustar headers: it rebuilds each
member's header from the (path, mode, size) the signed manifest promises
(`pkg_header_make`) and compares all 512 bytes; only the first member,
`+MANIFEST`, has its size read (`pkg_first_header`, then the same
comparison). `pkg_package_verify` checks a package that is in memory (the
manifest, the ABI stamp, every member in order, each hash, each table
against the one computed from the program, each program's ELF note against
its list, the padding, the two end blocks, nothing after). `struct
pkg_reader` does the same as bytes arrive, for a package too big for
memory: `pkg_reader_next` (a header) / `_data` (bytes in pieces of any
size) / `_done` (padding and the SHA-256) per member, then `_finish`; it
keeps the programs' page hashes in memory the caller gives
(`pkg_tables_bytes`: 32 bytes a page, 16 MiB for 2 GiB of programs) so
each table member is compared with the table its program made. It does
not read the ELF notes (the bytes are not kept): whoever installs a
program checks it (`pkg_elf_list_is`, or init's `wants_read`).
`pkg_tabler_*` makes (or compares) one table as bytes arrive: init's
comparison of its own table with the shipped one is one `memcmp`, or this.

**The page-hash table's magic** is `JAMPAGES`, as `<dataprog.h>` (PX) has
it; PO3's `jampages` was a proposal. PO3's writer, `tools/pagetable.c`
and the vectors now use PX's, so the shipped table and
`/data/etc/allow.d/<sha>` are the same bytes. `t_pkgfmt_table_is_allowd`
checks `pkg_tabler` against `dp_ptable_head` and `dp_ptable_hash`.

**What a package may not ask for** (`pkg_list_refused`): the words
`allow` refuses a program on `/data` (`dp_wants_refused`, same list;
`t_pkgfmt_lists_are_allows` compares the two on every word) and a list
without `posix`. That is a subset of the Mac's rule (`tree.list_problems`
knows every service); the final check is init's, with `wants_read` and
`dp_wants_refused`, on the program it reads.

**The journal** (`jamos-pkg-journal 1`, `/data/pkg/db/journal`; PO6
writes it with `pkg_journal_write`, PO5's settle reads it with
`pkg_journal_parse`). Lines in this order, each `\n`-ended, printable
ASCII, the grammar in `<pkgfmt.h>`: `op install|upgrade|remove`, `name`,
for install and upgrade `version`, `revision` and `manifest <sha256>`
(the SHA-256 of the new package's manifest, kept as `db/<name>.new` until
the swap is done: the journal alone must be enough to finish or undo),
for upgrade and remove `old <version> <revision> <sha256>` (the installed
manifest, `db/<name>`), `step`, upgrade's `busy <path>` lines (files left
at their `.new` names because a program runs from them: sorted, at most
4,096) and `end <sha256 of every byte before it>`. The steps are `begin
staged approved swapped revoked removed recorded`; install goes through
begin staged approved swapped recorded, upgrade adds revoked after
swapped, remove is begin revoked removed recorded (`pkg_journal_next`).
The end line makes a write cut short unreadable; the journal is not
signed, since only `pkg` and init can write `/data/pkg/db`, and a reader
trusts nothing it names (every file is checked against its signed
manifest). The text is canonical: what the reader accepts, the writer
writes back byte for byte (the fuzz test checks it).

**The tests.** The checks are written once, in `user/tests/utest/`
(`pkgcases.c` the vectors, `pkgfuzz.c` the mutations, `pkgjnl.c` the
journal, `pkgmisc.c` the small parts), and run in two homes: utest on Jam
OS (`pkgfmt.c`: `pkgfmt_vectors`, `_misc`, `_journal`, `_fuzz` and the
three comparisons with `<dataprog.h>` and `wants_read`; the vectors are
linked in by `tools/pkgvec2c.py` as `build/gen/pkgvectors.c`) and
`build/host/pkgcheck` in `make check`. They cover: every line of
`ports/vectors/CASES`, a package read whole and as a stream of random
chunks (the two must agree), `multi.jpk` (a vector added here: three
programs of different page counts, forty files, a path long enough for
the ustar prefix, an empty file), the version order, the path grammar,
lists, headers (any one changed bit of the first header is refused), page
tables against a hand-made one in every mode, ELF notes cut at every
length, the repository's names, the audit's range rule, and 10,000
mutations of packages, indexes, VULNS and manifests (with the signature
checked, a mutant is refused unless it is the original; read without it,
it keeps every rule of the format; both under the sanitisers on the Mac).
**`tools/ports.py pkgfuzz DIR`** adds the Python reference's side: about
3,800 mutated texts, archives, version pairs and paths with the answer
`pkgverify.py` gives each, and `pkgcheck` fails on any difference, in
either direction. It found a leniency in the reference's test-only
unchecked mode (a last line `sIgnature <hex>`), fixed in `pkgverify.py`.

**For PO5 and PO6.**
- init: `pkg_manifest_parse` with `/boot/ports.pub` (`update_key_parse`),
  `pkg_tabler` or `pkg_tables_bytes` for its own table of a program it
  read back, `pkg_elf_list_is` or `wants_read` for the note.
- bin/pkg: fetch the INDEX, `pkg_index_parse` with a `struct pkg_last`
  from `db/serial` (and the SHA-256 of the text kept beside it), derive
  the package's URL with `pkg_repo_path`, check the fetched bytes with
  `pkg_index_check`, read the package with `struct pkg_reader`,
  `pkg_version_cmp` for upgrades (plus the SHA-256 rule in PO3's notes),
  `pkg_vulns_parse` and `pkg_audit` for `pkg audit`.
- The caps (`PKG_FILE_MAX`, `PKG_FILES_TOTAL_MAX`, `PKG_ARCHIVE_MAX`) are
  `<pkgfmt.h>`'s and `pkgformat.py`'s, the same numbers (PO13 raised them).

**Not done here**: init's and `pkg`'s use of any of it (PO5, PO6); the
program lists' full rule set in C (the build's `checkwants.py` stays the
Mac's); compression (a must-understand manifest line later).

## PO5 notes

What track PO5 (the guard and init's approvals) built, against main
e06dd914.

**The guard.** `FS_VIEW_GUARD_PKG` (32, `<fsview.h>`; `FS_VIEW_FLAGS` is
63 now) refuses every change at or under the top-level `pkg`, the name
compared as FAT compares it (`fs_view_in_pkg`: case, leading spaces,
trailing dots and spaces), exactly as `FS_VIEW_GUARD_ETC` does for etc:
opens that write, mkdir, unlink, rename (either name), setattr, link,
and a writable subview rooted at or under it. Checked in libos's
`fs_view_check` (fat's views and fsserver use it unchanged) and in
extfs's `walk_may_change` and `views_sub`, judged where the path resolves
(a link into pkg is pkg); extfs had to change too, or it would have taken
the new bit without enforcing it. So with ext by default (M13.6's U11a)
`/data/pkg` is guarded already: nothing more for extfs (utest
`extfs_views` covers it; the name is folded as FAT folds it there too,
the stricter). init's approvals and settle use only libos's file calls
(the settle removes a file before renaming over it, which FAT needs and
ext doesn't mind). Every `:w` grant (`<os.h>` "grants")
sets it, on every mount, not only `/data`: a stick's top-level `pkg` is
read-only to programs too, and the prefix keeps its guard when M13.6
moves it to another mount. `:wp` is `/data` writable with only etc
guarded and hidden: bin/pkg's.

**The want** `mount /data rw pkg` (four words, `/data` and `rw` only)
grants `/data:wp`, shown as "/data (write, the packages too)".
`tools/checkwants.py` takes it only under user/services/ (not a test, not
a port); `dp_wants_refused` refuses it ("mount /data rw pkg"), so does
`pkg_list_refused` (and `pkgfuzz.py`'s copy), and utest's
`pkgfmt_lists_are_allows` holds the two to each other on it.

**pkgctl** (`abi/idl/pkgctl.idl`, protocol 85; `initctl.pkg_channel`,
method 13, the shell's channel only). init's side is
`user/services/init/pkg.c` (the channel, a worker thread as update.c's,
`KEY_PKG`) and `pkgapprove.c` (the work on paths given, so utest runs it
over a RAM disk: `pkgapprove.h`). Choices:

- **What approve trusts**: the manifest's signature by `/boot/ports.pub`
  (no key: every approve refused, "this build has no ports key") and the
  bytes init reads back itself. The manifest is copied out of bin/pkg's
  VMO first; each program is read whole into a VMO only init holds
  (`file_read_vmo`, at most `PKG_FILE_MAX`; **PO13 changed this: it is
  read in pieces, see its notes**), and every check is of those
  bytes: size and SHA-256 against the `file` line, the page table made
  from them (`pkg_tabler`) against the `table` line's size and SHA-256
  (the shipped `+TABLES` member is never read: the table written is
  init's own, and the test checks it is the shipped bytes), the ELF note
  against the manifest's list byte for byte (`pkg_elf_list_is`; so the
  list shown at install is the program's), `wants_read` then
  `dp_wants_refused` and `posix`. The file can change afterwards: the
  line approves the hash.
- **All or nothing**: every program checked first; then the tables, then
  the approvals' file written once, whole. A refusal writes nothing.
- **The line**: `<sha>\t/data/pkg/<path>\t<list as shown>\tpkg=<name>
  <version>-r<revision>`. The tag uses a space and `-r`, not the plan's
  `vim-9.1.0-r1`: names and versions may both hold `-`, so that form
  can name two packages; this one can't (a name has no space, a revision
  no `-r`). `dp_allow_tag` (`<dataprog.h>`) cuts it off a line's list.
  The same line twice is written once; a line for the path tagged with
  another package's name refuses the approve (two packages can't own one
  program); the owner's own lines (no tag) are left alone; old versions'
  lines stay until revoke (an upgrade's swap may run either).
- **STAGED** (`pkgctl.STAGED`): the programs are read at `<path>.new`, the
  lines name `<path>`. Any other flag bit: ERR_INVALID_ARGS.
- **revoke** (name, version, revision): every line with that exact tag,
  then the tables no line names; never an untagged line. It needs no
  signature (taking back is the safe direction).
- **No downgrade rule.** init can't tell an old signed package from a new
  one: `db/` is bin/pkg's to write, so a check against `db/<name>` would
  stop nothing a compromised bin/pkg couldn't undo first. The replay
  defence is the index's serial (bin/pkg's) and the owner's yes; a
  replayed manifest of another version fails on the hashes of the files
  actually there. **For the owner**: a compromised bin/pkg could
  reinstall an older signed version of a package; acceptable?
- **One channel**, one call at a time (the next request waits in the
  channel until the worker is free); a newer `pkg_channel` closes the
  older unless a call is being worked on (ERR_BAD_STATE). Answers are
  logged: `init: pkg: approved N programs`, `init: pkg: refused: <why>`,
  `init: pkg: revoke <tag>: N lines`.

**The settle** runs on the worker when `/data` first comes
(`data_came`), before anything else is asked of it. The commit point is
an install's or an upgrade's `approved` and a remove's `begin`: before
it the transaction is undone (the new manifest's files at `.new` go, any
line of the new version goes unless that version is the one installed,
`db/<name>.new` goes), from it on finished (each `.new` renamed over its
path, an upgrade's files the new version lacks removed, by FAT's names,
the old version's lines revoked, `db/<name>.new` made `db/<name>`; a
remove revokes, removes its files and its record). Every file touched is
one a signed manifest names, under the prefix, and that manifest's
SHA-256 must be the journal's. Every step can be done twice, so init
doesn't rewrite the journal as it goes: it removes it at the end, and a
cut during the settle settles the same way next time. A torn journal,
or one with no ports key, is left for bin/pkg and said in the log
(`init: pkg: settle: ...`). Busy files: at boot nothing runs from
`/data` yet, so their `.new` is renamed like the rest. **For PO6**: these
are init's step meanings (a step names what is done); bin/pkg's own
recovery should agree, or call nothing and let the next boot settle.

**The shell**: `allow -l` shows a package's line as `<list> [package
vim 9.1.0-r1]`; `allow -r <name>` over any package's line, and `allow
<file>` over a path one holds, refuse (sh_allow.c's rewrite: ERR_BAD_STATE,
nothing written) and say `pkg remove` takes it back.

**Known gaps.** The shell and init both rewrite `/data/etc/allow` whole
with no lock between them: an `allow` typed while a package installs can
lose init's new line (the program is then refused, never wrongly
allowed), and one racing a revoke can write the revoked line back (a
program whose files `pkg remove` deleted next; its bytes would still
have to be the signed ones). The plan's "the shell gets the channel from
init and hands it to bin/pkg" is PO6/PO7's (the shell's `pkg`); no
abi stamp is checked (PO7's `abi` line). Empty directories a remove
leaves stay.

What track PO8 built so far: **tools/ports-test.sh**, the ports half

**What there is.**
- `tools/ports-test.sh <outdir> <port>...`: builds the ports and their
  `runs` closure (`tools/ports.py build`), and for each port makes a copy
  of `build/jamos.img`, preinstalls into its data partition, boots it

  `<outdir>/<port>/` (serial log, screenshot, the generated `script.txt`;

- `tools/ports-preinstall.py`: `closure <port>...` (the ports to install),
  and `install <image> <port>...` (the mtools side, below). On the Mac's
  Python 3.9 and the PC's 3.12. It reads `build/ports/<name>/stage/stage.txt`
  and does not touch `tools/ports.py`.
- `ports/<port>/test` for zlib and xz.

**What is written into the image**, as `pkg` and init will have made it
(section 9's layout: the prefix is `/data/pkg`, paths relative to it, not a
directory per package):
- `/data/pkg/<path>` for every `program`, `file` and `licence` line of the
  stage list (the `library` files never go into a package; a `-test`
  subpackage's files are `file` lines too, so they are installed);
- `/data/pkg/db/<name>`: the manifest. **As first built (PO8) it was
  `jamos-pkg 1` with the `file`, `program` and `built-with` lines and no
  signature, which `pkg list` showed as "damaged". Since PO7 it is the
  signed manifest `ports.py package` makes** (the packages of
  `package.plan`, one for each `subpackage`, their `abi` the tree's stamp,
  `table` lines too), signed with the ports vectors' test key;
  `tools/ports-test.sh` puts that key's public half in the image as
  `/boot/ports.pub`, as `tools/pkg-test.sh` does: see the
  [PO7 notes](#po7-notes);
- `/data/etc/allow`: `<sha-256>\t/data/pkg/<path>\t<what the list asks
  for>` per program, the text as `<wants.h>` shows it (`/data (write)` for
  `mount /data rw`), since PO7 with the package's tag
  (`\tpkg=<name> <version>-r<rev>`) and its page table in
  `/data/etc/allow.d/<sha-256>`. Written by the Mac, so no `allow` question
  is asked;
- each program is read back from the image and its hash compared with the
  stage's before the boot; and the generated script runs `allow -l` and
  waits for every approval line, so a test that passes proves the shell
  read them.

**Programs run from `/data` on main today** (M8.6's `allow` path: the
shell reads the file whole into a VMO it alone holds, hashes it and runs
it if a line of `/data/etc/allow` has that path and hash). So the
approval lines are enough, and `run /data/pkg/bin/minigzip` works. Not
yet: PX's page-hash tables in `/data/etc/allow.d/` (the preinstall will
write them once PX has merged; the shell reads a program whole until
then), PO7's `/data/pkg/bin` on PATH (a test runs `run $P/<program>`;
when PATH has it, `$P` still works), `db/serial` and `db/journal` (PO6),
and the `pkg=` tag on the approvals (PO5). Nothing was copied to another
place to make a program runnable: the programs run from their package
paths.

**A port's `test`** is a script in the shell tests' format
(`tools/serial-feed.py`; `tools/shell-tests/*.txt` are the examples). The
generated script boots to the shell and, before the test, sets `T=x`,
`P=/data/pkg/bin` and `S=/boot/usr/bin` (sbase's tools) and goes to
`/data`; after it, it prints a done line, `reboot -f` and waits for the
reset. The test passes when every `wait` matched. Gotchas found writing
the first two (each cost a run):
- `wait 43771 text` is a **timeout of 43771 s** for `text`, not a wait for
  43771: a number first is read as the seconds. Make a number's line start
  with letters (`run $S/wc -c f | run $S/sed s/^/size-/`, then `wait
  size-43771 f`). A wrong number then fails, as it should (checked: a
  size changed by one failed the run).
- Build the text waited for from `$T` so it is not in the typed line; a
  hash or a plain output line needs no trick.
- The shell's own commands (`seq`, `cat`, `wc`, `sort`, ...) win by name and
  only POSIX programs take `<` and `>`: `run $S/seq 1 20000 > f`. The shell's
  `cat` refuses a binary file (use `cmp` or `sha256sum`); `sha256sum`
  takes a pipe and prints `<hash>  -`.
- A deterministic input needs no file in the repository: `run $S/seq 1
  20000 > f` is 108894 bytes whose SHA-256 the test carries.

**What it proved** (2026-10-11, the PC through `tools/remote-test.sh`,
both ports in one call, both PASS): zlib 1.3.2's minigzip, run from
`/data/pkg/bin`: compress and `-d` in place, `-c` to a file and through
a pipeline, levels 1 and 9, the same bytes out of two runs, a 3 MB
binary (`bin/utest`) and an empty file, hashes checked against values made
on the Mac; the compressed size (43771) is the 10-byte header, Python's
level-6 deflate and the 8-byte trailer; damage in the stream and in the
trailer fail with status 1; a file that isn't gzip comes out as it is, and
one cut short is taken quietly (upstream's own, the Mac's build of the same
source does the same). xz 5.8.4: `--version`, `-k`, `-t`, `-d`, `-c`
and pipes, presets 0 and 9, `-C sha256`, `-T2`, a text that isn't xz and a
damaged one (status 1 each), and a binary. Negative controls: a size
changed by one in zlib's test, and in xz's, each FAILed with its `wait`
named.

**Not done here**: pkg-test.sh (PO6's `pkg`); the `-test`
subpackage path has no port using it yet (zlib's `example` is PO9's);
`allow.d` tables (PX): done in PO7, with the signed manifests and the tags.

## PO6 notes

What track PO6 (bin/pkg) built, against main 3b25ffd1 (merged with main
21f0d1c7 before its last runs).

**What there is.** `user/services/pkg/` (bin/pkg, a native libos program):
`fsx.c` (every change to the prefix goes through it), `db.c` (what is
installed), `plan.c` (pure: order, dependents), `unpack.c` (a package as its
bytes arrive), `journal.c`, `txn.c` (one package's install, upgrade or
remove, and the settle), `http.c`, `repo.c`, `ctlc.c` (init's pkgctl
channel), `cmds.c` and `install.c` (the commands), `main.c`; `pkg.h` has the
shape. The commands are section 8's: `update [-f]`, `install <name>... |
<file.jpk>...`, `upgrade [<name>...]`, `remove [-r] <name>...`, `list [-u]`,
`info`, `files`, `audit`, `check`. Its list: `svc net`, `svc dns`, `mount
/boot r` (the ports key, the ABI stamp), `mount /usb* r` (a package to
install from a stick) and `mount /data rw pkg`: no `/data/etc`, so the
shell reads `pkg.repo` (else port 8080 of `net.host`) and passes it as
`pkg -R <address> <command>`; `pkg -R <address> ...` typed by the owner
uses another repository for that command. Roles (`<roles.h>`): `PKG_SR_CTL`
(init's pkgctl channel, given only to the commands that change things and
to `check`), `PKG_SR_ASK`, and `PROGRAM_SR_STOP`.

**The shell's side (PO7's, built minimal here because the end-to-end run
needs it).** `user/services/shell/cmd/pkg.c` takes the channel from init,
starts bin/pkg as a helper with it and the question's channel, and
`sh_run_helper_tick` (sh_program.c, a hook called every 50 ms by the
helper's wait loop with the read end of its output) lets it show a question
after the lines that lead to it. **The question's protocol** (the plan left
it open: a helper has no stdin): bin/pkg writes one message, the question's
text ("Install 3 packages, 2 programs?"), on `PKG_SR_ASK`; the shell shows
it with `[y/N]`, takes one key as `allow` does (typed-ahead keys dropped
first), and answers with one byte, `y` for yes. bin/pkg never reads the
keyboard and has no `-y`, so every approval is a key the owner typed. Not
here (PO7's): PATH's `/data/pkg/bin`, `type`, Tab, `update`'s abi line,
the shell test of `pkg list`/`pkg info` on a preinstalled package. **For
PO7/PO8**: bin/pkg reads `abi <16 hex digits>` from `/boot/build.txt` when
it is there (and refuses an index or package of another stamp); with no such
line nothing is checked. And PO8's preinstall writes manifests with no
signature line, which PO4's parser refuses (`pkg list` shows them as
"damaged"): write real signed ones, or at least a bare `signature` line.

**The transaction** (txn.c) follows section 9 and init's settle step for
step (the step names are init's: a step names what is done; the commit point
is `approved`, a remove's `begin`). install: journal `begin`, the manifest as
`db/<name>.new`, every file at `<path>.new` (written through a 64 KiB gather
buffer, synced, read back against its hash), `staged`, `pkgctl.approve`
(STAGED), `approved`, each `.new` renamed to its path (the old file removed
first), `swapped`, upgrade: `revoke` of the old version's lines (unless the
same version and revision: a rebuild, whose lines share the tag), `revoked`,
`db/<name>.new` made `db/<name>`, `recorded`, the journal gone. Failure,
refusal by init or Ctrl+C before the commit point undoes it at once (init's
undo: the staged files, the new version's lines, the new manifest). One code
runs both a transaction and the settle (`forward`, `undo`, `forward_remove`),
so they cannot disagree, and `pk_settle` runs at the start of install,
upgrade, remove and check. **The journal is replaced by writing
`journal.new`, syncing, removing `journal` and renaming**: FAT cannot rename
over a file and a torn in-place write would lose the step. A cut between the
removal and the rename leaves `journal.new` alone, so **init's settle was
changed (pkgapprove.c, a small edit outside this track's files)**: it reads
`journal.new` when there is no journal (cut short with no journal: nothing
began), and removes it with the journal; without that, init could undo an
install that a newer `journal.new` already committed and bin/pkg would then
finish it from the stale file. A running program's file: a file that fat
refuses to remove (`ERR_BUSY`) goes to the journal's `busy` lines with its
`.new` left, the journal stays at `approved` and `pkg` exits 3 ("vim is
running: ... run `pkg upgrade` again"); a removal revokes, removes what it
can and stays at `revoked`. The next run (or boot) carries on; `pkg check`
accepts either version's file for a package whose upgrade waits. A file
fat holds open is `ERR_BUSY` to `fs_unlink` today (utest `pkgtxn_busy`), so
the case is real before M12.5's Q7. Empty directories a removal leaves are
removed by `pkg remove` (best effort, not by init's settle).

**Choices the plan left open.**
- *Names the database keeps*: `serial`, `journal` and any name ending `.new`
  or `.sum` are refused as package names, and a package may not have a file
  under `db/` or ending `.new` (the staging name): checked when the head is
  read (so the owner is told before the question) and again before any write.
- `db/<name>.sum` holds "`<manifest sha> <package sha>`" lines (the old and
  the new one during a transaction): a rebuilt package of the same version
  and revision is newer by the signed index's hash (PO3's rule), and a line
  whose manifest is not the installed one is ignored, so a settle by init
  (which knows nothing of sums) leaves a usable file. With no sum a package
  is not "different".
- `db/serial` has `index <serial> <sha>` and `vulns <serial> <sha>` lines,
  written as `serial.new` and renamed (and read from `serial.new` if the
  rename was cut). Any index that parses is recorded; a damaged file is an
  error, not "nothing accepted". `pkg update -f` takes a lower serial.
- A package from the repository is fetched twice: its first bytes (the head:
  512 bytes of header and the signed manifest, then the connection is
  closed) for the question, and the whole after the yes, which must have
  that very manifest (the unpacker is given its SHA-256) and, whole, the
  size and SHA-256 the index names. Only then does init see it.
- bin/pkg refuses redirects and anything but `200`, bounds every wait
  (resolve and connect 10 s, head 20 s, a body that sends nothing 30 s, the
  whole transfer 60 s plus 16 KiB a second), and retries a connect made
  between the address and the link.
- `pkg install <file.jpk>` upgrades what is installed and refuses an older
  version ("remove that first"); its `runs` must be installed already. Files
  from a stick and names from the repository are not mixed in one command.
- Conflicts: a file another installed package has, or two packages of one
  plan have (by FAT's names), is refused before the question; a program with
  the name of a boot image program (`/boot/bin`, `/boot/usr/bin`) is a note
  in the plan.
- `pkg remove` asks too ("Remove 2 packages?"); `-r` removes what `runs` the
  named packages (dependents first); no dependency is removed because its
  dependents went.

**The transaction code runs over any prefix and any init** (`struct
pk_env`: the prefix, the key, the pkgctl calls as functions, and a hook that
takes the power away before the n-th change to the prefix), so utest runs it
over fat on a RAM disk against init's real `pkgapprove.c`, with packages
made and signed in the test (`user/tests/utest/pkgmk.c`).

**Tests** (docs/TESTING.md rows `pkgtxn.txt`, `pkgcut.txt`, `pkg-test.sh`):

## PO13 notes

**The limits.** A file is at most 1 GiB (`PKG_FILE_MAX`: `VMO_VERIFIED_MAX`,
