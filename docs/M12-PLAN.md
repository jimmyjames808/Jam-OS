# M12 plan: the interface review

Status (2026-10-07): a plan, nothing built. Written against main e323fefd,
with G1 built and merged and its PC sign-off still to come. **Waiting for
the owner's answers to the questions below before any agent starts.** M12
is wave 3 of [PLAN-M11-M12.5.md](PLAN-M11-M12.5.md#wave-3-m12-alone): it
runs alone, after waves 1 and 2 changed the interfaces, and nothing else
may change them while it runs.

Goal ([roadmap](ROADMAP.md#later)): **the system calls and the service
protocols reviewed and reshaped while changing them is cheap, before
POSIX (M13) builds on them and M14 freezes them, G1's compositor protocol
among them. devmgr's disks, filesystem services and mounts move into a
service of their own, and devmgr's protocol into IDL; variable-length IDL
arrays.**

**Done when** (the roadmap's row, "the review's findings fixed; nothing
frozen yet", made concrete):
- every finding of the four reviews (below) is fixed, or has an owner's
  "leave it" with the reason written next to it;
- devmgr holds no storage code, and both its protocol and the new
  storage service's are IDL files; the hand-written protocols left are
  named, each with why;
- the IDL has variable-length arrays, and `console.write` no longer
  copies 2048 bytes for every line;
- every kernel need of M13's POSIX layer is either built (and tested) or
  written down with its shape and its milestone;
- the call path is no slower: the reply-and-wait line in
  [BENCH.md](BENCH.md) no worse than its 765 ns on the PC;
- and, as every milestone: All tests and `soak 10` on the PC.

## What M12 is not

- **No freezing.** M14 freezes, after M13 has put its weight on the
  interfaces; M14 starts by reviewing what M12.5, M12.7, M13, M10 and
  M10.5 add ([ROADMAP.md](ROADMAP.md#later), M14's row).
- **No code check.** M12.1 reads all the code changed since M8.6's check
  (2079f350), the unchanged callers of every interface M12 changes, G1's
  docs pass and G1's independent review (the owner, 2026-10-05 and
  2026-10-07). Files over 800 lines and the service internals that touch
  no interface (the mixer's synchronous calls to hda, hda's one loop) are
  M12.1's or later.
- **No pagers** (M12.5): no file-backed or copy-on-write VMOs, no `mmap`
  of files.
- **No NVMe or GPT code** (M12.7). M12 may shape the disk protocols for
  them (question 7), nothing more.
- **No POSIX** (M13): no musl, file descriptors, `posix_spawn`, signals,
  terminal layer or pipes in libc. M12 only makes sure the kernel and the
  protocols have what M13 will stand on (questions 8 to 10 and 17).
- **No speed work.** The call's last 165 ns are a follow-up of their own
  ([ROADMAP.md](ROADMAP.md#smaller-follow-ups)); M12 only must not make the
  call slower.
- **No drivers that outlive their process**: their milestone comes after
  M12 ([M11.6-PLAN.md](M11.6-PLAN.md#x-drivers-the-design-note)); M12
  reviews fat's and the mixer's interfaces they will copy.
- **No new Wayland interfaces or versions**: those are additions G2's first
  ports ask for; upstream's protocols are not ours to freeze anyway.

**The rule for what M12 changes.** A change that breaks callers is
M12's: after M14 it costs a compatibility layer. An addition can come any
time, M14 included, so M12 adds only what M13 needs to start or what is
cheap while a track is in that code anyway. Everything is built into one
image, so no change keeps an old form beside the new one; the exceptions
are what an older build on the PC must still read during an `update`
(Risks).

## Found while writing this plan

A first pass over the interfaces, to seed the reviews (they read
everything again; this list is not the review).

**System calls and kernel headers**
1. **No thread-local storage.** `kernel/arch/x86_64/uentry.c` writes FS's
   base as 0 on every entry: "No TLS yet (FS is not saved per thread)".
   musl needs a thread pointer. Question 10.
2. **No lock that sleeps.** libos's `lock_take` pauses, then sleeps 20 us
   between tries (`user/lib/lock.c`); there is no wait on an address.
   musl's threads need a futex. Question 10.
3. **No call names a handle's type.** The keeper probes each handle with
   up to five calls (`user/lib/keep.c`), the compositor checks a
   clipboard handle is a channel end by a zero-byte read
   (`user/services/compositor/data.c`). Question 11.
4. **A failed send's handles.** A write or call that fails before its
   message is queued puts the handles back; one that fails after (a call
   timing out) has moved them (`kernel/abi/channel_sys.c`). The caller
   can't tell which from the status, which is why genidl refuses handle
   arguments. Question 1.
5. **Who pays for unread messages**: the sender, until they are read
   (ARCHITECTURE "IPC"). Question 2.
6. **Limits user code can't see.** A message's 64 KiB, its 64 handles and
   a queue's 1024 messages are in the kernel's own
   `kernel/include/jam/channel.h`; the drivers' `vmo_create` flags are in
   `<jam/driver.h>`; port limits in `kernel/include/jam/port.h`. They
   belong in `<jam/abi.h>`.
7. **Service protocols in kernel headers.** `<jam/abi.h>` defines the
   console's `open_keys` messages (`struct input_key_event`,
   `input_mouse_event`, `input_want`); `kernel/include/jam/startup.h`
   lists service roles (`SR_DEVMGR`, `SR_CONSOLE`, `SR_AUDIO`, ...) and the
   crash log's header. The kernel uses only the roles it gives the first
   process (and the crash log it hands init). The rest move to user
   headers.
8. **Three names for one thing.** `struct channel_read_args` has
   `bytes_cap` then `bytes`; `struct channel_reply_wait_args` has `bytes`
   then `bytes_cap` and `rn`/`rhn`; `struct channel_call_args` has `wn`,
   `rcap`, `rhcap`. One naming scheme and one order for the three.
9. **Time.** Every waiting call takes an absolute deadline; only
   `channel_call` and `channel_reply_wait` take a timeout too (a flag);
   `nanosleep` takes a deadline under a sleep's name (drivers call it
   `drv_sleep_until`). Question 19.
10. **The rights word.** Generic rights and the root's powers share it,
    out of order: `RIGHT_RESIZE` is bit 19, between the powers at 11-18
    and 20-21. Renumbered now (every caller uses the names), generic
    rights low and powers high, the cost is nothing.
11. **Calls with an argument they refuse.** `pci_bus_master(dev, enable)`
    refuses `enable` 1 (only the cap turns it on): it is an off switch.
    `vmo_create` takes a `dma_cap` that only gates the drivers' two flags.
12. **Two signal calls**: `event_signal` (events, any bits) and
    `object_signal` (user bits on any object). One may do.
13. **Names too long**: `process_create` and `thread_create` cut them
    silently, `klog_name` refuses them. One rule.
14. **Error codes POSIX will miss**: no not-a-directory, is-a-directory,
    not-empty or name-too-long; fat answers the unlink of a directory
    that isn't empty with `ERR_ACCESS_DENIED` (`user/services/fat/path.c`).
    Question 9.
15. **`sys_info` needs `RIGHT_ROOT_SYSINFO`**, so a POSIX `uname` in an
    ordinary program can't call it. The POSIX table (review K) decides
    whether the version and CPU strings need a call without a power.
16. **No copy-on-write child VMO** ("No VMO has a clone or copy-on-write
    child", `abi/syscalls.def`): `MAP_PRIVATE` file mappings need one,
    M12.5's or M13's to add.

**Protocols**
17. **Two protocols share id 3.** devmgr's hand-written protocol uses id 3
    (`DEVMGR_PROTOCOL_ID`, whose comment still says "next to the IDL's
    null (1) and edu (2)") and so does `idltest`; genidl checks ids only
    among the `.idl` files. A request meant for one would be taken by the
    other's server.
18. **devmgr names devices with magic vendors**: 0xfffa to 0xfffe stand
    for a filesystem's mount, a PCI class, a USB mount, a filesystem
    service and a USB interface, and 0xffff for "any" (`user/include/devmgr.h`).
    The IDL version gets a real address type.
19. **Fixed arrays that are really variable**: `console.write`'s 2048
    bytes, `input.text`'s 64, `audioctl.streams`' 640 (sixteen 40-byte
    records), `hda.jacks`' 1024 and `hda.info`'s 240 of text,
    `usb.get_descriptor` and `usb.control_in`'s 1024, `net.counts` and
    `netdev.stats`' 256, `dns.resolve`'s `addr0` to `addr3`,
    `compctl.notify`'s three 24-byte buttons in 72, every `fs` path's 256,
    initctl's names in 32, 16, 128 and 16, `music`'s three 256-byte paths,
    `serve`'s 128. Question 3.
20. **One-way messages outside the IDL**: usbbus's `interface_attached`
    ("NOT a call": ordinal 100, txid 0 and a handle), the keep protocol,
    the namespace's messages; and the opposite, input reports sent as
    blocking calls (hid waits for each key and each mouse report:
    `drivers/hid/hid.c`). Question 4.
21. **Several kinds of channel in one protocol, told apart by a prefix**:
    audio's `stream_*` ("so the generated audio_stream_* calls stay
    clear"), hda's stream channel, net's `sock_*` on a socket's channel,
    each refused on the wrong channel by hand. Question 5.
22. **Timeouts as arguments** beside the call's own deadline:
    `net.wait_change`, `net.echo`, `net.accept`, `dns.resolve`,
    `usb.bulk_in`, `usb.bulk_out`, `usbbus.wait_settled`. Question 19.
23. **The file protocol**: no exclusive create (`O_EXCL`), `readdir` one
    entry a call, a path at most 255 bytes, `file.stat` without `is_dir`.
    Question 8.
24. **The disk protocols**: `storage.partition` gives an MBR type byte;
    `block` one request at a time through a 64 KiB buffer. Question 7.
25. **`music.play` is `music.start` with options**: one of them can go.
26. **The namespace is full.** `<os.h>` names 16 services and
    `NS_MAX_SVCS` is 16; `SVC_NAME_MAX` is 10 and "devmgr-ctl" is 10. The
    next service needs both looked at.
27. **The startup message carries 16 handles, a promotion 64**
    (`STARTUP_MAX_HANDLES`, `STANDBY_MAX_HANDLES`): `spawn` fits ten extras
    beside a namespace.
28. **Stale words**: `struct spawn_args` says a program from elsewhere is
    refused "until the kernel can make a VMO executable" (`vmo_make_exec`
    does, since M8.6); `DR_INPUT` says "an input channel to the console"
    (it is the compositor's now).

**The compositor's protocol** (review W reads G1's list above): the
"JWL1" header and its ack counter, 16 KiB batches of at most 16 handles,
the window of 32 batches; the versions offered (`wl_compositor` 4,
`wl_seat` 5, `xdg_wm_base` 1, `wl_data_device_manager` 3,
`wp_cursor_shape_manager_v1` 2: `user/services/compositor/comp.h`), which
upstream has newer versions of (additions, for G2's ports); compctl's
three levels; the console's two methods left only for `nocomp`.

### Q1. Handles in a send that fails

Today a channel write or call that fails before its message is queued
gives the handles back to the caller; once queued they are gone. A call
that fails after the send (its deadline, the server closing) has moved
them, and the status doesn't say which happened. That is why genidl
refuses handle arguments, and why devmgr's `SET_CONSOLE` and `TEST_DISK`,
the keep protocol and usbbus's attach message are written by hand.

- **(A)** Always moved: whatever the status, every handle given to
  `channel_write`, `channel_call` or `channel_reply_wait` is gone when the
  call returns (Zircon's rule). A caller that wants to try again
  duplicates first.
- **(B)** Keep the give-back, and add an out-word saying whether the
  message went out.
- **(C)** Leave it; handle arguments stay outside the IDL.

*Recommendation: (A).* One rule, nothing new to check, and handle
arguments become safe in the IDL. Review K counts the callers that retry
a write with handles after `ERR_SHOULD_WAIT` (they must duplicate).
Depends on it: genidl's handle arguments, track D, track S2, the keep
protocol in IDL.

### Q2. Who pays for messages nobody reads

A queued message is charged to its sender's job until it is read. A
reader that never reads keeps the writer paying: the compositor keeps a
"lingering" slot for every client it disconnected until that client
closes its end (`user/services/compositor/conn.c`), and the clipboard's
owner writes up to 1 MiB into a reader's channel without waiting, up to
32 times each time the reader gets the keys.

- **(A)** As today.
- **(B)** When the writer closes its end, what it wrote and nobody read
  is charged to the reader's job from then on (dropped, as if read, if
  that job can't pay). The clipboard's owner closes after writing, so a
  reader that hoards pays for its own hoard, and the compositor closes a
  disconnected client's end at once.
- **(C)** A queue limit in bytes per channel, set when it is made.

*Recommendation: (B).* It fixes both cases with no new limit to choose,
and keeps "the sender pays" for every channel still open, which is what
stops a client from filling a service's job. (C) only if review K finds a
case (B) misses. Depends on it: K1, the compositor's connection code, the
clipboard's text in ARCHITECTURE.

### Q3. Variable-length arrays in the IDL: what shape

genidl has only fixed `u8[N]`, so `console.write` copies 2048 bytes for
every line and every `fs` request carries 256 bytes of path.

- **(A)** Two new types: `u8[<=N]` (a u16 length on the wire, then the
  bytes; C gets a pointer and a length) and `str[<=N]` (UTF-8,
  length-prefixed, no NUL on the wire; the generated server refuses bad
  UTF-8 or a NUL inside before any handler sees it). Several per message,
  after the fixed part.
- **(B)** Byte arrays only; each server checks its own strings.
- **(C)** (A) plus arrays of records (struct types in the IDL).

*Recommendation: (A).* Most cases are strings (paths, names, titles), and
one generated check replaces a NUL-and-length check in every server.
Records (`audioctl.streams`, `hda.jacks`) stay byte arrays of a C struct
until a third case asks for (C). Depends on it: track G, then every
protocol track.

### Q4. One-way messages in the IDL

Some messages need no answer: input reports (hid waits for the
compositor's answer to every key and mouse report today), usbbus telling
devmgr of a new interface, the keep protocol, the namespace's updates.

- **(A)** An `event` kind of method: written, never answered, the queue's
  limit is its flow control; may carry handles (with Q1's rule). The
  generated server reads them as it reads calls.
- **(B)** Keep everything a call; the hand-written ones stay hand-written.
- **(C)** Events, but without handles.

*Recommendation: (A).* It brings the last hand-written protocols into the
IDL and stops a driver waiting on the compositor's loop. Depends on it:
Q1, track G, tracks P1, P4, P6.

### Q5. One protocol for each kind of channel

`audio` serves two kinds of channel: an opener's (`open_output`) and a
stream's (`stream_start`, `stream_stop`, ...), told apart by a name prefix
and refused on the wrong channel by hand. hda's stream channel and net's
socket channels are the same.

- **(A)** A protocol per kind of channel (`audio` and `audio_stream`, each
  with its own ordinals); the generated server for a stream channel can't
  be sent an opener's method at all.
- **(B)** Keep the prefixes.

*Recommendation: (A).* The wrong-channel checks move from hand-written
code into the generator, and the names lose their prefixes. Depends on
it: track G, tracks P2, P3.

### Q6. The storage service: what moves, and its name

devmgr is 4,419 lines; its disks, filesystem services and mounts, with
fat's warm spares and keepers (`user/services/devmgr/disk.c`,
`user/services/devmgr/fsvc.c`, `user/services/devmgr/mounts.c`,
`user/services/devmgr/spare.c`), are about 1,800 of them.

- **(A)** All of that moves to a new service. devmgr keeps the drivers,
  usb-storage included, and hands each disk's `storage` channel to the new
  service; it starts and supervises fat (spares, keepers, state VMOs),
  serves the mounts, remounts, the ESP write and test disks, and its loop
  never waits inside a request (ARCHITECTURE "How a service waits").
- **(B)** Only the protocol goes to IDL; devmgr stays whole.

Name: **"volumes"** (`/svc/volumes`) is recommended. "storage" clashes
with `storage.idl` (usb-storage's protocol for one disk); "fshost" is
Fuchsia's word.

*Recommendation: (A), named volumes*, with the supervision code devmgr
and init both have now (`user/services/devmgr/spare.c` and
`user/services/init/spare.c` are near copies) folded into one libos
module. Depends on it: tracks S1, S2, D.

### Q7. Shape the disk protocols for GPT and NVMe now?

`storage.partition` gives an MBR type byte; `block` serves one request at
a time through a 64 KiB buffer. M12.7 brings GPT and an NVMe drive with
deep queues, on "the block interface M12 reviewed".

- **(A)** Shape now, build later: a partition gets a 16-byte type GUID and
  a name beside the MBR byte, and which scheme it came from; `block`
  allows several requests in flight on one channel (each at its own
  buffer offset, a bigger buffer). No GPT parsing and no NVMe code in M12.
- **(B)** Leave both protocols to M12.7, which changes them then, after
  M12.1's check.

*Recommendation: (A).* The protocols are reviewed once, and M12.7's
driver lands on them as the wave plan says. Depends on it: track S2,
M12.7.

### Q8. The file protocol, for POSIX

- **(A)** Now: paths as `str[<=4096]` (Q3); `readdir` answers a batch of
  entries per call; an exclusive create flag (`O_EXCL`); `is_dir` in
  `file.stat`; and fat keys its open files and their sharing by directory
  entry instead of by path, so renaming a directory that holds an open
  file (by its long name or its 8.3 alias) leaves no stale path (the M11.6
  review's finding 5). Directory handles (`openat`) wait for M13: an
  addition.
- **(B)** Leave the file protocol to M13.

*Recommendation: (A).* Each is a breaking change to `fs` or `file`,
cheapest now, and fat's lock is reviewed with them. Depends on it: track
P5.

### Q9. Error codes POSIX will need

There are 20 `ERR_*` codes. fat answers the unlink of a directory that
isn't empty with `ERR_ACCESS_DENIED`; the music player uses
`ERR_WRONG_TYPE` for "that is a file".

- **(A)** Add `ERR_NOT_DIR`, `ERR_IS_DIR`, `ERR_NOT_EMPTY`,
  `ERR_NAME_TOO_LONG` and `ERR_BUSY` now, answered by the filesystem
  servers, so M13 maps each to its errno one to one. An "interrupted"
  code waits for M13's signals.
- **(B)** M13's libc guesses the errno from the call and the code.

*Recommendation: (A).* Depends on it: tracks K3, P5.

### Q10. Thread-local storage and a lock that sleeps

The kernel sets FS's base to 0 for every thread ("No TLS yet"), and has
no wait on an address: libos's lock spins and sleeps 20 us between tries.
musl needs both (its thread pointer; its futex for mutexes and condition
variables).

- **(A)** In M12: a thread's FS base set when it starts and changeable by
  a call, saved on a switch; `futex_wait(addr, expected, deadline)` and
  `futex_wake(addr, count)` on the caller's own memory; libos's lock on
  them.
- **(B)** At M13, when musl first needs them.

*Recommendation: (A).* They change the thread model and the switch path,
which M12.1 then checks, and M13 starts on a kernel that has them. One
track (K4). Depends on it: M13.

### Q11. A call that names a handle's type

- **(A)** `handle_info(h, &info)`: the object's type, the handle's
  rights, the object's id, and for a channel end its peer's id.
- **(B)** A general `object_get_info(h, topic, buffer)` as Zircon has.
- **(C)** None: keep probing.

*Recommendation: (A).* One fixed struct covers the keeper (five probes a
handle become one call) and the compositor's clipboard check; job and
process information keep their own calls. Track K3.

### Q12. Re-arm a port binding inside `channel_reply_wait`

fat's cached read costs four system calls a request; a flag that re-arms
a once-only port binding in the reply-and-wait call would make it three
(the M11.6 review's B; the follow-up on the call's last 165 ns).

- **(A)** Add the flag in M12.
- **(B)** Leave it to the speed pass: it is an addition, possible even
  after M14.

*Recommendation: (B)*, unless the PC's `perop` shows the fourth call
matters. Depends on it: nothing in M12.

### Q13. Read-only DMA pins

A device that only reads a buffer (a transmit ring, a sound stream, a
command ring) could get it mapped read-only in the IOMMU, so not even its
own driver can make it write there: one flag on `vmo_pin` (M11's question
8, put on M12's list).

- **(A)** In M12, with D3's change to the same pin code; the drivers'
  transmit and sound rings use it.
- **(B)** Later (an addition).

*Recommendation: (A).* Small, and track K2 is in that code anyway.

### Q14. The full-screen console (`nocomp`), and lending the screen

G1 kept `nocomp` until its PC sign-off and left the rest to you. The
console keeps `connect_input` and `lend_screen` only for it, and
`lend_screen`'s mapping outlives its lease (a program can keep drawing
over the console: G1's plan, "Where the screen is today").

- **(A)** Keep `nocomp` as the safe mode, text only; `lend_screen` goes
  (under `nocomp` the splash is skipped and jamjar says it needs the
  desktop); `connect_input` stays.
- **(B)** Keep both, as today.
- **(C)** `nocomp` goes, and the console's screen and input methods with
  it.

*Recommendation: (A).* A safe mode with a shell is worth keeping (as
`smp=loader` was for M8.5); the borrowed framebuffer is the one hole G1
left open. Depends on it: track P1.

### Q15. What an input report carries

hid applies the US layout and sends a character with each key
(`input.key`'s `codepoint`); the compositor uses only the key and the
modifiers, with libos's keymap tables (G1's Q6).

- **(A)** The character goes; the `nocomp` console and the serial source
  use libos's keymap tables too.
- **(B)** Keep it.

*Recommendation: (A).* One place for a layout, so a second layout needs
no driver change. Track P1.

### Q16. libos's heap size

Every program's heap is 16 MiB of address space, committed as touched
(`user/lib/heap.c`); the compositor's worst case is about 23 MiB.

- **(A)** Reserve much more address space (1 GiB): a VMO's pages and
  tables cost only what is touched, and the job's page limit stays the
  real bound.
- **(B)** Each program sets its own size.
- **(C)** Keep 16 MiB.

*Recommendation: (A).* Nothing to choose per program, and the limit that
matters is already the job's. Track P6.

### Q17. What a pipe is

The clipboard uses a channel end as Wayland's pipe: the writer writes the
text as messages of bytes and closes, and the reader's `ERR_PEER_CLOSED`
is the end of the file. M13's shell pipelines, standard input and output
and `posix_spawn` need pipes too.

- **(A)** A pipe is a channel of byte messages, closed at the end; libc's
  `read` keeps what is left of a message.
- **(B)** A new kernel object, a byte stream (Zircon's socket).
- **(C)** A shared ring and an event, in user space (as the network's
  sockets).

*Recommendation: (A)* as M13's starting point, measured there. M12 only
writes it down as the rule, so the clipboard, G2's libwayland shim and
M13 agree. Depends on it: M13.

### Q18. A dead service's kept objects

Objects a dead fat made (an open file's buffer VMO) stay charged to its
dead job until closed, at most 256 kept handles (M11.6 plan, "Limits").

- **(A)** Leave it: bounded.
- **(B)** Charges follow an object to the successor's job: new kernel
  machinery.

*Recommendation: (A).*

### Q19. Time in arguments

System calls take absolute deadlines; two also take a timeout by a flag.
`nanosleep` takes a deadline. Seven IDL methods carry `timeout_ms` beside
the call's own deadline. M11.5 left a read-only time page (clock reads
without a system call) for M12 to place.

- **(A)** One rule: system calls take deadlines, with a timeout flag only
  where a flags word exists; `nanosleep` becomes `sleep_until`; an IDL
  method carries a timeout only when the server bounds a wait the caller
  doesn't (a `later` method), and the others drop theirs; the time page
  goes to M13, with `clock_gettime`.
- **(B)** Leave it.

*Recommendation: (A).* Tracks K3, P3, P4.

### Q20. M12's own independent review

The standing rule: big agent-written code is reviewed and fixed by an
agent that didn't write it. M12.1, right after M12, reads every line M12
changes and the unchanged callers of every interface it changes.

- **(A)** M12.1 is M12's review; M12 has no separate one.
- **(B)** A review-and-fix agent over M12 first, then M12.1.

*Recommendation: (A).* The same reading twice in a row; M12.1's kernel and
services tracks get M12's diff as their first read.

## Risks

- **Breaking every caller at once.** Each protocol track owns both ends of
  its protocols, so a change and its callers land in one merge, and a C
  caller of a changed stub fails to build. What the build can't see:
  messages made by hand (devmgr's `devmgr_call`, the keep protocol, the
  namespace, the hostile and wire-level tests that forge messages) build
  and fail only at run time. The protocol review lists every one, and each
  track runs the area scripts above.
- **Regenerating the glue.** Five syscall files, one IDL header per
  protocol and the Wayland tables are generated; two tracks' outputs
  merged by hand would build and be wrong. The rule above: regenerate after
  every merge, `make check` refuses stale output.
- **Services that replay requests**: a changed wire format with an
  unchanged state layout version would replay a request in the old
  format after a restart. The rule above (bump, run the restart tests).
- **The update across M12.** The PC runs a pre-M12 build that must fetch,
  check and start the M12 build: the update manifest, the offer, the
  bootfs format and the kexec hand-over between two kernels
  (`kernel/include/jam/kexec_handoff.h`) stay readable by the old build,
  or are versioned so that the old build refuses cleanly and `update -w`
  plus a firmware reboot still works. Tested with the old build fetching
  the new one in QEMU before the PC.
- **The storage split is on the boot path.** A broken split means no
  `/data` and no `/esp`; `nocomp` doesn't help. S1 is a pure move with
  every storage test unchanged before S2 changes a protocol, and the PC
  session starts with an everyday boot and the sticks.
- **M13's needs missed.** Review K's POSIX table comes from musl's own
  system call list and M13's row, not from memory; anything not built in
  M12 gets its shape and its milestone written down; M14 reviews M13's
  additions anyway.
- **The call path gets slower.** K1 changes the send path (txids, handle
  moves, charges on close); K4 the switch (the FS base). Both bench before
  and after; the PC's reply-and-wait line decides.
